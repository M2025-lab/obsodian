# 季度 OKR（2026Q4）— 深耕材料与考核阵地 × 横向拓域

## 主题：以一个领域为阵地，接触新项目与需求

本季度主线：**在深入掌握一个领域的前提下，同时了解多个领域**。阵地 = **材料域（starlord）+ 考核域（scm-workbench）**，两个领域咬合成一块阵地：

- **材料域是老阵地**：试用期深耕 starlord——主材任务全生命周期、材料配置、排程配置，已有大量文档积累，但材料配置"尚未完全理清"（周报遗留疑问），本季度补齐
- **考核域是新阵地**：11 月刚接手交接，历史上基装/材料考核分家（"八合一"没合好），交接会上明确"考核收口到一个人"——我就是收口的承接人
- **两者天然咬合**：考核吃 starlord 的材料事件（15 个上游 topic 之一）、写回 starlord 任务同步；材料的时间行为（备货→到货→送货→安装）正是考核指标的来源。**以材料为根（业务链路熟）、以考核为面（信息枢纽），两边互相印证**

即：以材料+考核为阵地，沿上下游自然外溢到相邻领域——订单 OMS·OFC、施工排程·工期、供应链·供应商、中控；且两域的演进伏笔（备货周期考核、台账回传、工期自动增减）全是跨域需求。

## O1 深入掌握材料与考核两域（权重 50%）

> 衡量"掌握"的标准：两域都能独立接需求、独立排查线上问题、别人问链路能当场讲清。材料补"配置深水区"，考核补"从零到维护者"。

| # | KR | 量化目标 |
|---|-----|---------|
| 1 | **考核域：从零到技术地图** | 输出考核系统完整技术地图 1 份（事件接入→指标计算→刷数重算→对外发布，覆盖 [[考核系统上下游交互清单（对端系统×交互信息总表）]] 全部通道，材料侧为主线），并完成 1 次部门内串讲 |
| 2 | **两域独立交付需求 ≥ 2 个** | 从需求评审→方案→开发→上线全流程独立负责（材料域或考核域均可，跨两域的需求优先）；沿用试用期质量线：提测 bug < 开发天数×2，无 A/B 级故障 |
| 3 | **成为两域问题的可求助点** | ① 考核：独立完成 ≥ 3 次考核数据问题排查/刷数（走 [[考核系统刷数接口使用指南（重算入口×批量调用SOP）]]），不依赖原维护人；② 材料：收口 starlord 材料配置遗留疑问（周报中"starlord 材料配置尚未完全理清"），输出材料配置全景笔记 1 份 |
| 4 | **验证两个"交接疑点"并给出结论** | ① 基装+材料考核代码层是否真正合并（收口的承接人就是我）；② 材料考核"单点→时间段（备货周期）"演进的可行性（合同备货周期字段能否驱动双节点考核）——各输出 1 份核实结论，为下季度埋伏笔 |

## O2 以材料+考核为阵地，接触新项目与需求、了解多个领域（权重 30%）

> 衡量"了解"的标准：不考核深度，考核**广度地图 + 需求参与次数**。目标不是精通这些域，而是知道每个域"解决什么问题、和两域交换什么信息、出问题找谁"。

| # | KR | 量化目标 |
|---|-----|---------|
| 1 | **摸清 ≥ 4 个相邻领域** | 沿两域上下游按领域聚类（订单 OMS·OFC / 施工排程·工期 / 供应链·供应商·集采 / 中控 / 全案履约），每个领域产出 1 篇"××域速览"笔记：业务定位 + 与材料/考核的信息契约 + 排查入口 |
| 2 | **主动承接跨域需求 ≥ 2 个** | 优先从交接会上已明确的需求池捞，材料侧优先：材料备货周期考核（时间段升级）/ 台账时间回传预测（含云助理手抄的供应商排产"预计交货日期"）/ 工期自动增减 / 北京工作日特殊规则——每个都是"以两域为阵地伸出的一次触角" |
| 3 | **参与 ≥ 3 场阵地外领域的需求评审** | 两域上下游的评审主动去听（供应商汰换、集采、施工包、排程侧），产出需求背景笔记，建立"谁在什么域解决什么问题"的通讯录 |
| 4 | **形成跨域排查能力** | 出现数据异常时，能沿事件源追溯到对端系统定位责任边界（是考核算错、材料发错、还是更上游发错）——Q4 内沉淀 ≥ 2 个完整案例进 [[20.知识沉淀]] |

## O3 沉淀与 AI 提效（权重 20%）

> AI 不单列目标，并入技术沉淀——考核域的学习/排查过程本身就是 AI 工具的练兵场（沿用试用期"学习→输出→复用"闭环）。

| # | KR | 量化目标 |
|---|-----|---------|
| 1 | **两域知识资产化** | 交接期散落的 16+ 份考核文档收口成 [[考核]] 目录的学习索引（材料线优先）；starlord 材料配置疑问收口（与 O1-3 联动）；Q4 新增 📚 级沉淀笔记 ≥ 4 篇（踩坑/排查/上游变更适配类），按既有 7 段模板 |
| 2 | **AI 提效至少落地 1 个阵地场景** | 候选：排程数据分析 skill 的全国化适配（交接会既定方向）/ AI 辅助考核数据异常排查（把异常排查四步法喂给 agent 做半自动定位，考核+材料事件链路最合适）/ 台账回传预测的数据处理——产出可演示的工具或 skill |
| 3 | **完成 1 次对外分享** | 考核系统串讲（与 O1-1 合并产出，材料线视角）或 AI 工具实践分享（ai围炉二季） |

## Review 节奏与衡量方式

- **月度自查**（月末最后一个工作日）：对照 KR 打分（0 / 0.3 / 0.6 / 1），写进 [[80.日报周报/ignore（日报不用看这些）/周报]] 当周 Issues；进度落后就调整 KR 而不是硬扛
- **证据链**：每个 KR 的完成证明 = 对应笔记链接 / commit / 分享录屏，写回本文件各 KR 下方
- **两条红线**：O1 的线上故障红线（无 A/B 级）沿用试用期标准不变；O2 的广度探索不许挤占 O1 交付——阵地优先于触角，跨域评审听不懂就先记问题回 O1 补课

> 一句话自检：**季度结束时，"材料+考核"两域应该能回答到别人把我当维护者对待的水平（考核收口的承接人、材料配置的活地图），"多领域"应该能回答到"知道找谁、知道在哪、能判断是不是它的问题"。**

1. 视频大模型应用——驳回任务拦截与通知收敛（上线）
对视频大模型应用中驳回的任务实现针对性拦截，收敛任务提交入口至自动通知，整条链路功能上线；减少驳回任务重复流转、告警触达更集中
2. LLM 聊天记录分析开发（roomie 群消息问题归类）
消费企微群消息落库（kafka → `roomie_group_message`），调用 LLM 将群聊消息归类为问题类型并整合成问题快照（谁问的/哪个项目/什么诉求），供后续 Agent 直接消费回答
关键指标：召回 ~99%（205/208）、类型一致 ~90%（312/348）、空批 0——迭代 R1→R7 七轮（重试机制、正反例库、收尾条款、类型后处理），确认「prompt 不动 + 规则后处理」架构稳态
3. Agent 问题回复开发（项目进展问答）
基于群内提出的问题，调用系统已有能力（鲁班节点进度、主材订单、送货排期、供应商信息）聚合查询、自动生成回答，帮助云助理快速掌握具体项目进展、替代多系统多页面挨个查
4. 送货进展群通知
对回收到的线下信息（正单预计入库、在库未送、反补预计到货 3 张报表，排线表待接入）整理汇总，将业主关注的到货时间、送货时间同步至项目经理群，替代云助理每日传表、拼文档、发汇总的手工链路


收获
本周四项工作（视频大模型驳回拦截上线、LLM 聊天记录分析、Agent 问题回复、送货进展群通知）技术上横跨视频大模型、LLM、Agent、报表推送，但价值面收敛为同一个故事：分别接管云助理「翻群、查表、查系统、发通知」四个手工动作。其中 LLM 聊天记录分析跑完 R1→R7 七轮迭代，沉淀出一套可复用的 LLM 工程方法论：动手前先离线回放定性错误构成（21 对错例拆成 3 对可治 + 18 对不可治，避免在治不了的问题上浪费轮次），验证时看「机制自己的账 + 总指标」两层账，当一轮改动的影响落在轮间漂移区间内即判定架构到顶、该收就收（R7 确认「prompt 不动 + 规则后处理」稳态：召回 ~99%、类型 ~90%、空批 0）——这套打法可直接复用到下一个 LLM 场景。
反思
本周精力几乎全部在 roomie/AI 提效方向，OKR 主阵地（材料+考核两域）推进为零——OKR 定完当天就该启动第一步（考核技术地图开工），下周必须落到具体产出，否则 O1 会变成「写在纸上的目标」；且 AI 练兵虽是 O3-KR2 的素材，但不能替代阵地建设。另外，四项工作里视频大模型应用是「上线了但无档」：拦截规则、上线指标、影响范围都没沉淀，违背「输出即资产」的一贯做法，下周需补齐，否则季度复盘无据可查。


下周工作：本周工作仍以 roomie 云助理群场景提效为主线（约 70% 精力）：LLM 聊天记录分析进入收官——拿 35 对两可口径清单找基线主人一次裁决（≥30 对可归档）；推进 Agent 问题回复联调，验证「台账能答的当场回」的真实命中率与响应时效；为上周上线的视频大模型驳回拦截功能补齐留档（拦截规则、上线指标、影响范围）；并将 R1→R7 沉淀的 LLM 迭代打法（先定性错误构成、两层账验证、稳态天花板识别）整理成方法论笔记，作为下一个 LLM 场景的启动模板。
