1. 真实的循环顺序（已验证，来自 src/query.ts 的 queryLoop）

每一轮 agent 循环、在调用模型之前，按顺序跑这些。源码注释原话：

"Runs BEFORE autocompact so that if collapse gets us under the autocompact threshold, autocompact is a no-op and we keep granular context instead of a single summary."

→ 便宜手段先跑，贵的总结最后兜底。我说的"懒惰降级阶梯"这个思想是真实存在的，只是名字和我的不完全对应。

3. ⑤ Auto-compact —— autoCompact.ts（真实实现）

阈值数学（:62, :72-91）

  • 有效窗口 = 模型上下文窗口 − MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000（基于"压缩摘要输出 p99.99 = 17,387 token"实测留余量）。
  • 触发阈值 = 有效窗口 − AUTOCOMPACT_BUFFER_TOKENS = 13_000 → 约在 ~93% 处开火。
  • 判断式：tokenCountWithEstimation(messages) − snipTokensFreed ≥ 阈值。减 snipTokensFreed 是因为 snip 后 assistant 的 usage 仍是裁剪前的，不扣会算错。

两个硬核工程细节（真实，不是我总结）

① 熔断器（:70, :260-265, :343）：MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3。注释写明原因——"1,279 个会话出现过 50+ 次连续失败（最多 3,272 次），每天白白浪费约 25 万次 API 调用"。连续失败 3 次就跳过，不再用注定失败的压缩轰炸 API。

② 先试 session memory 压缩（:288 trySessionMemoryCompaction）：把可归档记忆抽出去，比直接 LLM 总结旧对话更省。

主流程 autoCompactIfNeeded：递归保护（session_memory / compact 分叉会死锁，跳过）→ 熔断检查 → shouldAutoCompact → 先试 session memory → 不行就 compactConversation(...) → 成功重置失败计数，失败累加。

4. ③ Microcompact —— apiMicrocompact.ts（真实实现，思路很妙）

这一层完全不是"客户端总结"，而是把一个声明式策略交给 API 原生上下文管理（:35-61, :112-149）：

  • 策略 clear_tool_uses_20250919：当 input_tokens ≥ 180_000（默认警告阈值）触发，保留最近 40_000 token，把旧的工具结果/工具调用清掉（TOOLS_CLEARABLE_RESULTS = SHELL / GLOB / GREP / FILE_READ / WEB_FETCH / WEB_SEARCH 等）。
  • 策略 clear_thinking_20251015：保留推理模型的思考块（只清旧的）。
  • 关键：让 API 自己去裁，客户端只声明"超阈值就清哪些"，不消耗一次 LLM 调用、不丢语义颗粒度。注释 "Keep last 40k tokens like client-side"——和客户端 microcompact 的 token 值对齐。

这就是"先试最便宜手段"的极致：连一次总结调用都不花，纯靠 API 侧原生裁剪。

5. ② Snip + ④ Context collapse（⚠️ 代码被 DCE 剔除，讲设计意图）

② Snip（HISTORY_SNIP）：从 query.ts 调用 snipModule!.snipCompactIfNeeded() 返回 snipTokensFreed 可知——它定点切除"僵尸消息"（如巨型 build 日志这种特定大块），不总结整段。像剪刀剪掉某几段，不是把整本日记重写。

④ Context collapse（CONTEXT_COLLAPSE）：autoCompact.ts 注释把真实设计讲透了——"Collapse 开启时它就是上下文管理系统，90% 提交 / 95% 阻塞-分叉的流程 own 了 headroom 问题"；"autocompact 在 effective-13k（~93%）开火，正好夹在 collapse 的 commit-start(90%) 和 blocking(95%) 之间"。所以它是读取时投影合并：把多条消息合成一份折叠投影（视觉合并、不删），90% 提交折叠省 headroom，95% 快溢出时 recoverFromOverflow() 把已暂存折叠提交掉兜底。reactiveCompact 是 413（prompt-too-long）时的最后兜底。

6. ① Budget reduction（⚠️ 我的措辞，无同名模块）

真实里没有这个独立模块。它对应"别让单个工具输出把桶撑爆"——工具层对超大输出做截断/限制，加上 microcompact 里 API 原生清旧工具结果那一步。我单列成第①层是为了讲清"最便宜 = 根本不让大东西进桶"，但严格说它不是 Claude Code 的一个独立命名层。

7. 收口：和 DeepHarness 对照（你前面学的没白学）

  • 共同点：懒惰降级（便宜先上、LLM 总结兜底）——Claude Code 的 query.ts 顺序和 DeepHarness 的 compactIfNeeded（先免费剪枝再调 LLM）是同一哲学，且都已验证。
  • 最大差异：Claude Code 把 microcompact 做成交给 API 原生裁（声明式、零额外调用）；DeepHarness 的 spill/pruner 是客户端确定性剪枝 + 显式外置。前者更"借力 API"，后者更"自己可控、可审计"。
  • 想看逐行可读实现：Claude Code 三个层被 DCE 剔除，反而 DeepHarness 是 MIT 全开源、每行可读（你 0001–0003 课学的就是它）。所以"学会上下文管理"这条线，DeepHarness 才是能让你照着写骨架的那份。
