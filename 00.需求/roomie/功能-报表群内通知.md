**要做的事**：把云助理现在每天手动做的「拼四张 Excel → 数据分析 → 生成推送图片 → 发群」整条链路接进 Roomie，实现**企微外部群消息接入 roomie 推送**。

## 1. 数据依赖：四类报表

| 报表      | 数据来源                                                                | 接入状态  |
| ------- | ------------------------------------------------------------------- | ----- |
| 正单预计入库  | [衣柜到货进度](https://www.kdocs.cn/l/clgEYiDwrGo8) · 衣柜接龙正单 sheet        | ✅ 已接入 |
| 在库未送    | [衣柜到货进度](https://www.kdocs.cn/l/clgEYiDwrGo8) · 衣柜在库出库信息 sheet      | ✅ 已接入 |
| 明日送货    | 排线表                                                                 | ❌ 未接入 |
| 反补预计到工地 | [橱柜设计师下单反补台账](https://www.kdocs.cn/l/cbsmlzZL18Xm) · 反补到货时间（新）sheet | ✅ 已接入 |

现有接入文档覆盖 75% 的数据来源（4 张中 3 张），**剩余「明日送货」的排线表还未接入**——当前优先接入其余三个文档，先行打通链路。

## 2. 现状

**报表接入现状**：衣柜到货进度、橱柜设计师下单反补台账均已接入小师傅（construction 服务）：由 construction **定时 download 线上文档**，供小师傅查询使用。

**推送现状**（云助理工作平台的企微推送功能）：

1. 云助理每日上传四类依赖 Excel；
2. 平台做数据分析，落库 `wecom_push_orders`；
3. 生成每日推送图片，**手动**推送至群。

**去重规则**：如果在「明日送货」里出现，就不会在「在库未送」里重复提醒。

## 3. 方案

两条路线，分歧在于 **download 逻辑是否复用 construction 已有的**：

### 方案 1：construction 分析 + agenda 推送（复用现有 download）

- 依赖 construction 中**已下载的文档**，在 construction 中加入文档数据分析逻辑（分析规则复用云助理工作平台现有的）；
- 群消息推送能力放在 agenda 中；
- construction 定时调用 agenda 的群消息推送功能完成推送。

**优点**：不重复开发 download 链路，复用已稳定运行的定时任务。
**代价**：分析逻辑沉在 construction，推送链路横跨两个服务（construction → agenda）。

### 方案 2：agenda 独立成套（download + 分析 + 推送）

- 在 agenda 中重新写一套 download 逻辑；
- 加入文档数据分析逻辑；
- 直接推送 roomie 群。

**优点**：链路收敛在一个服务内，后续维护和演进（如接排线表、调整推送规则）不牵动 construction。
**代价**：download 逻辑重复开发一份，与小师傅侧的数据来源出现两份并行实现。

## 3.1 已落地改动（agenda 侧，2026-11-11）

> 方案 1 / 方案 2 的分歧只在 **download + 分析** 归谁；两案都要求「群消息推送能力放在 agenda」，这部分已先行落地——construction 定时任务后续调 agenda 的推送入口即可。

推送接口：Roomie `huiju-chat-workbench` **发送消息（私聊、群聊）** `/api/msg/pushMsg`（weapons [1879071](https://weapons.ke.com/project/21048/interface/api/1879071)），KE-PASS IAM 加签（复用已入库的 roomie.api 凭据）。

### Apollo 配置（全部可配，改配置不发版）

| 键 | 说明 | 默认 |
| --- | --- | --- |
| `roomie.push.enabled` | 推送总开关（一键止血） | `false` |
| `roomie.push.group-ids` | 推送群ID（企微群聊 groupId，即事件报文里的数字 groupId），多个逗号分隔 | 空 |
| `roomie.push.robot-uc-code` | 推送机器人系统号 | 空 |
| `roomie.push.business-push-type` | 业务推送类型（接口必填） | `agenda_report` |
| `roomie.push.low-priority-send` | 走低优先级发送通道（文档建议 api 推送都走低优，不影响坐席） | `true` |
| `roomie.push.send-interval-ms` | 多群连发的逐条间隔（接口标注注意 QPS） | `200` |

### 代码改动（分支 `feat/20261111/roomie-group-msg`）

| 层 | 文件 | 内容 |
| --- | --- | --- |
| manager | `RoomieApiClient` / `RoomieApiClientImpl` | 新增 `pushGroupText()`：sessionType=2 群聊 + msgTypeCode=1 文本；requestNo=时间戳+自增序列；失败**抛异常**（主动外发不像回查可静默降级） |
| manager | `RoomiePushResult`（新增） | pushMsg 回执（errno=0 仅代表任务下发成功，送达走异步回调 topic `huiju-chat-workbench-push-msg-callback(-test)`） |
| service | `RoomiePushSettings`（新增） | 读取 `roomie.push.*`，沿用 consumer 侧「String 接值 + 去行内注释」容错 |
| service | `RoomiePushService` / `RoomiePushServiceImpl`（新增） | 逐群串行推送 + 群间 sleep 控 QPS；单群失败不中断其余群 |
| web | `RoomiePushController`（新增） | `POST /api/v1/open/roomie/push`（推默认群）、`POST /api/v1/open/roomie/push-groups?groupIds=`（定向）；入参 raw body 免转义 |
| dao | `RoomiePushItemResult`（新增） | 每群推送结果（success/traceId/errMsg） |
| service | `RoomieStartupLogger` | 启动自检补推送段：配置一行 + 机器人空/群空/api 未就绪 ERROR |
| start | `bootstrap-test/preview/prod.properties` | 补 `roomie.push.*` 配置段；test 已填机器人，**prod/preview 默认 enabled=false 待群确认后开** |
