# Excel 与项目信息接入

> 🔗 飞书：https://beike.feishu.cn/docx/D1GudrBTZolGhLxyKyKc9RjSnKb
>
> 📅 2026-11-10 讨论整理稿——对应接入方案 §3.2（材料送货进展）与 §3.5（项目信息聚合查询）的落地细化

我理解云助理现在需要我们给他提效的功能点：从每日排线数据里获取明天什么项目、谁家明日发货退费书（发什么品类呢？）。
以及现在仓库中有哪些材料已经入库，通过每日各种供应商的入库表来记录谁家的什么品类，比如橱柜、衣柜已经到库。

总结：排线表只要表中有对应数据，我们只需要记录这个表发出来的日期，以及表中记录的项目ID、地址、客户姓名即可。
而定制柜、橱柜入库表需要记录客户项目ID、地址以及到库时间。

## 功能点一：定制柜/橱柜送货日期（排线表 + 入库表）

**要实现的功能**：通过数据回收群的两张 Excel（排线表 + 入库表），查询定制柜/橱柜的入库时间和送货时间。全链路统一 姓名+项目id。

**实现方式**：

1. **落库**：排线表群 / 实际入库群切企微，自动抓取群内 Excel，解析后分别落两张数据表，**分开落、不合并**——排线是预计、入库是事实，合并发生在查询时，不在落库时（两张表的落库字段模型见文末附）：
   - `dispatch_plan`（明日派车）：发车信息只关心当前数据，不关心历史数据，覆盖式更新（可落 MD 文件，也可覆盖式写表）；
   - `inbound_fact`（入库事实）：每晚将新增的入库材料 append 到表当中，存在即已入库。
1. **查询**：以 projectOrderId 为 key，对着事件历史算生命周期，输出当前卡点与对应日期：

2. **查不到时区分三种含义**：还没排线（在途/在库备送）/ 已经送完 / 数据没落——Agent 回复要区分，否则 PM 会把「没排线」理解成「系统坏了」。

3. **注意**：派车表不留历史，改期/分批的回溯不可用；分批可借入库表「件数」列辅助判断（见文末附）。

## 功能点二：供应商工厂交货时间（人工补录闭环）-待调研

**要实现的功能**：从供应商侧拿到工厂交货时间，并更新到数据表中——作为送货进展的一个状态字段（projectOrderId + 品类 + 承诺交期 + 来源 + 录入人 + 更新时间，upsert 写入）。

**实现方式**：背景结论（11-05 会议）：供应链**有这个数据，但没有让供应商必填的运营手段**——不走供应商主动回填或接口，走「云助理作业流程带出」，即接入方案 §3.3 消息转发 + §3.4 外呼的触发场景之一，外加一个录入动作，**不新增链路，只是给进展数据补一个字段**：

1. **每日上午 job 圈单**：考核时间在未来三天内、且工厂交货时间为空或已过期的单子 → 推云助理待办（「每日上午刷新」落在这个 job 的节奏上）；
2. 云助理对这批单走 **§3.3 转发**（供应商群 @ 对接人）或 **§3.4 外呼** 去要时间；
3. 拿到后在 Roomie 侧边栏/工作台**录入回写**，upsert 到工厂交期表。

录入人默认云助理；后续供应商侧出现自填口子（必填/接口）再切换数据源。

**附带红利**：入库表天然是工厂交货承诺的事实闭环——供应商承诺 11/8 交（人工录入）、入库表 11/12 才出现，承诺 vs 实际偏差免费沉淀，后续供应商考核可直接使用。

## 功能点三：姓名查报价 + 项目ID + 货单任务

**要实现的功能**：根据客户姓名查品类报价信息，并顺链拿到项目 ID 和货单任务——对应接入方案 §3.5 聚合查询的一个具体切面，是整条送货进展查询链的**入口**。

**实现方式**：姓名是弱 key（会重名），查询必须两步：

**第一步 · 姓名 → projectOrderId**（`/utopia-hestia/api/order/project/page/luban/v2`）：

- 鲁班项目列表页底层查询，返回项目卡片全集（大区、地址、签约时间、项目状态、项目经理等）；
- 重名时带辅助字段列表让用户选择确认，消歧信息大概率现成，无需拼第二个接口。

**第二步 · projectOrderId 查询**——报价先行：货单查询依赖报价产出的品类，送货进展只需 projectOrderId、可与报价并行：

| 路 | 数据源 | 产出 |
|---|---|---|
| ① 报价 | `/utopia-atom/api/budget-bill/list` | 品类报价信息（顺带拿到品类） |
| ② 货单（依赖 ① 的品类） | `/scm-beiwo/api/refactor/goods/order/list/query`（OMS） | 按品类查货单任务 |
| ③ 送货进展（与 ① 并行） | 落库数据（功能点一的两张表 + 工厂交期表） | 入库/排线/工厂交期状态 |

各路结果组装成「项目详情」单次回复（对应 §3.5 的 Agent 自动回复 + 侧边栏一站式查询两种形态）。

**架构结论**：内部聚合服务统一封装——凭证在服务侧统一管理，接口封装 + 落库数据 join 都在服务内完成，Roomie 侧只需一个 Skill 对接聚合服务一个端点（Skill 直连被否：要配三家网关凭证，且无法 join 本地落库的进展数据）。

**接口口径待核实**：① 姓名参数精确还是模糊匹配；② 分页参数（重名用户要翻页拿全）；③ `page/luban/v2` 的数据权限口径——这类页面底层 API 经常把数据权限烤在接口里（PM 登录看自己大区、管理员看全部），Agent 用服务号调它看到的数据范围必须先确认，否则会出现「PM 能查到的单，Agent 查不到」的漏数据。

## 附：两张 Excel 的落库数据模型

### 派车表（明日派车信息表）——单一来源、格式稳定

表内列：运单号、项目单号、客户、户主。落库字段：

| 落库字段             | 源列   | 说明                   |
| ---------------- | ---- | -------------------- |
| `projectOrderId` | 项目单号 | 与系统查询链统一             |
| `customerName`   | 客户   |                      |
| `address`        | 户主   | 列名为「户主」，实际内容是否为地址待确认 |
| `waybillNo`      | 运单号  | 一次派车的唯一单号            |
| `planDate`       | 报表日期 | 即「明日发车日」             |

存储只关心当日快照、不留历史（覆盖式更新或 MD 文件均可）；

### 供应商入库表——多家供应商、格式不一

表内列（并集）：订单类型（橱柜衣柜 / 反补）、客户姓名、地址、项目单号、件数、通知提货时间、提货日期、送货日期。**部分供应商只送橱柜，表中没有订单类型列**——因此抽公共模型：结构化公共字段 + 剩余列转 JSON 兜底：

| 落库字段              | 源列                  | 说明                   |
| ----------------- | ------------------- | -------------------- |
| `projectOrderId`  | 项目单号                | 与系统查询链统一             |
| `customerName`    | 客户姓名                |                      |
| `address`         | 地址                  |                      |
| `orderType`（或者品类） | 订单类型                | 无此列的供应商默认从**文件标题中取** |
| `inboundDate`     | 提货日期（到仓日期）          | 以实际表为准；无独立日期列时取报表日期  |
| `extra`（JSON）     | 件数、通知提货时间、送货日期 等其余列 | 各供应商差异列的兜底容器         |

注：入库表自带「送货日期」列（供应商口径的**计划**送货日），先落 JSON；实际发车以派车表为准。若 Agent 话术需要报计划送货日，再将其提为结构化字段。
