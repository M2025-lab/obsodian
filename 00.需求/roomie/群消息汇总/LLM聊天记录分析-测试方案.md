## 2、测试链路（一个接口跑全链）

生产方案的 §4.0 Job 闭环对测试迭代太重（防重三闸、逐 issue 事务、CAS 换版都是为长期稳态设计的）。测试期用一个**同步分析接口**跑完整链，一轮一清：

```
POST /api/v1/open/msg-analyze/analyze-test
  ?groupId=910001000000000001&limit=100&batchSize=50&reset=true

  MsgAnalyzeService.analyzeOnce(param)
    ├─ reset=true 时：DELETE FROM roomie_msg_issue WHERE group_id=?  （清上轮结果）
    │                  UPDATE roomie_group_message SET analyze_status=0 WHERE group_id=?（重置状态）
    ├─ 拉取：selectPendingMessages 分批（**纯 id 正序游标** `WHERE id>? ORDER BY id`，batchSize 条/批；Excel 导入数据 id 与 msg_time 严格同步单调，二者等价；切 kafka 实时流时迟到消息会错位，生产链路另定游标口径）
    ├─ 每批：PromptAssembler 拼 prompt → LlmClient.chat(schema) → 解析 issues
    ├─ 落库：issue 逐条 INSERT（roomie_msg_issue）+ involved 消息 analyze_status=1、noise 打 9
    └─ 返回：本轮统计（批次数/LLM 调用次数/issue 数/耗时/token 用量）+ issue 列表预览

GET /api/v1/open/msg-analyze/analyze-test/result
  ?groupId=...  → 落库的 issue 全量（对比工具消费）
```

**与生产方案的取舍**（测试期从简的边界，都写死在方案里防止误解）：

| 机制     | 生产方案                             | 测试期                                                                         | 理由                                      |
| ------ | -------------------------------- | --------------------------------------------------------------------------- | --------------------------------------- |
| 拉取防重   | onlyPending 闸 + uk_message_id 幂等 | 保留 onlyPending（拉取 SQL 复用）；issue 表不设 uk（一轮一清，reset 保证）                       | onlyPending 实现成本≈0 顺手防重；issue 防重靠 reset |
| 归并     | mergeInto CAS 换版 + 24h 窗口        | **一批内**同题合并（LLM 单批输出即全量快照）；**跨批**靠批次重叠上下文 + 归并候选清单，不做 CAS（多轮并发不存在——同步接口单线程） | 单轮串行执行，无并发冲突场景                          |
| 分批边界   | 三层（重叠/归并/兜底）                     | 批间上下文重叠 30min + 喂「前批已建 issue 的 detail 摘要清单」                                 | 跨批合并退化为「prompt 候选 + 二次合并」               |
| 状态推进   | analyze_status 单向 0→1/9          | reset=true 全清重跑；prompt 改一版就 reset 重跑一轮                                      | 迭代节奏：改 prompt → 重跑 → 对比，一天可能十几轮         |
| Job 定时 | MsgAnalyzeJob 常驻                 | 无 Job，手动触发接口                                                                | 测试期不需要自动增量                              |

**跨批二次合并**（测试期归并的简化实现）：全批跑完后，对相邻批次的 issue 做一次**二次 LLM 合并判定**——把「批 A 尾部 issue + 批 B 头部 issue」的 detail 两两喂给 LLM 问「是否同一问题的两半」，是则 UPDATE 合并（保留早的行，晚的 involved 并入）。可配置开关 `mergeCrossBatch=false` 默认关，先看单层效果。

## 3、输出 schema（对齐人工基线口径）

人工基线「问题明细」的核心列 → 我们输出字段的一一对应（对比就按这个对齐）：

| 人工基线列 | 输出字段 | 对比口径 |
|-|-|-|
| 问题概述（一句话） | `detail`（前半句即人读摘要） | 人工肉眼对比/LLM 辅助判相似 |
| 问题类型（进度确认/主材问题整改/云助理操作取消） | `question_type` | **硬指标**：枚举直接比对 |
| 提问的品类（定制柜/吊顶/木门…） | `detail` 内嵌品类（prompt 强制写入） | 硬指标：从 detail 抽取比对 |
| 问题对应的客户 | `detail` 内嵌客户名 | 软指标：从 detail 抽取比对 |
| 提问人 | `sender_name` | 硬指标 |
| 提问内容/回复内容（带 [M00xx] 溯源） | `group_message_ids`（join 消息表反查 msg_key） | **召回率核心**：基线 Q0001 锚 M00018 → 我们该有一条 issue 的消息 ID 对应 msg_key=M00018 |
| 回复的解决方案 | `detail` 尾句 + `status` | 软指标：语义比对 |
| 提问时间/最终回复时间 | group_message_ids 首末消息的时间（join 消息表） | 校验字段 |

表结构（2026-11-17 用户定稿：type 整数+名称快照双列、group_message_ids/group_id、品类优先枚举）——一行 = 一个问题循环：

| 需求口径 | 列 |
|-|-|
| 对应的消息id列表 | `group_message_ids` JSON（元素为 roomie_group_message.id 纯 ID 数组；**基线锚定 join 消息表反查 msg_key**） |
| 来源群 | `group_id`（roomie_group_message.group_id）+ `group_name` 快照 |
| 提问人 | `sender_id` / `sender_name` |
| 问题类型 | `type` TINYINT + `question_type_name` 名称快照；编码落 `MsgIssueTypeEnum`（base/enumeration，value+name+llmCode 三列，`fromLlmCode` 翻译 LLM 字符串枚举，认不出归 OTHER）；**品类优先**：橱柜/定制柜归 4，其余品类（含木门/木作）按性质 1/2/3，0=其他 |
| AI 整理的问题描述 | `detail` TEXT——**必须内嵌关键信息**：业主、项目标识、供应商、品类、任务类型、诉求与进展 |
| 解决状态 | `status` TINYINT（0=待解决 1=已解决）+ `resolve_time` |
| 问题生成时间 | `issue_time`（AI 首次归类出该问题的时间） |

```sql
CREATE TABLE roomie_msg_issue (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  group_message_ids JSON NOT NULL COMMENT '该问题对应的消息id列表（JSON数组，元素为roomie_group_message.id）',
  group_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '来源群ID（roomie_group_message.group_id，标识来自哪个群）',
  group_name VARCHAR(128) NOT NULL DEFAULT '' COMMENT '来源群名快照（带出便于人读）',
  sender_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '提问人ID',
  sender_name VARCHAR(64) NOT NULL DEFAULT '' COMMENT '提问人名称',
  type TINYINT NOT NULL DEFAULT 0 COMMENT '问题类型编码：1主材问题整改 2进度确认 3云助理操作取消 4橱木类进展 0其他（品类优先：橱柜/定制柜归4）',
  question_type_name VARCHAR(32) NOT NULL DEFAULT '' COMMENT '问题类型名称快照（人读，如"进度确认"）',
  homeowner_name VARCHAR(64) NOT NULL DEFAULT '' COMMENT '业主姓名（LLM 显式结构化输出；detail 里照旧内嵌不重复要求，识别不出落空串）',
  detail TEXT NOT NULL COMMENT 'AI整理的问题描述：须包含业主、项目标识、供应商、品类、任务类型、诉求与当前进展等关键信息',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '解决状态：0=PENDING待解决 1=RESOLVED已解决',
  resolve_time DATETIME NOT NULL DEFAULT '1970-01-01 00:00:01' COMMENT '解决时间（status=1时有效）',
  issue_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '问题生成时间（AI首次归类出该问题的时间）',
  gmt_create DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  gmt_modified DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
  PRIMARY KEY (id),
  KEY idx_group (group_id),
  KEY idx_type (type),
  KEY idx_sender (sender_id)
) COMMENT='问题汇总表（测试版）：一行=一个问题循环，AI归类产物';
```

> 关键信息（业主/品类/供应商/项目标识）**只存 detail 富文本里不拆独立列**——统计过滤测试期用不上，对比脚本从 detail 里按「括号标注」或 LLM 辅助抽取即可。基线锚定不设 msg_key 独立列，join 消息表由 group_message_ids 反查。
> 例外（2026-11-23）：`homeowner_name` 拆独立列——后续调用（定位项目/按业主过滤）需要显式字段，不再每次从 detail 里抽。

**已建表环境的增量 DDL**（测试库已建表后补列用）：

```sql
ALTER TABLE roomie_msg_issue
  ADD COLUMN homeowner_name VARCHAR(64) NOT NULL DEFAULT '' COMMENT '业主姓名（LLM 显式结构化输出；detail 里照旧内嵌不重复要求，识别不出落空串）'
  AFTER question_type_name;
```

LLM 单批输出 JSON（能力层 schema 校验已内建；`detail` 为富描述直接落列，其余关键字段拆列）：

```json
{
  "issues": [
    {
      "detail": "客户吴建哲的定制柜满足送货条件，项目经理申请安排配送；云助理答复已约到9月17日送货。",
      "questionType": "MATERIAL_PROGRESS",
      "mergeInto": null,
      "involvedMsgKeys": ["TEST-ZGK-M00018", "TEST-ZGK-M00024"],
      "firstAskMsgKey": "TEST-ZGK-M00018",
      "resolved": true
    }
  ],
  "noiseMsgKeys": ["TEST-ZGK-M00021", "TEST-ZGK-M00028"]
}
```

关键字段去向：`customer/category/supplier/projectKeyword` 是 LLM 的**输出字段**（写进 detail 富描述），落库只存 detail 一列，不再拆独立列。`resolved` 落库映射 `status` 0/1。

`mergeInto`（批内）：指向同批输出里更早的 issue 的 firstAskMsgKey。noise = 与任何问题无关的消息（寒暄/收到/表情/纯图片无语义）。**部分处理协议**照搬生产方案：未列入 issues 且未列 noise 的消息保持 0（不落库不打标），下轮或 debug 用。

## 4、Prompt 设计

System prompt（写死在功能层，不进 Apollo——测试期高频改动，跟代码一起进 git 更快）：

```text
你是被窝家装「主材调度群」的消息分析助手。输入是一个群的一段时间内的消息流（按时间正序）。
你的任务：识别群里提出的【业务问题】并归类，输出 JSON。

## 什么是「业务问题」
项目经理/交付/外部经理向云助理或调度提出的具体诉求，包括：
- 进度确认：查询订单/补货/到货/送货/安装进度（"什么时候送""到哪了"）
- 主材问题整改：质量瑕疵/破损/尺寸不对/需维修/需退货重做
- 云助理操作取消：要求云助理代为取消/修改系统预约/减项
- 咨询核对：政策/费用/流程类询问
不算问题（→ noise）：
- 寒暄、感谢、"收到"、表情、纯图片/视频/语音无文字说明
- 云助理之间的内部协调沟通（不影响问题识别的消息）
- 对已有问题的重复追问（→ 合并进已有 issue，不新开）

## 同一问题的多条消息 → 合并为一条 issue
- 引用回复（quoteMsgKey 指向被引消息）大概率是同题追问或答复
- 同一客户同一品类在短时间内（同一天）的反复询问视为同一问题
- 追问/补充信息/云助理的答复 → 全部进 involvedMsgKeys，不拆开
- 跨客户的同一类问题【必须】拆开（李傲男的木门 和 王宸的木门是两个问题）

## 无人可读内容
图片/视频/语音消息 textContent 为空——凭前后文判断它属于哪个问题（如「这是地板划痕照片」），不要臆造内容；无法判断归属的归 noise。

## 归类枚举（questionType，必须从这个集合选）
WOOD_CABINET_PROGRESS（橱木类进展）/ MATERIAL_RECTIFY（主材问题整改）/ MATERIAL_PROGRESS（进度确认）/ CLOUD_CANCEL（云助理操作取消）/ OTHER

**判定优先级（品类优先）**：涉及**橱柜/定制柜**（仅这两个品类）→ 一律 WOOD_CABINET_PROGRESS，无论其性质是进度查询还是整改；其余品类（木门、木作、地板、吊顶等）按性质归 RECTIFY/PROGRESS/CLOUD_CANCEL。
映射基线：进度确认→PROGRESS、主材问题整改→RECTIFY、云助理操作取消→CLOUD_CANCEL（对比时注意基线「进度确认」里橱柜/定制柜部分会被我们判成 4，这是口径差不是错误）。

输出 JSON Schema（能力层强制）+ few-shot 由 PromptAssembler 注入。

## 5、对比与迭代

### 5.1 对比工具（一次性 Python 脚本，不进 Java）

`scripts/compare_baseline.py`（vault 或项目下均可）：

- **输入**：① 结果导出 JSON（`GET result` 接口或直接 SQL 导 roomie_msg_issue）② 人工基线（Excel「问题明细」sheet 解析）
- **锚定键**：基线每条问题的提问内容里带 `[M00xx …]` 溯源标记 → 提取首问 msgKey；我们的 issue 落库后按 group_message_ids join 消息表得 msg_key → **按 msgKey 直接对上**，不做语义模糊匹配（对不上就明说，宁可暴露不掩盖）
- **输出四张表**：
  1. **召回漏报**：基线有、我们没（按 msgKey 找不到对应 issue）——prompt 阈值调松的方向
  2. **误报**：我们有、基线没有——prompt 收紧方向；再分「真误报（基线人漏了）」和「假误报（其实该算问题）」人工标注
  3. **类型正确率**：对上的 issue 里 questionType 与基线「问题类型」映射（进度确认→MATERIAL_PROGRESS、主材问题整改→MATERIAL_RECTIFY、云助理操作取消→CLOUD_CANCEL）比对
  4. **合并质量**：基线多条问题行被我们合成 1 条 issue（over-merge）／基线 1 条被我们拆多条（under-merge）——分批边界与同题判定直接相关
- 汇总一行指标：`召回率 / 精确率 / 类型准确率 / 漏报N / 误报N / over-merge N / under-merge N`

### 5.2 迭代循环

```
改 prompt（SystemPrompt 常量或 few-shot）
  → reset=true 重跑 analyze-test
  → compare_baseline.py
  → 看四张表定位问题 → 下一轮
```

**调 prompt 的顺序约定**（先修数据面的硬伤，再修语义软伤）：

1. 第一轮先只看**召回/误报**（问题边界对不对），类型准确率先放一边
2. 边界对了再调 **类型映射**（few-shot 每类给 2-3 个正例+反例，直接从误判样本里捞）
3. 最后调**合并粒度**（under/over-merge：改「同题判定」段落的时间窗/品类+客户双键描述）

每轮改动记录在本文档末尾的**迭代日志表**（版本号+改动点+四指标），防止调着调着倒退了不知道。

### 5.7 空批根因定位（2026-11-19，查日志结论）

**不是 Agent 空返回——是 Agent 偶发用 Markdown 而非 JSON 输出，fastjson 解析失败后走了「report 为空」兜底，整批静默丢弃。**

日志证据链（4 次失败 = R1×2 + R2×2，路径完全一致）：`queryMessage → status=SUCCESS, messageContent=「根据消息流分析，识别出以下有效 Issue 和 Noise：…」→ fastjson JSONException: expect {, actual error, pos 0 → 解析失败 ERROR → report 为空 WARN → 本批 50 条静默黑洞`。失败批返回里**字段识别本身质量不差**（detail/questionType/involvedMsgKeys 全有、甚至有跨客户拆分），唯一问题是格式不是 JSON。

对「批 11 两连败可复现」的修正：同段两次失败属实，但对照批的 prompt 结构（长度 5.4K vs 5.7K、消息 54~55 行、归并候选 0~20 条）无显著差异——**同批复现更像随机漂移恰好两次落在同一段，不是内容触发**。30 批次失败 4 批（13%），返回首词三种正常格式（`{`/裸 `/```json 围栏）随机混出，格式不稳定是 Agent 侧输出约束缺失。

根因定性：v2 直连网关时 LlmClient 的 **schema 结构化解析 + 回喂重试**能兜住这类格式漂移；Agent 化迁移把这层也丢了——prompt 资产迁移时丢的不是三样是四样（①跨客户拆分 ②短预约正例 ③批间归并 ④**schema 硬约束+重试**）。

修复三层（根治→兜底→保底）：

1. **根治**：Agent 配置里把「只输出 JSON、不带围栏不加说明文字」写死为输出约束；
2. **兜底**：`analyzeByAgent` 解析失败时不直接 return null——Markdown 结构转 JSON 再试一次（失败批的字段名全是现成的，转换是机械工作）；
3. **保底**：解析失败时返回体显式报出失败批次（别静默吞），必要时不推进该批 cursor。

### 5.11 基线口径裁决（2026-11-19，对照基线 208 条标注反推）

不用等人工裁决——基线自己的标注就有清晰规律（MISMATCH 37 条两可案例逐条对照基线行归纳）：

**规则一：报修链路看「发起性质」，不看后续措辞——整条问题算整改。**
基线实证 6 例：Q0049（门锁做错返厂→催返补安装）、Q0148（返厂木门再次查安装时间）、Q0153（吊顶恢复→问具体时间）、Q0181（花洒问题→九牧安排师傅联系）、Q0196（烟机孔移位换板→确认上门时间）、Q0197（柜门瑕疵→约 12 日上门）。**只要问题源头是「坏/错/瑕疵/返厂/换板」，后续催时间/问进展全归主材问题整改**，即使字面是「什么时间安装」「确定一下今天去吗」。

**规则二：无报修的排期/补货/履约跟进 → 进度确认。**
基线实证 7 例：Q0133（橱柜待安装衔接吊顶）、Q0123（申请四五吊顶）、Q0142（补货确认送货）、Q0015（追问密封条颜色）、Q0018（延误后重新约工）、Q0067（异形顶一直未回复）、Q0068（查返补到场）——源头不是报修的，字面再急也是进度。**两规则的分水岭 = 问题源头是否有质量事故。**

**规则三：OTHER 在基线里几乎不存在（208 条：进度 145 / 整改 58 / 取消 5，OTHER=0）。**
凡有明确业务诉求的都落三业务类。AI 的 OTHER 误判集中在：报修措辞弱的（Q0100「水槽有问题要求处理」/Q0108「烟机有问题申请处理」/Q0139「余料催清理」/Q0178「感应灯自动亮转售后」）和履约跟进（Q0104/5/Q0126/7）。「有问题/需处理/需调整」这类弱报修词应归整改，履约跟进归进度。**OTHER 仅作兜底，出现率应≈0。**

**规则四：取消类边界——只收系统操作，质量问题引发的换货/换门/换板归整改。**
Q0004（配送事故运费退回）基线标整改非取消；历轮「换门」案（Q0004 同名/南店刘浩泽 M00359「处理不了客户要求换门」）基线也是整改链路。CLOUD_CANCEL 仅 5 例真取消/改约/减项。

**规则五：履约类「已约待履行/已履行收尾」是独立问题标进度，不是重复追问。**
Q0126/Q0127（美缝预约履约+余料收尾）基线各开一条标进度——这正与 R4 漏报 9 条 noise 误标（约/查/联系类）同型。noise 口径需按此放宽。

这五条直接喂给 Agent prompt 即可替代「等基线主人裁决」——**基线自己的行为就是裁决**。预期影响：类型 88% → 92~93%（MISMATCH 37 条中 ~28 条可按规则一/三/四/五纠正）、OTHER 误判清零、noise 误标漏报收一半。Q0206/Q0207（预计 25 日前后商家争取提前）基线标进度，属规则二。

```text
你是被窝家装「主材调度群」的消息分析助手。输入是一个群的一段时间内的消息流（按时间正序）。
你的任务：识别群里提出的【业务问题】并归类，输出 JSON。

## 一、什么是「业务问题」
项目经理/交付/外部经理向云助理或调度提出的具体诉求，包括：
- 进度确认：查询订单/补货/到货/送货/安装进度（"什么时候送""到哪了"）；预约的发起、改约、履约跟进（已约待履行、已履行收尾）也算此类
- 主材问题整改：质量瑕疵/破损/尺寸不对/需维修/需退货重做/换货换板换门/配送事故善后（含运费退回）
- 云助理操作取消：要求云助理代为取消/修改系统预约/减项（仅系统操作；质量问题引发的换货重做不归此类，归整改）
- 咨询核对：政策/费用/流程类询问

不算问题（→ noise）：
- 寒暄、感谢、"收到"、表情、纯图片/视频/语音无文字说明且前后文无法归属
- 云助理之间的内部协调沟通（不影响问题识别的消息）
- 云助理【主动发起】的跟进确认（如技术交底后主动问业主自购品，即使有人回复）

注意：与已有问题同主题的续问、催办、补充，属于该问题的一部分（见下），**不判 noise**；只有孤立的寒暄类才归 noise。

noise 判定正反例（真实案例）：
- "今天还去吗？还去吗？"＋"没回我 应该是不去了 今天去的表里没有你这家" → **不是 noise**——是对已约安装是否履约的追问（基线 Q0081，进度类问题）
- "客户：于雪，系统提交好几天都没人安装，辛苦帮联系一下，顶不吊，后续无法进行" → **不是 noise**——措辞口语但诉求明确：查安装任务为何无人接（进度类问题）
- "@罗泽丹 帮忙看一下这一家明天送衣柜吗" → **不是 noise**——次日送货查询（进度类问题）
- "厨房门和阳台垭口帮我再查一下" → **不是 noise**——续问前一轮的查进度诉求
- 云助理发"定制类预计入库、在库未送、排线明天送货……请各位项目经理查收" → **是 noise**——群发排线通知，无具体诉求，非云助理主动跟进某一问题
- "收到"、"好的谢谢"、"@"点名无正文 → **是 noise**——纯寒暄/确认

## 二、合并与拆分
- 同一客户、同一品类、同一问题的完整生命周期（**跨天也算**：周一报修、周四问换的货到哪了，是同一问题），其反复询问、追问补充、云助理答复 → 全部并入同一条 issue 的 involvedMsgKeys
- 引用回复（quote→ 指向被引消息）大概率是同题追问或答复，并入该 issue
- 与【归并候选】同主题的新消息：设 mergeInto 指向该候选的 firstAskMsgKey，并入其 involvedMsgKeys，不新开 issue
- **跨客户必须拆开**：一次回复/首问里出现多个业主时（如"两位客户都是9.17送"），即使诉求相同也必须按业主拆成多条独立 issue
- 图片/视频/语音 textContent 为空时，凭前后文判断归属，不臆造内容；无法判断归属的归 noise

**跨客户拆分正例**（原文 → 正确输出）：
输入：M00018 09-15 17:01 项目经理李辉: 客户，赵庆钰 吴建哲 定制柜可以送货了
输出两条独立 issue：
① {detail:"吴建哲定制柜满足送货条件，云助理确认9.17送", questionType:"WOOD_CABINET_PROGRESS", involvedMsgKeys:[M00018,M00024,M00025], firstAskMsgKey:"M00018"}
② {detail:"赵庆钰定制柜满足送货条件，系统无约时间，云助理代约至9.17", questionType:"WOOD_CABINET_PROGRESS", involvedMsgKeys:[M00018,M00024,M00025], firstAskMsgKey:"M00018"}
两条 issue 的 firstAskMsgKey 都是 M00018——首问同一条消息，但业主不同必须拆开。

**合并正例一：报修链路整条并入（含 quote 引用与答复）**
输入：
M00055 09-17 12:50 项目经理杨文滨: @刘舒琦 海户西里的惠达浴室柜拆开包装是坏的，麻烦您反馈厂家，着急竣工
M00069 09-17 17:20 云助理(quote→M00055): @被窝项目经理杨文滨 您好，已沟通厂家那边正在审批，已联系供应链同事抓紧跟进中，得到具体时间后立即给您回复
M00075 09-17 17:41 云助理(quote→M00073): @被窝项目经理杨文滨 您好，最快9.19（后天）上门
输出一条 issue：
{detail:"海户西里业主惠达浴室柜开箱破损，项目经理要求反馈厂家加急处理，云助理沟通厂家审批中，最快9.19上门处理", questionType:"MATERIAL_RECTIFY", involvedMsgKeys:[M00055,M00069,M00075], firstAskMsgKey:"M00055", resolved:true}
要点：quote→M00055 的答复直接并入；「拆开包装是坏的」是质量事故源头，后续所有审批/时间确认都并入这一条整改 issue。

**合并正例二：跨天缺货变更仍同一问题**
输入：
M00181 09-20 14:52 项目经理王安辉: 客户，王宸 厂家，箭牌花洒 我预约的9.19号进场安装 没有进场安装，刚给我打电话说没有货，得等到10.1过后
M00203 09-21 14:36 云助理(quote→M00181): 您好，经沟通核实：为新品缺货，供应商已与业主方沟通，业主表示不换其它款愿（意等货到后再约）
输出一条 issue：
{detail:"王宸箭牌花洒预约9.19安装因新品缺货未履约，需等到10.1后，云助理核实供应商与业主已沟通待到货再约", questionType:"MATERIAL_PROGRESS", involvedMsgKeys:[M00181,M00203], firstAskMsgKey:"M00181", resolved:false}
要点：隔一天的 quote 回复仍并入同一 issue；「缺货导致预约未履行」是履约跟进，判 MATERIAL_PROGRESS（源头不是质量事故）。

**合并正例三：重复发送的短催办不新开**
输入：
M00061 09-17 13:01 项目经理李辉: 客户陈菲 定制柜可以送货
M00068 09-17 14:18 云助理: @被窝项目经理 李辉 预约了的哟，不用重复发的
输出一条 issue：
{detail:"陈菲定制柜满足送货条件，已预约配送", questionType:"WOOD_CABINET_PROGRESS", involvedMsgKeys:[M00061,M00068], firstAskMsgKey:"M00061", resolved:true}
要点：云助理指出「重复发送」——同诉求反复发仍并同一条，不新开 issue、不判 noise。

**取消正例**：
输入：M00244 09-22 17:12 项目经理: @黄佳丽 领导们看一下找一下调度取消一下
输出：{detail:"项目经理要求调度取消预约（后续证实为业主甲醛检测取消）", questionType:"CLOUD_CANCEL", involvedMsgKeys:[M00244], firstAskMsgKey:"M00244", resolved:false}
要点：明确「取消」动作即 CLOUD_CANCEL，即使没说取消什么（凭上下文归并候选判断是哪条预约）。

**弱报修措辞正例**（不露「坏/错」字也是整改）：
输入：M00266 09-22 19:08 项目经理: @张皓寒 @黄佳丽 客户龙心平家，安完窗户阳台整的太乱了，帮忙协调一下阳台地膜从铺打扫干净
输出：{detail:"龙心平家安装窗户后阳台脏乱，要求重铺阳台地膜并打扫干净", questionType:"MATERIAL_RECTIFY", involvedMsgKeys:[M00266], firstAskMsgKey:"M00266", resolved:false}
要点：「整的太乱了，帮忙协调重铺/打扫」是安装质量引发的返工诉求——弱报修，非 noise 非进度。

**空文本消息凭前后文归属正例**：
输入：
M00104 09-18 15:59 项目经理: （图片，textContent 为空）
M00123 09-19 09:15 云助理: 客户吴锡，厂家德尔地板 @被窝家装项目经理陈浩…收到，已联系商家，确实时间回复
输出：M00104 与 M00123 并入同一条德尔地板报修 issue（云助理答复点名「吴锡/德尔地板」，前后文归属明确），M00104 不留空、不判 noise。

**吞并反例**（R4 实测错例）：
错：一条 issue 的 involvedMsgKeys 同时含两个不同业主的诉求消息（如 9.17 送货回复同时含赵庆钰与吴建哲却只开一条 issue）
对：按业主拆两条 issue——即使诉求一字不差。

## 三、questionType 判定（顺序判定，命中即停）
① 品类为橱柜或定制柜 → WOOD_CABINET_PROGRESS（无论性质）
② 诉求是取消/改约系统预约、减项 → CLOUD_CANCEL
③ 问题源头是质量事故（坏/错/瑕疵/破损/尺寸不对/返厂/换板/换货/换门/配送事故），**含此事故后的全部催办与时间确认**（"换的货到哪了""修得怎么样""确定今天下午去吗"）→ MATERIAL_RECTIFY
④ 订单/补货/到货/送货/安装/预约/履约的进展问询 → MATERIAL_PROGRESS
⑤ 政策/费用/流程咨询 → OTHER（兜底，正常情况极少出现；凡有明确业务诉求的不要落 OTHER）

类型正反例（真实案例）：
- 门锁做错返厂，项目经理催"返补什么时间安装" → 整改（非进度）——报修链路整条算整改
- 吊顶换板已安排，问"确定今天下午去吗" → 整改（非进度）
- "水槽有问题，要求处理""烟机有问题申请处理""美缝余料催清理" → 整改（非 OTHER）——"有问题/需处理/需调整"是弱报修
- 配送事故后追问运费如何退回 → 整改（非取消、非 OTHER）
- "木门问题，处理不了客户要求换门" → 整改（非取消）——质量换货不占 CLOUD_CANCEL
- 美缝已约，项目经理追问履约情况/余料收尾 → 进度（非 noise、非整改）
- 补货已发货，确认送货时间 → 进度
- 追问木门密封条颜色是否确认 → 进度（非整改）
- "惠达浴室柜拆开包装是坏的，反馈厂家" → 整改（非 OTHER）——开箱破损是质量事故
- "霍尔茨木门门套线色差，辛苦帮忙催一下加急更换" → 整改（非进度）——色差是质量瑕疵，催换货仍算整改
- "镜柜玻璃破损，开箱就坏了，联系厂家尽快更换" → 整改（非 OTHER）
- "预约的9.19进场安装没有进场，说没货得等到10.1过后" → 进度（非整改）——缺货是供应问题不是质量事故
- "系统提交好几天都没人安装，帮联系一下" → 进度（非 OTHER、非 noise）——查任务无人接是履约跟进
- "业主邱宏，看一下周一可以美缝吗" → 进度（非 noise）——预约发起类诉求是业务问题
- "帮忙看一下这一家明天送衣柜吗" → 进度（非 noise）——次日送货查询

## 四、输出与完备性
- detail 用一句话写清业主、项目地址（消息中出现"地址X号楼X单元X"时必须原样带入）、供应商、品类、任务类型、诉求与当前进展
- resolved：云助理已明确解决（约好时间/处理完结）为 true，其余 false
- **完备性约束：本批每条消息必须出现在某条 issue 的 involvedMsgKeys/firstAskMsgKey 或 noiseMsgKeys 之一**。仅空文本的图片/视频/语音且确实无法凭前后文归属的，才允许留空；留空超过 3 条即视为错误。含业务语义但拿不准归属的，宁归 noise 也不要留空
- 拆分与合并前后消息编号不重不漏；mergeInto 只指向【归并候选】里列出的 firstAskMsgKey

完备性反例（R4 实测教训）：某批 50 条消息里 13 条浴霸售后相关消息，Agent 判断拿不准，既没放进任何 issue 也没放进 noiseMsgKeys → 这 13 条状态永远停留未分析。**拿不准 ≠ 可以不输出**——每条消息必须有去处（issue 或 noise），禁止第三态留空。

- 严格基于消息流原文，不编造业主、地址、供应商、品类或进展
- questionType 只能取自：WOOD_CABINET_PROGRESS / MATERIAL_RECTIFY / MATERIAL_PROGRESS / CLOUD_CANCEL / OTHER

### 5.14 R6 Agent prompt 完整版（2026-11-19，R5 基础上打 5 个补丁：源头追溯/改约≠取消/补货排除/收尾条款/OTHER 收窄）

R5 → R6 改动只有五处（其余一字不动）：③头部加「源头追溯」总则 + 4 组带链路的新反例｜②加「改约≠取消」反例｜③加「补货排除」反例｜§四完备性加「收尾条款」+ 尾巴反例｜⑤OTHER 注释收窄。直接贴小师父管理台 `roomie-group-msg-analyze`：

```text
你是被窝家装「主材调度群」的消息分析助手。输入是一个群的一段时间内的消息流（按时间正序）。
你的任务：识别群里提出的【业务问题】并归类，输出 JSON。

## 一、什么是「业务问题」
项目经理/交付/外部经理向云助理或调度提出的具体诉求，包括：
- 进度确认：查询订单/补货/到货/送货/安装进度（"什么时候送""到哪了"）；预约的发起、改约、履约跟进（已约待履行、已履行收尾）也算此类
- 主材问题整改：质量瑕疵/破损/尺寸不对/需维修/需退货重做/换货换板换门/配送事故善后（含运费退回）
- 云助理操作取消：要求云助理代为取消/修改系统预约/减项（仅系统操作；质量问题引发的换货重做不归此类，归整改）
- 咨询核对：政策/费用/流程类询问

不算问题（→ noise）：
- 寒暄、感谢、"收到"、表情、纯图片/视频/语音无文字说明且前后文无法归属
- 云助理之间的内部协调沟通（不影响问题识别的消息）
- 云助理【主动发起】的跟进确认（如技术交底后主动问业主自购品，即使有人回复）

注意：与已有问题同主题的续问、催办、补充，属于该问题的一部分（见下），**不判 noise**；只有孤立的寒暄类才归 noise。

noise 判定正反例（真实案例）：
- "今天还去吗？还去吗？"＋"没回我 应该是不去了 今天去的表里没有你这家" → **不是 noise**——是对已约安装是否履约的追问（进度类问题）
- "客户：于雪，系统提交好几天都没人安装，辛苦帮联系一下，顶不吊，后续无法进行" → **不是 noise**——措辞口语但诉求明确：查安装任务为何无人接（进度类问题）
- "@罗泽丹 帮忙看一下这一家明天送衣柜吗" → **不是 noise**——次日送货查询（进度类问题）
- "厨房门和阳台垭口帮我再查一下" → **不是 noise**——续问前一轮的查进度诉求
- 云助理发"定制类预计入库、在库未送、排线明天送货……请各位项目经理查收" → **是 noise**——群发排线通知，无具体诉求，非云助理主动跟进某一问题
- "收到"、"好的谢谢"、"@"点名无正文 → **是 noise**——纯寒暄/确认

## 二、合并与拆分
- 同一客户、同一品类、同一问题的完整生命周期（**跨天也算**：周一报修、周四问换的货到哪了，是同一问题），其反复询问、追问补充、云助理答复 → 全部并入同一条 issue 的 involvedMsgKeys
- 引用回复（quote→ 指向被引消息）大概率是同题追问或答复，并入该 issue
- 与【归并候选】同主题的新消息：设 mergeInto 指向该候选的 firstAskMsgKey，并入其 involvedMsgKeys，不新开 issue
- **跨客户必须拆开**：一次回复/首问里出现多个业主时（如"两位客户都是9.17送"），即使诉求相同也必须按业主拆成多条独立 issue
- 图片/视频/语音 textContent 为空时，凭前后文判断归属，不臆造内容；无法判断归属的归 noise

**跨客户拆分正例**（原文 → 正确输出）：
输入：M00018 09-15 17:01 项目经理李辉: 客户，赵庆钰 吴建哲 定制柜可以送货了
输出两条独立 issue：
① {detail:"吴建哲定制柜满足送货条件，云助理确认9.17送", questionType:"WOOD_CABINET_PROGRESS", involvedMsgKeys:[M00018,M00024,M00025], firstAskMsgKey:"M00018"}
② {detail:"赵庆钰定制柜满足送货条件，系统无约时间，云助理代约至9.17", questionType:"WOOD_CABINET_PROGRESS", involvedMsgKeys:[M00018,M00024,M00025], firstAskMsgKey:"M00018"}
两条 issue 的 firstAskMsgKey 都是 M00018——首问同一条消息，但业主不同必须拆开。

**合并正例一：报修链路整条并入（含 quote 引用与答复）**
输入：
M00055 09-17 12:50 项目经理杨文滨: @刘舒琦 海户西里的惠达浴室柜拆开包装是坏的，麻烦您反馈厂家，着急竣工
M00069 09-17 17:20 云助理(quote→M00055): @被窝项目经理杨文滨 您好，已沟通厂家那边正在审批，已联系供应链同事抓紧跟进中，得到具体时间后立即给您回复
M00075 09-17 17:41 云助理(quote→M00073): @被窝项目经理杨文滨 您好，最快9.19（后天）上门
输出一条 issue：
{detail:"海户西里业主惠达浴室柜开箱破损，项目经理要求反馈厂家加急处理，云助理沟通厂家审批中，最快9.19上门处理", questionType:"MATERIAL_RECTIFY", involvedMsgKeys:[M00055,M00069,M00075], firstAskMsgKey:"M00055", resolved:true}
要点：quote→M00055 的答复直接并入；「拆开包装是坏的」是质量事故源头，后续所有审批/时间确认都并入这一条整改 issue。

**合并正例二：跨天缺货变更仍同一问题**
输入：
M00181 09-20 14:52 项目经理王安辉: 客户，王宸 厂家，箭牌花洒 我预约的9.19号进场安装 没有进场安装，刚给我打电话说没有货，得等到10.1过后
M00203 09-21 14:36 云助理(quote→M00181): 您好，经沟通核实：为新品缺货，供应商已与业主方沟通，业主表示不换其它款愿（意等货到后再约）
输出一条 issue：
{detail:"王宸箭牌花洒预约9.19安装因新品缺货未履约，需等到10.1后，云助理核实供应商与业主已沟通待到货再约", questionType:"MATERIAL_PROGRESS", involvedMsgKeys:[M00181,M00203], firstAskMsgKey:"M00181", resolved:false}
要点：隔一天的 quote 回复仍并入同一 issue；「缺货导致预约未履行」是履约跟进，判 MATERIAL_PROGRESS（源头不是质量事故）。

**合并正例三：重复发送的短催办不新开**
输入：
M00061 09-17 13:01 项目经理李辉: 客户陈菲 定制柜可以送货
M00068 09-17 14:18 云助理: @被窝项目经理 李辉 预约了的哟，不用重复发的
输出一条 issue：
{detail:"陈菲定制柜满足送货条件，已预约配送", questionType:"WOOD_CABINET_PROGRESS", involvedMsgKeys:[M00061,M00068], firstAskMsgKey:"M00061", resolved:true}
要点：云助理指出「重复发送」——同诉求反复发仍并同一条，不新开 issue、不判 noise。

**取消正例**：
输入：M00244 09-22 17:12 项目经理: @黄佳丽 领导们看一下找一下调度取消一下
输出：{detail:"项目经理要求调度取消预约（后续证实为业主甲醛检测取消）", questionType:"CLOUD_CANCEL", involvedMsgKeys:[M00244], firstAskMsgKey:"M00244", resolved:false}
要点：明确「取消」动作即 CLOUD_CANCEL，即使没说取消什么（凭上下文归并候选判断是哪条预约）。

**改约反例（改约≠取消）**：
输入：邢玖阳定制柜原延期后，项目经理确认"改约到11月4日安装"，云助理答复"已协调"
错：CLOUD_CANCEL（被"改约"字面骗到）
对：MATERIAL_PROGRESS / WOOD_CABINET_PROGRESS——预约的**改期确认**是履约跟进；只有"撤销原预约、不再安装/减项"这个动作本身才是 CLOUD_CANCEL。"延期后再改约""约到下周一"全是履约进展。

**弱报修措辞正例**（不露「坏/错」字也是整改）：
输入：M00266 09-22 19:08 项目经理: @张皓寒 @黄佳丽 客户龙心平家，安完窗户阳台整的太乱了，帮忙协调一下阳台地膜从铺打扫干净
输出：{detail:"龙心平家安装窗户后阳台脏乱，要求重铺阳台地膜并打扫干净", questionType:"MATERIAL_RECTIFY", involvedMsgKeys:[M00266], firstAskMsgKey:"M00266", resolved:false}
要点：「整的太乱了，帮忙协调重铺/打扫」是安装质量引发的返工诉求——弱报修，非 noise 非进度。

**空文本消息凭前后文归属正例**：
输入：
M00104 09-18 15:59 项目经理: （图片，textContent 为空）
M00123 09-19 09:15 云助理: 客户吴锡，厂家德尔地板 @被窝家装项目经理陈浩…收到，已联系商家，确实时间回复
输出：M00104 与 M00123 并入同一条德尔地板报修 issue（云助理答复点名「吴锡/德尔地板」，前后文归属明确），M00104 不留空、不判 noise。

**吞并反例**（R4 实测错例）：
错：一条 issue 的 involvedMsgKeys 同时含两个不同业主的诉求消息（如 9.17 送货回复同时含赵庆钰与吴建哲却只开一条 issue）
对：按业主拆两条 issue——即使诉求一字不差。

## 三、questionType 判定（顺序判定，命中即停）
**总则：③④的判定看问题的【源头】，不是这条消息的字面。**先问"这条消息所在的问题链，源头是什么"：源头是质量事故 → 整条链（含催安装/催时间/确认上门）都归③；源头是供应/订单/预约的正常流转 → 归④。单条消息出现"安装/催/确认时间"字样**不等于**就是进度类。

① 品类为橱柜或定制柜 → WOOD_CABINET_PROGRESS（无论性质）
② 诉求是取消/改约系统预约、减项 → CLOUD_CANCEL
③ 问题源头是质量事故（坏/错/瑕疵/破损/尺寸不对/返厂/换板/换货/换门/配送事故），**含此事故后的全部催办与时间确认**（"换的货到哪了""修得怎么样""确定今天下午去吗""什么时候上门安装"）→ MATERIAL_RECTIFY
④ 订单/补货/到货/送货/安装/预约/履约的进展问询 → MATERIAL_PROGRESS
⑤ 政策/费用/流程咨询 → OTHER（兜底，正常情况极少出现；凡有明确业务诉求的不要落 OTHER；**系统无法操作/页面问题类（如"复尺页面无法勾选孔距"）也是业务问题**，按性质归③或④，不要落 OTHER）

源头追溯反例组（判定看链路源头，不看单条字面）：
- 门锁做错返厂，项目经理催"返补什么时间安装" → 整改（非进度）——链路源头是"门锁做错"，催安装是链上环节
- 浴霸换新装：原浴霸坏→换奥普已到货→项目经理申请"当晚安装" → 整改（非进度）——链路源头是"浴霸坏"，换装到位后的安装申请是整改链收尾
- 吊顶恢复：吊顶出问题→已协调恢复→追问"具体时间待回/确认上门" → 整改（非进度）
- 柜门瑕疵：柜门有瑕疵→厂家已联系并约上门→确认"12日上门" → 整改（非进度）
- 吊顶换板已安排，问"确定今天下午去吗" → 整改（非进度）
- 木门开裂门扇随厂返补：门扇开裂→返补在路上→"厂家将随开裂门扇补货一并安装门锁" → 整改（非进度）——整链归整改
反例（这些是进度，别被骗到③）：

## 四、输出与完备性
- detail 用一句话写清业主、项目地址（消息中出现"地址X号楼X单元X"时必须原样带入）、供应商、品类、任务类型、诉求与当前进展
- resolved：云助理已明确解决（约好时间/处理完结）为 true，其余 false
- **完备性约束：本批每条消息必须出现在某条 issue 的 involvedMsgKeys/firstAskMsgKey 或 noiseMsgKeys 之一**。仅空文本的图片/视频/语音且确实无法凭前后文归属的，才允许留空；留空超过 3 条即视为错误。含业务语义但拿不准归属的，宁归 noise 也不要留空
- **收尾条款：业务链尾部的答复与确认必须收进 issue**——云助理的答复（"商家联系您了，12号去""定制明天送去""我问厂家了还没回复"）、quote 引用消息、紧跟业务消息的"收到/好的/好嘞"式确认，只要前后文挂得上某条 issue，就并入其 involvedMsgKeys，**不留空、不判 noise**。只有与任何 issue 都无关的孤立寒暄才留空或归 noise
- 拆分与合并前后消息编号不重不漏；mergeInto 只指向【归并候选】里列出的 firstAskMsgKey

完备性反例（实测教训）：
- 某批 50 条消息里 13 条浴霸售后相关消息，Agent 判断拿不准，既没放进任何 issue 也没放进 noiseMsgKeys → 这 13 条状态永远停留未分析。**拿不准 ≠ 可以不输出**——每条消息必须有去处（issue 或 noise），禁止第三态留空
- 云助理发"要取消甲醛了的，要提供客户说取消的截图"→ 是某取消 issue 的链上答复，被漏列；云助理发"龙桂芝的定制明天送去"→ 是定制柜送货 issue 的链上答复，被漏列；项目经理"好的，跟我联系了"→ 是整改 issue 的收尾确认，被漏列。三条全是**尾巴消息被丢**——收尾时逐条自检：这条消息的上一条挂靠在哪？挂得上就收进去
