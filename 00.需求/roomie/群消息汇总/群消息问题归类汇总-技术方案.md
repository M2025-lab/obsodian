# 群消息问题归类汇总-技术方案

> 飞书文档：<链接占位>

## 1、背景[必选]

- 需求文档：[[00.需求/roomie/云助理群场景提效·Roomie接入初版方案]] §3.1（优先级 ①：群消息问题归类汇总）、[[10.工作/技术方案/云助理Roomie-群场景提效-技术方案]] §4.4（三层清洗归类与演进路径）
- 范围：roomie 群消息**已通过 kafka 事件落库**（`roomie_group_message`，eden-agenda 运行中）；本期做 4.4 演进路径中「AI 分析归类」的**数据层**——新增**问题汇总表** + **供 AI 调用的两个接口**（消息查询接口 + 归类结果落库接口），把落库消息归类为几个问题类型并汇总统计。

现状：群消息全量落库已完成（消费 `huiju-chat-workbench-chat-group` topic，`RoomieGroupChatHandler.java:47`），但消息只是原始记录，没有「哪些是问题、属于什么类型」的结构化归类——云助理仍需人工翻消息流。本次把归类动作交给 AI（编排在外部：Roomie Agent / 独立 job），eden-agenda 只提供数据读写接口。

> 边界：消息拉取落库链路（已上线）、层2 解决方式/层3 具体行为（已确认只做层1 问题类型）、侧边栏展示页、转发/外呼/自动回复——本期均不做。

## 2、需求理解[必选]

| # | 需求点 | 口径（已确认） |
|-|-|-|
| 1 | AI 链路位置 | **数据接口 + 外部 AI**：eden-agenda 只出消息查询/归类落库数据 API，AI 编排在 Roomie Agent/Skill 或独立 job 调用；服务内不依赖 LLM 网关选型 |
| 2 | 归类深度 | **只做层1 问题类型**（总方案 4.4 三层中的层1：是否是问题、问题类型、归属项目与供应商线索）；层2 解决方式/层3 具体行为不做，但表结构预留字段位（避免二期上三层时改表） |
| 3 | 数据库 | 新增**问题汇总表**（一条问题消息一条记录），承载归类结果与汇总统计 |
| 4 | 接口 | 两个供 AI 调用：① **查聊天数据库接口**（按群/时间增量拉取待分析消息，带防重机制）；② **落库接口**（AI 分析结果批量写入问题汇总表） |
| 5 | 汇总形态 | 明细表 + 聚合查询接口（按问题类型/群/时间统计），不单独建汇总结果表 |
| 6 | 防重 | 双保险：消息表加分析状态列（单向流转）+ 问题表消息唯一键——同一条消息不允许被反复识别问题（总方案 §2-16 口径） |

## 4、详细设计

### 4.0 总体链路

```
roomie_group_message（已落库，kafka 事件链路不变）
   ▲ 读（增量游标）                    │ 状态回写（analyze_status 0→1）
   │                                  ▼
┌─────────────────────────────────────────────────┐
│ eden-agenda：两个 open 数据接口                    │
│  GET  /api/v1/open/msg-analyze/pending   ← AI 侧拉 │
│  POST /api/v1/open/msg-analyze/report    ← AI 侧回 │
│  GET  /api/v1/open/msg-analyze/summary   ← 汇总统计 │
└─────────────────────────────────────────────────┘
   ▲                        │
   │ HTTP（外部 AI 编排：Roomie Agent / 独立 job）    │
   ▼
问题类型标签 + 归属线索 ──→ roomie_msg_issue（问题汇总表）
```

AI 侧职责：拉取待分析消息 → 调 LLM 判断是否问题 + 问题类型 → 回传结构化结果。eden-agenda 职责：圈定增量范围（防重）、存储归类结果、汇总统计。两侧仅以 HTTP 接口耦合，LLM 选型/prompt/编排节奏完全在外部（对应总方案 4.4 的 TODO「LLM 网关选型未定」——本期不被它卡住）。

### 4.1 查询接口（供 AI 拉取待分析消息）

复用 §3 游标分页先例（`msg_time DESC, id DESC` 复合游标 + hasMore），拉取方向改为**时间正序**（AI 按聊天顺序理解上下文更自然）：

| 参数 | 类型 | 说明 |
|-|-|-|-|
| groupChannelId | String | 可选，按群过滤 |
| startTime / endTime | Long(毫秒) | 可选，时间窗 |
| onlyHuman | Boolean | 默认 **true**：`sender_type IN (1,2,3)`（过滤机器人/AI 消息，口径同 RoomieAdminMapper.xml:66） |
| onlyPending | Boolean | 默认 **true**：`analyze_status = 0`（只拉未分析——防重的第一道闸） |
| cursorTimeMillis / cursorId | Long | 复合游标（同 §3 先例）；**首游标**由 AI 侧持久化，从上次处理位置继续 |
| pageSize | Integer | 默认 50，上限 200（单批喂 LLM 的条数上限） |

返回字段：`id / msgKey / groupId / groupChannelId / groupName / senderId / senderName / senderType / msgType / textContent / msgTime / analyzeStatus / nextCursorTime / nextCursorId / hasMore`。

上下文构造（同群前后消息）**由 AI 侧用 groupChannelId + 时间窗自查**，不在本接口展开——本接口只管圈定待分析增量。

### 4.2 落库接口（AI 回传归类结果）

`POST /api/v1/open/msg-analyze/report`，body 为数组（批量，一次回传一批消息的归类）：

```json
{
  "results": [
    {
      "messageId": 12345,                    // roomie_group_message.id
      "isQuestion": true,                    // false → 标记 analyze_status=9（噪音），不进问题表
      "questionType": "MATERIAL_PROGRESS",   // 层1 问题类型枚举（见 4.3）
      "questionSummary": "问定制柜什么时候安装",  // AI 一句话摘要（列表展示用）
      "projectKeyword": null,                // 归属线索【可选】AI 从消息中抽到的项目标识/业主名
      "supplierKeyword": null,               // 归属线索【可选】供应商/品牌关键词
      "confidence": 0.92                     // AI 置信度
    }
  ]
}
```

写入逻辑（服务端，逐条处理）：

| 场景 | 行为 |
|-|-|
| isQuestion=false | 只更新消息行 `analyze_status=9`（噪音跳过）——不进问题表 |
| isQuestion=true 且 messageId 未在问题表 | insert 问题表（uk_message_id 唯一键防重）+ 更新消息行 `analyze_status=1` |
| messageId 已在问题表（重复回传） | update 覆盖归类字段 + 状态保持 1（重分析覆盖语义） |

> 防重双保险（§2-6 口径）：① 接口圈定 `analyze_status=0`（4.1），已分析消息不会再被拉到；② 问题表 `uk_message_id` 唯一键兜底——即使双通道并发写，一条消息最多一条问题记录。`analyze_status` 单向流转（0→1/9），不回退。

### 4.3 问题类型枚举（层1，沿用总方案 4.4 口径）

| code | 含义 | 典型消息 |
|-|-|-|
| MATERIAL_RECTIFY | 主材问题整改 | 供应商责任类：整改、谁负责 |
| DELIVERY_ADJUST | 送装预约与调整 | 改约、取消订单（甲醛不做了） |
| BIZ_VERIFY | 业务办理与信息核实 | 各类办理事项与核实 |
| CUSTOM_CABINET | 定制柜进度咨询 | 台账/系统可查的进度问询 |
| MATERIAL_PROGRESS | 主材进度确认 | 系统依赖供应商数据的进度问询 |
| OTHER | 其他/兜底 | 是问题但不属于上述五类 |

> 枚举仅作为接口约定传给 AI 侧（prompt 里定义）；服务端**不校验枚举合法性**（存原字符串），后续类型调整不动服务代码——一期类型还在摸索期，避免改枚举就发版。

### 4.4 问题汇总表模型

一张明细表承载归类结果（汇总走聚合查询，不建结果表）：

| 字段 | 类型 | 说明 |
|-|-|-|
| message_id | BIGINT | 来源消息 ID（uk 唯一键） |
| msg_key / group_channel_id / group_name | VARCHAR | 消息定位三件套（从消息表带出，免 join） |
| sender_id / sender_name | VARCHAR | 提问人（「以人为维度」汇总的分组键） |
| question_type | VARCHAR(32) | 层1 问题类型（4.3 枚举） |
| question_summary | VARCHAR(256) | AI 摘要 |
| project_keyword / supplier_keyword | VARCHAR(128) | 归属线索（原样存 AI 抽取值；映射校准是二期事） |
| confidence | DECIMAL(4,3) | AI 置信度 |
| resolve_method / action_param | 预留 | 层2/层3 字段位（本期恒空，**避免二期上三层时改表**） |
| analyze_time | DATETIME | 归类落库时间 |

### 4.5 汇总统计接口

`GET /api/v1/open/msg-analyze/summary`：按维度聚合返回，供展示/评估用。

| 参数 | 说明 |
|-|-|
| groupChannelId / questionType | 可选过滤 |
| startTime / endTime | 时间窗（默认近 7 天） |
| groupBy | `question_type`（默认）/ `sender_id` / `group_channel_id` |

返回：各分组的问题条数 + 占比 + 明细下钻（`GET /msg-analyze/issues` 分页查问题表明细，游标分页同 4.1 模式）。对应总方案一期目标「拿到问题和问题归类的数量」。

## 5、接口改动

全部为**新增**接口（新增 `MsgAnalyzeController`，对齐 ExcelPushController.java:29 的 `/api/v1/open/**` 风格；存量接口零改动——kafka 落库链路与管理页查询不动）：

| 接口路径 | 接口文档 | 改动点 | 估时 |
|-|-|-|-|
| `GET /api/v1/open/msg-analyze/pending` | 待分析消息分页（4.1）：时间正序游标 + onlyPending + onlyHuman | 新增 Controller → `MsgAnalyzeService.pagePending` → 复用 `RoomieGroupMessageDao` 扩展查询 | |
| `POST /api/v1/open/msg-analyze/report` | AI 归类结果批量落库（4.2）：数组 body，逐条 upsert 问题表 + 回写 analyze_status | 新增 Controller → `MsgAnalyzeService.report` → 问题表 Dao（新增） | |
| `GET /api/v1/open/msg-analyze/summary` | 汇总统计（4.5）：groupBy 聚合 | 新增 Controller → `MsgAnalyzeService.summary` → 聚合 SQL | |
| `GET /api/v1/open/msg-analyze/issues` | 问题明细分页（4.5 下钻） | 新增 Controller → `MsgAnalyzeService.pageIssues` | |

> 消息表 `analyze_status` 回写在 report 接口内完成（4.2 写入逻辑表），无独立回写接口；kafka 消费链路（RoomieGroupChatHandler）**零改动**——analyze_status 落库时默认 0，无需动 handler。

## 7、表结构改动

```sql
-- 新增：问题汇总表（一条问题消息一条记录）
CREATE TABLE roomie_msg_issue (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  message_id BIGINT UNSIGNED NOT NULL COMMENT '来源消息ID（roomie_group_message.id）',
  msg_key VARCHAR(128) NOT NULL DEFAULT '' COMMENT '消息定位key（带出免join）',
  group_channel_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '来源群channelId（带出）',
  group_name VARCHAR(128) NOT NULL DEFAULT '' COMMENT '群名快照（带出）',
  sender_id VARCHAR(64) NOT NULL DEFAULT '' COMMENT '提问人ID（以人为维度汇总的分组键）',
  sender_name VARCHAR(64) NOT NULL DEFAULT '' COMMENT '提问人名称（带出）',
  question_type VARCHAR(32) NOT NULL DEFAULT 'OTHER' COMMENT '层1-问题类型：MATERIAL_RECTIFY/DELIVERY_ADJUST/BIZ_VERIFY/CUSTOM_CABINET/MATERIAL_PROGRESS/OTHER',
  question_summary VARCHAR(256) DEFAULT NULL COMMENT 'AI一句话摘要',
  project_keyword VARCHAR(128) DEFAULT NULL COMMENT '归属线索：项目标识/业主名（AI原样抽取值）',
  supplier_keyword VARCHAR(128) DEFAULT NULL COMMENT '归属线索：供应商/品牌关键词',
  confidence DECIMAL(4,3) NOT NULL DEFAULT 0 COMMENT 'AI置信度',
  resolve_method VARCHAR(32) DEFAULT NULL COMMENT '层2-解决方式（预留，本期恒空）',
  action_param JSON COMMENT '层3-具体行为（预留，本期恒空）',
  analyze_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '归类落库时间',
  gmt_create DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  gmt_modified DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_message (message_id),
  KEY idx_type_time (question_type, analyze_time),
  KEY idx_sender (sender_id),
  KEY idx_group (group_channel_id)
) COMMENT='问题汇总表：AI归类结果（层1问题类型），一条问题消息一条记录';

-- 变更：消息表加分析状态列（防重第一道闸）
ALTER TABLE roomie_group_message
  ADD COLUMN analyze_status TINYINT NOT NULL DEFAULT 0 COMMENT 'AI分析状态：0=未分析 1=已归类为问题 9=噪音（非问题）',
  ADD KEY idx_analyze_status (analyze_status, msg_time);
```

## 8、风险评估

| # | 风险点 | 评估 |
|-|-|-|
| 1 | **report 批量写放大**：AI 侧单批回传（上限 200 条/批，4.1 pageSize 上限对齐），逐条 upsert 问题表 + 更新消息行 = 2×N 条 DML | 问题表 insert 与消息行 update 分组批量执行（batch executor）；单接口加总耗时日志，超 3s 告警。量级参考：3 个 PM 群 4.1 条问询/天，全量消息日均百级，单批远到不了上限 |
| 2 | **pending 接口游标扫描走索引**：`analyze_status=0` 存量随时间只增不减（AI 未消费时积压） | `idx_analyze_status (analyze_status, msg_time)` 复合索引覆盖查询；AI 侧首游标从当前时间起（不回刷全量历史），存量历史消息按需一次性圈定时间窗处理 |
| 3 | **summary 聚合查询**：全表 GROUP BY 在问题表数据量增长后变慢 | 时间窗强制（默认近 7 天，必带 analyze_time 范围）；idx_type_time / idx_sender 索引前缀命中分组列 |
