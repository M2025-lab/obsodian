## 1、背景[必选]

- 需求文档：[[00.需求/roomie/云助理群场景提效·Roomie接入初版方案]] §3.1（优先级 ①：群消息问题归类汇总）、[[10.工作/技术方案/云助理Roomie-群场景提效-技术方案]] §4.4（三层清洗归类与演进路径）
- 范围：roomie 群消息**已通过 kafka 事件落库**（`roomie_group_message`，eden-agenda 运行中）；本期做 4.4 演进路径中「AI 分析归类」的**数据层**——新增**问题汇总表** + **供 AI 调用的两个接口**（消息查询接口 + 归类结果落库接口），把落库消息归类为几个问题类型并汇总统计。

> 边界：消息拉取落库链路（已上线）、层2 解决方式/层3 具体行为（已确认只做层1 问题类型）、侧边栏展示页、转发/外呼/自动回复——本期均不做。

## 2、需求理解[必选]

## 4、详细设计

### 4.0 总体链路

```
roomie_group_message（已落库，kafka 事件链路不变）
   │ 读（增量游标，analyze_status=0）    │ 状态回写（先写问题行后打标）
   ▼                                  ▲
┌──────────────────────────────────────────────────────┐
│ eden-agenda：msganalyze 功能层（本期新增）              │
│  MsgAnalyzeJob（定时，节奏可配）                        │
│   ├─ 拉取增量 → 拼 prompt → 调 LLM → 反序列化           │
│   ├─ 问题快照落库（4.2 写入逻辑）                       │
│   └─ 汇总统计（4.5）                                   │
├──────────────────────────────────────────────────────┤
│ LLM 能力层（通用，无业务语义——见 4.7）                  │
│  LlmClient.chat(systemPrompt, userPrompt, schema)    │
│   → 结构化 JSON（能力层做协议对接与解析重试）            │
├──────────────────────────────────────────────────────┤
│ 数据接口（open，联调/外部消费备选入口）                  │
│  GET pending / POST report / GET summary / issues    │
└──────────────────────────────────────────────────────┘
```

**分工**：能力层只管「prompt 进、JSON 出」（协议、鉴权、解析、重试）；功能层（msganalyze 包）管业务——拉取圈定（防重）、prompt 拼装、快照落库、汇总统计。AI 编排不再依赖外部消费方——job 在服务内闭环，open 接口保留为联调与后续 Roomie Agent/Skill 的消费入口。

### 4.1 查询接口（供 AI 拉取待分析消息）

复用 §3 游标分页先例（`msg_time DESC, id DESC` 复合游标 + hasMore），拉取方向改为**时间正序**（AI 按聊天顺序理解上下文更自然）：

| 参数 | 类型 | 说明 |
|-|-|-|-|
| groupChannelId | String | 可选，按群过滤 |
| startTime / endTime | Long(毫秒) | 可选，时间窗 |
| onlyHuman | Boolean | 默认 **true**：`sender_type IN (1,2,3)`（过滤机器人/AI 消息，口径同 RoomieAdminMapper.xml:66） |
| onlyPending | Boolean | 默认 **true**：`analyze_status = 0`（只拉未分析——防重的第一道闸） |
| cursorTimeMillis / cursorId | Long | 复合游标（同 §3 先例）；**首游标**由 AI 侧持久化，从上次处理位置继续 |
| pageSize | Integer | 默认 50，上限 200（单批喂 LLM 的条数上限） |

返回字段：`id / msgKey / groupId / groupChannelId / groupName / senderId / senderName / senderType / msgType / textContent / quoteMsgKey / msgTime / analyzeStatus / nextCursorTime / nextCursorId / hasMore`。`quoteMsgKey` = 被引用消息的 msg_key（消息表已存 quoteGlobalMsgId，RoomieGroupChatHandler.java:117；而 msg_key 优先取 globalMsgId，RoomieGroupChatHandler.java:139——两者天然对齐），是 AI 识别「同题追问」的主要锚点（见 4.2 归并）。

> 拉取语义 **at-least-once**：`analyze_status` 只在 report 落库成功时推进，AI 中途失败下轮重拉是预期行为（防丢）；重拉的重复回传由 `uk_message_id` 幂等吸收。AI 侧游标丢失同样无害——服务端按 `analyze_status` 过滤，不信任客户端游标。

上下文构造（同群前后消息）**由 AI 侧用 groupChannelId + 时间窗自查**，不在本接口展开——本接口只管圈定待分析增量。

### 4.2 落库接口（AI 回传问题快照）

`POST /api/v1/open/msg-analyze/report`——**回传单位是「问题」不是「消息」**：AI 一批拿 50 条消息，输出 K 个问题快照（K << 50），每个快照声明它吸收了哪些消息；判为噪音的消息显式列在 noise 清单。

```json
{
  "issues": [
    {
      "mergeInto": null,                     // 【归并·可选】归并到已有问题时传锚点（issueId / msgKey）
      "headline": "刘一彤家合金门什么时候安装",       // 一句话（列表展示）
      "questionType": "MATERIAL_PROGRESS",   // 层1 问题类型枚举（见 4.3）
      "confidence": 0.92,                    // AI 置信度
      "snapshot": {                          // 整合快照，两层：
        "detail": "PM张三 11-13 在赵公口群问刘一彤家（BJ12345）合金门安装时间；已知订单已到库未送、客户期望本周安装；供应商尚未答复",
        "elements": {                        // 机读五要素 → 人/后续 AI/Skill 可直接消费
          "asker":       {"name": "张三", "role": "PM", "senderId": "..."},
          "subject":     {"projectId": "BJ12345", "customer": "刘一彤", "category": "合金门", "supplier": "霍尔茨"},
          "intent":      "QUERY_INSTALL_SCHEDULE",
          "knownFacts":  ["订单已到库未送", "客户期望本周安装"],  // 含上下文中已有的答复
          "expected":    "安装排期时间"
        }
      },
      "involvedMessages": [
        {"messageId": 123, "role": "FIRST_ASK"},
        {"messageId": 125, "role": "FOLLOW_UP"},
        {"messageId": 126, "role": "REPLY", "fact": "云助理答：在库未送"}
      ]
    }
  ],
  "noiseMessageIds": [130, 131],             // 明确判为非问题的消息 id 列表
  "processedUpTo": {"cursorTimeMillis": 1763000000000, "cursorId": 8848}
}
```

**快照的两层结构**：

| 层 | 字段 | 消费方 |
|-|-|-|
| 人读层 | headline（列表）+ detail（详情页：全量重写的完整描述，不是首问原文+计数） | 云助理问题列表/详情 |
| 机读层 | elements 五要素：**谁问的**（asker）/**哪个项目**（subject：项目/客户/品类/供应商）/**什么诉求**（intent）/**已知事实**（knownFacts，含已有答复）/**期望产出**（expected） | 后续 AI 消费与 Skill 执行：intent 选 Skill、subject 填参数、knownFacts 进 prompt——即总方案层2/层3 的落地雏形，本期只产出结构、不驱动执行 |

**零散信息整合成一条的机制**：拆条/追问/引用/已有答复全部进 `involvedMessages`（每条标 role：FIRST_ASK / FOLLOW_UP / REPLY），REPLY 消息的结论抽进 `knownFacts`——一行问题快照即「这个问题的当前全貌」，人和 AI 都不需要回群消息流拼上下文。

写入逻辑（服务端，**逐 issue 处理**，每个 issue 一个事务）：

| 场景 | 行为 |
|-|-|
| 新问题（无 mergeInto） | insert 问题行（parent_issue_id=NULL，snapshot_version=1）→ involved 消息打 `analyze_status=1` |
| 归并（带 mergeInto，锚点=已有问题） | **CAS 换版**：`snapshot_version < 新版号` 才 update 快照字段（headline/detail/elements/knownFacts 全量覆盖）+ `ask_count` 原子自增、`last_ask_time` 更新 → 新 involved 消息打 `analyze_status=1`；旧版本回传被版本号挡掉（并发乱序安全） |
| 归并锚点解析失败（问题行不存在/已闭环） | 降级为独立新问题行 insert（不阻断整批），日志告警 |
| involved 里的 messageId 已是 1/9（重复回传/误吸收） | 跳过打标（状态单向流转），计数不重复加 |
| noise 清单消息 | 只打 `analyze_status=9` |

**部分处理协议（AI 一批没分析完时防丢）**：未出现在任何 issue 的 involvedMessages、也不在 noise 清单里的消息**保持 0 不动**，下轮重拉。因此 noise 必须显式声明——服务端**不做「没提到=噪音」的兜底推断**（会把未处理消息错杀成噪音）。

**问题层归并口径（防止同一问题被反复生成）**：

- 追问判定权在 AI（能看到上下文），服务端不做指纹/关键词去重——服务端硬校验是二次猜测，误合并（两条真不同的问询被指纹撞上）比偶发多计一条更伤统计：前者无声无息坏数据，后者抽检可见可修；
- 归并窗口 N 小时（默认 24h，Apollo 可配）：仅归并窗口内 `status=PENDING` 的未闭环问题；窗口外或已闭环的重问 = **新问题循环**（隔天重问是合法新问询，合并进旧问题反而丢时效信号）；
- 归并输出的是**新版全量快照**（AI 重写 detail/elements），不是增量拼接——快照永远是问题的当前全貌；
- 首问行 `ask_count` 即回答时效的代理指标：追问越多 = 越久没被解决（对应总方案 3.4 漏答提醒的数据底座）。

> 防重双保险（§2-6 口径）：① 接口圈定 `analyze_status=0`（4.1），已分析消息不会再被拉到；② 问题表 `uk_message_id` 唯一键兜底——即使双通道并发写，一条消息最多一条问题记录。`analyze_status` 单向流转（0→1/9），不回退。

### 4.3 问题类型枚举（层1，沿用总方案 4.4 口径）

| code | 含义 | 典型消息 |
|-|-|-|
| MATERIAL_RECTIFY | 主材问题整改 | 供应商责任类：整改、谁负责 |
| DELIVERY_ADJUST | 送装预约与调整 | 改约、取消订单（甲醛不做了） |
| BIZ_VERIFY | 业务办理与信息核实 | 各类办理事项与核实 |
| CUSTOM_CABINET | 定制柜进度咨询 | 台账/系统可查的进度问询 |
| MATERIAL_PROGRESS | 主材进度确认 | 系统依赖供应商数据的进度问询 |
| OTHER | 其他/兜底 | 是问题但不属于上述五类 |

> 枚举仅作为接口约定传给 AI 侧（prompt 里定义）；服务端**不校验枚举合法性**（存原字符串），后续类型调整不动服务代码——一期类型还在摸索期，避免改枚举就发版。

### 4.4 问题汇总表模型

**行粒度 = 一次问题循环（issue cycle），不是一条消息**：一个问题的拆条/追问/引用复读不独立成行，挂靠首问行——同一问题多次拉取只推进首问行的 `ask_count`，不反复生成新问题（对应需求 §2-6 问题层防重）。

一张明细表承载归类结果（汇总走聚合查询，不建结果表）：

| 字段 | 类型 | 说明 |
|-|-|-|
| message_id | BIGINT | **首问消息** ID（uk 唯一键） |
| msg_key | VARCHAR(128) | 首问消息定位 key（归并锚点解析入口） |
| parent_issue_id | BIGINT NULL | 归并树锚点；**NULL = 独立问题（首问行）**，非 NULL = 挂靠追问行（mergeInto 降级场景） |
| ask_count | INT | 问题循环内追问次数（首问行冗余，原子自增） |
| first_ask_time / last_ask_time | DATETIME | 首问/最近追问时间（归并窗口判定依据） |
| status | VARCHAR(32) | 问题闭环状态（预留：PENDING/RESOLVED；本期恒 PENDING——归并窗口判定用） |
| group_channel_id / group_name | VARCHAR | 消息定位三件套（从消息表带出，免 join） |
| sender_id / sender_name | VARCHAR | 提问人（「以人为维度」汇总的分组键） |
| question_type | VARCHAR(32) | 层1 问题类型（4.3 枚举） |
| question_summary | VARCHAR(256) | AI 摘要 |
| project_keyword / supplier_keyword | VARCHAR(128) | 归属线索（原样存 AI 抽取值；映射校准是二期事） |
| confidence | DECIMAL(4,3) | AI 置信度 |
| resolve_method / action_param | 预留 | 层2/层3 字段位（本期恒空，**避免二期上三层时改表**） |
| resolve_time | DATETIME | 闭环时间（预留，本期恒空） |
| headline | VARCHAR(256) | 一句话标题（人读层·列表展示） |
| snapshot_json | JSON | 整合快照（4.2 body 的 snapshot 原样落：detail 人读 + elements 五要素机读） |
| involved_message_ids | JSON | 吸收的消息 id 列表（含 role：FIRST_ASK/FOLLOW_UP/REPLY——零散信息归一条的凭证） |
| known_facts | JSON | 已知事实（含上下文中已有答复；独立于 snapshot 便于后续 Skill 直接取） |
| snapshot_version | INT | 快照版本（CAS 换版：归并回传按版本号防旧覆盖新） |
| analyze_time | DATETIME | 归类落库时间 |

### 4.5 汇总统计接口

`GET /api/v1/open/msg-analyze/summary`：按维度聚合返回，供展示/评估用。

| 参数 | 说明 |
|-|-|
| groupChannelId / questionType | 可选过滤 |
| startTime / endTime | 时间窗（默认近 7 天） |
| groupBy | `question_type`（默认）/ `sender_id` / `group_channel_id` |

返回：各分组的问题条数 + 占比 + 平均追问次数（ask_count 均值，回答时效代理指标）+ 明细下钻（`GET /msg-analyze/issues` 分页查问题表明细——headline 快照列直接可读，游标分页同 4.1 模式）。对应总方案一期目标「拿到问题和问题归类的数量」。

**统计口径**：问题数只数 `parent_issue_id IS NULL` 的首问行（追问不重复计数）；追问次数聚合 `ask_count`。

### 4.6 拉取-标记闭环（防重复生成机制）

一条消息的完整生命周期（拉取怎么做 + 标记怎么打）：

```
kafka 落库                                    analyze_status = 0（建列默认值）
   │
   │  ┌────────────── AI 循环（外部编排，节奏自定，可多实例可重启）─────────┐
   │  │                                                               │
   ├──① 拉取：GET pending（onlyPending=true，只读）                      │
   │     只返回 analyze_status=0 的消息；拉取本身不改任何状态              │
   │     游标 (msg_time,id) 正序翻页——仅是翻页效率工具，防重不依赖它       │
   │                                                                   │
   ├──② 分析：LLM 把零散消息整合成问题快照（headline/detail/五要素，纯外部）│
   │                                                                   │
   └──③ 回传：POST report → 服务端逐 issue 写库（每 issue 一个事务）       │
         a. 先写问题行：insert 新快照行 / mergeInto CAS 换版自增         │
            （uk_message_id 在此挡住一切重复 insert）                     │
         b. 后打标记：update involved + noise 消息 analyze_status=1/9    │
   └───────────────────────────────────────────────────────────────────┘
   ▼
下轮 pending：已标记消息永不返回 → 不再进入 AI 上下文 → 不会再次生成
```

**三条核心规则**（拉取与标记的全部机制设计）：

| # | 规则 | 为什么 |
|-|-|-|
| 1 | **回传成功才标记，拉取永不标记**：标记与问题行写入同一事务，且**先写问题行、后打标记** | 顺序反了（先标记后写行）则中断 = 消息已标记但问题记录不存在 = **问题丢失**且下轮永远拉不回；正序则中断 = 下轮重拉重报 → uk 吸收 = 幂等重放——**宁可重放，不可丢失** |
| 2 | **标记单向流转 0→1/9，无失败中间态** | 分析/写库失败就不标记（保持 0），下轮自然重试；不需要清理「卡在处理中」的消息，也没有状态回退的入口 |
| 3 | **逐 issue 处理，非整批事务** | 单个 issue 失败不影响同批其他 issue：成功 issue 的 involved 已标记，失败 issue 的消息保持 0 下轮只重试失败的那部分 |

**重复生成的三道闸**（独立成立，任一漏掉另一道兜底）：

| 闸 | 挡住什么 | 机制 |
|-|-|-|
| 拉取闸 | 已分析消息再次进入 AI 上下文 | onlyPending 过滤——已标记消息不出现在下轮拉取结果里，AI 根本「看不到」它，无从再生成 |
| 唯一键闸 | 同一 messageId 被重复回传成两行 | uk_message_id：重复回传走 update 覆盖，insert 第二行在数据库层不可能发生 |
| 快照闸 | 同一问题的追问每次拉取都生成新问题 | mergeInto CAS 换版（4.2）：问题行数只由首问决定，追问只是把快照换到新版本——快照永远是问题的当前全貌 |

**故障推演**（拉取-标记链路上所有「会不会重复/会不会丢」的场景）：

| 场景 | 结果 | 为什么安全 |
|-|-|-|
| AI 拉取后、回传前崩溃 | 消息保持 0，下轮重拉同批 | at-least-once 预期行为：重拉防丢，重传被 uk 吸收防重 |
| 回传落库成功但 HTTP 响应丢失（AI 超时重发） | update 幂等覆盖一次（快照按 snapshot_version 防旧盖新） | 无第二行产生 |
| 两个 worker 并发回传同一问题 | CAS 版本号串行化，低版本被拒 | 无重复、无旧覆盖新 |
| AI 侧游标丢失/回退 | 无影响 | **服务端按 analyze_status 过滤是唯一事实源**，正确性不依赖客户端游标——游标只是翻页效率优化 |
| 归并锚点解析失败 | 降级独立新行 + 告警日志 | 偶发多计一条，抽检可见可修（优于无声丢问题） |
| AI 一批部分没分析完（上下文超长截断） | 未吸收且未列 noise 的消息保持 0 | 部分处理协议（4.2）：服务端不做「没提到=噪音」推断，下轮重拉续处理 |
| report 半批成功半批失败 | 成功 issue 的 involved 已标记，失败 issue 的消息保持 0 | 下轮只重试失败部分（规则 3） |

> AI 侧因此**可以完全无状态**：不持久化游标、不记处理清单、可随时重启可多实例——防重的全部状态都在服务端两处（`analyze_status` 列 + `uk_message_id` 唯一键），AI 只做「拉→析→报」三步循环。（job 形态下「AI 侧」即服务内 MsgAnalyzeJob，无状态特性同样成立——job 重启从 `analyze_status=0` 续跑。）

**批次边界完整性**（分批拉取把一个对话切成两半怎么办——如 50 条一批，某问题横跨 40-60 条）：

拉取闸只防「重复分析」，不保「上下文连续」：批 A 把 1-40 条打标后，这些消息从下轮拉取结果里消失（onlyPending 过滤），批 B 拉到 41-60 条时，AI 看到的续聊段天然没有前文——后半段可能被误判成新问题，或语义残缺归进 noise。三层解法，全部复用既有机制、零新增表/列：

| 层 | 机制 | 挡住什么 |
|-|-|-|
| ① 上下文重叠（拉取侧） | job 拉完一批后，按批次最早一条的 msg_time 向前回看时间窗（默认 30 分钟，Apollo 可配）拉同群消息——**不过滤 analyze_status**，作为只读上文注入 prompt（即 §4.1「上下文构造由 AI 侧用 groupChannelId + 时间窗自查」伏笔的落地） | 续聊段看得见前文 → 追问/引用关系不断裂 |
| ② 归并候选（缝合侧） | 归并窗口（24h）内 PENDING 问题的 headline/id 清单喂进 prompt（§4.7 PromptAssembler 既有设计）——批 B 即使没识别出是续聊，凭语义相似也能输出 `mergeInto` 指向批 A 建的问题 | ①失效时的语义缝合 |
| ③ 快照闸（兜底） | 前两层都失效、真拆成了两行：后续批次仍可凭归并候选合并（PENDING 期间随时可归并），人工抽检也可修——归并输出的是**新版全量快照**，合并不丢信息 | 拆开的两行最终收敛为一行 |

prompt 层两条约定：上文消息「仅供理解连续性，不得输出为 involvedMessages、不得列为 noise」；**边界留尾**——批末尾明显未完的对话（刚追问还没等到答复），可不把末几条列为 involved、保持 0，下轮和续聊一起重看——对话是否结束的判定权在 AI，服务端不做二次猜测（同 §4.2 拆条判定口径）。

**能力层接口**（一个方法，全部通用语义；实现即 zeus `AiManager` 的 agenda 版——`openAiChatModelGenerate(configKey, ChatMessage...)`（AiManager.java:58）换成带泛型解析的门面）：

```java
public interface LlmClient {
    /**
     * 通用 chat：system prompt + user prompt 进，结构化 JSON 出。

     * 对齐 zeus AiManager.java:90），仍失败抛 LlmFormatException。
     */

}
```

| LlmRequest 字段 | 说明 |
|-|-|
| configKey | 模型配置 key（AiModelConfig 注册表：apiUrl/apiKey/model/fallbackModel/retryTimes 全在 Apollo，对齐 zeus） |

**能力层职责边界**（五件事，全部与业务无关）：① 网关协议对接（solon-ai，鉴权/域名走 Apollo）；② 重试（网络类 + fallbackModel 降级链——对齐 zeus AiManager.java:97-124 的主模型→降级模型循环；格式类带错误回喂重试）；③ 结构化解析（对齐 zeus parseResult 的剥 ```json/`&lt;think&gt;`（AiManager.java:162-183），再加解析失败回喂重试）；④ 调用观测（token/耗时/模型名日志——对齐 zeus 的 usage 日志）；⑤ 模型注册表（AiModelConfig）。**不含**：prompt 内容、枚举校验、业务写入——这些全在功能层。

## 8、风险评估

| # | 风险点 | 评估 |
|-|-|-|
| 1 | **LLM 批量调用放大**：job 单轮扫 `analyze_status=0` 全量积压消息逐批调 LLM（批次 50–200 条消息/次），高峰期或首次回刷时一轮几十次调用 | job 单轮设处理上限（批次数可配，默认 10 批/轮，剩余下轮续跑——`analyze_status` 圈定天然支持断点）；能力层加单批 token 上限保护（超限批次缩半重拼）；量级参考：3 个 PM 群全量消息日均百级，稳态一轮 1–2 批 |
| 2 | **report 批量写放大**：单批回传（上限 200 条/批，与拉取 pageSize 上限对齐），逐 issue upsert 问题表 + involved 消息打标 = 2×N 条 DML | 问题表 insert 与消息行 update 分组批量执行（batch executor）；单接口加总耗时日志，超 3s 告警。量级参考：3 个 PM 群 4.1 条问询/天，问题行数远小于消息数 |
| 3 | **归并自增并发**：同一首问行的多条追问同批/多批并发 report，`ask_count+1` 与 CAS 换版竞争 | `UPDATE ... SET ask_count = ask_count + 1` 原子自增（非读改写）；快照换版带 `snapshot_version` 条件（旧版被拒）；同批内顺序执行天然串行 |
| 4 | **pending 游标扫描走索引**：`analyze_status=0` 存量随时间只增不减（job 未开时积压） | `idx_analyze_status (analyze_status, msg_time)` 复合索引覆盖查询；job 首游标从当前时间起（不回刷全量历史），存量历史消息按需一次性圈定时间窗处理 |
| 5 | **summary 聚合查询**：全表 GROUP BY 在问题表数据量增长后变慢 | 时间窗强制（默认近 7 天，必带 analyze_time 范围）；idx_type_time / idx_sender 索引前缀命中分组列 |
