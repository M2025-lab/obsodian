## R1【专利法第22条第2款 · 新颖性】—— 最致命，且是自行造成的

**审查意见（模拟）**：本申请方案对应的系统已于 2026 年 8 月上线运行。申请人未主张优先权，亦无证据表明申请日前该技术方案处于保密状态。若该系统在上线后可由供应商、设计师、工长等不特定主体访问或使用，则构成本申请日前的**公开使用**，本申请不具备新颖性。

**针对本交底书的证据**：交底书第 16 行自述"已完成开发并于 2026 年 8 月上线……当前处于线上数据观察阶段"；同一文档第 12/15 行记录了涉及供应商与设计师的通知动作。这些自述本身就是审查员要找的证据。

**风险等级**：**极高**（不可通过修改权利要求克服，属于申请日之前的既成事实）

**关键辨析（也是最可能的转机）**：
- 中国专利法第 24 条的六个月宽限期**只适用于三种情形**：中国政府主办或承认的国际展览会首次展出、规定的学术/技术会议首次发表、他人未经同意泄露。**"自己产品上线"不在其列。**
- 但"公开使用"的构成要件是：**技术内容处于公众想得知就能够得知的状态**。因此需要逐项核实：
  1. 上线范围是内部灰度还是全量？开关命中名单之外的人是否能看到相关功能入口？
  2. 能访问该功能的主体（工长、供应商、设计师）是否**负有明示或默示的保密义务**？（例如仅限签约合作方、有保密协议、系统水印与权限管控、无对外宣传）
  3. 是否存在对外宣传材料（内部公告外发、发布会、公众号、客户宣讲）**公开了实现方式**（不是"有这个功能"，而是"怎么实现的"）？功能存在本身通常不足以公开"实现方案"，这一点对申请人有利。

**答复/规避策略**：
1. 立即与 IP 部确认上线是否构成公开（这是决定性的、无法事后补救的一步，**越早越好**）。
2. 若确有公开风险：将申请标的**切换到申请日前尚未公开的增强特征**上——例如本交底书中"定时自动执行通道 + CAS 幂等门禁 + 采纳情况回写"这部分是开发后期（08-19~08-20）才定版落地的，若其细节未随上线对外暴露，可作为独立的申请主体，甚至另起一件申请。
3. 保留证据：上线记录、权限配置、访问日志、保密约定，用于在审查阶段证明"未处于公众可得知状态"。

## R2【专利法第2条第2款 + 第25条第1款第2项 · 客体】—— 会被指"业务规则的本质"

**审查意见（模拟）**：权利要求所限定的内容主要为一种任务处理与人员分工的管理规则。其中：判定结果的分类与展示顺序、按城市/工程部门/作业人员的放量名单、考核时间与当前时间的比较阈值（3 天）、建议上门时间的确定，均属于**经营规则与人为约定**；其执行依赖通用计算机与网络，未对计算机内部性能或硬件资源利用带来改进。因此不属于专利法第 2 条第 2 款所称的技术方案。

**针对本交底书的证据**：
- 设计要点 1（四态枚举）、要点 3（灰度名单）、要点 6（分桶与排序）——**纯业务约定色彩最重**；
- 步骤 S2 中"考核时间与当前时间差值不超过阈值（如 3 天）"——典型的业务规则参数；
- 步骤 S2 的排序规则（按项目分组、组内按考核时间升序）——属于信息展示规则。

**风险等级**：**高**（这是软件方法类申请的常态障碍）

**答复/规避策略**：
1. **砍掉独权里的业务规则，只留技术特征**。可保留为从属权利要求或实施例，但不能出现在独立权利要求中。
2. 把独权重新锚定在两个真正属于技术手段的点上：
   - **多通道并发下的任务状态一致性控制**：以同一个状态字段（执行方式）作为人工批量通道与定时自动通道的**唯一竞争资源**，通过条件更新（CAS）实现互斥——这解决的是"分布式并发写入冲突"的技术问题，有明确的技术手段与技术效果；
   - **跨表数据一致性回填**：主数据源与兜底数据源的读取优先级与回写策略，解决"机器结果与人工修改结果的冲突覆盖"这一数据一致性技术问题。
3. 在有益效果中补**技术性指标**（不要只写"效率提升"这种经营效果）：并发冲突拦截次数、重复通知执行率降为 0、对上游识别服务的调用次数下降比例（缓存命中率）、批量执行的失败隔离率。**"降低对下游系统的无效调用、避免重复写入"就是标准的技术效果表述。**

## R3【专利法第22条第3款 · 创造性】—— 最可能真正收到的那条

**审查意见（模拟）**：本申请与最接近的现有技术（工作流/任务派发系统 + 配置中心灰度发布 + 乐观锁并发控制）相比，区别技术特征为：将识别结果映射为多态判定、按判定分桶查询、双通道执行、采纳情况记录。上述区别特征均为本领域常规技术手段：
- 多状态枚举与状态机流转：**常规设计**；
- 缓存 + 定时轮询以削峰：**常规性能优化手段**；
- 通过配置中心按维度下发灰度名单：**公知技术**（对比文件已公开按地域/用户分组的开关控制）；
- 以"未处理→已处理"的条件更新实现幂等：**数据库乐观锁的教科书用法**，本领域技术人员有明确动机将其用于防重复提交；
- 记录用户对推荐结果的采纳情况：**常规日志与埋点**。
因此，在对比文件基础上得到本申请的技术方案对本领域技术人员而言是显而易见的，不具备突出的实质性特点。

**风险等级**：**高**（组合型软件方案最常被这条驳）

**答复/规避策略**（核心是论证"协同效果"，而不是逐个争辩"这个手段不常见"——那是争不赢的）：
1. **主张特征之间的相互支撑关系**，而非并列堆叠：
   - 判定结果的状态值**同时**决定：进入哪个查询桶、是否具备自动执行资格、CAS 门禁的更新条件、失败时的处置分支。也就是说，"识别态"与"任务执行态"是**双向绑定**的一个状态空间，而不是两个独立步骤。这一点在检索到的现有技术（巡检识别 + 派工，二者单向传递）中通常不具备。
   - 采纳反馈回写会改变后续判定的准入（可写成"基于采纳情况调整自动化放行的品类范围"）——**闭环自适应**是区别于"单向识别+执行"的关键，务必在申请文件中把这个闭环写实，哪怕现有实现只做到"记录"。
2. **量化预料不到的技术效果**：需要真实数据支撑，例如"双通道上线后重复通知类工单从 X 笔/月降到 0"、"对上游识别服务的日均调用量由 N 次降为 1 次/日/任务"。**没有数字的争辩基本无效。**
3. **收敛特征数量**：从 7 个要点收敛到 2~3 个，并在说明书中用整段篇幅论证这 2~3 个特征"并非简单叠加"。要点过多反而会被认定为"拼凑"。

## R4【专利法第26条第3款 · 公开不充分】—— 中等风险，但最好补

**审查意见（模拟）**：说明书未清楚说明下列内容，所属技术领域的技术人员无法实现：
1. **判定结果的产生依据**：上游识别服务依据哪些识别项、何种阈值将现场判定为"可通知/不可通知/无法判断"？"无法判断"与"不可通知"的界限是什么？
2. **参数依据**：延期预警的 3 天阈值如何确定？"识别日期为昨日"作为候选条件的原因？
3. **执行实现细节**：批量并行执行采用何种并发模型（线程池规模、超时、失败重试、事务边界）？"单件异常不阻塞整批"如何实现？
4. **采纳判定规则**：当机器推荐与最终提交"部分一致"时（图片三张中命中一张、时间相差一天），归入哪一类？多张图片的顺序是否参与比对？
5. **附图缺失**：仅有附图建议清单，未提供任何正式附图，而方法权项的步骤无法脱离流程图理解。

**风险等级**：**中**（可以补，但必须在申请日之前补，事后无法补救）

**答复/规避策略**：
1. 交底书阶段就把上述 1、2、4 的规则**写死**（哪怕写成"优选地，依据以下识别项……"）。对上游识别服务，写"通过上游识别服务获取，其可采用任意公知的影像识别方式，优选为……"——**把不可控部分作为前置输入引述，而不是作为本发明的技术特征**，这同时也是 R5 的应对。
2. 3、5 属于实现细节，补充"本领域技术人员可依据上述描述实现"的具体优选例即可，不必穷尽。
3. 附图至少三张：方法主流程图、双表数据关系图、双通道幂等时序图。

## R5【专利法第26条第4款 + 细则第20条第2款 · 支持性与必要技术特征】—— 撰写阶段必然出现

**审查意见（模拟）**：
1. 若按交底书"识别结果接入模块 / 任务节点数据模块 / 自动化记录模块 / 查询触达模块 / 执行模块 / 配置模块"撰写装置权利要求，属于**纯功能性模块划分**，各模块仅为完成相应功能的程序集合，实质仍是上述方法，未记载任何具体技术手段的对应结构，得不到说明书支持。
2. 若独立权利要求写入"四个判定状态"，则保护范围与发明实质贡献不匹配：**他人在识别侧改用三态或五态、或在执行侧改用信号量/版本号替代 CAS，即可轻易规避**，保护范围形同虚设。

**风险等级**：**中高**（不是被驳的理由，而是"授权了也没用"的风险，很多软件专利死在这里）

**答复/规避策略**：
1. 独权采用**上位概括 + 从属下位限定**的层次：
   - 独权：判定结果集合至少包括"指示满足执行条件的第一状态"与"指示不满足的第二状态"；**不写"四个"**；
   - 从权 1：进一步包括"无法判断"状态及其处置分支；
   - 从权 2：进一步包括"现场已完成需关闭"状态及其推送动作。
2. 幂等特征也做层次化：独权写"依据任务执行状态字段的条件更新确定执行资格"（涵盖 CAS、版本号、信号量等一切等价手段），从权再限定为"以未执行态向目标态的原子条件更新"。
3. 装置权项采用"处理器 + 存储器 + 当程序被处理器执行时实现上述方法"的标准写法，或直接写存储介质权项，避免纯功能模块。
4. **另配一套"系统 + 方法 + 存储介质"三件套**，不要只报方法。

## R6【细则第20条第1款 · 清楚性】—— 形式问题，但会拖慢进度

**审查意见（模拟）**：权利要求及说明书用语不清楚：
1. **主体名称不统一**："工地负责人""作业人员标识""工长""项目经理"混用，无法确定权利要求的执行主体与对象；
2. **一词多义**："一键通知"既是一个**操作动作**（用户点击），又是一个**枚举值**（notify_execute_type=1 的取值），同一术语承担两种含义；
3. **口语化与比喻表述**："落库""兜底""分桶""桶""削峰"不适合作为权利要求用语；
4. **内部代号外泄**：未脱敏的"Apollo 开关""小师傅""edar-starlord""judge_remark 中的 |Jx"等内部系统名、配置 key、字段技巧，会造成权利要求不清楚，并公开内部技术架构。

**风险等级**：**低（可改）但如果不在交底书阶段处理，会退回重写多轮**

**答复/规避策略**：开工前建立术语对照表并替换全文：

| 交底书用语 | 建议统一为 |
|---|---|
| 工长 / 项目经理 / 工地负责人 | **作业人员**（首次出现时定义"指工地现场负责执行任务的人员，例如工长"） |
| 一键通知（动作） | **批量提交** |
| 一键通知（枚举值） | **人工批量执行方式** |
| 落库 / 暂存 | **写入记录表 / 缓存** |
| 兜底 | **作为次级数据源回退读取** |
| 分桶 / 桶 | **分类集合 / 集合** |
| 削峰 | **降低对上游服务的调用频次** |
| 小师傅 / Apollo / edar-starlord | **作业端应用 / 配置中心 / 任务调度系统** |

## R7【申报策略 · 发明点发散导致单一性不良】—— 不是审查员的理由，是代理人会退回的问题

**模拟意见（代理人视角）**：交底书列出七个并列的设计要点，横跨"识别结果接入""查询展示""并发执行""缓存策略""反馈闭环"五个不同环节。它们是否属于**一个总的发明构思**？若是，独立权利要求应当如何概括？按现稿，无论怎么写都会落入两难：
- 若七点全写进独权 → 保护范围过宽（几乎等于"任何受理识别结果并按状态执行任务的系统"），**必因创造性被驳**；
- 若只写其中一点 → 另外六点失去保护，且申请人会认为没有保护到位。

**策略**：
1. **拆件申报**，比硬塞一件更容易授权、也更值钱：
   - **主案 A**：识别结果接入与分态分桶处置（步骤 S1-S3）——卖点是"识别态与任务态的双向绑定"；
   - **副案 B**：人工批量与定时自动双通道的幂等执行及采纳反馈回写（步骤 S4-S6）——卖点"唯一竞争资源 + 自适应闭环"，这件**最可能避开必然被驳的组合特征堆叠**。
2. 两案共享同一说明书（同日申请，互为分案基础），互相引用而不重复。
3. 缓存与轮巡（要点 7）**不要单独申报**，作为实施例写入，成本高、授权价值低。

## 结语：审查员最想让申请人回答的三个问题

1. **你的方案解决的是"技术问题"还是"管理问题"？** —— 答"并发写入冲突与跨表数据一致性"。
2. **这些手段为什么不是公知常识的简单拼装？** —— 答"判定态与执行态共用一个状态空间、且采纳结果反哺准入，形成闭环，单独任一手段都不产生该效果"。
3. **凭什么说效果是预料不到的？** —— 答数字，不答形容词。

这三问答得上，方案就站得住；答不上，再多要点也只是增加驳回通知书里被引用的段落数量。
