## 1、背景[必选]

- 父需求：[[00.需求/通知复尺自动化/通知复尺自动化-迭代最终汇总]]（一期已上线：识别结果落库、批量查询、一键通知、自动通知）
- 范围：仅 edar-starlord 本工程；上游识别链路（`/api/recognize/task/result`）不动

一期目标是观测「系统通知占比、AI 采纳率、驳回率」，但通知任务的**提交/驳回动作**与**系统识别结果**目前没有权威的服务端关联记录：识别结果应用与否、驳回任务此前是手动还是自动通知，均无法从现有表还原。本期在 `handleNode` 提交/驳回链路上挂载记录逻辑，落一张新表，作为指标计算的服务端数据源。

## 2、需求理解[必选]

| # | 触发 | 判定/动作 | 记录内容 |
|---|---|---|---|
| 1 | 通知任务（taskType=3 复尺）通知节点提交完成 | 查 `material_site_recognize_result`（已改 upsert，仅存最新结果）：`judge_result=1` → 被应用；`judge_result=2/3/4` **及查无记录** → 未被应用（均进分母） | 应用状态 + 识别结果快照 + 是否经过系统识别 |
| 2 | 同上 | 记录本次通知的执行方式：手动 / 一键 / 自动 | `notify_execute_type` + `ai_adoption_type` 快照 |
| 3 | Handle 入参 `qualified=2`（驳回） | 每次驳回都记录；关联**本次以 qualified=2 提交的节点 ID**；查识别表取驳回时刻判定结果；**上一轮执行方式查新表的提交记录** | 驳回事件 + judge_result 快照 + 上一轮执行方式 |
| 4 | 存量数据 | 上次子需求上线以来已完成通知任务约 20 万条，**不回刷**（量级不现实） | 记录自本次上线起算；存量任务上线后被驳回时"上一轮执行方式"记 0-未知（预期边界，见 4.5） |

### 3.3 时序事实（决定设计）

一键/自动链路都在 `handleNode` **返回之后**才写 `notify_execute_type`（3.1 ⚠️处）。若在 handleNode 内部（含 afterCommit）读识别表判断执行方式，一键/自动场景读到的仍是 0（未执行），会误判为手动。

关键结论：一键/自动**不经过任何 Controller**——凡从 Controller 入口进来的提交即手动，无需改 `DispatchHandleParam` 传执行方式；Controller 调用点天然在 handleNode 事务（@Transactional :147）提交之后。

## 4、详细设计

### 4.1 新表与新增类

新表 `material_notify_execute_record`（事件流水，DDL 见第 7 节）。粒度：**每次提交/驳回各一条**，多轮 restart 天然多条（每轮节点 ID 不同），`uk_node_record(task_dispatch_node_id, record_type)` 唯一键兜底防重。

存量不回刷（约 20 万条历史完成量级），全部记录由 handleNode **调用方**在返回后实时挂载产生，**不设 record_source 字段**。由此带来的边界：上一轮提交发生在本上线之前的任务，上线后被驳回时归因为 0-未知（4.5 单独成桶，随存量任务消化自然衰减）。

| 新增类 | 模块 | 说明 |
|---|---|---|
| MaterialNotifyExecuteRecord(.Example) / Mapper / XML / Dao | dao | 仿 MaterialNotifyTaskAutomation 生成物风格：Mapper 继承 BaseMapper，查询统一走 selectByExample 条件拼接（含 orderByClause + limitStart/limitSize），不建自定义查询方法 |
| NotifyExecuteRecordTypeEnum | base | 1-通知提交 / 2-驳回（新增） |
| NotifyExecuteRecordService(Impl) | service | `recordAfterHandle(nodeId, qualified, notifyExecuteType)`：由各调用点在 handleNode 返回后触发（4.2），异步执行 + 整体吞异常仅打日志；内部完成条件过滤、识别表查询、AI 采纳比对、落库（4.3/4.4） |

复用枚举：NotifyExecuteTypeEnum（含 3-手动）、NotifyJudgeResultEnum、AiAdoptionTypeEnum，均不改。

### 4.2 挂载点：handleNode 返回后调用记录 Service（DispatchHandleParam 零改动）

执行方式**由入口区分**（3.4 事实：一键/自动为进程内直调、不经 Controller，故凡从 Controller 进来的提交即手动）。四个调用点统一调 `NotifyExecuteRecordService.recordAfterHandle(taskDispatchNodeId, qualified, notifyExecuteType)`，operator 与 AI 采纳快照均由 Service 内部重查/比对得出（不传参）：operator 取节点 submitBy/submitName；`ai_adoption_type` 由识别表推荐值与节点提交值比对算出（4.3 步骤 5）。所有调用点均在 handleNode 事务（@Transactional :147）提交之后，**无需 TransactionSynchronization/afterCommit 注册**。

| # | 调用点 | notifyExecuteType |
|---|---|---|
| 1 | TaskDispatchController.handle :51 返回 true 后 | null → 手动(3) |
| 2 | MaterialMeasureTaskController.handle :164 返回 true 后 | null → 手动(3) |
| 3 | batchHandleNotifyTasks：handleNode(:472) 成功且 classifyAdoption(:474) 之后 | 一键(1) |
| 4 | autoExecuteNotifyTasks：handleNode(:714) 成功后 | 自动(2) |

调用点 3/4 同样透传 qualified（批量入参 item 携带 qualified，NotifyTaskBatchQueryServiceImpl:470）——当前业务一键/自动仅提交可通知任务（qualified≠2），属防御性处理。

`/material-task/batch/dispatch/handle`（TaskDispatchController.batchHandle:64-71 → batchHandleNode 逐件 handleNode）**本期不接入，已确认**：该入口的提交/驳回暂不产生记录；后续如需接入，batchHandleNode 返回后补一行同款调用即可（方法签名不变）。

### 4.3 提交记录（Service 内部逻辑）

`recordAfterHandle` 异步执行（线程池），整体吞异常仅打日志：

1. 联表重查 node + task（`TaskDispatchNodeDao#listTaskByCondition`，TaskDispatchNodeExtMapper.xml:278-285，SQL 仅按 `taskDispatchNodeIds=[nodeId]` 查）——**handleNode 返回 true ≠ 本次真实完成节点**（幂等分支 :176-177、变更单、零售无模板分支同样返回 true）；Java 侧公共拦截按序：①存在性 ②`taskType==RECHECK_SCALE(3)` ③`processCode` 非空（排除零售无模板单）④node `processStatus==COMPLETED` ⑤`materialCode` 在 Apollo 自动通知规则白名单内（NotifyAutomationConfig#parseAutoNotifyRules:65 → NotifyExecuteRecordServiceImpl:109-116，与自动通知同一配置源），每项独立日志便于排查漏记原因；
2. `qualified==2` → 转 4.4 驳回分支（**不限 nodeType**，被驳回提交的是复尺执行节点）；否则为通知提交分支，分支内先要求 `nodeType==NOTIFY_CAN_START(20)`（非通知节点如复尺执行节点的合格提交不落记录）再继续；
3. `selectByEntity(projectOrderId, materialCode, taskType=3)` 查识别表（upsert 仅一条最新，NotifyTaskAutomationServiceImpl:40-44 同款查询）；
4. 判定：无记录 → `recognized=0, judge_result=0, applied=0`；有记录 → `recognized=1, judge_result=快照（识别表该字段为空时落 0）`，`applied = (judge_result==1) ? 1 : 0`。全表无 NULL 列（VARCHAR 空哨兵=空串、TINYINT=0）；Java 侧 null 字段经 `insertSelective` 自动省略该列、由 DB DEFAULT 兜底落哨兵值，写入代码零改动；
5. 执行方式：入参 notifyExecuteType 非空取之，为空 → `MANUAL_NOTIFY(3)`；`ai_adoption_type` 不由调用方传入，Service 内部**直接复用**一键链路的 `classifyAdoption`/`splitImages`（NotifyTaskBatchQueryServiceImpl:753-769/:372-379，二者纯函数、不依赖实例状态，由 `private` 放宽为 `public` 实例方法；NotifyExecuteRecordServiceImpl `@Resource` 注入 NotifyTaskBatchQueryServiceImpl 调用，避免逻辑重复。两 Service 互相注入成环，均为字段注入 + Boot 2.1 默认允许循环引用，Spring 三级缓存可解）：比对**识别表推荐图片/recommend_visit_time** 与 **节点提交 images/notice_retain_time**（completeTaskDispatchNode :628-629 落库值），双采纳=1 / 双未采纳=2 / 仅图片=3 / 仅时间=4；识别表无记录或无推荐图片 → NULL。自动链路提交值即识别表推荐值（:718-719），比对结果天然=1，与原硬编码一致；
6. insert：node_id=本次通知节点 ID，event_time=node.submitTime，operator=node.submitBy/submitName，gb_code=联表 DTO taskNode.gbCode（冗余，供指标查询城市维度，见[[00.需求/通知复尺自动化/通知复尺自动化-指标查询接口-技术方案]] 3.1）；**命中 `uk_node_record` 跳过**（重复提交/重复调用去重，Controller 层无法区分幂等返回，以此兜底）。

**边界（均不计入，已确认）**：① 零售无模板分支（步骤 1 processCode 过滤）；② 前置收口 `completePreTask`/`completePreTaskNode` 批量置 COMPLETED（备注"上游系统已对应任务"）——不经过 4.2 挂载点；③ OMS/SDM 同步等内部直调自动收口（3.4 末行）——非真实通知动作，同②口径；④ 自动通知规则白名单外的品类（步骤 1 ⑤）——仅观测 Apollo 配置内品类，配置扩品类后新事件自动纳入，无需发布。收口量如需观测，另行按备注单独统计，不属本方案。

### 4.4 驳回记录（Service 内部逻辑）

`qualified==2` 分支（驳回仅来自调用点 1/2 两个 HTTP 入口；一键/自动不发起驳回）。过滤同 4.3 步骤 1（taskType=3、processCode 非空），**nodeType 不限**（被驳回提交的是复尺执行节点）：

1. 查识别表取**驳回时刻** judge_result 快照与应用状态（同 4.3 步骤 3-4）；
2. 上一轮执行方式：查新表 `task_dispatch_id=当前任务 && record_type=1` 按 event_time 倒序取最新一条的 `notify_execute_type`；查不到记 0（存量任务，4.5）；
3. insert：record_type=2，node_id=**本次以 qualified=2 提交的节点 ID**，operator=本次提交人；`uk_node_record` 去重同 4.3。

### 4.5 指标口径

统计窗口一律取**本次上线之后**（event_time 过滤）；存量不回刷，上线前数据不参与任何指标。

| 指标 | 口径 |
|---|---|
| 识别结果应用率 | `record_type=1 AND recognize_applied=1` / `record_type=1` 全量 |
| 未应用细分 | `recognized=1 AND applied=0`（AI 判不可通知但人工仍通知） vs `recognized=0`（未经系统识别） |
| 分执行方式驳回率 | `record_type=2 AND notify_execute_type=X` / `record_type=1 AND notify_execute_type=X`（X∈1/2/3） |
| AI 采纳下钻 | `record_type=1` 按 `ai_adoption_type` 分组 |

驳回记录 `notify_execute_type=0`（未查到上一轮提交记录）**单独成桶，不计入任何执行方式的驳回率分子**。0 桶两种来源：①上一轮提交发生在本次上线前（存量任务，预期，随消化自然衰减）；②挂载条件漏洞（异常）。上线初期 0 桶占比高属正常，观察其单调下降；若长期不降需排查②。

### 4.6 与现有功能的兼容性核查

| # | 现有功能 | 核查结论 |
|---|---|---|

## 7、表结构改动

新建通知任务执行记录表（其余表无变更）：

```sql

    `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
    `project_order_id` BIGINT NOT NULL DEFAULT 0 COMMENT '项目订单id',
    `material_code` VARCHAR(50) NOT NULL DEFAULT '' COMMENT '品类编码',

    `operator_id` VARCHAR(64) NOT NULL DEFAULT '' COMMENT '操作人id；空串-无',
    `operator_name` VARCHAR(128) NOT NULL DEFAULT '' COMMENT '操作人姓名；空串-无',
    `event_time` DATETIME NOT NULL DEFAULT '1900-01-01 00:00:00' COMMENT '事件时间（节点提交时间）',
    `gmt_create` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `gmt_modified` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_node_record` (`task_dispatch_node_id`, `record_type`),
    KEY `idx_task_dispatch` (`task_dispatch_id`, `record_type`),
    KEY `idx_project_material` (`project_order_id`, `material_code`, `task_type`),
    KEY `idx_record_time` (`record_type`, `event_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='通知任务执行记录表（识别结果应用与驳回追踪）';
```

## 8、风险评估

- 主链路每次通知节点提交/驳回新增：handleNode 返回后线程池异步查询——1 次 node+task 联表（`listTaskByCondition`，node 主键 + task 主键关联）+ 1 次识别表（走 `idx_project_task_material`）+ 驳回另查新表 1 次（走 `idx_task_dispatch`）+ 1 次 insert，单条级、事务提交后执行，不占用主事务时间。无批量/循环调用，无存量刷数负载。
