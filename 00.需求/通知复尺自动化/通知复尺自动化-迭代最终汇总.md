## 1. 需求汇总

### 1.1 需求背景

项目经理/工长名下存在多个「通知类任务」（本期聚焦**通知复尺**，室内门品类），处理繁琐、影响效率。通过工地**摄像头**与工人拍摄的**照片**判断现场交界面是否满足复尺通知的执行标准，满足则自动判断/自动填充，减少人工判断与操作成本。

整体链路：

```
摄像头采集 / 工人拍照
  → 上游分析（调度层）判断是否满足可通知标准
  → 判断结果批量回调主材任务（POST /api/recognize/task/result）
  → 落新表 material_notify_task_automation（只新增不更新，暂存判定）
  → 小师傅/首页：批量查询判定结果（可通知 + 延期预警）→ 一键通知批量执行
  → push 消息（09:10 / 13:00 / 19:00 悬浮框推送，本期未做）
```

### 1.2 需求目标

1. **判定结果落库**：接收上游识别判定结果并暂存，字段完整可追溯（项目/品类/任务类型/识别日期/建议上门时间/判定结果/备注/关键帧图片）。
2. **查询触达**：工长在小师傅端可按项目汇总查看「可通知任务」与「延期预警任务」，含考核时间、图片、建议上门时间、工地地址，紧迫任务排前。
3. **一键执行**：可通知任务支持批量一键通知，与现有单件提交通道（`/material-task/dispatch/handle`）完全一致，且防重复执行。
4. **开关控量**：Apollo 开关按 城市 / 工程部 / 工长 维度灰度放量（fail-closed）。

### 1.3 验收标准（对照需求背景.md）

| # | 验收项 | 标准 |
| --- | --- | --- |
| 1 | 接收落库 | 上游按我方 8 字段必传调用 `/api/recognize/task/result`，批量落库成功，images 逗号拼接、日期 `yyyy-MM-dd`；不落更新、同维度每日一条 |
| 2 | 判定枚举 | 1-可通知 / 2-不可通知 / 3-无法判断 / 4-现场已完成需关闭，上游按我方枚举值直传 |
| 3 | 可通知列表 | 工长全部工地（或指定项目）下「激活未完成 + 判定=1」的任务，按项目汇总返回（地址在分组上），组内按品类 → 考核时间升序 |
| 4 | 延期预警列表 | 「激活未完成 + 判定∈{2,3,无记录}」且**命中预警**（考核时间−当前 ≤ 3 天，超期保留）的任务；**未经系统判定的任务也必须露出** |
| 5 | 一键通知 | 逐件与单件提交通道行为一致；已被其他路径处理的件数单独返回（automation CAS 门禁 `notify_execute_type` 0→1） |
| 6 | 开关 | 开关A（城市 OR 工程部 OR 工长）命中才返回/放行；配置缺失=不命中（fail-closed） |
| 7 | 时间窗口 | 摘要接口仅在 09:10-10:00 / 13:00-14:00 / 19:00-21:00（含端点）返回计数，窗口外返回 0/0 |

### 5.3 关键实现逻辑

**一期落库（`NotifyTaskAutomationServiceImpl`）**
- 批量构建记录后 `batchInsert` 一次落库；`recognize_time`/`recommend_visit_time` 按 `yyyy-MM-dd` 解析（非法抛业务异常）；`images` 逗号拼接；`notify_execute_type`/`ai_adoption_type` 初始 0。
- Controller 上 `@Validated` + 方法参数 `@NotEmpty @Valid`：**根对象为 List 时 Hibernate Validator 不级联校验元素**，已按项目既定方案（注入 Validator / @Validated 方法级）处理（参见知识沉淀《批量List接口@Valid校验失效排查》）。
