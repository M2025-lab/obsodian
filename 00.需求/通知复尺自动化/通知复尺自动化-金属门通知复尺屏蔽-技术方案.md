## 1、背景

一期上线后，通知复尺的自动通知是"命中开关就不再展示、也不允许手动提交"。但现场存在**驳回重启**场景：任务被驳回后重新激活（`task_dispatch_node.restart > 0`），此时旧规则会把重启后的任务继续屏蔽掉，工长既看不到列表也提交不了，任务卡死。

本期要做的是：**引入"识别结果策略"维度，让重启后的任务按策略决定是否重新露出给人工，同时自动通知侧按策略决定是否代劳提交。**

## 2、需求理解

核心是三条链路的展示/执行口径，统一由三个维度决定：

| 维度 | 取值来源 | 含义 |
|---|---|---|
| **A** 命中自动通知开关 | `NotifyAutomationConfig.isAutoNotifyOpen` | 该品类（+城市/工长/工程部）已开启自动通知 |
| **R** 有驳回 | `task_dispatch_node.restart > 0` | 任务被驳回并重启过 |
| **S** 识别结果策略 | `material_site_recognize_result.result_strategy` | 0-使用最新-不延迟，1-复用上次，2-使用最新-延迟 |

派生口径：

- **有新视频** = `S ∈ {0, 2}`（`ResultStrategyEnum.isUseNewVideo`）
- **可通知** = `judge_result == 1`

### 2.1 一键通知（列表展示）

| 命中 A | 有驳回 R | 策略 S | judge | 是否展示 |
|---|---|---|---|---|
| 是 | 否 | 0 / 1 / 2 | 1 | **不展示** |
| 是 | 是 | 0 / 2（有新视频） | 1 | **展示** |
| 是 | 是 | 1（复用上次） | 1 | **不展示** |
| 是 | 是 | 0 / 2（有新视频） | 2 不可通知 | 不展示 |
| 否 | 任意 | 任意 | 1 | **展示** |

代码：`NotifyTaskBatchQueryServiceImpl#queryNotifyTaskSplit`（master 344–349 行）

```java
if (notifyAutomationConfig.isAutoNotifyOpen(task.getMaterialCode(), gbCode, null, null)
        && !(hasRestarted(task.getTaskDispatchNodeId())
        && ResultStrategyEnum.isUseNewVideo(materialNotifyTaskAutomation.getResultStrategy()))) {
    continue;   // 不展示
}
```

### 2.2 手动通知（handle 接口拦截）

| 命中 A | 有驳回 R | 结果 |
|---|---|---|
| 是 | 否 | **拦截**，报「{品类}复尺已启用自动通知，无需手动提交」 |
| 是 | 是 | **放行**（人工兜底） |
| 否 | 任意 | **放行** |

代码：`TaskDispatchController#handle`（master 56–61 行）

> 手动通知**不看策略 S**，只看「命中开关 + 是否驳回」。重启后放行是**有意设计**，给人工留兜底口子。

### 2.3 自动通知（定时任务执行）

候选来源：`selectByEntity(judgeResult=1, taskType=3)`，且 `images ≥ 3` 张。
执行条件（master 836–846 行）：

| 命中 A | 有驳回 R | 策略 S | 是否执行 |
|---|---|---|---|
| 是 | 否 | 0 使用最新-不延迟 | **执行** |
| 是 | 否 | 1 复用上次 | **执行** |
| 是 | 否 | 2 使用最新-延迟 | 不执行（等延迟） |
| 是 | 是 | 0 / 2（有新视频） | **执行** |
| 是 | 是 | 1（复用上次） | 不执行 |
| 否 | 任意 | 任意 | 不执行 |

```java
boolean noDelayOrUseLast = USE_LATEST.getValue().equals(strategy) || REUSE_LAST.getValue().equals(strategy);
boolean isUseNewVideo    = ResultStrategyEnum.isUseNewVideo(strategy);
if (!((isOpenAuto && !hasRestart && noDelayOrUseLast) || (isOpenAuto && hasRestart && isUseNewVideo))) {
    continue;
}
```

### 2.4 三链路对照速查

| 场景 | 一键通知 | 手动通知 | 自动通知 |
|---|---|---|---|
| 命中 + 无驳回（S=0/1） | 不展示 | 拦截 | 执行 |
| 命中 + 无驳回（S=2） | 不展示 | 拦截 | 不执行 |
| 命中 + 有驳回 + S=0/2 | **展示** | 放行 | 执行 |
| 命中 + 有驳回 + S=1 | **不展示** | 放行 | 不执行 |
| 未命中 | 展示 | 放行 | 不执行 |

## 4、关键设计点

### 4.1 查询维度：二元组 → 三元组

原来按 `(project_order_id, material_code)` + 外层单值 `task_type` 查，无法一次查询混排多种任务类型。改为 **每个 Dimension 自带 taskType**，SQL 用三元组 IN：

```xml
where (project_order_id, material_code, task_type) in
<foreach collection="dimensions" item="d" open="(" separator="," close=")">
  (#{d.projectOrderId}, #{d.materialCode}, #{d.taskType})
</foreach>
```

> ⚠️ **调用方必须保证每个 Dimension 的 taskType 非空**（DAO 层不校验）。传 null 会静默匹配不到，不报错。当前两个调用点都传 `DEFAULT_TASK_TYPE` 常量。

### 4.2 重启判断统一用 join 出来的字段

自动通知的 `nodeList` 来自 `listTaskByCondition`，SQL 里已 join 出 `node.restart as restartCount`（`TaskDispatchNodeExtMapper.xml:42`），所以循环内直接用 `node.getRestartCount()`，**不要**再逐个 `getById` 造成 N+1：

```java
boolean hasRestart = node.getRestartCount() != null && node.getRestartCount() > 0;   // Integer 必须判空再拆箱
```

### 4.3 数据表变更

`material_site_recognize_result` 新增列（**上线前必须先执行**）：

```sql
ALTER TABLE `material_site_recognize_result`
    ADD COLUMN `result_strategy` TINYINT NOT NULL DEFAULT 0
        COMMENT '结果策略：0-使用最新-不延迟，1-复用上次，2-使用最新-延迟'
        AFTER `ai_adoption_type`;
```

- `NOT NULL DEFAULT 0` ⇒ 存量行回填 0 = `USE_LATEST`，老数据行为不变
- 线上已确认该列已存在

### 4.4 策略"有记忆"

`receiveTaskResult` 的更新走 `updateById(record)`（selective），`resultStrategy` 为 null 时不拼该列 ⇒ **不传即保持库里原值**。前提是**上游每次必传**（已与上游确认）。
