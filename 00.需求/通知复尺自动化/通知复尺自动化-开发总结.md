## 1. 需求背景

复尺（recheck）完成后，系统识别出「需要再次上门」的任务，生成**通知任务**：工长在通知页面确认期望上门时间与图片，系统按确认结果执行通知动作（改状态、激活下一节点、发推送）。本次开发把这条链路从「人工逐条操作」升级为「识别 → 填充 → 确认 → 自动/批量执行」的自动化闭环，并补齐通知页面所需的数据查询与保存能力。

## 2. 交付接口全景（7 个接口）

| # | 接口 | 方向 | 职责 | 关键实现点 |
|---|------|------|------|-----------|
| 1 | `POST /api/recognize/task/result` | 外部→本系统 | 识别结果接入，写入 `material_notify_task_automation` | 8 字段全必填；images 逗号拼接；`notify_execute_type/ai_adoption_type` 固定 0；judge 由 remarks 中的 `\|Jx` 决定；日期 yyyy-MM-dd |
| 2 | `POST /api/material/notify/task/save` | 通知页→本系统 | 手动保存 images + noticeRetainTime 到 `task_dispatch_node` | 仅写 node 两列，不触发 handleNode 全链路；node 不存在/为空抛 `ERROR_PARAM_ILLEGAL` |
| 3 | `POST /api/material/notify/task/auto-fill` | 通知页→本系统 | 页面内容自动填充 | node 优先、automation 兜底（仅 node 缺图或缺时间才查昨日判定行）；Apollo 开关 A 未命中返回空 VO（fail-closed） |
| 4 | `POST /api/material/notify/task/batch/query` | 通知页→本系统 | 按项目分组批量查询 | judge=1→notifyTasks、judge=2/3/无记录→delayTasks（按 `estimated_time<=now+3d` 过滤）、judge=4→丢弃；组内按 estimatedTime 升序（越近今日越靠前） |
| 5 | `POST /api/material/notify/task/batch/handle` | 通知页→本系统 | 批量执行通知 | 逐节点 items 明细（每项独立 images/时间）；并行调 handleNode 全链路；单件异常不阻塞整批；返回 `{successCount, alreadyHandledCount}` |
| 6 | `POST /api/material/notify/task/auto/execute` | 定时/系统→本系统 | 每日自动执行通知 | 扫描 automation `judge_result=1 + notify_execute_type=0 + task_type=3 + recognize_time=昨日零点`；CAS 门禁写 `notify_execute_type=2`；按 (projectOrderId, materialCode) 反查 node，restart 去重；返回 `{candidateCount, executedCount, skippedCount, failedCount}` |
| 7 | `POST /api/material/notify/task/site/complete/query` | 通知页→本系统 | 现场已完成（第三桶）查询 | judge=4 桶，复用 batch/query 管线，受开关 A 过滤，无 summary 时间窗限制 |

**链路关系**：识别结果 → `/result` 落库（接口 1）→ 通知页 `batch/query`（4）展示 → `auto-fill`（3）预填 / `save`（2）手动改 → `batch/handle`（5）或 `auto/execute`（6）执行 → 已完成看 `site/complete/query`（7）。

**配套功能**：
- `summary` 汇总接口（notify/delay 两桶计数，仅 09:10-10:00 / 13:00-14:00 / 19:00-21:00 时间窗内统计）。
- Apollo 开关两枚（均 fail-closed，默认 `{}` 全关）：
  - `notification.remeasure.automation.open`（开关 A，功能级）：城市/工长/工程部 三集 OR。
  - `notification.remeasure.automation.autoNotify`（开关 B，品类级）：`auto/execute` 按 material_code 三集 OR。

### 4.3 造数关键决策与迭代（踩过的反复点）

1. **订单号三换**：自造订单号 → 用户提供 16 个真实订单号（本机 macOS Vision OCR 提取，取前 4 个 `826072010000001909` 等）→ 用户先后两次换号 → **最终定版 3 个**：`546068027139760128`（proj 9100000001，M01/M02）、`577257627351097344`（proj 9100000002，M03/M04）、`499472368956997632`（proj 9100000004，M05）。
2. **规模精简**：15 行 → 5 用例 / 4 订单 → 5 用例 / 3 订单。仅 `order_no`/`home_order_no` 用真实号，`project_order_id` 自造（假项目 → RPC 取不到真实订单 → 开关只能走 projectManagers 维度，方案已注明）。
3. **automation 判定口径**：**当天零点 → 昨日零点（T+1）**，查询用 `DATE_SUB(CURDATE(), INTERVAL 1 DAY)` 精确等值（recognize_time 是 DATE 列，非范围）。
4. **judge 分支全覆盖**：M01=1 / M02=2 / M03=3 / M04=4 / M05=1，覆盖 4 种 judge + 延期窗口命中/过滤 + autoNotify 命中(M05)/跳过(M01) + 重启去重 + 负向用例。
5. **预期断言**：batch/query notify=2/delay=2 + 双 projectOrderId 过滤；auto/execute 首次 2/1/1/0、复测 0/0/0/0；handle(M01) success=1 + 幂等 already=1。

## 5. 踩坑点汇总

### 5.1 校验类（最大的一类坑）

| # | 坑 | 结论/解法 |
|---|----|----------|
| 1 | **`@Valid @RequestBody List<X>` 不校验元素**：Hibernate Validator 只对「bean 字段上的 @Valid」级联，根对象是 List/数组时 `validator.validate()` 直接不触发元素约束（HV 6.0.18 本地对照实验实测 violations=0） | 批量接口两选一：① Wrapper 包一层（改变 HTTP 契约）；② service 手动 `validator.validate()` 循环；③ Controller 类标 `@Validated` + `@NotEmpty @Valid @RequestBody List<X>`（method validation 会级联容器元素，本项目最终选这个） |
| 2 | **Feign 接口上的 @Valid 注解不继承**，Controller 实现方法必须显式写 | Controller 逐接口补 `@Valid @RequestBody` |
| 3 | **`[""]` 能绕过 `@NotEmpty`**：非空集合但元素为空串 | 校验不能只靠集合注解，需逐元素 isBlank 检查 |
| 4 | **List 元素上的注解不级联**（items 列表里每项的 @NotNull 不生效） | items 手写循环校验每项 nodeId 非空 |
| 5 | **删 `@NotEmpty` 后旧消费方失去保护**：notify 接口改走 items 后，顶层 `taskDispatchNodeIds` 的 @NotEmpty 与契约冲突必须删 | 两处旧消费方（TaskDispatchController.batchHandle、MaterialTaskInstallerTaskServiceImpl）补手动非空校验保持等价 |

### 5.2 数据/字段类

| # | 坑 | 结论/解法 |
|---|----|----------|
| 6 | `task_dispatch_node` 实际表**无 `source` 列**（model 有但 DB 无） | INSERT 列清单去掉 source，否则 unknown column |
| 7 | `material_notify_task_automation` 表**无 state 列** | SELECT 不能写 state（方案文档已规避） |
| 8 | `recognize_time` 是 **DATE 列，精确等值匹配**（= 昨日零点），非范围 | 造数用 `DATE_SUB(CURDATE(), INTERVAL 1 DAY)`；历史数据查不到 |
| 9 | CAS SQL `notify_execute_type in (0, null)` 语义误导 | 该列永不为 null，`in(0,null)` 等价 `=0` → 修正为 `=0`；且 CAS SQL 无条件写 `ai_adoption_type`，必须显式赋 `=1` |
| 10 | TEMPORARY TABLE **跨 session 失效** | 分开 session 执行报表不存在 → v2 纯 INSERT 零建表 |
| 11 | **无全局 Jackson date-format**：Date 字段序列化行为因字段注解而异 | handle/save 的 Date 字段带 `@JsonFormat(pattern="yyyy-MM-dd HH:mm:ss", timezone="GMT+8")` → 传**字符串日期**与注解对齐 |
| 12 | **@JsonProperty 下划线字段名**：`NotifyTaskQueryParam` 的 task_type/project_order_id 是 snake_case | 此前 curl 用驼峰 taskType/projectOrderId 字段被忽略（taskType 落 null 默认 3 侥幸可用，projectOrderId 过滤完全失效） |
| 13 | Spring 的 `StringUtils` 只有 `isEmpty` 无 `isNotEmpty` | 用 `!StringUtils.isEmpty(...)` |

### 5.3 构建/启动类

| # | 坑 | 结论/解法 |
|---|----|----------|
| 14 | 编译 `-pl api,dao,service,web` 报 reactor 找不到 | 实际模块名是 `edar-starlord-api` 等**全名** |
| 15 | `-am` 编译 manager 报 `MaterialTaskRouteInstance` 找不到（api 刚编译类的时序抖动） | 重跑一次 BUILD SUCCESS |
| 16 | 启动报 `ArrayIndexOutOfBoundsException: 0`，三方库 treasurechest `CommonEnvironmentPostProcessor:39` 取 `getActiveProfiles()[0]` 越界 | 保证启动带 active profile（IDEA 运行配置 `Active Profiles=local`）；根治需改三方库源码 |
| 17 | `hotdeploy/mapper` 存在运行时 mapper 副本 | 改 Mapper.xml 时需镜像同步，否则线上/热部署加载旧 SQL |

### 5.4 业务/测试类

| # | 坑 | 结论/解法 |

## 6. 反复修改的地方（按时间序）

| # | 事项 | 反复过程 | 最终结论 |
|---|------|---------|---------|
| 1 | **/result 校验方案** | ① 发现 `@Valid List` 不生效 → ② 改 service 手动 `validator.validate()` 循环 → ③ 用户改选纯注解方案 `@Validated` + `@NotEmpty @Valid`（Controller）→ ④ 用户又要求「不用 validator 直接手写」→ validateParams 8 字段手写（数值 `==null`、字符串 isBlank、日期 isBlank+DateUtil.parse 格式聚合一次返回） | 手写校验 + 日期格式聚合；错误字段名统一 wire 下划线（project_order_id/material_code/images） |
| 2 | **images 空元素策略** | 最初要求 `[""]` 报错 → **决策反转**：`["", "url"]` 不报错，**剔除空元素**入库 url；仅过滤后为空才报错 | `filterImages`：逐元素 isBlank 剔除+trim+回写 `param.setImages(...)` |
| 3 | **造数临时表** | v1 用 TEMPORARY TABLE → 用户反馈「没有 autotest 的表」（跨 session 失效） | v2 纯 INSERT 零建表零临时表 |
| 4 | **订单号** | 自造 → OCR 真实订单前 4 个（8260 系列）→ 换号 → 再换号 | 最终 3 个（5460/5772/4994 系列），5 用例 |
| 5 | **automation 判定口径** | 当天零点 → **昨日零点（T+1）** | `selectYesterdayByProjectAndMaterial`，造数 `DATE_SUB(CURDATE(), INTERVAL 1 DAY)` |
| 6 | **batch/handle 入参契约** | ① 扁平 `BatchDispatchHandleParam{taskDispatchNodeIds, images, noticeRetainTime}`（BeanUtils.copyProperties 把同一份 images/时间套到所有节点，**无法区分归属**）→ ② 新建 items 列表字段 `NotifyTaskHandleItemParam{taskDispatchNodeId, images, noticeRetainTime}`，notify 只走 items → ③ 最终提交类名定为 **`NotifyNodeHandleItem`**（配合 `NotifyBatchHandleParam`），更贴近项目既有命名 | items 逐节点明细；顶层旧字段不再作为 notify 执行依据；`@NotEmpty` 删除 + 旧消费方补手动校验 |
| 7 | **sortTasks 排序方向** | ① 原 `comparing(materialCode).thenComparing(estimatedTime)`（品类优先）→ 用户指出「排反了，越靠近今日越靠前」→ ② 改为 `comparing(estimatedTime).thenComparing(materialCode)` → ③ 用户说「没区别」→ ④ 又说「我看错了不用改」 | 已落盘新版本：**考核时间升序为主键（超期负差在前），品类为次键** |
| 8 | **日期传输格式** | 反编译结论「毫秒时间戳最稳」→ 逐字段核实发现 handle/save 的 Date 带 `@JsonFormat` | **字符串日期**（`yyyy-MM-dd HH:mm:ss`）与注解对齐 |
| 9 | **JSON 字段命名** | 一直用驼峰 taskType/projectOrderId | 核实 `@JsonProperty("task_type")` → **snake_case**，方案文档契约表同步修正 |
| 10 | **CAS SQL** | `in (0, null)` → `= 0`（用户确认该列永不为 null） | 同步惠及一键通知 batch 路径 |
| 11 | **工程部获取路径** | 调研 4 条路径（订单维度 projectDepartmentCode / 组织祖先链 / 北京按工长反查 / 班组→管理员） | auto-execute 用订单维度路径①，**无需改动**（只读调研） |
| 12 | **自动化测试脚本** | `test_notify_interfaces.sh` 交付后被用户**删除** | 改手工 curl 逐接口验证 |

## 7. 遗留事项与风险

1. **接口 5/6 触发真实下游副作用**（Kafka/ES/推送）：测试时注意顺序，避免污染线上数据。
2. **site/complete/query 无 summary 时间窗**：与 summary 口径不同，联调时别按 summary 预期断言。
3. **`@Valid @RequestBody List<X>` 失效属项目隐性误区**：项目内 15+ 处同类写法均未真正校验，本次仅修了 notify 相关链路；其余接口如有批量校验诉求需按第 5.1 节方案处理（已沉淀知识库：`/Users/mirror/wiki/20.知识沉淀/📚 批量List接口@Valid校验失效排查与解决方案.md`）。
4. **treasurechest 启动 AIOOBE**：当前靠「启动必带 active profile」规避，根治需改三方库源码或注入默认 profile 的 EnvironmentPostProcessor。
5. **开关 fail-closed**：生产环境上线前必须配置两枚 Apollo 开关，否则功能静默全关（列表空、自动执行全跳过）。
