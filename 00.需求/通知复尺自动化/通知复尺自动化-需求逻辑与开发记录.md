## 1. 需求概述

**背景**：项目经理/工长名下存在多个「通知类任务」（本次聚焦**通知复尺**），处理繁琐、影响效率。本次通过工地**摄像头**与工人拍摄的**照片**判断现场交界面是否满足复尺通知的执行标准，满足则自动判断/自动填充，减少人工操作。

**整体链路**：

```
摄像头采集 / 工人拍照
  → 上游分析（调度层）判断是否满足可通知标准
  → 判断结果通知主材任务（POST /api/recognize/task/result）
  → 落新表 material_notify_task_automation（只新增不更新，一期仅暂存）
  → 小师傅/首页：批量查询判断结果 → 一键通知批量执行
  → push 消息（09:10/13:00/19:00 悬浮框推送）
```

**一期范围**：摄像头+照片判断是否满足通知标准；满足则自动填充表单（图片 + T+3 期望上门时间），由人工提交；开城开关 `notification.remeasure.automation.open-city-engineering-forcemanucid-dept`（城市-工程部-品类-工长级联）。

**配套功能**：小师傅触达（首页/项目详情/测量复尺列表）、首页限时任务、push 消息。需要「批量查询判断结果」+「批量执行通知任务」两个接口。

## 2. 核心业务逻辑（已定稿）

### 2.1 判定结果枚举（我方定义，上游直传枚举值）

| 值 | 含义 | 业务去向 |
| --- | --- | --- |
| `1` CAN_NOTIFY | 可通知 | 归入 `notifyTasks` |
| `2` CANNOT_NOTIFY | 不可通知 | 归入 `delayTasks`（延期预警） |
| `3` CANNOT_JUDGE | 无法判断 | 归入 `delayTasks`（延期预警） |
| `4` SITE_COMPLETED | 现场已完成需关闭 | 本期不返回，另接口处理 |

### 2.2 task_type 口径（已定稿为 Integer，推翻 5 位拼接串）

**最终口径：`task_type` 存整数任务类型**（`3`=通知复尺，`11`=通知安装），DB 列 `INT UNSIGNED`，接收接口入参即整数，**落库零解析**。

- 早期曾采用「5 位拼接串」（`task_dispatch.task_type`2位 + 分隔`0` + `node_type`2位，如 `"03020"`=复尺+通知节点20）存入 VARCHAR(16)，后**被推翻**：字段改回 INTEGER，拼接串方案废弃。
- 推翻影响：二期 batch/query 的 `NotifyTaskTypeUtil.parse` 拆串与 automation 关联键（task_type 原值）**需按 Integer 口径改造**，另项处理。

### 2.3 recommend_visit_time（上游直传必传）

`recommend_visit_time`（期望上门时间）由**上游直传必传**，格式 `yyyy-MM-dd`，我方直接落库；早期「`= recognize_time + 3 天`」的 T+3 计算规则**已取消**。`recognize_time`（上游发识别结果日期）为 T 的时间基准，格式 `yyyy-MM-dd`，接收接口 8 项入参均必传（含 recommend_visit_time）。

### 2.4 任务匹配链路（上游不传 task_dispatch_id）

按 项目+品类+任务类型 反查，两跳定位到具体 node：

```
① task_dispatch    : project_order_id + material_code + task_type=3(复尺) + process_status=2 → task_dispatch_id（取最新）
② task_dispatch_node: task_dispatch_id + node_type=20(通知可启动) + process_status=2 + state=1 → node_id（取最新）
```

### 2.5 工长维度查询（automation 为判定源，node 表为主体）

- automation 表**无 foreman_id**：先靠 node 表 `executor_id=工长 ucid` 收敛工地集合；
- 查询以 `task_dispatch_node`「激活未完成」任务为主体，automation **仅补充判定字段**（judge/remark/图片/T+3 时间）。
- automation 关联键 = `(project_order_id, material_code, task_type整数)` + `recognize_time=当天`（精确维度，见 2.6；二期改造项）。

### 2.6 归组规则

| 通知节点状态 | automation 判定 | 归组 |
| --- | --- | --- |
| 已完成/未激活/已取消 | 不区分 | 不处理 |
| 激活未完成 | judge=1 | `notifyTasks` |
| 激活未完成 | judge=2 / 3 / 无记录 | `delayTasks`（含"未经系统判定"的预警任务，必须露出） |
| 激活未完成 | judge=4 | 本期不返回 |

### 2.7 后端排序（前端按返回顺序直渲即分组）

工地(project_order_id) → 品类(material_code) → 组内「考核时间−当前时间」**升序（紧迫在前）**。响应仅回 `assessmentTime`（=`platform_check_time`），不放差值。

### 2.8 并发保护（一键通知双层 CAS）

node 表无乐观锁，靠 `process_status` 条件更新（2→3）：`WHERE id=? AND process_status=2`，affected=1 才成功；失败即"已被其他路径处理"，前端需明确提示。task_dispatch 同理二次校验。

### 4.3 关键设计与改造决策

1. **task_type 定稿为 Integer**：一期最初 Integer → 二期临时改 String（拼接串）→ **最终 DB 定稿回退 Integer（3=复尺）**，5 位拼接串方案废弃。接收/落库已按 Integer 对齐；2026-08-18 二期 batch/query 按 Integer 口径重建，**`NotifyTaskTypeUtil` 拆串废弃**。
2. **automation 关联改精确维度**：由「项目 IN × 品类 IN 笛卡尔范围 + 内存取最新」改为「精确 `(project, material, task_type)` 维度 + `recognize_time=当天`」，避免范围查询误扫到非目标项目/品类记录；同维度当天仅一条，SQL 无 order by。
3. **recognize_time 取当天零点**：`DateUtil.parse(DateUtil.format(new Date()), DEFAULT_DAY_FORMAT)`，与一期落库口径（`yyyy-MM-dd` 解析）一致；传 `new Date()` 会导致 MySQL DATE/DATETIME 比较永不命中。
4. **查询主体是 node 表而非 automation**：延期预警含"未经过系统判定"的任务，automation 无记录也必须露出；automation 只做判定字段补充。
5. **考核时间 = `node.estimated_time`**（非 platform_check_time）；延期命中预警「`estimated_time − 当前时间 ≤ 3 天`」，排序差值升序（超期负差在前）。
6. **返回按项目汇总**：`NotifyTaskProjectGroupVO{projectOrderId, projectAddress, tasks}`，地址在分组上（`ProjectOrderDetailBO.projectAddress`），任务内不重复。
7. **二期 batch/query 为普通 Controller**（不定义 Feign，仿 `MaterialTaskInstallerTaskController`）；入参 `taskType` 可空默认 3、`projectOrderId` 非必传。
