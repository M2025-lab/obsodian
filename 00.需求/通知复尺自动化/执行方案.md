# 识别结果接收接口与落库方案（一期）

> 本部分为「接收上游判断结果 → 落库」的落地设计。落点工程：**edar-starlord（主材任务系统）**。
> 数据表：`material_notify_task_automation`（主材通知任务自动化记录表）。
> 原则：**只新增、不更新**；一期仅暂存，不触发通知/任务业务逻辑。

## 1. 接口定义

| 项 | 值 |
| --- | --- |
| 路径 | `POST /api/recognize/task/result` |
| 调用方 | 调度层 → 主材（edar-starlord） |
| 用途 | 接收上游识别结果并暂存 |
| 请求体 | 见下方 `NotifyTaskResultParam` |
| 响应 | `ResultDTO<Void>`，成功返回 `success()` |
| 暴露形式 | **Controller + Feign**（参照 `SupplierMessageSyncFeign` / `SupplierMessageSyncController`） |

接口形式选型：api 模块定义 `@FeignClient("edar-starlord")` 接口，web 模块 Controller 实现之，供调度层 Feign 调用。

## 2. 数据表 DDL（最终版）

```sql
CREATE TABLE `material_notify_task_automation` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    `project_order_id` BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '项目订单id',
    `material_code` VARCHAR(50) NOT NULL DEFAULT '' COMMENT '品类编码',
    `task_type` INT(11) UNSIGNED NOT NULL DEFAULT 0 COMMENT '任务类型：3-通知复尺，11-通知安装等',
    `judge_result` TINYINT NOT NULL DEFAULT 0 COMMENT '最新系统判定结果：0-未判定，1-任务可通知，2-任务不可通知，3-无法识别是否可通知，4-现场已完成任务需关闭',
    `judge_remark` VARCHAR(1024) NOT NULL DEFAULT '' COMMENT '判断备注',
    `images` VARCHAR(8192) NOT NULL DEFAULT '' COMMENT '通知任务图片，逗号分隔',
    `recognize_time` DATE NOT NULL DEFAULT '1900-01-01' COMMENT '上游识别结果日期，T的时间基准',
    `recommend_visit_time` DATE NOT NULL DEFAULT '1900-01-01' COMMENT '最新判定期望上门时间，T+3',
    `notify_execute_type` TINYINT NOT NULL DEFAULT 0 COMMENT '通知执行方式：0-未执行，1-一键通知，2-自动通知',
    `ai_adoption_type` TINYINT NOT NULL DEFAULT 0 COMMENT 'AI建议采纳情况：0-未处理，1-采纳，2-未采纳，3-图片采纳，4-上门时间采纳',
    `gmt_create` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `gmt_modified` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',

    PRIMARY KEY (`id`),
    KEY `idx_project_task_material` (`project_order_id`, `task_type`, `material_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='主材通知任务自动化记录表';
```

> **task_type 口径定稿为 INT**：接收接口存整数任务类型（3=复尺），**不再是**早期的 5 位拼接串（`"03020"`）方案——该口径已废弃。若表按旧口径已建，需：
>
> ```sql
> ALTER TABLE `material_notify_task_automation`
>     MODIFY COLUMN `task_type` INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '任务类型：3-通知复尺，11-通知安装等';
> ```

| `project_order_id` = `123456789012345678` | `project_order_id` | 直接映射（Long） |
| `material_code` = `"029001001"` | `material_code` | 直接映射 |

| `judge_result` = `1`（我方枚举值） | `judge_result` | 直接落库，取值见第 4 节枚举（上游按我方定义直传，**无映射**） |

## 6. 逻辑要点

1. **批量接收**：入参为 `List<NotifyTaskResultParam>`，逐条校验构建后一次 `batchInsert` 落库。
2. **只新增不更新**：每次回调批量新增记录，不做 upsert。
3. **必传强校验**：8 项入参任一缺失/格式非法 → 整体报参数错误（不做部分成功）。
4. **recommend_visit_time 上游直传**：不再由我方 T+3 计算（`= recognize_time + 3 天` 规则取消，上游直接给日期）。
5. **写库路由**：默认走 slave，插库实现参照现有 insert 服务写法（`CallRecordDaoImpl` 未显式 `routeMaster`），实施时验证实际命中 master。
6. **一期仅暂存**：不触发通知、不操作任务状态，仅做接收 + 落库。
7. **task_type 整型直存**：入参 Integer（3=复尺），落库零解析。
8. **NOT NULL 兜底**：`batchInsert` 为全列插入，`notify_execute_type`/`ai_adoption_type`/`gmt_create`/`gmt_modified` 需 service 显式赋值（0 / `new Date()`），防列约束冲突。

## 7. 任务匹配与结果落点（automation → task_dispatch → task_dispatch_node）

### 7.1 匹配链路（上游不传 task_dispatch_id，按 项目+品类+任务类型 反查）

```sql
-- ① 主表定位：项目 + 品类 + 任务类型(=3 复尺) → task_dispatch_id
SELECT d.id
FROM task_dispatch d
WHERE d.project_order_id = ?
  AND d.material_code = ?
  AND d.task_type = 3          -- 复尺
  AND d.process_status = 2     -- 激活未完成
ORDER BY d.gmt_create DESC     -- 取最新（防御「再次复尺」产生多条）
LIMIT 1;

-- ② 节点定位：task_dispatch_id + 通知节点 → node_id（业务结果落 node 表）
SELECT n.id
FROM task_dispatch_node n
WHERE n.task_dispatch_id = ?
  AND n.node_type = 20         -- 通知可启动（通知复尺对应 20，已确认）
  AND n.process_status = 2
  AND n.state = 1
ORDER BY n.gmt_create DESC     -- 取最新（防御 restart 重启后多条通知节点）
LIMIT 1;
```

- `u_task_code` 暂不可用，匹配跳过。
- `executor_id` = 工长 ucid（与 Apollo 开关维度对齐）。

### 7.2 工长维度查询（automation 表为判定源）

**判定源 = `material_notify_task_automation`**（上游识别结果标记：`judge_result=1` 可通知）。自动化表**无 foreman_id**，工长维度靠 node 表 `executor_id` 收敛工地范围，再回 automation 表取可通知标记，最后匹配到具体 node 任务。

```sql
-- ① 定位该工长全部工地：node 表 executor_id=工长 → project_order_id 集合
SELECT DISTINCT project_order_id
FROM task_dispatch_node
WHERE executor_id = ? AND state = 1;

-- ② 判定源：从 automation 表筛出该工长工地下的「可通知」记录集
--    得到 (project_order_id, material_code, task_type) 待处理集合
SELECT project_order_id, material_code, task_type
FROM material_notify_task_automation
WHERE project_order_id IN (工长工地集合)
  AND judge_result = 1;      -- 上游判定可通知（旧 notify_status 列已删，本轮只以 judge_result 为判定源）

-- ③ 记录集逐条两跳匹配，落到具体 task_dispatch_node（见 7.1）
--    最终返回可执行通知的具体 node 任务（node_type=20 且激活未完成）
```

要点：
- **automation 表只提供"哪些任务可通知"的标记**，具体可执行的通知节点仍在 node 表（`node_type=20` + `process_status=2`）。
- 若①返回的工地集合较大，②可用 `idx_project_task_material` 索引命中。

### 7.4 并发保护（双层 CAS）

node 表无乐观锁，靠 `process_status` 条件更新，防止重复提交：

```sql
UPDATE task_dispatch_node
SET process_status = 3,            -- 激活未完成 → 激活已完成
    images = ?,                    -- 上传照片
    notice_retain_time = ?,        -- 期望上门时间
    ai_adoption_type = ?,
    notify_execute_type = 1,       -- 一键通知
    end_time = NOW()
WHERE id = ? AND process_status = 2;   -- CAS：affected=1 才成功
```

更新 `task_dispatch` 同理按其 `process_status`/`version` 二次校验。失败（affected=0）即"任务已被其他人处理"，返回给前端。

## 8. 第二步：批量查询通知任务详情 — batchQueryNotifyTasks（二期）

> ✅ **2026-08-18 已按定稿口径实现**（普通 Controller，非 Feign）。`task_type` Integer、`projectOrderId` 非必传、node_type 写死 20、assessmentTime=`node.estimated_time`、按项目汇总分组、延期≤3天差值升序。

### 8.1 接口定义

| 项 | 值 |
| --- | --- |
| 路径 | `POST /api/material/notify/task/batch/query` |
| 调用方 | 小师傅 / 首页（前端） |
| 用途 | 查询该工长全部工地（或指定项目）下「可通知」与「延期预警」任务详情，**按项目汇总** |
| 请求体 | `NotifyTaskQueryParam`：`taskType`（Integer，**可空默认 3**，后续其他通知类型如 `11` 预留）；`projectOrderId`（Long，**非必传**，不传查全部工地） |
| 工长来源 | `OperatorContextHandler.getContext().getOperator().getUcid()`（web 层取，前后端既有惯例），**不走 body** |
| 响应 | `NotifyTaskBatchQueryVO`：`notifyTasks` + `delayTasks`（各为 `NotifyTaskProjectGroupVO[]`，按项目分组，地址在分组上） |
| 暴露形式 | **普通 web Controller**（`NotifyTaskBatchQueryController`，不定义 Feign，仿 `MaterialTaskInstallerTaskController`） |

### 8.2 查询主体与判定规则

查询以 **`task_dispatch_node` 表「激活未完成」任务为主体**（不能只查 automation——延期预警含"未经系统判定"的任务，automation 无记录也要露出）；`material_notify_task_automation` **仅补充判定字段**。

| 通知节点状态 | 系统识别结果(automation) | 归组 |
| --- | --- | --- |
| 已完成/未激活/已取消 | 不区分 | 不处理 |
| 激活未完成(process_status=2) | judge_result=1（可通知） | `notifyTasks` |
| 激活未完成 | judge=2（不可通知）/3（无法识别）/无 automation 记录 | `delayTasks` |
| 激活未完成 | judge=4（现场已完成需关闭） | 本期不返回（另接口） |

**延期预警定义**：该工长全部工地下，「激活未完成」且（「系统判定未达到可通知标准」judge=2/3 **或**「未经过系统判定」无 automation 记录）且「命中预警」的任务。
**命中预警 = `考核时间 − 当前时间 ≤ 3 天`**（考核时间 = `node.estimated_time`）；超期（负差）任务保留并排最前。

### 8.3 查询链路（复用 `listTaskByCondition` 一次 JOIN，Integer 口径）

```
入参 executorId（context 取）+ taskType(整数，缺省3) + projectOrderId(非必传)
  → taskDispatchNodeDao.listTaskByCondition:
       executorIdList=[工长 ucid]
       + taskTypeList=[taskType] + nodeTypeList=[20]（node_type 写死）
       + processStatus=2 + state=1×2（node/task）
       + projectOrderId（非空则传）
  → 一次 JOIN task_dispatch 返回 TaskDispatchDTO
     （含 taskDispatchNodeId/projectOrderId/materialCode/Name/supplierName/estimatedTime）
  → automation 表按 (project_order_id, material_code, task_type) 精确维度 + recognize_time=当天 取判定
     （行构造 IN；recognize_time 取服务端当天零点，与一期落库口径一致；同维度当天仅一条，无 order by）
     → 补 judgeResult/judgeReason/images/recommendVisitTime
  → 内存归组（judge=1→notify；2/3/无→delay；4→跳过）
  → delayTasks 过滤（考核时间 ≤ now + 3 天）
  → 任务内排序（品类 → 考核时间升序）→ 按项目聚合分组（项目间 projectOrderId 升序，地址在分组上）
```

### 8.4 分组排序（后端做）

- **任务内排序**：品类(material_code) → 考核时间(=`node.estimated_time`)升序；延期组内「`assessmentTime`−当前时间」差值**升序（超期负差在前，紧迫任务在前）**。
- **分组排序**：按 `projectOrderId` 升序；**地址在项目分组上**（`ProjectOrderManager.getProjectOrders` 的 `projectAddress`），任务内不重复地址。
- 响应仅含 `assessmentTime`（=`node.estimated_time`），不放差值。

### 8.6 Apollo 开关（通知复尺自动化）

| key | 名称 | 结构 |
| --- | --- | --- |
| `notification.remeasure.automation.open` | 开关A：功能开关 | 单规则 `{"cities":[],"projectManagers":[],"departments":[]}` |
| `notification.remeasure.automation.autoNotify` | 开关B：自动通知开关 | 品类码 → 各一套规则 `{"品类A":{...},"品类B":{...}}` |

- **命中规则（OR）**：`gbCode∈cities` **OR** `工长ucid∈projectManagers` **OR** `工程部code∈departments`。
- 维度数据：城市 = `ProjectOrderDetailBO.gbCode`；工长 = 查询 executorId；工程部 = `ProjectOrderDetailBO.orderDto.projectDataExt.projectDepartmentCode`（逐层兜底，参考 `TaskDispatchTraceServiceImpl`）。
- **接点**：开关A 在 `queryNotifyTaskSplit` 内统一过滤（`NotifyTaskBatchQueryServiceImpl.filterByFeatureSwitch`），**列表 + 摘要同口径**（摘要计数自动一致）。开关B 本次只交付 `NotifyAutomationConfig.isAutoNotifyOpen` 方法 + 配置，**接点留给自动通知功能开发时接入**。
- **fail-closed**：配置缺失/非法/入参为空 → 不命中（false）；解析异常 `log.warn` + false。
- 落地类：`service/config/NotifyAutomationConfig.java`（仿 `SaleHomeCardConfig`，每次调用现解析，Apollo 变更即时生效）。
