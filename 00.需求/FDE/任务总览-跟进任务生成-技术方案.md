## 1、背景

云助理作业台需要"跟单任务"体系：对项目尾款、返补货单、材料任务三类业务数据自动生成催办任务（催尾款、催返补二次下单、催返补接单、D 类催办 D1-D16），任务随业务状态自动流转（已完成/已取消/风险升级），云助理在任务总览页跟进处理。本工程（artisan-construction）承接任务生成与流转引擎，云助理作业台为消费方。

## 2、需求理解

|#|需求点|说明|
|---|---|---|
|1|任务类型|四类：催尾款、催返补下单、催返补接单（前次完成串行触发）、D 类催办（D1-D16，仅一批/二批品类的任务节点）|
|2|生成方式|尾款/返补任务**只监听消息驱动（创建、完成、取消、风险升级均由业务消息触发）；材料任务（D 类催办）定时任务 + 实时状态处理**双触发|
|3|状态机|待跟进 → 跟进中；终态：已完成（业务完成）/ 已取消 无需跟进（云助理手动关闭）；跟进动作一旦发生不可退回待跟进|
|4|风险等级|预警（黄，创建即预警）/ 延期（红，超考核时间升级）；各类型升级时点见 3.3~3.5|
|5|任务实体|任务名称（自动生成）+ 任务类型 + 关联业务任务（供应商/品类/任务节点/业务任务 id/处理人）+ 项目上下文（订单 id/阶段/项目经理/交付专家/云助理）+ 风险等级 + 状态|
|6|D 类催办生成逻辑|都有排程：全流程链路从后往前找第一个未完成任务且前置依赖全完成；距考核 ≤3 自然日创建（预警），考核当天升级（延期）|
|7|任务去重|同一项目同一业务节点已有未完成的催办任务时不新建，在原任务上继续跟进 ， 去除终态(不能包含无需跟进)的|
|8|页面功能|任务总览页：筛选、项目聚合/平铺切换、写跟进（转跟进中）、手动关闭（无需跟进）、跟进记录|
|9|一期项目范围|一期仅对指定项目订单集合生效：moma 定时任务读取在线文档订单列表调后端接口写入 Redis 白名单，任务生成/流转均基于该订单范围跑|

### 3.2 数据模型与状态机

**任务状态机**（新增枚举 `FollowUpTaskStatusEnum`，位置 `base/enumeration/followup/`）：

|code|枚举|含义|进入条件|触发方|
|---|---|---|---|---|
|0|WAIT_FOLLOW|待跟进|任务自动创建|系统|
|1|FOLLOWING|跟进中|云助理执行任意跟进操作（写跟进/外呼等）|云助理|
|2|FINISHED|已完成|关联业务任务完成|系统自动|
|3|CANCELED|已取消|关联业务任务取消|系统自动|
|4|NO_NEED|无需跟进|云助理手动关闭|云助理|

状态流转规则：

|当前状态|触发条件|目标状态|
|---|---|---|
|待跟进|云助理填写跟进记录|跟进中|
|待跟进 / 跟进中|关联业务任务完成|已完成|
|待跟进 / 跟进中|关联业务任务取消|已取消|
|待跟进 / 跟进中|云助理手动关闭|无需跟进|

- 跟进中 → 待跟进**不可逆**
    
- 已完成 / 已取消 / 无需跟进为**终态**，不可回退；终态任务不参与去重判断(无需跟进需参与)（同节点可重新创建）考核时间 已确认
    

  

**风险等级****枚举**（新增 `FollowUpRiskLevelEnum`）：0 预警（黄，创建即预警）/ 1 延期（红，超考核时间升级）。

**幂****等与去重**： ( biz_id(任务id, 尾款的订单id、货单号) + taskType)

### 3.3 材料任务催办（D 类）：定时 + 实时状态处理

**双触发，共用同一套重算引擎** **`FollowUpEngine.recalculate(projectOrderId)`**：

- **定时**：新增 `FollowUpScanTask`（service/task/，模式参照 DeliveryProcessTask.java:37,65），`@Assignment(key="follow-up-task-scan-task", cn="跟单任务生成")`，入口 `RedissonLockUtil.tryFairLock` 加锁；遍历 Redis 白名单内订单逐单重算（见 3.6）。定时负责：创建距考核 ≤3 天的预警任务、考核当天风险升级延期(基于定时任务计算最新结果，diff对比字段变更 或者任务变更）
    
- **实时（异步事件 → 延迟队列表 → 定时消费）：排程任务完成/需求变更、模版升级、下货单等业务点发 Spring 事件，事件不直接触发重算**，而是写入延迟队列表，由独立定时任务每 10 分钟按订单维度消费——10 分钟内同一订单的多个事件合并为一次重算：
    
    - 新增事件 `FollowUpRecalculateEvent`：字段 `projectOrderId`、`triggerScene`（TASK_FINISH / DEMAND_CHANGE / TEMPLATE_UPGRADE / DELIVERY_ORDER）
        
    - 发布点（均在业务处理+持久化完成之后）：
        

|场景|发布位置|依据|
|---|---|---|
|排程任务完成|`BusinessChangeMessageHandleServiceImpl.handleMaterialTaskNodeFinish`（:1388）"完成任务"分支（:1476）持久化之后|BusinessChangeMessageHandleServiceImpl.java:1388,1476|
|需求变更完成|`NeedChangeHandler.handleBiz`（:133）处理尾部|NeedChangeHandler.java:78,133|
|模版升级|`DeliveryProcessServiceImpl.handleProcessTemplateChange`（:1003）单订单模版升级处理尾部（模板变更先落 WAIT 记录由定时任务逐单执行，入口见 DeliveryProcessCfgTemplateChangeListener.java:30）|DeliveryProcessServiceImpl.java:1003|
|下货单|`BusinessChangeMessageHandleServiceImpl.handleOrderChangeEventWithLock`（:1192）锁内 `handleOrderChangedEvent`（:1206）处理成功之后|BusinessChangeMessageHandleServiceImpl.java:1192,1206|
|考核时间变更|||

- **入队**：新增 `FollowUpRecalculateEventListener`，`@TransactionalEventListener(phase = AFTER_COMMIT)` + 异步线程池，仅做一件事——insert `follow_up_recalculate_queue`（订单 id + trigger_scene，状态=待处理）；入队幂等：同订单存在待处理记录则跳过（uk 唯一约束兜底）；发布/入队异常仅告警
    
- **消费**：新增定时任务 `FollowUpQueueConsumeTask`（`@Assignment(key="follow-up-queue-consume-task")`，**每 10 分钟调度**，入口 Redisson 锁）：扫待处理队列记录 → **按 projectOrderId 去重**（10 分钟窗口内同订单多条只执行一次）→ 逐单调 `FollowUpEngine.recalculate(projectOrderId)` → 成功后记录置已处理；失败置失败并保留，下轮重试（超 24h 告警丢弃，由 FollowUpScanTask 定时兜底）
    

**重算引擎逻辑**（单订单）：

1. **查询排程任务****实例**：按 projectOrderId 查本地排程任务实例（`delivery_process_task`，字段见 DeliveryProcessTask.java:117,143,163,218），得到该订单全部材料任务及其状态、考核时间
    
2. **品类-任务类型过滤**：每个品类只催其配置的 taskType 列表上的任务（品类→taskType 映射 Apollo 配置 `follow.up.task.generate.rule`，见 3.3 末尾）；品类或 taskType 不在配置内的不创建催办
    
3. **定位当前应执行任务**：任务链路取自**配置层**——先根据订单的排程模版 id 获取该品类的 ruleId，再根据 ruleId 查询 starlord 获取子流程配置（节点链路及前置依赖）：
    
    1. 从当前任务看依赖 只看前置一层任务即可
        
    2. 校验其前置依赖：有多个前置依赖的**全部完成才算通过**；前置未全完成则该任务不催、不继续往前找
        
    3. 通过 → 该任务即"当前应执行任务"（任务状态数据源：本地 `delivery_process_task`，字段见 DeliveryProcessTask.java:117,143,163,218）
        
4. **定位当前应执行任务时跳过"后置任务已完成"的任务**：带 `successor_finished=1` 标识的任务（其后置任务已有完成的）视为已过节点，不作为应执行任务、继续往前找
    
5. **创建/升级判定**（对定位到的"当前应执行任务"）：
    

|距考核时间|动作|
|---|---|
|> 3 自然日|不创建任务（已有未终态任务维持）|
|≤ 3 自然日|创建催办任务（状态=待跟进，风险=预警黄）|
|考核当天及以后|风险升级为延期（红）|

1. **状态流转**：重算发现该任务对应排程任务已完成 → 任务置已完成；取消 → 已取消
    
2. 任务名称自动生成 催尾款 返补 催返补下单、接单
    

**后置任务已完成标识回写**（新增逻辑，挂在排程任务完成链路上）：排程材料任务完成持久化之后（`BusinessChangeMessageHandleServiceImpl.handleMaterialTaskNodeFinish` :1476 完成分支后），按该订单任务链路（模版 id → 品类 ruleId → starlord 子流程配置）取已完成任务的**前置任务**，为其回写 `successor_finished=1`（幂等：已为 1 不重复刷，批量 update）。作用：链路中后置任务已完成的节点即使自身未完成也不再催办，重算引擎据此跳过。

**Apollo 配置**`follow.up.task.generate.rule`（key 为品类 code，value 为该品类需要跟进的任务 taskType 列表，taskType 取 `DeliveryProcessTaskTypeConstant`）。开关字段说明：

|字段|作用|
|---|---|
|`enabled`|跟单任务功能总开关，false 时全部链路（定时扫描、队列消费、消息 Handler）停跑，即回滚开关|

|`materialUrge.enabled`|D 类材料催办子开关，可在总开关开启下单独灰度材料任务|

### 3.4 尾款任务：只监听消息

不扫表、不重算——每条消息到达时按状态机直接流转，处理逻辑幂等（终态跳过）。新增 `FinalPaymentFollowUpHandler`（kafka 消费，`@EventType(bizType, serverName)` 路由，模式参照 MaterialDelayProcessChangedListener.java:19）：

|消息场景|处理逻辑|
|---|---|
|瓦工作业验收完成(待补补充code)|查尾款状态：未收齐 → 创建催尾款任务（待跟进，预警黄）|
|基装验收完成|未终态催尾款任务且尾款仍未收齐 → 风险升级为延期红|
|尾款收齐|未终态催尾款任务 → 已完成|
|项目取消 / 客户退款|未终态催尾款任务 → 已取消|

- 尾款收齐状态判定依赖尾款消息体携带（**消息字段口径待确认**，见第 5 节）
    
- 瓦工/基装验收完成消息若由本工程内验收链路产生，则改为链路内发 Spring 事件（调研确认消息来源后定）

### 3.5 返补任务：只监听消息（两类任务串行）

com.ke.utopia.construction.service.consumer.ScmOrderChangedHandler（kafka 消费，同 3.4 路由模式）：

|消息场景|处理逻辑|
|---|---|
|售中补货单创建|补货单类型=售中补货 且 创建时间 ≥ 2026-08-26 → 创建催返补二次下单任务（待跟进，预警黄）|
|供应商完成二次下单|该补货单的催返补二次下单任务 → 已完成；**同一事务内串行创建**催返补接单任务（待跟进，预警黄，不升级延期）|
|供应商已接单|催返补接单任务 → 已完成|

### 3.6 一期项目范围控制（Redis 订单白名单）

一期只对指定项目订单集合生效。范围数据流转：**moma 侧定时任务（外部）读取在线文档中的项目订单列表 → 调后端范围同步接口写入 Redis → 三类链路基于该范围执行**：

- **范围同步接口**`POST api/construction/follow-up/task/scope/sync`（新增 `FollowUpTaskScopeController.syncScope`）：入参订单号列表（全量覆盖式），校验后整批写入 Redis
    
- **Redis 结构**：key `construction:follow_up:project_scope`（String，JSON 数组），每次同步整值覆盖
    
- **范围校验点**：① 3.3 定时扫描入口（白名单为空不执行）+ 实时重算监听器；② 3.4/3.5 消息 Handler 入口（订单不在范围内直接 ack 跳过）
    
- moma 侧读在线文档→调接口属外部实现，不在本工程展开

|operateType|含义|附加入参|处理逻辑|
|---|---|---|---|
|FOLLOW|写跟进|content（必填，≤500）|insert `follow_up_record` + 任务置**跟进中**（仅待跟进可转；跟进中可继续追加）、`last_follow_up_time=now`|
|NEXT_FOLLOW|约下次跟进|nextFollowUpTime（必填）|更新任务 `next_follow_up_time`，任务状态不变（待跟进/跟进中均可约）；如带 content 同时记一条跟进记录|
|CLOSE|手动关闭|closeReason（必填）|校验当前状态为待跟进/跟进中，置**无需跟进**（终态）|

- 三种操作均事务执行，服务端状态校验兜底；**跟进动作一旦发生不可退回待跟进**
    
- 跟进记录 `POST /follow-up/task/records`：按 taskId 倒序返回全部记录（操作类型、内容、下次跟进时间、关闭原因、操作人、时间）——三种操作统一落 `follow_up_record` 流水
    

外部操作（外呼等）由云助理作业台调 handle 接口（operateType=FOLLOW）同步，状态同样转跟进中。
