## 1、背景

一期（任务总览-跟进任务生成-技术方案）已上线跟单任务生成与闭环链路（D 类材料催办 / 催尾款 / 催返补下单 / 催返补接单）。本需求（3.5，261021 新增）针对**返补下单及下单前置流程**新增催办任务：橱柜定制柜集采切换后线上返补单走问题单流程，需按问题单状态催对应角色处理/审批/完善解决方案；非集采订单走线下台账（AI 扒数据维护在金山云文档），需对未下单登记的订单催首次下单。

已与需求方确认的口径：

- 集采路**消费问题单变更消息**（准实时）；上游消息方案已定（文档：https://beike.feishu.cn/docx/KfCVd1LccoaLdpx8sTWcm5j4neh）：复用 topic utopia-work-order-topic，新增两个 bizType（问题单状态变更/方案状态变更），消息体只带状态，品类等经聚合查询接口反查。
- 非集采路**定时任务读金山云文档全量对比**；读文档骨架代码已写在 feat/50559773/follouUpProblem 分支，本方案完成字段对齐与业务处理。
- sourceType 新增 2 个（问题单数据、返补非集采台账数据），taskType 新增 3 个（催处理、催上级审批、催首次下单）。
- 不按 0826 时间过滤；台账数据只读。
- 问题单发起人角色、品类记录在任务上：品类复用既有 materialCode/materialName；**发起人角色新增独立字段 sponsor_role**（台账路按问题单发起人角色枚举名称匹配成 code 落库）记录，不占用 handlerRole（新任务类型 handlerRole 置空，不记录处理人角色——催上级审批要找的"发起人上级"由跟单人按发起人角色自行判断）。
- 新两路任务沿用订单范围表 follow_up_project_scope 灰度控制（范围外订单不创建）。

## 2、需求理解

| #   | 需求点       | 口径                                                                                                                             |
| --- | --------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 1   | 任务来源      | 两路：① 集采线上返补（0826 后线上化，与问题单对接，解决方案=补货类型）→ 消费问题单变更消息；② 非集采走线下台账（AI 扒数据维护金山云文档）→ 定时任务读文档全量对比                                      |
| 2   | 任务类型（3 个） | **催处理**：问题单状态流入 8（方案待审批），催发起人再处理；**催上级审批**：问题单状态流入 7（待提交解决方案），催发起人的上级审批；**催首次下单**：方案状态流入 0（待完善）且问题单状态 0（催完善解决方案）；非集采台账路只有催首次下单 |
| 3   | 集采路任务流转   | 事件驱动流入/流出：流入满足建任务条件（按消息体状态判定）→ 反查取品类后建任务；流出（previous→当前 不再满足）→ 对应未终态任务置已完成；状态值一律用上游枚举                                          |
| 4   | 非集采路全量对比  | 取"非集采订单走台账扣款流程"=是 且"下单类型"=未下单登记的行（按表头名取值）：任务表无该工单未终态任务 → 创建；Excel 里不存在或筛选条件已变更（不再满足）→ 对应任务置已完成                                 |
| 5   | 记录字段      | 问题单发起人角色（台账路按发起人角色枚举名称匹配 code）、品类                                                                                              |
| 6   | 范围控制      | 两路均校验 follow_up_project_scope，范围外订单不创建                                                                                         |

## 4、详细设计

### 4.1 枚举扩展

FollowUpSourceTypeEnum 新增 2 值（追加在 FINAL_PAYMENT 之后，不动既有值）：

|code|枚举名|含义|
|---|---|---|
|4|PROBLEM_ORDER|问题单数据（集采线上返补）|
|5|OFFLINE_REPLENISH_LEDGER|返补非集采台账数据（金山云文档）|

FollowUpTaskTypeEnum 新增 3 值（String code，风格对齐现有）：

|code|枚举名|含义|触发条件|
|---|---|---|---|
|problem_order_handle|催处理|催发起人处理被驳回的问题单|问题单消息：solution=3 且 workOrderState 流入 8（方案待审批，WorkOrderStateEnum）|
|problem_order_approve|催上级审批|催发起人的上级审批|问题单消息：solution=3 且 workOrderState 流入 7（待提交解决方案，WorkOrderStateEnum）|
|problem_order_first_order|催首次下单|催完善解决方案 / 催首次下单|集采：方案消息 solution=3 且 status=0 且 workOrderState=0；台账：非集采订单走台账扣款流程 且 下单类型=未下单登记|

**bizId 约定**（与既有"来源+业务 id"模式一致）：集采路=workOrderId（问题单唯一 ID）；台账路**=工单 id**（台账"工单id"列，即上游 work_order 体系的同一实体）——**两路 bizId 同体系**，同单唯一一条在跟任务。幂等键=bizId+taskType（同 createWaitTask 判重模式）。

**引用影响面**（grep 全量核实）：

- taskType/sourceType 为 String/Integer 直存，无 switch 白名单逻辑引用枚举全值——新增值零改动。
- ES FollowUpEsData（task_type/source_type keyword）、查询参数（`taskTypes List<String>`、sourceType Integer）字段已有，新枚举值天然透传，mapping 不变。
- 前端任务总览页需同步两枚举字典（上游依赖见第 6 节）。

### 4.3 问题单消息路（集采线上返补）

上游消息方案已定（文档：https://beike.feishu.cn/docx/KfCVd1LccoaLdpx8sTWcm5j4neh，服务名 artisan-work-order）：

| 项         | 值                                                     |
| --------- | ----------------------------------------------------- |
| Topic     | utopia-work-order-topic（复用现有，dev 已核实，测试/生产以配置中心实际值为准） |
| bizType ① | issue-order-state-change（问题单状态变更）                     |
| bizType ② | issue-order-solution-state-change（方案状态变更）             |
| 消费组       | 业务方申请独立 group.id（不可与其他服务共用，否则消息被分摊）                   |
| 聚合键       | eventContextKey=workOrderId（Kafka record key，同单事件保序）  |
| 去重        | 外层 eventId 框架级去重 + 任务按 bizId+taskType 业务幂等            |

**两个 Handler**（service/consumer，路由模式参照 ScmOrderChangedHandler.java:25 @EventType(bizType, serverName)，serverName=artisan-work-order）：IssueOrderStateChangeHandler / IssueOrderSolutionStateChangeHandler。消息体（payloadData，上游已定字段，非 TODO）：

|字段|类型|说明|
|---|---|---|
|workOrderId|Long|问题单唯一 ID（bizId）|
|workOrderNo|String|父问题单号|
|projectOrderId|Long|项目订单 ID|
|projectOrderType|Integer|项目订单类型|
|workOrderState（方案事件：workOrderState 快照）|Byte|问题单状态，取 WorkOrderStateEnum|
|solution|Integer|方案类型，取 WorkOrderSolutionTypeEnum（补货=3）；问题单事件取主表、方案事件取方案层|
|previous*（各状态前值）|—|创建事件为 null|
|solutionId / solutionOrderNo / status（仅方案事件）|Long/String/Integer|方案层唯一 ID/单号/状态（WorkOrderSolutionStatusEnum）|

> ⚠️ **消息体不携带品类/角色/货单**（上游明确：一对多关系、前置状态可能无方案，经聚合接口反查更稳定）——sponsorRole、品类均需反查获取，见下。

**反查聚合接口**（Feign：IssueOrderStateQueryApi#query，POST /api/issue/order/state/query，上游新增）：精确反查只传 workOrderId、pageNum=1、pageSize=1。**状态判断直接用消息体**（流入/流出由消息内 previous→当前值判定），反查仅取落库信息——品类一个单固定一个品类，skuList 取第一条：

|本方案字段|出参来源|说明|
|---|---|---|
|品类 materialCode/materialName|skuList[0]（父单或 solutionList[] 中方案类型=3 的那条）|商品品类，非问题分类；**单固定单品类，取一条**|

**处理逻辑**（新增 ProblemOrderFollowUpServiceImpl，结构参照 FinalPaymentFollowUpServiceImpl；**状态值一律用上游 api 包枚举**——WorkOrderStateEnum / WorkOrderSolutionStatusEnum / WorkOrderSolutionTypeEnum，不自建副本）：

**① IssueOrderSolutionStateChangeHandler（方案状态变更）**——催首次下单：

```text
方案状态消息到达
  ├─ 前置过滤：solution ≠ 3（补货，WorkOrderSolutionTypeEnum）→ 直接 ack 返回
  ├─ 流入（status=0 待完善 且 workOrderState=0 处理中）→ 满足建催首次下单：
  │   范围校验 inScope(projectOrderId) → 反查聚合接口（按 workOrderId）取品类 →
  │   按 bizId+taskType 判重，无未终态任务则创建 problem_order_first_order（待跟进+预警）
  └─ 流出（previousStatus=0 且 status≠0，方案从待完善流转走）→ 该 workOrderId 的
      problem_order_first_order 未终态任务置已完成（bizId+taskType 定位）
```

**② IssueOrderStateChangeHandler（问题单状态变更）**——催上级审批/催处理（只处理 7/8 的流入流出）：

```text
问题单状态消息到达
  ├─ 前置过滤：solution ≠ 3（主表方案类型非补货）→ 直接 ack 返回
  ├─ 流入 workOrderState=7 → 反查取品类 → 判重后创建 problem_order_approve 催上级审批
  ├─ 流入 workOrderState=8 → 反查取品类 → 判重后创建 problem_order_handle 催处理
  ├─ 流出（previousWorkOrderState ∈ {7,8} 且 workOrderState ∉ {7,8}）→ 对应催上级审批/催处理任务置已完成
  └─ 流入 workOrderState ∈ {1 已完成, 3 已取消}（终态）→ 该 workOrderId 全部未终态任务置已完成/已取消
```

**状态 → 任务类型路由**（枚举口径为上游 WorkOrderStateEnum，状态语义以上游枚举为准）：

|触发事件|流入条件|应建任务类型|
|---|---|---|
|方案状态变更|solution=3 且 status=0 且 workOrderState=0|problem_order_first_order 催首次下单|
|问题单状态变更|solution=3 且 workOrderState=7|problem_order_approve 催上级审批|
|问题单状态变更|solution=3 且 workOrderState=8|problem_order_handle 催处理|
|问题单状态变更|workOrderState ∈ {1,3}（终态）|不建；全部未终态任务置已完成/已取消|
|其他|—|不建任务|

- 任务 name 自动生成：催上级审批 / 催处理 / 催首次下单（不带业务 id；关联单号、品类在任务明细字段中已可见）
- 终态兜底：workOrderState=1 已完成 / 3 已取消 → 该问题单全部未终态任务置已完成/已取消
- 幂等：重复/延迟/乱序消息与补录同时命中时，按 bizId+taskType 业务幂等（createWaitTask 判重模式），流出完成按 bizId+taskType 定位
- ES 双写：写任务走 FollowUpRepositoryImpl 既有 insert/update，无需额外处理
- 后门初始化：FollowUpTaskBackDoorController 增 init-problem-order-task（**按订单号**调聚合接口：projectOrderId + solution=3 + unfinishedOnly=true 分页补录该订单全部未终态补货问题单、按各自当前状态生成任务，供存量/联调），模式参照 init-replenish-task（:120）；补录完复扫一次校准（上游建议）
