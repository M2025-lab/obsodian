## 1、背景

一期（任务总览-跟进任务生成-技术方案）已上线跟单任务生成与闭环链路（D 类材料催办 / 催尾款 / 催返补下单 / 催返补接单）。本需求（3.5，261021 新增）针对**返补下单及下单前置流程**新增催办任务：橱柜定制柜集采切换后线上返补单走问题单流程，需按问题单状态催对应角色处理/审批/完善解决方案；非集采订单走线下台账（AI 扒数据维护在金山云文档），需对未下单登记的订单催首次下单。

已与需求方确认的口径：

- 集采路**消费问题单变更消息**（准实时）；消息上游暂未提供，本方案占位实现，topic/bizType/消息体字段待上游给出后接线。
- 非集采路**定时任务读金山云文档全量对比**；读文档骨架代码已写在 feat/50559773/follouUpProblem 分支，本方案完成字段对齐与业务处理。
- sourceType 新增 2 个（问题单数据、返补非集采台账数据），taskType 新增 3 个（催处理、催审批、催首次下单）。
- 不按 0826 时间过滤；台账数据只读。
- 问题单发起人角色、品类记录在任务上：品类复用既有 materialCode/materialName；**发起人角色新增独立字段 sponsor_role**（落 code）记录，不占用 handlerRole（新任务类型 handlerRole 置空，不记录处理人角色——催审批要找的"发起人上级"由跟单人按发起人角色自行判断）。
- 新两路任务沿用订单范围表 follow_up_project_scope 灰度控制（范围外订单不创建）。

## 2、需求理解

|#|需求点|口径|
|---|---|---|
|1|任务来源|两路：① 集采线上返补（0826 后线上化，与问题单对接，解决方案=补货类型）→ 消费问题单变更消息；② 非集采走线下台账（AI 扒数据维护金山云文档）→ 定时任务读文档全量对比|
|2|任务类型（3 个）|**催处理**：问题单状态 8（上级审批驳回），催发起人再处理；**催审批**：问题单状态 7（待上级审批），催发起人的上级审批；**催首次下单**：问题单状态 0 & 解决方案状态 0（催设计师完善解决方案）；非集采台账路只有催首次下单|
|3|集采路任务流转|问题单状态流转后：把之前类型的未终态任务置已完成，生成新类型任务（消息驱动，逐条消息按当前状态收敛）|
|4|非集采路全量对比|取 F 列=非集采订单走台账扣款流程 且 C 列=未下单登记的行：任务表无该单未终态任务 → 创建；Excel 里不存在或 C 列已变更（不再满足筛选）→ 对应任务置已完成|
|5|记录字段|问题单发起人角色（名称映射成 code）、品类|
|6|范围控制|两路均校验 follow_up_project_scope，范围外订单不创建|

## 4、详细设计

### 4.1 枚举扩展

FollowUpSourceTypeEnum 新增 2 值（追加在 FINAL_PAYMENT 之后，不动既有值）：

|code|枚举名|含义|
|---|---|---|
|4|PROBLEM_ORDER|问题单数据（集采线上返补）|
|5|OFFLINE_REPLENISH_LEDGER|返补非集采台账数据（金山云文档）|

FollowUpTaskTypeEnum 新增 3 值（String code，风格对齐现有）：

|code|枚举名|含义|触发条件|
|---|---|---|---|
|problem_order_handle|催处理|催发起人处理被驳回的问题单|问题单状态 8（上级审批驳回）|
|problem_order_approve|催审批|催发起人的上级审批|问题单状态 7（待上级审批）|
|problem_order_first_order|催首次下单|催完善解决方案 / 催首次下单|集采：问题单状态 0 & 解决方案状态 0；台账：F 列=非集采订单走台账扣款流程 且 C 列=未下单登记|

**bizId 约定**（与既有"来源+业务 id"模式一致）：集采路=问题单 id；台账路**无问题单号，bizId=订单号+品类code 拼接**（{projectOrderId}_{materialCode}，参照返补 REPLENISH_ORDER 的 bizId=品类_supplier 拼接模式，FollowUpReplenishServiceImpl.java:199-200）——同订单同品类唯一一条在跟任务；品类为空的行 bizId 退化为订单号，同订单仅一条任务。幂等键=bizId+taskType（同 createWaitTask 判重模式）。

**引用影响面**（grep 全量核实）：

- taskType/sourceType 为 String/Integer 直存，无 switch 白名单逻辑引用枚举全值——新增值零改动。
- ES FollowUpEsData（task_type/source_type keyword）、查询参数（taskTypes List<String>、sourceType Integer）字段已有，新枚举值天然透传，mapping 不变。
- 前端任务总览页需同步两枚举字典（上游依赖见第 6 节）。

### 4.2 发起人角色字段与 Apollo 配置

**follow_up_task 新增独立字段 sponsor_role（发起人角色 code）**，三个新任务类型统一记录发起人角色；handlerRole 对新任务类型置空（不记录处理人角色——催审批要找的"发起人上级"由跟单人按 sponsorRole 自行判断）。取值：**问题单消息路消息体直接带角色 code（sponsorRoleCode，无需映射）；台账路源数据只有角色名称（如"设计师"），经 Apollo 映射转 code**。新增 Apollo 配置（挂 FollowUpConfig，与既有 follow.up.task.* 同域管理）：

```properties
# 角色名称 -> 角色code（仅台账路用；映射不到时落原始名称并 log.warn，不阻塞建任务）
follow.up.task.role.name.code.map = {"设计师":"DESIGNER","项目经理":"PM","交付专家":"DELIVERY_EXPERT"}
```

> ⚠️ TODO（待与产品确认）：**待确定台账"发起人角色"列会出现哪些角色名称**（运营/AI 手工维护列，实际取值集合需先看真实文档）；同时与问题单上游对齐角色 code 字典（消息路直接带 code，code 取值需与台账映射后的 code 同一套）。角色集合确认后再定映射表初始值；映射表非白名单——台账冒出新角色名称时 Apollo 动态补映射即可，落原始名称兜底保证不阻塞建任务。code 侧建议对齐公司角色体系标准 code。

### 4.3 问题单消息路（集采线上返补）

> ⚠️ 需求与代码现状不一致：问题单变更消息上游**暂未提供**（topic/bizType/消息体字段均未定），本节按假定消息体完整实现业务逻辑，@EventType 注解 bizType 留占位常量，上游给出后接线——逻辑零改动、仅改注解值。

**新增 ProblemOrderChangedHandler**（service/consumer，路由模式参照 ScmOrderChangedHandler.java:25 @EventType(bizType, serverName)），消息体假定字段（DTO ProblemOrderChangeEvent，全部字段标 TODO 待上游确认）：问题单 id、projectOrderId、问题单状态 status、解决方案状态 solutionStatus、解决方案类型 solutionType（补货）、**发起人角色 code sponsorRoleCode**（消息直接带 code，无需映射）、品类 code/name。

**处理逻辑**（新增 ProblemOrderFollowUpServiceImpl，结构参照 FinalPaymentFollowUpServiceImpl）：

```text
消息到达
  ├─ 前置过滤：解决方案类型 ≠ 补货 → 直接 ack 返回
  ├─ 范围校验：inScope(projectOrderId)（FollowUpScopeServiceImpl.java:122）不通过 → ack 返回
  ├─ 跟进人解析：resolveHandlerByProjectOrderId（一次，订单维度复用）
  ├─ 按 bizId=问题单id 查未终态任务（同单最多一条在跟）
  ├─ 无未终态任务 → 按当前状态应建类型创建（下表），状态=待跟进/风险=预警
  ├─ 有未终态任务 且 类型 == 应建类型 → 维持，仅刷新 sponsorRole/品类/考核时间（update）
  └─ 有未终态任务 且 类型 ≠ 应建类型（流转）→ 旧任务置已完成 + 创建新类型任务（同一事务，参照
     FollowUpReplenishServiceImpl.java:101-105 "GENERATE 完成下单任务+创建接单任务"的串行模式）
```

**状态 → 任务类型路由**：

|问题单状态|解决方案状态|应建任务类型|
|---|---|---|
|7 待上级审批|—|problem_order_approve 催审批|
|8 上级审批驳回|—|problem_order_handle 催处理|
|0|0|problem_order_first_order 催首次下单|
|其他组合|—|不建任务；已有未终态任务置已完成|

- 任务 name 自动生成：催审批 / 催处理 / 催首次下单（不带业务 id；关联单号、品类在任务明细字段中已可见）
- 终态兜底：问题单完成/取消类状态消息（具体值待上游）→ 该问题单全部未终态任务置已完成/已取消
- ES 双写：写任务走 FollowUpRepositoryImpl 既有 insert/update，无需额外处理
- 后门初始化：FollowUpTaskBackDoorController 增 init-problem-order-task（按问题单 id 反查当前状态生成，供存量/联调），模式参照 init-replenish-task（:120）

### 4.4 非集采台账路（金山文档全量对比）

> ⚠️ 需求与已写代码不一致：已写的 RowSyncListener 用**行号水位做增量**（只处理新增行），但需求是**全量对比**（旧行 C 列变更要触发任务完成）——以需求为准，本节改为全量读取、去水位化。

**（1）字段对齐**：ProblemOrderRowBo 扩充字段（EasyExcel 按表头名 @ExcelProperty 映射替换现按列索引 0/1 硬取）：

|字段|台账列（表头名）|用途|
|---|---|---|
|projectOrderId|项目订单id/订单号|范围校验、订单信息拼接、**bizId 拼接**|
|materialCode / materialName|品类|落任务品类两列、**bizId 拼接**|
|sponsorRoleName|发起人角色|名称→code 映射（4.2）|
|processType|F 列（非集采订单走台账扣款流程）|筛选条件|
|orderRegisterStatus|C 列（未下单登记）|筛选条件|
|rowIndex|—（行号）|日志定位|

> ⚠️ TODO（待真实文档确认）：各列表头名/列位置（现代码注释同样标注"表头名待真实文档确认"）；C 列"未下单登记"的准确枚举文案。

**（2）全量对比引擎**（RowSyncListener 改造：解析行全部收集到内存 List，doAfterAllAnalysed 后统一 diff；台账行数量级为运营手工维护清单，预计 ≤ 千行，内存可控）：

```text
全量读文档（去掉 watermark 增量与推进逻辑，WATERMARK_KEY 仅保留作"上次同步行数"日志）
  ├─ 应跟进集合 = 行过滤：F列=非集采订单走台账扣款流程 且 C列=未下单登记 且 inScope(订单id)
  ├─ 现有任务集合 = follow_up_task: sourceType=5 且 taskType=problem_order_first_order 且未终态
  ├─ diff-创建：应跟进集合中无未终态任务的 → 创建（bizId={订单号}_{品类code}，待跟进+预警，sponsorRole=发起人角色 code，
  │   跟进人按订单大区解析；role/material 从行数据映射落库）
  └─ diff-完成：现有任务中 bizId 不在应跟进集合（Excel 不存在 / C 列已变更 / 品类变更 / 出范围）→ 置已完成
```

- 幂等：重复执行 diff 结果收敛（无未终态才建、消失即完成），定时重跑天然自愈
- 执行入口：复用既有 KdocsProblemOrderSyncTask（@Assignment key=kdocs-problem-order-sync-task）与后门 /backdoor/problem-order-sync，建议调度频率 ≥30 分钟（导出接口实测 39s+，见风险评估）

**（3）定时任务链路**：syncProblemOrders 返回值保留文本摘要；解析→diff→建/完任务整体 try-catch，异常记 error 不推进任何状态（下次重跑全量自愈）。
