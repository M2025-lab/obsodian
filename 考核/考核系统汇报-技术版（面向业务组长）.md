# 考核系统（scm-workbench）接手汇报 — 技术版

> 汇报对象：业务组长
> 汇报目标：证明我已吃透系统实现，具备独立承接需求和改造系统的能力
> 整理时间：2026-10-31（基于代码全量走读：611 个 Java 文件 / 约 10.5 万行 / 28 个 Controller / 32 张 MySQL 表 + 1 张 Hive 表；并综合 7 月家装业务系统讨论会纪要与 starlord 项目笔记）

---

## 一、一句话定位与系统规模

**scm-workbench 是供应链履约时效考核系统**：对家装建材供应链全链路各环节（下单、接单、备货、测量报价、通知送货、送达、签收等）的完成时效做自动化考核评分，同时管理端上的履约任务（待办卡片）。

| 维度 | 规模 |
|---|---|
| 工程结构 | 6 个 Maven 模块（api / base / dao / service / job / start） |
| 代码量 | 611 个 Java 文件，约 10.5 万行 |
| 接口 | 28 个 Controller（含 9 大业务域 + 45 个运维后门接口）、20 个对外 Feign API |
| 数据 | 32 张 MySQL 表 + 1 张 Hive 报表宽表（`rpt.rpt_indicator_eva_da`） |
| 技术栈 | Spring Boot + MyBatis-Plus + Feign/Eureka + Kafka（utopia-event-driven）+ Redis/Redisson + ES + Apollo + Sentinel |
| 外部依赖 | 20+ 个 Feign RPC（OMS/OFC/starlord/施工排程/商家/供应商…）、10+ 个 Kafka 消费 topic |

### 1.1 系统在全链路中的位置（上下游边界）

家装履约全链路：**报价签约（中控）→ 选品 → 复尺/变更 → 确品 → 下单 → 供应链接备发 → 安装（施工包/班组）→ 验收**，全程由**工地进度驱动**（发货、安装都要匹配施工阶段，批量约货/批量安装/分批验收）。scm-workbench 站在这条链路的"计时裁判"位置：

```
中控/OMS（订单） ──┐
OFC 履约中控 ──────┼─ Kafka 节点消息 → scm-workbench（考核计算 + 履约任务）
施工排程（工期） ──┘         ↕ 双向同步
                    edar-starlord（主材任务轴：一个任务=一个材料品类，管人管进度）
```

- **与 starlord 的关系**：主材任务生命周期中"货主材 + 考核"是并行分支；workbench 的 `fulfillment_task` 通过 `SyncMaterialTaskService` 同步主材任务，starlord 节点配置里的"平台考核时间"与 workbench 计算结果互为上下游。
- **供应商汰换联动**：汰换场景（`extend.replacement` 打标）触发 workbench 的 `/fulfillmentTask/deal/replacement/refresh` 考核重算；紧急+立即汰换还会经 Hive 反查已发货货单驱动 OMS 取消重下。

## 二、核心心智模型：配置 → 规则 → DAG → 计算 → 结果 → 任务

我已经建立了完整的心智模型，整个系统可以压缩成一条链：

```
【配置层】底线指标(n_indicator_base_config) + 一城一策(n_indicator_cus_config)
     ↓ source_id + source_type 关联
【规则层】indicator_compute_rule（from_nodes → to_node，版本化管理）
     ↓ 规则即"边"，事件(indicator_event/indicator_base_event)即"节点"
【引擎层】内存 DAG（JVM 缓存 + Redisson 版本号控制刷新）
     ↓ OFC Kafka 节点变更消息实时触发
【计算层】EvalOrderService（旧）/ EvalScheduleOrderService（新）
     ↓ 时间参考点 + 间隔 + 工作日/自然日日历（假期字典跳过节假日）
【结果层】indicator_order（货单级宽表）→ indicator_project_order（项目级）
          → indicator_task_dispatch_node（用工任务级）→ ES/Hive 报表
【任务层】fulfillment_task 履约任务（考核时间同步 assessment_time，
          并同步 VSS / OFW / starlord 等外部系统）
```

**每个指标 = 时间参考点 + 时间间隔 + 日历类型**。例如"接单节点起，自然日 3 天内送达"。这个公式化设计是系统可扩展的关键——新增考核基本靠配置，不靠改代码。

> 💡 **规则模型同构**：上游 starlord 的主材节点"平台考核时间"配置（`n_material_time_cfg` + `n_material_time_relation`，如"基装验收之后 11 工作日"）与 workbench 的规则模型（`from_nodes` → `to_node` + `schedule_relation` + `duration/duration_type`）**是同一套"基准节点 + 相对关系 + 间隔 + 日历类型"范式**。理解了这一层同构，两个系统的配置可以互相印证，排查跨系统时效问题也有了统一语言。

## 三、两套考核模型（新老并行，这是我接手后最先搞清楚的点）

| | 旧模型：全国材料考核 | 新模型：排程材料考核 |
|---|---|---|
| 适用场景 | 非排程项目 | 排程项目（`schedule_project` 白名单 + 主材排程开关） |
| 驱动方式 | 事件节点 DAG（`indicator_event` + 规则边） | 施工工期排程节点 + 配送流程节点配置（`indicator_base_event`） |
| 核心类 | `EvalOrderService` + `IndicatorDAGService` | `EvalScheduleOrderService` + `IndicatorScheduleDAGService` |
| 结果字段 | `base/cus_eval_result` | `base/cus_eval_result_new` |
| 接口标识 | 无前缀 `/api/workbench/**` | `/v2/**` 前缀 + `WorkbenchForScheduleController` |

- 分流入口：`OfcFulfillmentEventHandler` 内调 `EdarStarlordRpc.queryProjectInScheduleSwitch()` 判断走哪套。
- 版本演进：2.0（JSON 整包存 content）→ 2.5 重构（`n_` 维度表 + 统一规则表 + 版本管理）→ 排程考核（白名单灰度中）。
- **改任何配置类需求，第一步先确认走新版还是旧版链路**（旧版 `IndicatorConfigWriteController` 已 `@Deprecated`）。

## 四、核心链路走读（方法级，证明我能追到底）

### 链路 1：OFC 节点变更 → 考核计算（全系统最核心）

```
Kafka topic: ofc-fulfillment-node
 → ScmOfcListener (@KafkaListener)
 → EventDrivenSubscriberV2.persistAndHandleMessage()   # 消息落地 event_sub 表去重，可追溯
 → OfcFulfillmentEventHandler.handleBiz()              # 全系统消息总闸，内部分三支：
    ├─ doExecuteModifyTask()    # 任务类节点：完成旧任务、激活新任务
    ├─ doExecuteGenerateTask()  # 货单类节点：按 OFC 流程配置循环创建接单/备货/进仓任务
    └─ doExecute()              # 考核计算（异步线程池 indicatorCalcExecutor）：
        ├─ OmsRpc.queryBaseByOrderNo()                 # 取子单
        ├─ EdarStarlordRpc.queryProjectInScheduleSwitch()  # 分流新旧模型
        ├─ IndicatorDAGService.transEventNodeByOrder() # DAG 中定位起始节点
        └─ EvalOrderService.calculateIndicatorByEvents()
            ├─ getFigureNodeList()      # DFS 遍历 DAG 找待计算节点
            ├─ buildTimeDataContext()   # 批量拉 5 个数据源轨迹（工期/OFC/OMS/主材任务/返补单）
            └─ doEval() → processRules()
                ├─ TimeProcessor.processTime()   # 工作日/自然日计算
                ├─ selectFinalTimeline()         # 多组候选取最早/最晚
                ├─ updateOrder()                 # 写 indicator_order.eval_result_new
                ├─ updateFulfillmentTask()       # 同步任务考核时间
                └─ publishEvent(IndicatorChangedEvent)  # 指标变更后续处理
```

### 链路 2：排程考核的触发与增量计算（新模型，我做过专项梳理）

- **增量机制**：`checkBasicDiff` 用 Redis 缓存（key 含 projectOrderId+nodeCode，2 小时过期）比较基装包节点时间，只有变化的节点才触发下游重算；MQ 场景传 false（增量），手动刷新传 true（全量强制）。
- **计算范围**：`getBaseEventsBySchedule` 产出两类节点——`startNodes`（变化源头，沿出边找受影响的下游）+ `extNodes`（签前补算节点，直接补入待计算集合）。
- **规则选取**：按 ruleId 分组排序，"限定供应商/配送类型"的配置优先于"不限制"配置，只取第一组方案；组内按 indexId 算候选时间，最终按 funcName 取最早/最晚。
- **DAG 缓存**：`rebuild` 按 version 缓存基础结构（本地 cache，最大 100 项、10 分钟过期），`getScheduleDAG` 每次把编码关系连接成对象引用图（入边/出边）并过滤孤立节点。

### 消息出口（Producer 侧）：考核不只监听，也对外发声

发送统一走 `Producers`，基于 utopia-event-driven 的 `persistPublishMessage`——**先落 `event_pub` 表再发 Kafka**（可靠发送、失败可补偿，与消费侧 `event_sub` 落表机制对称）。共 3 个 topic、4 个 bizType：

| Topic | bizType | 触发时机 | 业务含义 |
|---|---|---|---|
| `workbench_indicator_change` | `indicator_changed` | 内部 Spring 事件 `IndicatorChangedEvent`（4 个来源：`EvalOrderService` 旧模型算完 / `EvalScheduleOrderService` 新模型算完 / `ExamineIndicatorWriteService` / `ToolService` 手动）→ `IndicatorChangedListener.checkValidToProducer()` 校验后转发 | **对外广播考核结果变更**，下游订阅 |
| `fulfill_node_change` | `fulfill_node_change` | `ScmOfcListener` 消费 OFC 节点消息后调 `FulfillNodeService.broadcastNodeChangeMessage()` | **中继广播销售单节点变更**（把 OFC 消息重新包装转发，让不直接订阅 OFC 的下游也能感知） |
| `schedule_data_recovery` | `workbench-assessment-time-change` | `EvalScheduleOrderService` 排程考核算完 → `ConstructionScheduleService.sendAssessmentChange()` | **考核时间变更回传施工排程**（新模型与排程系统的闭环） |
| `schedule_data_recovery` | `workbench-scm-data-recovery` | ⚠️ 路由已注册、Payload 类存在，但当前代码无活跃发送点 | 疑似预留/历史遗留，列入待清理项 |

注意两级事件结构：计算完成先发 **JVM 内 Spring 事件**（`@Async` 独立线程池 `IndicatorChangeMsgExecutor`，解耦计算与后续处理），`IndicatorChangedListener` 过三道闸门后才真正外发 Kafka——不是每次计算都无脑广播：

1. `updatedEval` 为空不发（计算了但结果没变，收敛消息量）；
2. 订单创建时间早于 Apollo 配置的 `synEffectiveTime` 不发（灰度切换控制）；
3. `checkValidToProducer()`：北京黑名单区域 && 非排程项目不发——**这部分考核由 starlord 计算并同步供应商，workbench 再发就重复**；仅精装全案/团装/翻新放行。

Listener 同时负责把内部 BO 翻译成对外契约 `IndicatorChangePayload`（按指标拆条、历史命名兼容），并 try-catch 全包——对外广播失败不影响已落库的考核主流程。可靠性上是分层取舍：内部事件不可靠但便宜（JVM 崩溃会丢，靠后门重算兜底），过滤后的少量消息才进 `event_pub` 可靠通道。

### 链路 3：履约任务生成（策略模式）

`FulfillmentTaskWriteService` 按 task_type 分发到 `AbstractTaskService` 子类：
`NoticePlaceOrderService`（下单）、`NotifyDeliveryTaskService`（通知送货）、`DeliveryGoodTaskService`（送货）、`InstallTaskSignService`（安装签收）、`QuotationTaskService` / `QuotationAcceptanceTaskService`（报价/报价验收）、`DesignReviewTaskService`（设计审查）、`ApplyRescaleTaskService`（申请复尺）等，由 `FulfillmentTaskServiceMapping` 做映射。**新增任务类型 = 新增一个子类 + 注册映射，不动主流程。**

## 五、如果给我新需求，我怎么改（需求类型 → 改动点映射）

这是本次汇报的重点。我把可预见的需求类型和对应改动路径整理如下：

| 需求类型                  | 改动点                                                                                                                                                 | 是否要发版 | 难度/风险                                |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ----- | ------------------------------------ |
| 调整考核时效/间隔（如 3 天改 5 天） | 纯配置：v2 配置接口改 `indicator_compute_rule`，注意 DAG 缓存刷新                                                                                                   | 否     | 低；风险在缓存不生效，需调 `/dag/refresh`         |
| 新增一城一策个性化规则           | 配置 `n_indicator_cus_config` + 规则表（校验：个性化间隔 ≤ 底线）                                                                                                    | 否     | 低                                    |
| 新增考核指标（新节点）           | `dic_rule_node` 加节点字典 → `indicator_base_event`/`indicator_event` 加事件 → 配规则；若涉及新消息源需加 Kafka 监听                                                       | 视情况   | 中；重点验证 DAG 边的连通性                     |
| 新增履约任务类型              | 新建 `AbstractTaskService` 子类 + `FulfillmentTaskServiceMapping` 注册 + 枚举；若要同步外部系统再加 Sync 服务                                                            | 是     | 中；模板清晰，有 8+ 个现成子类可抄                  |
| 新品类/新订单模式接入           | 确认走旧模型还是排程模型；排程侧需进 `schedule_project` 白名单 + 主材排程开关                                                                                                  | 视情况   | 中；分流逻辑在 `OfcFulfillmentEventHandler` |
| 报表/查询类需求              | ES 查询在 `controller/read/es/`，离线报表改 Hive `rpt_indicator_eva_da` 日任务                                                                                  | 视情况   | 低                                    |
| 上游系统对接（给外部提供数据）       | `scm-workbench-api` 模块加 Feign 接口 + Controller 实现（Controller implements Api 是固定模式）                                                                   | 是     | 低                                    |
| 供应商汰换引发的考核重算          | `/api/workbench/fulfillmentTask/deal/replacement/refresh`；注意 `fulfillment_task_ext` 的 replacement 打标与 starlord 侧汰换消息（`supplier_replace_message`）的联动 | 否     | 中；跨系统链路，需同时核对 starlord 任务状态          |
| 线上数据修复                | 45 个后门接口：`/api/refresh/eval/order`（按货单重算）、`/api/refresh/eval/schedule/projectOrder`（重算排程考核）、`/api/refresh-data/**`（修任务）                             | 否     | 需流程管控（见第六节）                          |

**我的改码习惯**：所有 Controller 无类级前缀、路径全在方法级注解，全局搜 URL 片段即可定位；分层命名有严格规律（Controller → Service → Dao → Mapper/ExtMapper → DO），枚举统一在 `base/constant/`；`doc/http/` 下有 4 个 .http 文件含真实调用示例可直接执行验证。

## 六、我识别出的风险点与技术债（接手后主动盘点）

1. **新老模型并行**：两套 DAG 服务、两套结果字段（`*_eval_result` vs `*_eval_result_new`）、新旧配置表并存。改需求必须先判断链路，误改旧链路会导致排程项目考核不生效。→ 建议明确旧模型下线时间表。
2. **缓存一致性靠手动**：改规则后 DAG 缓存不会自动失效，依赖人工调后门刷新；`checkBasicDiff` 的 Redis 缓存 2 小时过期后，即使业务时间没变也会误判为"变化"触发重算（幂等但浪费算力）。
3. **手动刷新接口无事务保护**：`refreshEvalScheduleProjectOrder` 串行处理项目，中途异常直接终止循环且前面已执行的更新不回滚；接口返回成功也不代表异步下游同步已完成。→ 批量修数据时需要拆分小批 + 事后核对。
4. **`checkBasicDiff` 的 null 边界**：代码只识别 `1970-01-01 00:00:00` 默认时间字符串，没有把 null 作为默认时间兜底，正常比较分支可能 NPE。→ 已列入我的待修复清单。
5. **后门接口数量大（45 个）且无审批留痕**：线上修数据全靠它们，但缺乏操作审计。→ 建议至少加操作日志上报。
6. **`event_sub` 按季度手工分表**（`event_sub_2025_qN`）：需要周期性建表归档，漏了会写入失败。
7. **消息处理的隐式约定**：`getNodesBeforeContract` 用 `estimatedTime < 2000-01-01` 作为"需补算"的占位判断，属于隐式契约，上游改动可能悄悄破坏它。
8. **配置体系复杂、易配错、刷数成本高（业务侧已确认的痛点，非我的主观判断）**：7 月业务讨论会明确提到——系统配置化程度高但"很少有人能配明白"，配置维度多（分公司 × 订单版本 × 单据类型 × 品类 × 供应商 × 配送方式），且存在北京/全国历史逻辑差异（北京 1.0 单节点自选 vs 全国固定模板）；配错后要靠人工刷数修复，联动成本高。管理诉求多变导致系统多版迭代（1.0 → 2.0 → 2.5 → 排程），"系统要给业务陪跑"。**这正好解释了为什么系统长成今天这个样子——不是设计失误，是业务快速变化的适配结果。**
9. **对应的技术机会——AI 三步走（会上已定方向，我可以承接落地）**：① 第一步让 AI 做 check，自动识别配置错误；② 第二步赋予 AI 写能力，代替人工改表/刷数；③ 第三步让业务人员直接与 AI 交互完成配置调整。系统 45 个后门接口 + 明确的表间关联链路，恰好是给 AI 做"配置校验 + 受控刷数"的理想底座——这是我接手后最愿意投入的效能方向。

## 七、下一步计划

- **短期（1-2 周）**：跟一次完整的线上需求/工单闭环；把第六节第 3、4 条小风险修掉；整理后门接口使用 SOP。
- **中期（1 个月）**：主导一次配置类需求上线（走 v2 链路）；补齐排程考核灰度项目清单与放量节奏的理解。
- **长期**：推动新老模型收敛方案评估，减少双链路维护成本；承接 AI 三步走第一步（配置 check）的落地——把第六节第 8、9 条从"痛点"变成"产出"。
