## 四、排查决策树（症状 → 入口 → 根因）

> 总原则（沿用异常排查四步法）：**先定位数据在哪断，再判断谁的责任边界，最后才是修**。每一步的"查什么"落到具体表/接口/工具，见 §五 库表地图。
> ⚠️ 本节为代码走读推演，未经实操验证——每个分支留了「实测记录」占位，跑过就回填。

### 症状①「指标没算出来」（单子没有考核结果）

```
1. 消息到了吗？
   查 event_sub_2025Qx（bizType + receiptNo/projectOrderId + 时间窗）
   ├─ 没记录 → 上游没发 / topic 配置问题 → 责任在源头，拿单号找对端
   └─ 有记录 → 走 2
2. Handler 消费了吗？
   查应用日志（bizType + 单号）；反序列化失败会抛异常且 event_sub 有原始报文
   ├─ 抛异常/无消费日志 → payload 结构问题，回查原始报文对比 DTO
   └─ 正常消费 → 走 3
3. key 匹配到事件节点了吗？（静默丢弃高危区）
   按 [[考核系统事件映射梳理（Handler对照表与Key拼接规则）]] 拼 key
   （旧：l_{categoryId}_{actionType}；新：{categoryId}_{ofcCode}）
   查 indicator_event / indicator_base_event 有没有这个 code
   ├─ 字典没有该 code → 新节点没配事件 → 静默忽略，不报错（维护手册 §2.2）
   │   → 修法：dic_rule_node → indicator_event → 配规则 → 刷 DAG 缓存 → 重算
   └─ 匹配到了 → 走 4
4. 项目走的新模型还是旧模型？
   查 schedule_project 白名单 + starlord 排程开关
   ├─ 开关翻转 → 项目静默切链路，旧字段停止更新（维护手册 §2.3）
   └─ 模型正确 → 走 5
5. 重算一遍看结果（后门刷数）
   POST /api/refresh/eval/schedule/projectOrder（新）/ /api/refresh/eval/order（旧）
   → 结果出来了 = 历史消息丢/消费失败；还不出来 = 计算内部问题 → 换症状②
```

### 症状②「算出来的数不对」

```
先问：错的是"考核时间"还是"及时/超时判定"？
1. 锚点时间对不对？（一切计算的起算点）
   查上游单据字段（factStartTime 等实际时间）；注意隐式契约：
   1970-01-01 = 无实际时间占位、<2000-01-01 = 需补算（维护手册 §2.4）
   ├─ 锚点错 → 输入问题，找上游
   └─ 锚点对 → 走 2
2. 规则配置对不对？（三处独立配置，排查时逐一核对）
   底线 indicator_base_config / 一城一策 indicator_cus_config（旧）
   n_indicator_* （新） / 排程规则（排程侧下发，rebuild 时消费）
   ├─ 配置错 → 走配置修正 + 刷缓存 + 重算存量（维护手册 §一 三问）

3. 日历口径对不对？（跳假跳错 = 天数错）
   GET /api/holidayCache/get 看缓存值 vs 实际安排

   └─ 日历对 → 走 4
4. 两套模型串了？（新旧分家的历史遗留）
   看 result 落在哪组字段：*_eval_result（旧）vs *_eval_result_new（新）
   └─ 对不上预期模型 → 回症状① 第 4 步查开关
```

## 五、库表地图（32 表四类归位）

> 依据：`scm-workbench-dao/resources/mapper/` 35 个 Mapper（含按季度分表）+ `doc/init.sql` / `refactor2.5.sql` / `auth.sql` / `hive/rpt_indicator_eva_da.sql`，2026-11-26 核实。
> 排查时先判断"我要看的数据属于哪一类"，再定位表——**按季度分表的查近几季，跨季排查注意表名后缀**。

### A. 配置类（规则怎么配——症状②第 2 步查这里）

| 表 | 管什么 | 新旧 |
|---|---|---|
| `indicator_base_config` | 底线指标（全国统一） | 旧 |
| `indicator_cus_config` / `indicator_config`(+ext/history) | 一城一策（战区/大区/分公司/店铺维度） | 旧 |
| `n_indicator_base_config` / `n_indicator_cus_config` | 底线 + 一城一策 | **新（v2.5）** |
| `indicator_compute_rule`(+history) | 计算规则（节点关系→DAG 边） | 新 |
| `indicator_event` / `indicator_base_event` | 事件字典（key 匹配的目标，症状①第 3 步） | 旧/新 |
| `dic_rule_node` / `dic_branch_company`(+ext) | 节点字典 / 分公司字典 | 公共 |
| `indicator_branch_config` / `indicator_category_config` | 分支 / 品类配置 | 公共 |
| `schedule_project` | **排程项目白名单（新旧模型分流总闸）** | 新 |

### B. 事件进（消息到了吗——症状①第 1 步查这里）

| 表 | 管什么 |
|---|---|
| `event_sub_2025Q1~Q4`（按季度分表） | Kafka 入站消息落表：幂等去重 + 原始报文可回查（**排查第一站**） |
| `redo_log` | 重做日志 |

### C. 事件出 / 结果类（算出来了吗——症状②/③查这里）

| 表 | 管什么 |

| `construction_schedule_snapshot` | 排程快照（checkBasicDiff 对比的基线） |
| Hive：`rpt.rpt_indicator_eva_da` | 报表宽表（数据分析侧消费） |

### D. 任务类（履约待办——症状④查这里）

| 表 | 管什么 |
|---|---|
| `fulfillment_task` | 履约任务主表（待办卡片，与 starlord 双向同步） |

### 三层缓存（改配置 ≠ 生效，还要刷缓存）

| 缓存 | 刷法 |
|---|---|
| DAG 本地缓存 | `/dag/refresh`、`/api/remove/schedule/dag/cache` |
| 节假日 Redis（滑动 TTL，可能永不回源） | `POST /api/holidayCache/delete` |
| checkBasicDiff Redis（2h） | 等 2h 或手动处理 |
