# 03. IndicatorScheduleDAGService#checkBasicDiff —— 基装包节点变化判定

> 位置：`IndicatorScheduleDAGService.java:986`（`checkBasicDiff`）；同构兄弟 `checkConstructionDiff` 在 :957

## 一、功能是什么

判断**基装包（施工包）任务节点**自上次计算以来是否发生了变化（完成/预计时间变动），返回「有变化的节点 code 集合」。这是排程考核的**增量触发机制**：只有变化过的基装包节点才会被圈进本次重算范围，避免全量重算。

后门接口调用时传 `forceAll=true`，语义变成「无视缓存，全部节点视为有变化」→ 强制全量重算基装包相关指标。

## 二、逻辑实现

```java
public Set<String> checkBasicDiff(String projectOrderId, List<DeliveryProcessTaskDTO> tasks, boolean forceAll) {
    Set<String> res = new HashSet<>();
    for (DeliveryProcessTaskDTO task : tasks) {
        if (!BASIC_PACKAGE_ACTION_TYPE_SET.contains(task.getTaskType())) continue; // 只看基装包五类
        // 取时间：作业开始节点取 factStartTime(优先)/predictStartTime；其余节点取 factEndTime(优先)/predictEndTime
        String time = BASE_CONSTRUCTION_WORK_START.equals(task.getTaskType())
                ? (!DEFAULT_TIME.equals(task.getFactStartTime()) ? task.getFactStartTime() : task.getPredictStartTime())
                : (!DEFAULT_TIME.equals(task.getFactEndTime())   ? task.getFactEndTime()   : task.getPredictEndTime());
        // Redis key 粒度 = 项目 + 节点
        String key = "scm-workbench:schedule-basic-package-diff:" + projectOrderId + ":" + task.getNodeCode();
        boolean diff = forceAll || !redisClient.existsKey(key) || !time.equals(redisClient.get(key));
        redisClient.set(key, time, apolloConfig.getScheduleInterval()); // 写回最新值, TTL=schedule_interval(默认7200s)
        if (diff) res.add(task.getNodeCode());
    }
    return res;
}
```

要点：

- **diff 判定三条件取或**：`forceAll`（后门全量）／键不存在（首次）／值不相等（时间变了）。无论是否 diff，都把最新时间写回 Redis（刷新 TTL），所以连续两次刷数之间该键不会过期（TTL 滑动续期）。
- **时间取值规则**：`DEFAULT_TIME="1970-01-01 00:00:00"` 是排程侧「无值」哨兵，实际时间为空时退化为预计时间。
- 返回的 `nodeCode` 形如 `base_construction_work_start`（taskType 本身），供 [[04.IndicatorScheduleDAGService-getBaseEventsBySchedule|getBaseEventsBySchedule]] 与 DAG 节点的 `scheduleCode + "_" + categoryId` 匹配。

**同构方法 `checkConstructionDiff`（:957）**：对**工期节点**做同样的事，但它把九个关键工期时间（开工交底/技术交底/水电验收/瓦木验收/基础完工验收/竣工验收/软装验收/一二批材料进场）拼成一个字符串，只用**一个** Redis key（`scm-workbench:schedule-construction-diff:{poId}`）整存整取，返回 boolean。后门链路里因为它已被 `constructionDiff=true` 短路（全量），所以没被调用，但正式链路在用，理解 checkBasicDiff 就等于理解它。

## 三、调用了谁 / 为什么

| 被调方法 | 为什么调用 | 一句话简介 |
|---|---|---|
| `redisClient.existsKey / get / set` | diff 的存储介质 | Redis 客户端薄封装（`scm-workbench` 的 RedisClient） |
| `apolloConfig.getScheduleInterval` | diff 键的 TTL | Apollo 配置 `schedule_interval`，默认 7200 秒 |

无其他方法调用——叶子方法（Redis + 纯比较逻辑）。

## 四、下钻终点

- 〔Redis〕`scm-workbench:schedule-basic-package-diff:{projectOrderId}:{nodeCode}`（基装包，节点级粒度）；`scm-workbench:schedule-construction-diff:{projectOrderId}`（工期，项目级粒度）。TTL 均为 Apollo `schedule_interval`。
- 〔纯函数〕时间优选规则（fact 优先、predict 兜底、DEFAULT_TIME 哨兵）。

## 五、备注

- **后门语义**：`forceAll=true` 时结果 = 传入 tasks 中全部基装包 nodeCode（仍然只包含 `BASIC_PACKAGE_ACTION_TYPE_SET` 五类）。所以「后门全量重算基装包」实际依赖上游 `queryScheduleNode` 只拉了这五类（见 [[11.ConstructionScheduleRpcService]]）。
- TTL 由 `schedule_interval` 控制的含义：若正式链路超过 2 小时没触发该项目计算，缓存过期 → 下次触发时天然全量 diff。这是「防漏算」兜底，也解释了为什么后门刷数后 2 小时内正式事件触发不会再重复全量。
- 排除了 `standardDeleteStatus != 0` 的任务是在上游 Controller 就过滤掉的，这里拿到的 tasks 已是未删除集合。
