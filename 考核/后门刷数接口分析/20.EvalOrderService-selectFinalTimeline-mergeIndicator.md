# 20. EvalOrderService#selectFinalTimeline / mergeIndicator —— 复用的两个纯函数

## 一、功能是什么

`EvalOrderService` 本体是**旧全国货单考核**的计算引擎（另一条链路），但排程链路复用了它的两个无状态方法：

- `selectFinalTimeline(funcName, timelines)`——多段计算结果择一（最早/最晚）；
- `mergeIndicator(旧列表, 新指标)`——新旧考核结果 JSON 合并（同指标名替换）。

## 二、逻辑实现

### selectFinalTimeline（:950）

```java
if ("最早".equals(funcName)) {
    return timelines.stream().min(comparing(expectTime, nullsLast).thenComparing(expectStartTime, nullsLast)).orElse(null);
}
return timelines.stream().max(comparing(expectTime, nullsFirst).thenComparing(expectStartTime, nullsFirst)).orElse(null);
```

「最早」= expectTime（应完成时间）最小者，同值再比 expectStartTime；「最晚」相反。空列表返回 null（上游判 null 放弃本载体）。

### mergeIndicator（:670）

```java
// 目标：旧列表里同 indicatorName 的元素被新元素替换，其余保持原顺序；新指标若旧列表没有则追加到尾部
for (sdo : 旧列表) {
    if (未出现过该 indicatorName) {
        res.add(sdo.indicatorName.equals(新.indicatorName) ? 新 : sdo);   // 命中即替换
    }
}
if (res 里没有新指标名) res.add(新);
```

保持顺序的动机（代码注释原话）：「尽可能保持顺序不变，这样可以减少 MySQL 更新的执行次数」——JSON 字符串与库里逐字节一致的概率更高，16 号文档的比对幂等才容易命中。

## 三、调用了谁 / 为什么

无任何调用——纯内存集合运算，叶子。

## 四、下钻终点

- 〔纯函数〕两个方法本体。宿主类 EvalOrderService 的其余 1100+ 行属于旧考核链路，不在本接口范围内。

## 五、备注

- 排程链路对旧引擎的依赖只有这两个函数 + `DEFAULT_TIME` 常量引用——**重构旧 EvalOrderService 时这两个方法不能动语义**，否则排程侧跟着变。
- mergeIndicator 的去重键是 `indicatorName`；如果 baseEvalResult JSON 里出现同名重复行（历史脏数据），merge 只会替换第一行、丢弃后续重复——顺带「洗」掉重复指标。
- selectFinalTimeline 的 nullsLast/nullsFirst 处理「某段时间算不出来」的比较：最早口径下 null 排最后（不选它），最晚口径下 null 排最前（会选中！）——最晚模式下若某段 expectTime 为 null，结果可能拿到一条 expectTime=null 的时间线，上游 `figureRes.getFigureTime() == null` 判断兜住。
