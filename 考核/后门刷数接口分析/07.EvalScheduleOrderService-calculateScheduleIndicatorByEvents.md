# 07. EvalScheduleOrderService#calculateScheduleIndicatorByEvents —— 排程考核计算总控

## 一、功能是什么

排程考核计算的**总指挥**（正式链路与后门链路共用）。输入 startNodes/extNodes（计算范围）+ syncMaterialTask 开关，输出是副作用——落库三张表、外发三条通道。整个方法就是一条流水线的四步编排：

```
圈计算节点(正向DFS) → 圈数据节点(反向入边) → 一次拉全量轨迹(RPC/DB) → 逐节点算数+落库+外发
```

后门链路里 `syncMaterialTask = inSchedule`（项目排程开关），即「进了排程的项目，算出的考核时间要回写 starlord 主材任务」。

## 二、逻辑实现

```java
public void calculateScheduleIndicatorByEvents(String projectOrderId, List<ScheduleEventNode> startNodes,
                                               List<ScheduleEventNode> extNodes, Boolean syncMaterialTask) {
    // 0) 初始化任务载体容器（此时是空壳，真正装载在 getFigureNodeList 内部完成）
    ScheduleAllNode scheduleAllNode = ScheduleAllNode.builder()...build();

    // 1) 正向遍历：从 startNodes 沿边 DFS，找出全部待计算节点（同时把货单/用工载体装载进 scheduleAllNode）
    List<ScheduleEventNode> figureNodeList = indicatorScheduleDAGService.getFigureNodeList(startNodes, scheduleAllNode);

    // 2) extNodes 并入（去重：已在 figureNodeList 里的不重复加）
    ...for (extNode : extNodes) if (!exists.contains(extNode.getUniqCode())) figureNodeList.add(extNode);

    // 3) 反向遍历：对每个待计算节点的入边，找出计算它所需的前置数据节点
    List<ScheduleEventNode> dataNodeList = indicatorScheduleDAGService.getDataNodeList(figureNodeList, scheduleAllNode);

    // 4) 一次性拉取全部前置节点的轨迹（多次RPC合并→5次：项目单/排程任务/主材任务/OFC货流/fulfillment_task）
    List<NodeTimeTrackV2> nodeTrackList = getScheduleTimeTrack(projectOrderId, scheduleAllNode, dataNodeList);

    // 5) 算数：逐节点套规则算考核时间，写库、发消息
    doScheduleEval(figureNodeList, nodeTrackList, scheduleAllNode, syncMaterialTask);
}
```

两处 INFO 日志（获取计算节点/获取数据节点）打印 uniqCode 列表，是排查「为什么没算到某指标」的第一落点。

## 四、下钻终点

本方法是编排层，自身无直接 IO。全部终点经由四个子方法：见 [[08.IndicatorScheduleDAGService-getFigureNodeList]]（DB 四表 + RPC 两个）、[[12.EvalScheduleOrderService-getScheduleTimeTrack]]（RPC 四个 + DB 一表）、[[14.EvalScheduleOrderService-doScheduleEval]]（Redis 日历 + DB 三表写 + Kafka 两条 + MQ Event + RPC 回写）。

## 五、备注

- **数据拉取设计**：`getScheduleTimeTrack` 是「一次性拉全」而不是逐节点拉——代码注释明示「多次RPC→5次」。排程/主材/OFC 三路 RPC 各一次 + fulfillment_task 一查 + 项目单一查。后门批量刷数时，每个项目固定约 7~8 次 RPC（含准入与 DAG 侧），评估刷数速率时按这个口径。
- `scheduleAllNode` 在 1) 步被 `getFigureNodeList` 填充（orderNodeMap/dispatchNodeMap/orderMap/projectOrderMap），在 4) 步又被 `getScheduleTimeTrack` 补充（baseDataContext、innerInterval、relateNodeId）——同一个容器贯穿全程，注意它不是并发安全的，但本链路单线程串行使用。
- extNodes 的语义是「不作为 DFS 起点，直接算」——所以签前节点即使不在工期 DFS 可达路径上也会被计算，但它们**没有出边遍历**（不会带动下游），这正是「补算」的含义。
