# 23. ConstructionScheduleService —— 排程协作三工具（Kafka 外发/规则/日历）

## 一、功能是什么

排程协作的三个入口方法（本链路用到）：

1. **`sendAssessmentChange(payload)`**——考核时间变化同步给排程系统（Kafka）；
2. **`getIndicatorRules(version)`**——考核规则 = 正常规则 + 返补规则合并（给 DAG rebuild 用）；
3. **`queryCalendarByYear(year)`**——日历 RPC 包一层 + bitmask 汇总（给 HolidayService 用）。

（类里另有 queryConstructionScheduleDetailNew 含虚拟瓦木时间替换、restoreConstructionSchedulePartial 等，服务其他链路。）

## 四、下钻终点

- 〔Kafka〕topic `schedule_data_recovery`（配置 `kafka.topic.schedule_data_recovery`，默认值同名），bizType `workbench-assessment-time-change`（与 `SCHEDULE_TASK` 共享该 topic）。消费者是排程系统 artisan-construction 侧。
- 〔RPC〕artisan-construction `queryAssessmentRuleCfgList`、`queryRebateRuleList`、`queryCalendarDay`

## 五、备注

- **每次 dealOrderNode/dealDispatchNode 成功算完必发一条**（sendAssessmentMessage 不看 update 标志）——后门批量刷数会对 `schedule_data_recovery` 产生与载体数量等量的消息，通知排程消费方注意峰值。
- `Producers.send` 内部 catch 全部异常只记日志——Kafka 挂了刷数照样「成功」，事后补对账要靠排程侧。
- `getIndicatorRules` 的 null 防御返回空列表而非抛错：模板查不到 → rebuild 建出空规则 DAG → 上游静默无结果。排查「项目有模板但指标全空」时先看这两个 RPC 的返回。
- 三个方法彼此独立，这个类只是「排程相关杂项」的收纳盒，没有内聚的业务状态。
