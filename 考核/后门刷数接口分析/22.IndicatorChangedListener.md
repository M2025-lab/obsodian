# 22. IndicatorChangedListener —— 送达指标变化的进程内事件消费者

## 一、功能是什么

消费 Spring 进程内事件 `IndicatorChangedEvent`（由 16 号文档 `dealOrderNode` 在「**送达指标**更新成功 + syncMaterialTask 开启」时发布），把考核结果变化转成 Kafka `IndicatorChangePayload` 消息发往供应商同步链路（`workbench_indicator_change` topic）。**异步**执行（`@Async("IndicatorChangeMsgExecutor")`）。

排程链路只发「送达及时」一种；本监听器同时服务旧链路的其他指标事件（事件体通用）。

## 二、逻辑实现

```java
@EventListener @Async("IndicatorChangeMsgExecutor")
public void handleIndicatorChangedEvent(IndicatorChangedEvent event) {
    // updatedEval 为空直接返回（排程链路恒为 [送达及时] 单元素集）
    for (indicatorName : event.getUpdatedEval()) {
        组装 IndicatorChangePayload{orderNo, projectOrderId, branchCode, indicatorName, categoryId, deliveryId, flowType,
                                    baseIndicatorResult{expectCompTime, realCompTime, evaluation, ...}, cusIndicatorResult{...}};
        if (indicatorName == "送达") indicatorName = "送达及时";      // 兼容历史数据格式
        // 双开关：订单创建时间 >= Apollo syn_effective_time 且 checkValidToProducer(event)
        if (event.orderCreateTime >= synEffectiveTime && checkValidToProducer(event)) {
            producers.send(new PayLoadData(INDICATOR_CHANGED, orderNo, payload));
        }
    }
}
```

**`checkValidToProducer`（区域与版本白名单）**——「北京 && 非排程」的货单不同步（那部分由 starlord 自己算自己同步）：

```
if (区域不在 Apollo qvyu_black_list || 任务模式==SCHEDULE) return true;   // 非黑名单区域 或 排程任务 → 可同步
// 黑名单区域再逐条开洞：
if (fulfillmentMode == "hardcover_house") return true;                   // 精装全案
if (项目版本 in {V2_5团装整装, V2_5团装全案}) return true;                 // 团装
if (项目版本 == V2_5局部翻新) return true;                                // 翻新
return false;
```

## 三、调用了谁 / 为什么

| 被调方法 | 为什么调用 | 一句话简介 |
|---|---|---|
| `projectOrderRpc.getByProjectOrderId` | 黑名单区域判版本时查项目详情 | RPC 查项目单 |
| `Producers.send` | 消息外发 | Kafka producer 封装 |
| `apolloConfig.getSynEffectiveTime` / `getQvyuBlackList` | 双开关配置 | Apollo 配置读取 |

## 四、下钻终点

- 〔Kafka〕topic `workbench_indicator_change`（`kafka.config.common-queue-02...topic` 配置，默认值 workbench_indicator_change），bizType `INDICATOR_CHANGED`
- 〔RPC〕shuttle-order `projectOrderService.getByProjectOrderId`（仅黑名单区域触发）
- 〔Apollo〕`syn_effective_time`（生效时间闸门）、`qvyu_black_list`（区域黑名单，逗号分隔）

## 五、备注

- **只有「送达」指标走这条路**：排程链路 `dealOrderNode` 发布事件时 `updatedEval` 固定为 `[送达及时]`。其余指标（下单/接单/备货…）的对外同步不在本事件，而是 [[23.ConstructionScheduleService-sendAssessmentChange|23 号文档]] 的排程 Kafka 消息 + [[21.SyncMaterialTaskService-syncAssessmentTime|21 号文档]] 的 starlord 直写。
- 事件发布条件是 `update==true`（fulfillment_task 真的变了才发）——但监听器内部**还会再过滤**（时间闸门+区域白名单），两层漏斗。刷数无效果时逐层排查。
- `@Async` 线程池 `IndicatorChangeMsgExecutor` 与计算线程解耦；监听器整体 try-catch（事件消费失败不影响计算主流程）。
- 类里的静态 `taskTypeMap`（事件名→taskType，含「生成时间/激活时间」变体）被 [[13.TimeExtractor族|FulfillmentTimeExtractor]] 复用做事件名翻译——这个类身兼「监听器+字典」两职，重构时注意。
