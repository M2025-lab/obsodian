# 06. IndicatorScheduleDAGService#rebuild —— 从规则模板构建 DAG

## 一、功能是什么

缓存 miss 时，把「排程侧的规则模板配置」+「workbench 侧的基础事件字典」组装成一张 `ScheduleDAG`（节点 + 边规则），并写回 Guava 缓存。这是「考核规则长什么样」的唯一装配点——**改了模板想立刻生效，靠本方法（或先清缓存）**。

## 二、逻辑实现

四步（对应代码注释 1.0~2.0）：

**① 基础数据准备**
```java
List<IndicatorBaseEvent> allBaseEvents = getAllBaseEvents();            // DB: indicator_base_event 全量有效行
List<ProcessNodeCfgDTO> processNodeCfgList = constructionScheduleService.getIndicatorRules(version); // RPC: 模板规则 + 返补规则
processNodeCfgList = ...filter(cfg -> isNotEmpty(cfg.getMaterialCode())); // 只留带材料 code 的规则
```

**② 材料/基装包映射展开**：从规则里收集 `materialCode→materialName`（含规则行里 `relationMaterialCode`），得到本模板涉及的**全部品类集合** categoryMap。

**③ 初始化事件节点**——品类 × 事件的全组合：
```java
// 工期类事件（EventTypeEnum.CONSTRUCTION_SCHEDULE）：每条基础事件 → 1 个节点, uniqCode = event.code
// 品类类事件（其余 EventType）：categoryMap 每个品类 × 每条基础事件 → 1 个节点, uniqCode = categoryId_event.code
//   基装包品类也走这条逻辑（基装包"品类" = 施工包ID）
```

**④ 初始化边规则**——规则行 → `ScheduleEdgeRule`：
```java
for (每个 ProcessNodeCfgDTO cfg)                 // cfg = 材料×供应商×履约方式×taskType 的配置块
  for (每个 NodeAssessmentRuleCfgDTO ruleCfg) {   // ruleCfg = 一条「前置→目标」关系
    ruleId  = materialCode_supplierCode_deliveryType_taskType_restartType   // getRuleId()
    codeFrom = convertNodeCode(ruleCfg.relationNodeCode, relationMaterialCode, cfg.taskType, scheduleCodeToCode)
    codeTo   = convertNodeCode(ruleCfg.nodeCode,        cfg.materialCode,   cfg.taskType, scheduleCodeToCode)
    // 同 ruleId + 同 divide(indexId) 聚合成一条 ScheduleEdgeRule（codeFromList 多对一）
    // funcName = (valueRetrievalLogic==0 或 restart) ? "最晚" : "最早"     ← 多 indexId 并存时的最终取值策略
    // restartType: REBATE→replenish(返补), RESTART→restart(重启)
    // timeRef = TIME_REF_MAP: BEFORE→之前 / AFTER→之后 / CURRENT→当天
  }
// scheduleEventRuleMap 完全打平 → List<ScheduleEdgeRule> → ScheduleDAG → 写回 SCHEDULE_DAG_CACHE
```

**`convertNodeCode(nodeCode, categoryId, targetTaskType, scheduleCodeToCode)`**（:463）——排程侧节点 code → workbench DAG 节点 uniqCode 的翻译器：

| 场景 | 判定 | 产出 |
|---|---|---|
| 工期类节点 | categoryId 为空 | `scheduleCodeToCode.get(nodeCode)`（不带品类前缀） |
| 生成类节点 | taskTypeStr == `task_generate` | `{categoryId}_{task的code}_generate` |
| 激活类节点 | taskTypeStr 以 `task_activate` 开头 | `{categoryId}_{task的code}_active` |
| 普通品类节点 | 其余 | `{categoryId}_{事件的code}` |

**`getAllBaseEvents()`**（:486）：`indicator_base_event` 表 `is_delete=0` 全量查询——基础事件字典（事件名/ofcCode/scheduleCode/taskInfo/timeType/eventType 的对照表）。

## 四、下钻终点

- 〔DB〕`indicator_base_event`（`select ... where is_delete = 0`，全表有效行，无 projectOrderId 过滤——字典是全局的）
- 〔RPC〕artisan-construction `queryAssessmentRuleCfgList(version)`、`queryRebateRuleList()`
- 〔Guava〕写 `SCHEDULE_DAG_CACHE.put(version, json)`

## 五、备注

- **节点规模**：`品类数 × 基础事件数` 级别的节点量 + 工期节点。缓存 maximumSize=100 个 version，大城市模板数量级在几十，基本装得下。
- `funcName`（最晚/最早）来自规则 `valueRetrievalLogic`：取值逻辑 0 表示「取最晚」，同时 restart（重启）场景强制「最晚」——重启任务的考核时间要覆盖旧任务，取最晚更安全。
- `deliveryId` 特判：`cfg.getSupplierCode().equals("9999999")` → 传给规则的是 `-1`（不限制供应商）。排程侧用 9999999 表达「不限供应商」，workbench 侧统一语义是 `-1`。
- 边规则聚合键是 `{ruleId, divide}` 两级：ruleId 定「哪条规则」，divide（indexId）定「规则内第几段前置」，同 indexId 的多个 codeFrom 是「或」关系（任一前置命中即可参与计算）。
- rebuild 期间若规则里出现字典中不存在的 scheduleCode，`scheduleCodeToCode.get` 返回 null 会拼出 `categoryId_null` 这类脏 codeFrom；后续 getScheduleDAG 建边时「找不到节点」日志可发现。新增基础事件字典行时注意与模板同步。
