# 01. ToolController#refreshEvalScheduleProjectOrder —— 接口入口

> 位置：`scm-workbench-start/.../controller/ToolController.java:230`（`@PostMapping("/api/refresh/eval/schedule/projectOrder")`）

## 一、功能是什么

新排程考核的**项目级全量重算后门**。传入一批项目订单 ID，对每个项目：

1. 判断是否属于「排程考核」体系（白名单或排程开关命中其一即算）；
2. 若命中，拉取基装包任务 → 判断基装包节点是否有变化 → 在考核 DAG 上圈出本次要重算的节点集合；
3. 调用排程考核计算引擎，把这些节点的考核时间（应开始/应完成/实际完成/是否超期）全部重算并落库、外发。

它与正式生产链路的区别**只有入口**：正式链路由 Kafka 事件（事件粒度、增量）触发同一套 Service；本后门是 HTTP 手工触发、项目粒度、全量。所以它天然是「刷数/修复」工具。

## 二、逻辑实现

```java
for (String projectOrderId : projectOrderIds) {
    try {
        Boolean scheduleInit = indicatorScheduleDAGService.isScheduleProject(projectOrderId); // 白名单
        Boolean inSchedule   = edarStarlordRpc.queryProjectInScheduleSwitch(projectOrderId);  // 排程开关
        if (scheduleInit || inSchedule) {
            // 1) 拉基装包任务（只拉 BASIC_PACKAGE_ACTION_TYPE_SET 五类）
            List<String> targetTaskTypeList = new ArrayList<>(EnumTransformUtil.BASIC_PACKAGE_ACTION_TYPE_SET);
            List<DeliveryProcessTaskDTO> tasks = constructionScheduleRpcService.queryScheduleNode(projectOrderId, null, targetTaskTypeList);
            // 2) 过滤掉 standardDeleteStatus != 0（已逻辑删除）的任务
            tasks = tasks.stream().filter(t -> DeleteStatusEnum.NO.getCode().equals(t.getStandardDeleteStatus())).collect(...);
            // 3) forceAll=true：忽略 Redis diff 缓存，认为全部基装包节点都有变化
            Set<String> basicNodeCodeSet = indicatorScheduleDAGService.checkBasicDiff(projectOrderId, tasks, true);
            // 4) 圈定重算范围：工期节点全量(start) + 签前节点(ext) + 基装包diff节点(start)
            FigureScheduleParam scheduleParam = indicatorScheduleDAGService.getBaseEventsBySchedule(projectOrderId, true, true, basicNodeCodeSet);
            // 5) 计算引擎跑数（inSchedule 作为 syncMaterialTask 透传）
            if (scheduleParam != null) {
                evalScheduleOrderService.calculateScheduleIndicatorByEvents(projectOrderId, scheduleParam.getStartNodes(), scheduleParam.getExtNodes(), inSchedule);
            }
        }
    } catch (Exception e) {
        throw new ServiceException(ServiceExceptionEnum.RPC_CALL_FAILURE.getCode(), "排程考核后门计算失败", e);
    }
}
```

关键分支解读：

- **准入是「或」关系**：`scheduleInit || inSchedule`。白名单（`schedule_project` 表）是排程考核灰度期控制手段；排程开关（starlord）是业务侧真实状态。后门重算宁可多算不可漏算。
- **`getBaseEventsBySchedule(projectOrderId, true, true, basicNodeCodeSet)`** 两个布尔都是 true：`constructionDiff=true` → 工期节点全部进 startNodes（全量重算工期相关指标）；`beforeContract=true` → 签前节点（设计/测量/复尺/下单等未签合同前节点）进 extNodes 一并补算。
- **`checkBasicDiff(..., forceAll=true)`**：后门专属语义——绕过 Redis 缓存比对，把传入的全部基装包节点当作「有变化」，从而强制重算基装包相关指标。正式链路里事件触发时传 `false` 走缓存比对。
- **`scheduleParam == null` 直接跳过**：说明该项目没有配置排程规则模板（拿不到 indicatorVersion → DAG 建不出来），属于正常静默。
- **异常行为与兄弟接口不同**：旧接口 `/api/refresh/eval/projectOrder` 是 catch 后记日志继续下一个；本接口 catch 后**直接抛 ServiceException 中断整个循环**（后面 ID 不再处理）。批量刷数时一旦某个项目失败要整批重跑。

## 五、备注

- **后门接口无鉴权**：ToolController 是工具集合，生产环境暴露需运维侧控制访问（网关/内网）。
- **幂等性**：链路本身按「重算覆盖」设计——落库前有值比对（`baseEvalResult` 不变不 update、fulfillment_task 时间不变不 update），所以重复刷同一批项目是安全的；但外发 MQ/Kafka 不做去重，下游需容忍重复消息。
- **注意旧接口的坑别带过来**：旧 `/api/refresh/eval/projectOrder` 里 `edarStarlordRpc.queryProjectInScheduleSwitch(projectOrderId)` 命中是 `continue` 跳过（排程项目不走旧考核）；本接口里 `inSchedule` 命中反而是**要算**（排程项目走新考核），语义完全相反，刷数时别看串。
- `getBaseEventsBySchedule` 第 3 参 `basicNodeCodeSet` 为空集合时（该项目没有基装包任务），基装包分支自然不生效，不影响主流程。
