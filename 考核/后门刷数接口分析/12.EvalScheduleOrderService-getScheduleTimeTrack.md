# 12. EvalScheduleOrderService#getScheduleTimeTrack —— 轨迹抽取（一次拉全）

## 一、功能是什么

把上一步圈出的**数据节点**变成「时间轨迹」`List<NodeTimeTrackV2>`——每个节点的多条 `{completeTime 实际完成时间, assessmentTime 已有考核时间, orderNo, dispatchId, restartCount, supplierId, nodeId...}` 记录。设计原则是**数据一次性拉全**（5 路 RPC/DB），再在内存里按事件类型用 Extractor 族切分，避免逐节点打 RPC。

## 二、逻辑实现

```java
public List<NodeTimeTrackV2> getScheduleTimeTrack(String projectOrderId, ScheduleAllNode scheduleAllNode, List<ScheduleEventNode> dataNodeList) {
    // 0) {categoryId -> orderNos} 索引（从已装载的 orderMap 构建）
    // 1) 构建数据上下文 BaseDataContext（一次性拉全）
    BaseDataContext dataContext = buildScheduleTimeDataContext(projectOrderId, categoryOrderNoMap, eventTypeMap);
    scheduleAllNode.setBaseDataContext(dataContext);
    // 2) 给载体回填任务耗时 innerInterval 与关联关系 relateNodeId（数据来自排程 tasks）
    initInnerIntervalAndRelateNodeId(scheduleAllNode, scheduleCodeToName, dataContext.getTasks());
    // 3) 按 eventType 分发到对应 Extractor 抽轨迹
    for (ScheduleEventNode eventNode : dataNodeList) {
        TimeExtractor extractor = timeExtractorFactory.findExtractor(EventTypeEnum.getEnumByValue(eventNode.getEventType()));
        res.addAll(extractor.getScheduleTimeTrack(eventNode, dataContext, categoryOrderNoMap));
    }
    // 4) 清洗：过滤无效日期（null/1970 哨兵），两个时间都空的轨迹剔除
    ...
    return res;
}
```

**`buildScheduleTimeDataContext`（:776）——五路数据一次拉全**：

| 路径 | 来源 | 内容 |
|---|---|---|
| projectOrderDto | RPC `projectOrderService.getByProjectOrderId` | 项目单基本信息（后续区域/版本判断用） |
| tasks | RPC `queryScheduleNode(projectOrderId, null, null)`（**不限 taskType 全量**）+ 过滤删除 | 工期数据 + 基装包 + 任务耗时（period/relationTaskId）都在这批里 |
| dispatchDetails | RPC `edarStarlordRpc.taskDetail`（taskStates/nodeStates=YES） | 全量主材任务明细 + 供应商映射 |
| orderFlowTimes | RPC `ofcRpc.queryDispatchInfoByFlowMainNoList(orderNos)`（仅当数据节点里有 OFC 类事件才拉） | 货流动作时间（通知送货/送达/签收…）；**5020 统一转 6166**（代销直送送达动作归一） |
| fulfillmentTasks | DB `fulfillment_task`（project_code + is_delete=0） | 履约任务时间（生成/激活/通知保留时间），按 `categoryId_taskType` 分组 |

OMS/返补/施工包三路当前为占位空集合（注释「暂无, 以后再说」）。整体 try-catch RpcException：**失败仅记日志，返回半空的 dataContext 继续跑**——对应指标算不出但不炸链路。

**`initInnerIntervalAndRelateNodeId`（:685）——载体补刀**：从排程 tasks 里找带品类前缀的节点（`nodeCode = taskType_categoryId`），把 `period`（任务耗时）回填到对应载体 `innerInterval`、`factStartTime` 回填实际开始时间；同时维护 `relateNodeId`（关联指向）：
- 下单载体 → 指向其配置的复尺任务（`relationTaskId`）——「下单及时」用复尺时间做前置时靠它；
- 复尺用工载体 → 指向通知复尺任务（完成时修正 / 未完成时兜底关联）。
匹配条件含 taskType/品类/供应商/履约方式/nodeType 全等，且「已设置过就跳过」，未完成任务排在后面保证已完成的优先占位。

## 五、备注

- **Controller 层已拉过一次基装包 tasks**（只拉五类），本方法又全量拉一次（不限类型）——同一个后门链路里 `queryScheduleNode` 会被调 2 次。这是「圈范围」和「拉数据」两阶段各自独立取数的代价。
- `initInnerIntervalAndRelateNodeId` 的排序（`dispatchNodeId` 降序、null 最后）是为了「已完成任务先占位、未完成兜底」——若排程侧有多条同品类任务行，先到的赢，后续跳过（`innerInterval > 0` 即视为已设置）。
- RpcException 吞掉的设计意味着：**starlord/OFC 抖动时刷数「看起来成功」但对应指标全空**。刷数后要抽查核对，别只看接口返回 success。
- 轨迹的 `assessmentTime` 字段是「该节点此前算出的考核时间」——它参与下一轮计算（前置事件未实际发生时用其考核时间递推），这是考核链路「级联重算」的机制基础。
