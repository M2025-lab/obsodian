# 08. IndicatorScheduleDAGService#getFigureNodeList —— 圈计算节点 + 载体装载

## 一、功能是什么

两件事一次完成：

1. **圈计算节点（figureNodeList）**：从每个 startNode 沿出边 DFS，把「规则与项目实际载体匹配」的下游节点全部收进来——即本项目**真正会算**的指标节点集合；
2. **装载任务载体（scheduleAllNode）**：把项目下的货单载体（indicator_order/indicator_project_order → ScheduleOrderNode）和用工载体（starlord 主材任务 → ScheduleDispatchNode）装进 `scheduleAllNode`，供后续步骤按 `品类×taskType` 挂到节点上。

**为什么 DFS 要看载体**：DAG 结构是模板级的（含全部品类），但某项目可能只买了两个品类的材料。DFS 每走一条边都问「这条边的规则有没有能匹配上的本项目载体」，没有就不走——所以图在项目维度上被载体「裁剪」了。

## 二、逻辑实现

```java
public List<ScheduleEventNode> getFigureNodeList(List<ScheduleEventNode> startNodes, ScheduleAllNode scheduleAllNode) {
    initOrderNode(scheduleAllNode);      // 先装载货单载体（DB）
    initDispatchNode(scheduleAllNode);   // 再装载用工载体（RPC）
    for (startNode : startNodes) {       // 多起点各自 DFS，结果合并
        dfs(startNode, scheduleAllNode, circleVisited, figureNodeList);
    }
    return distinctNodes(res);           // 去重（保留靠后出现者）
}
```

**`initOrderNode`（:597）——货单载体装载**：
- 查 `indicator_order`（该项目全部未删货单）→ 每张货单 × 6 个货单 taskType（接单/备货/入仓/通知送货/送达/签收）生成 ScheduleOrderNode，装进 `orderNodeMap[categoryId][taskType]`；`fulfillmentDeliveryId` 按履约方式取仓库 ID 或供应商 ID；`replenish` 按 secondType 判断是否返补单。
- 下单载体单独装配：查 `indicator_project_order` + 查 `fulfillment_task`（taskType=下单、未取消），**只保留存在对应主材任务的下单载体**（否则算出结果没地方存）；再查 `fulfillment_task_ext`（replacement=1）拿汰换标记，标到 ScheduleOrderNode.replacement / replaceDate。
- 顺带把 `orderMap`（id→IndicatorOrder）与 `projectOrderMap`（id→IndicatorProjectOrder）放进 scheduleAllNode——后续落库直接复用这批 DB 实例，避免覆盖并发修改。

**`initDispatchNode`（:709）——用工载体装载**：
- RPC 拉项目全部主材任务 `taskDetail` + 汰换任务 ID `getReplacementTaskIds`；
- 只保留 8 类用工 taskType（测量/设计/复尺/设计审核/一次安装/安装/打磨/结晶），每个任务节点（TaskNodeDetail）→ ScheduleDispatchNode，装进 `dispatchNodeMap[categoryId][taskType]`；
- RPC 失败时**直接 return**（dispatchNodeMap 留空）——不抛异常、不中断，代价是本轮用工节点全部算不出来。

**`dfs`（:551）——图遍历〔纯函数〕****：
```java
if (circleVisited.contains(current.uniqCode)) return;   // 判环（DAG 理论无环，防御性）
circleVisited.push(...);
for (edge : current.edgeOutList) {
    // 下游节点挂的载体 × 边上规则 匹配 → 才继续走
    if (hasFilterNode(edge.ruleList, getOrderDispatchNode(nextNode, scheduleAllNode))) {
        figureNodeList.add(nextNode);
        dfs(nextNode, ...);
    }
}
circleVisited.pop();
```

**`hasFilterNode`（:571）——载体×规则匹配〔纯函数〕**，规则与载体匹配成功的条件（或）：
- 货单载体命中：`rule.categoryId == orderNode.categoryId` && (`rule.deliveryId=="-1"` 或 等于 orderNode.fulfillmentDeliveryId) && (`rule.deliveryType==-1` 或 等于 orderNode.deliveryType)
- 用工载体命中：`rule.categoryId == dispatchNode.categoryId` && 供应商同理 && (rule.restart && dispatchNode.restartCount>0 或 !rule.restart && restartCount==0)

**`getOrderDispatchNode`（:526）**：按节点名查静态字典 `EVENT_ENTITY`（事件名 → [载体类型(0货单/1用工), taskType, nodeType]），从 orderNodeMap/dispatchNodeMap 取该节点名对应的载体集合——即「这个事件节点上挂哪些项目实例」。

## 四、下钻终点

- 〔DB〕`indicator_order`（project_order_id + is_delete=0）；`indicator_project_order`（同条件）；`fulfillment_task`（project_code + task_type=下单 + status≠取消 + is_delete=0；以及汰换标记查询不限定 project——`andReplacementEqualTo(1).andProjectOrderIdEqualTo(poId)` 在 fulfillment_task_ext 上）；`fulfillment_task_ext`（replacement=1 + projectOrderId）
- 〔RPC〕starlord `taskDispatchV2Feign.taskDetail`、`taskDispatchV2Feign.getReplacementTaskIds`
- 〔纯函数〕`EVENT_ENTITY` 静态字典（事件名→载体三元组，覆盖测量/设计/复尺/设计审核/一次安装/安装/打磨/结晶/下单~签收共 40+ 事件）

## 五、备注

- **下单载体的「存在主材任务才保留」过滤**是硬约束：indicator_project_order 里的下单载体若没有对应 fulfillment_task 主材任务（`categoryId_deliveryId` 匹配不上），直接丢弃——算出下单指标也没地方写。
- `initDispatchNode` 的静默失败是「用工指标整批丢失」的隐形坑：日志「查询主材任务失败」后 return，主流程照常跑完，只是 dispatchNodeMap 全空 → DFS 里用工边全部不匹配 → 用工节点不进计算范围。刷数后「用工指标没更新」先查这条日志。
- `distinctNodes` 用「反转→distinct→反转」实现「保留靠后出现的重复元素」——因为 DFS 后访问到的节点其 edge 引用更完整，保留后者更安全。
- 载体上此时 `innerInterval`（任务耗时）与 `relateNodeId`（关联关系）还是初始值/空，它们由 [[12.EvalScheduleOrderService-getScheduleTimeTrack|getScheduleTimeTrack]] 的 `initInnerIntervalAndRelateNodeId` 补齐。
