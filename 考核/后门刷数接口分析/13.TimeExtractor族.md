# 13. TimeExtractor 族 —— 轨迹抽取的策略模式实现

## 一、功能是什么

`TimeExtractor` 接口的 8 个实现，每个负责一种**事件类型（EventTypeEnum）**的轨迹抽取——把 BaseDataContext 里对应数据源的原始记录翻译成 `NodeTimeTrackV2`（节点 code + TimeInfo 列表）。`TimeExtractorFactory` 在启动时收集全部 Spring Bean 按 `getSupportedType()` 注册成路由表，运行期 `findExtractor(eventType)` O(1) 查找。

排程链路走 `getScheduleTimeTrack(ScheduleEventNode, ...)`；旧货单链路走 `getNodeTimeTrackV2(EventNode, ...)`——多数实现的 schedule 版是「把 ScheduleEventNode 降维成 EventNode 后复用旧版逻辑」。

## 二、逻辑实现（按数据源逐个看）

| Extractor | EventType | 数据源（BaseDataContext） | 轨迹逻辑要点 |
|---|---|---|---|
| `ConstructionTimeExtractor` | CONSTRUCTION_SCHEDULE | constructionList（从排程 tasks 整理的工期节点→日期） | 按 `node.scheduleCode` 匹配工期 sequenceCode，时间全部作为 **completeTime**（工期时间视为实际时间）；同一节点取「实际优先、预计兜底」 |
| `BasicPackageTimeExtractor` | BASIC_PACKAGE_SCHEDULE | basicPackageTasks（基装包五类任务） | `taskType[_start]` + 施工包ID 匹配节点；`base_construction_work_start` 取 factStartTime 否则 predictStartTime，其余取 fact/predict EndTime；DEFAULT_TIME 哨兵跳过；只有 completeTime |
| `MaterialTaskTimeExtractor` | TASK_DISPATCH | taskDispatchDetailSimpleDTOS（starlord 主材任务） | 按 taskType+nodeType 过滤任务节点；按 timeType（通知/生成/实际/激活）选时间字段；**跨供应商品类特判**（橱柜/定制柜套内套外的内部复尺按品类去重 singleRecheckNodeIds）；完整 TimeInfo（orderNo/supplierId/restartCount/crossSupplier 标记） |
| `OfcTimeExtractor` | OMS_OFC | orderFlowTimes（OFC 货流动作） | 按 `node.ofcCode`（动作码）+ 品类 orderNos 过滤货流记录，operationTime → completeTime；主材任务里的 estimatedTime → assessmentTime（先估后实：没发生就有预估时间） |
| `FulfillmentTimeExtractor` | FULFILLMENT | fulfillmentTasks（DB 履约任务） | 经 `IndicatorChangedListener.getTaskType(事件名)`（含「生成时间/激活时间/通知送货-可上门时间」等变体名）映射 taskType；按 timeType 取 noticeRetainTime/createTime/activeTime → completeTime |
| `OmsTimeExtractor` | OMS | dataContext.subOrderComplexDtos | 当前实现返回空（OMS 数据源未接，占位） |
| `ReplenishTimeExtractor` | REPLENISH | replenishReceiveDtos | 空实现（占位） |
| `CubeTimeExtractor` | CUBE | cubeDtos | 空实现（占位） |

MaterialTaskTimeExtractor 的 schedule 版（:142）就是字段拷贝成 EventNode 后调 getNodeTimeTrackV2；OfcTimeExtractor 的 schedule 版（:130）同理（少拷 timeType）。

## 三、调用了谁 / 为什么

族内无 RPC/DB——**全部消费 BaseDataContext 已拉好的内存数据**（这是「一次拉全」架构的另一半：抽取阶段零 IO）。依赖关系：

- 依赖 [[12.EvalScheduleOrderService-getScheduleTimeTrack|12 的 buildScheduleTimeDataContext]] 预先填充对应数据源字段；
- `FulfillmentTimeExtractor` 依赖 `IndicatorChangedListener.taskTypeMap`（静态事件名→taskType 映射，含历史别名）。

## 四、下钻终点

- 〔纯函数〕全部 8 个实现 + Factory 路由。
- 数据源终点即 [[12.EvalScheduleOrderService-getScheduleTimeTrack]] 的五路 RPC/DB——本层不再下钻。

## 五、备注

- **新增事件类型 = 加一个 Extractor**：实现接口、`@Component`、返回对应 EventTypeEnum，Factory 自动收录。忘记注册不会报错，只是 findExtractor 返回 null 直接 NPE——`getScheduleTimeTrack` 主循环里没判空，注意。
- `OfcTimeExtractor` 的「estimatedTime → assessmentTime」配合后门全量重算的语义：送达节点未实际发生时，轨迹里带的是主材任务预估时间，18 号文档的 `filterTimeInfos` 会决定用 complete 还是 assessment 参与计算。
- 工期/基装包 extractor 都把时间当 completeTime（realFlag=1 实际时间），而主材任务的预估是 assessmentTime（realFlag=0）——`realFlag` 最终决定考核结果的「真实性」标记（全部前置为实际时间才算 real）。
