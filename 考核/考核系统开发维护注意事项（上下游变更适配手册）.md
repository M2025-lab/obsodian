# 考核系统（scm-workbench）开发维护注意事项 — 上下游变更适配手册

> 用途：接手考核系统后，日常开发和维护的"变更反应手册"。核心回答一个问题：**上游/下游/配置发生变化时，考核系统要不要动、动哪里、动完之后还要做什么固定动作。**
> 依据：代码全量走读 + 考核时间计算逻辑专项梳理（问题清单详见该文档 §14）。

---

## 一、总原则：收到任何变更通知，先过三个问题

1. **它碰不碰计算链路的输入契约？**（日历数据、节点消息、规则配置、锚点时间来源）——碰了就必须评估适配，考核是"计时裁判"，输入口径变了判罚结果就变。
2. **它碰不碰考核的对外输出契约？**（`workbench_indicator_change` payload、回传排程的考核时间、`fulfillment_task.assessment_time`、ES/Hive 报表字段）——碰了要通知下游、确认兼容。
3. **动完之后，缓存和存量数据怎么办？**——考核系统有三层缓存（DAG 本地缓存、节假日 Redis 缓存、checkBasicDiff Redis 2h）和大量**已算完的存量结果**，改了逻辑/数据不等于存量自动修正，必须走重算 SOP（见 §六）。

一句话：**考核系统没有"改完即生效"，只有"改完 + 刷缓存 + 重算存量 + 验证下游广播"四步闭环。**

---

## 二、上游依赖清单：谁变了、我会怎样、要做什么

### 2.1 施工排程（artisan-construction / ConstructionScheduleService）——耦合最深、风险最高

| 上游变更 | 对考核的影响 | 必须做的适配 |
|---|---|---|
| **新增日历类型**（如"台风停工"） | ⚠️ **急性全局故障**：`typeBitmaskMap.get(type)` 查不到新枚举返回 null → `reduce(0, Integer::sum)` 拆箱 NPE → `queryCalendarByYear` 抛异常 → **所有考核计算失败**（ConstructionScheduleService:129-134） | ① 升级 `artisan-construction-base` jar（`ConstructionCalendarTypeEnum` 在外部 jar 里，bitmask = `1 << value`）；② 在 `typeBitmaskMap` 补映射（或先加 `getOrDefault(type, 0)` 防御，保证不升级也不炸）；③ **决策**：新类型要不要进 `HolidayService:37-78` 的五档口径常量（48/12304/16378…）——即"自然日/工作日跳过它吗"；④ 确认新 bit 与现有 14 个枚举不重叠（bitmask 用 `+` 拼接，重叠即口径错乱）；⑤ 回归 `figureAssessmentTime` 正/反/当天顺延三类用例 |
| **修改日历打标口径**（除夕算不算春节、调休周六只打 ADJUST_WORK_DAY 不打 DOUBLE_CEASE、周末漏打双休标） | **静默口径漂移**：workbench 对上游打标零校验（问题 C2），跳过策略全凭上游习惯，改打标 = 改考核结果，且无任何报错 | ① 拿 `GET /api/init/holiday/figureFactDays` 和 `/api/holidayCache/get` 对改动前后同一天做对比；② 明确哪些指标口径受影响（对照时间计算文档 §6.3 口径全景表）；③ 受影响时段存量单走重算 SOP |
| **日历数据补录/修正**（事后补调休） | 滑动 TTL 下缓存可能永不刷新（D2）；且**已算完的考核不会自动重算**（A3，没有"日历变了→触发重算"机制） | 固定两步：`POST /api/holidayCache/delete` 删缓存 → `/api/refresh/eval/order`（旧）/ `/api/refresh/eval/schedule/projectOrder`（新）刷受影响范围。**建议把这两步写进团队 SOP，上游补录日历后主动通知考核侧。** |
| **排程规则 DTO 变更**（`ProcessNodeCfgDTO` / `NodeAssessmentRuleCfgDTO` 加字段、改语义） | `getIndicatorRules`（版本规则 + 返补规则合并）与 `rebuild` 构图直接消费这些字段；`scheduleRelation/duration/durationType/divide/restartType` 任一语义变化都改变 DAG 边和计算结果 | ① 确认反序列化兼容（新增字段一般安全，改语义必须同步改 `rebuild`/`convertNodeCode`）；② 新字段若参与口径（如新 timeType 值），检查 `TimeProcessor.determineInterval` 的中文魔法字符串 switch 是否覆盖（A6：不认识直接 RuntimeException） |
| **排程节点类型变更**（基装包五类任务之外新增节点） | `queryScheduleNode` 只拉五类（指派工人/施工排期/施工开始/施工/施工验收），`BASIC_PACKAGE_ACTION_TYPE_SET` 之外的新节点不进 `checkBasicDiff`，**考核感知不到它的变化** | 评估是否要把新节点纳入 diff 范围 + `indicator_base_event` 加事件 + 配规则 |
| **排程回传契约变更**（`schedule_data_recovery` / `workbench-assessment-time-change`） | 这是考核→排程的闭环出口（`sendAssessmentChange`），payload 变化影响排程侧展示 | 与排程团队对 payload 后再改 |

📌 **日历覆盖范围（2026-11-01 核实）**：`getCalendar(year)` 传当年、上游实际返回 **year-2 ~ year+1 共 4 年**数据，workbench 不过滤原样入 map；缓存 key `{year-2}{year}{year+1}_holiday_` 即覆盖声明（`year-2` 不是笔误）。**常规跨年场景（12 月走进 1 月、1 月重算 12 月单）不盲。** 残余边界：① 锚点/行走区间超出 4 年窗口仍被 `getOrDefault(date,0)` 静默当工作日；② year+1 段完整性依赖上游打标节奏（明年节假日安排通常 11~12 月才公布），Q4 需巡检、上游补标后删缓存。

### 2.2 OFC（履约中控）——消息总闸

| 上游变更 | 对考核的影响 | 必须做的适配 |
|---|---|---|
| **新增节点（ofcCode）** | 新节点消息进来后：任务侧走 `doExecuteGenerateTask` 按 OFC 流程配置建任务；考核侧 **DAG 里没有对应事件节点就不会计算**——静默忽略，不报错 | `dic_rule_node` 加节点字典 → `indicator_event`（旧）/ `indicator_base_event`（新）加事件 → 配 `indicator_compute_rule` 规则 → **刷 DAG 缓存**（`/dag/refresh`、`/api/remove/schedule/dag/cache`） |
| **节点 code / 语义变更**（改名、拆分、合并） | `indicator_event.code = 品类+ofcCode` 的映射失配 → 消息匹配不到事件 → 考核不触发或触发错节点 | 全量核对 `dic_rule_node` / `indicator_event` / `indicator_base_event` 里的 code 引用；查 `event_sub` 表确认消息是否落地、是否被 handler 消费 |
| **payload 结构变更** | `event_sub` 落表可追溯，反序列化失败会在 handler 层暴露 | 用 `event_sub` 表回查失败消息；确认 `OfcFulfillmentEventHandler.handleBiz()` 三分支（任务/货单/考核）是否都兼容 |

### 2.3 starlord（edar-starlord，主材任务）

| 上游变更 | 对考核的影响 | 必须做的适配 |
|---|---|---|
| **排程开关逻辑变更**（`queryProjectInScheduleSwitch`） | 这是**新旧模型分流总闸**：返回值变化 = 项目从旧链路切到新链路（或反之），两套 DAG、两套结果字段（`*_eval_result` vs `*_eval_result_new`）、两套接口 | ① 切换前确认项目在 `schedule_project` 白名单状态；② 切换后旧字段结果不再更新，报表/下游若还在读旧字段要同步迁移；③ 灰度节奏与上游对齐 |
| **主材任务节点配置变更**（`n_material_time_cfg` "平台考核时间"） | 与 workbench 规则模型同构（基准节点+相对关系+间隔+日历类型），两边配置需互相印证，否则跨系统时效对不上 | 用统一范式核对两侧配置；排查跨系统时效问题时先对齐两边的"参考点/间隔/日历类型"三要素 |
| **汰换消息变更**（`supplier_replace_message`） | 触发 `/fulfillmentTask/deal/replacement/refresh` 考核重算 + `fulfillment_task_ext` replacement 打标联动 | 跨系统链路，改动需同时核对 starlord 任务状态与 workbench 重算结果 |
| **同步契约变更**（`SyncMaterialTaskService`） | `fulfillment_task` ↔ starlord 任务双向同步断链 | 核对同步字段映射；`inSchedule=true` 才同步主材任务（用工任务 `mode=7` 例外：更新成功即同步，不受开关控制） |

### 2.4 OMS / 其他上游

- **OMS 子单结构变更**：`queryBaseByOrderNo` 是考核计算第一步取数，字段缺失会导致锚点时间取不到。
- **返补单（ArtisanWorkOrderRpc）**：`buildTimeDataContext` 五数据源之一，返补规则（`queryRebateRuleList`，不传 version）单独合并进规则集。
- **上游时间字段语义变更**（factStartTime/predictStartTime、默认时间约定）：⚠️ 系统存在**隐式契约**——`1970-01-01 00:00:00` 当"无实际时间"占位、`estimatedTime < 2000-01-01` 当"需补算"占位。上游改默认值/占位约定会悄悄破坏 `checkBasicDiff` 和 `getNodesBeforeContract`。

## 三、下游消费方清单：我变了，要通知谁

| 出口 | 契约 | 变更注意 |
|---|---|---|
| Kafka `workbench_indicator_change`（bizType `indicator_changed`） | `IndicatorChangePayload`：按指标拆条、含历史命名兼容字段 | **改字段/改语义前必须盘点订阅方**；Listener 翻译层在 `IndicatorChangedListener`，try-catch 全包（广播失败不影响主流程，但下游会丢消息，靠后门重算兜底） |
| Kafka `schedule_data_recovery`（bizType `workbench-assessment-time-change`） | 考核时间回传施工排程（新模型闭环） | 排程侧展示依赖它，改考核时间语义要同步 |
| Kafka `fulfill_node_change` | 中继广播 OFC 销售单节点变更 | 下游是不直接订阅 OFC 的系统，OFC 消息格式变化会穿透到这里 |
| `fulfillment_task.assessment_time` 同步 VSS / OFW / starlord | 端上待办卡片的"还剩多久超时" | 考核时间算错会直接放大到端上用户可见 |
| ES / Hive `rpt.rpt_indicator_eva_da` | eval_result JSON explode 打平成指标粒度 | **改 eval_result JSON 结构 = 改报表 DDL/ETL**，需同步数据团队；重推入口 `/api/workbench/es/indicator/rePush/byIndicatorId` |
| Feign API（`scm-workbench-api` jar，20 个接口） | 上游引 jar 直接调 | 改 DTO 要发新版 jar 并确认调用方升级节奏 |

**广播三道闸门**（改结果≠下游一定收到，排查"下游没更新"先查这里）：① `updatedEval` 为空不发；② 订单创建时间早于 Apollo `synEffectiveTime` 不发；③ 北京黑名单 && 非排程项目不发（这部分由 starlord 计算同步，避免重复）。

## 四、内部配置变更：不碰代码也要当"发布"对待

| 变更 | 注意事项 |
|---|---|
| 考核规则调整（间隔/时效） | 走 v2 配置接口（旧版 `IndicatorConfigWriteController` 已 `@Deprecated`）；**改完必须刷 DAG 缓存**，否则不生效；一城一策个性化间隔 ≤ 底线（校验在配置侧）；底线自然日会锁死一城一策为自然日（IndicatorComputeRuleService:261-263） |
| **指标改名/新增指标** | ⚠️ `HolidayService:80-124` 的 `indicatorHolidayMap` 用**中文指标名当 key**——改名/新增而注册表没跟上，工作日口径**退化成纯自然日**，只有一条 `LOGGER.error("不识别的indicatorName")`，不阻断、结果照写照广播（A2）。**任何指标名变更必须同步这个硬编码注册表**，并确认新指标该用哪档口径（48/12304/16378） |
| timeRef / interval 配置 | timeRef 是中文魔法字符串精确匹配（"当天/之前/之后"，无 trim，变体直接 RuntimeException）；interval 是 BigDecimal 但 `intValue()` 静默截断（配 2.5 按 2 算，A6）——配置界面应限制整数 |
| Apollo 配置 | `synEffectiveTime`（广播灰度）、`schedule_interval`（checkBasicDiff 缓存 TTL，默认 7200s）、北京黑名单；改动即时生效、无发布记录，**改前留档** |
| 白名单/灰度 | `schedule_project` 表 + 主材 `materialScheduleSwitch` 双条件都过才走排程链路 |

## 五、周期性/时间敏感事项（不用谁通知，到点自己发生）

| 时间窗 | 风险 | 动作 |
|---|---|---|
| **每年 Q4（✏️ 修正：常规跨年不盲）** | 日历覆盖 year-2 ~ year+1 共 4 年（上游传当年返 4 年，2026-11-01 核实），12 月走进 1 月、1 月重算 12 月单均正常。残余风险：① year+1 段新鲜度——明年节假日安排通常 11~12 月才公布，上游未打标期间跨年行走"查得到日期但 type=0"→ 该跳的没跳，且滑动 TTL 下补标后不删缓存拿不到；② 锚点超出 4 年窗口（远期事前考核、year-3 之前历史单重算）仍静默当工作日（`getOrDefault(date,0)`，RuleUnit:97） | Q4 抽查跨年单前先 `/api/holidayCache/get` 确认 year+1 段打标是否完整；上游补标后删缓存 + 重算受影响范围 |
| 跨年夜（12-31 24:00 前后） | `now().getYear()` 调两次的毫秒竞态（B5；4 年覆盖下即便存错 key，N 年数据本身含 N+1 年，危害有限）；`figureAssessmentTime` 结果恒钉 23:59:59 | 知晓即可 |
| 每季度初 | `event_sub_2025_qN` 按季度手工分表，**漏建表 = 消息落地写入失败** | 季度前检查下季分表是否已建 |
| Redis 故障时 | 日历缓存硬依赖 Redis、无降级（B3）：Redis 不可用 → 全部考核计算失败 | 故障期间考核计算会堆积，恢复后关注补偿；长期方案是给日历加 JVM 本地缓存（D1） |

## 六、固定动作 SOP（改完任何东西之后）

**1. 判断链路**：这个项目走旧模型还是排程新模型？（`queryProjectInScheduleSwitch` + `schedule_project` 白名单）——误改旧链路，排程项目考核不生效。

**2. 刷缓存**（按涉及面选择）：

| 缓存 | 刷新入口 |
|---|---|
| DAG（旧模型，JVM + Redisson 版本号） | `/dag/refresh` |
| 排程 DAG（本地 cache，100 项/10 分钟） | `/api/remove/schedule/dag/cache` |
| 节假日（Redis，滑动 TTL 实际永不过期） | `POST /api/holidayCache/delete` |
| checkBasicDiff（Redis 2h） | 等过期，或手动刷新传 forceAll=true |

**3. 重算存量**：`/api/refresh/eval/order`（旧，按货单）/ `/api/refresh/eval/schedule/projectOrder`（新，按项目）。⚠️ 手动刷新**无事务保护、串行处理、中途异常即终止且不回滚**——批量修数拆小批 + 事后核对；接口返回成功 ≠ 异步下游同步完成。

**4. 验证闭环**：`/api/tool/projectAssessment` 查现状 → `/api/init/holiday/figureFactDays` 验日历口径 → 查 `event_sub`/`event_pub` 确认消息进出 → 抽查下游（排程回传/ES/端上任务卡片）。

**5. 留痕**：45 个后门接口**无审计**，每次线上修数自行记录（时间、范围、原因、操作人）——在补上操作日志上报之前，这是唯一追溯手段。

## 八、给 AI 配置 check（三步走第一步）的规则素材

上述适配点中，**机器可校验**的候选规则（承接 7 月讨论会已立项方向）：

1. 指标名 ∈ `indicatorHolidayMap` 注册表（防 A2 静默退化）；
2. timeRef ∈ {当天, 之前, 之后} 且无前后空格；interval 为整数且在合理值域（防 A6/B1/B2）；
3. 一城一策间隔 ≤ 底线间隔；底线自然日 ⇒ 一城一策必须自然日；
4. 规则引用的 from_nodes/to_node 均存在于 `dic_rule_node`，且 DAG 连通（防新节点配了规则但图不连通）;
5. 锚点/行走区间不超出日历覆盖窗口 year-2 ~ year+1（窗口外预警，防 A1 残余盲区）；
6. 配置变更后 DAG 缓存刷新是否执行（防"改了不生效"）。
