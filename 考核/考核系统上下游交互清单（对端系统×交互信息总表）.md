| # | Topic | bizType | Payload（代码核实的字段） | 触发时机 | 下游/用途 |
|---|---|---|---|---|---|
| 1 | `workbench_indicator_change` | `indicator_changed` | `IndicatorChangePayload`：**indicatorName（指标名）、orderNo、projectOrderId、branchCode、categoryId、deliveryId、FlowType** + `baseIndicatorResult` / `cusIndicatorResult`（各含 **isCusIndicator、configType、expectCompTime（应完成时间）、realCompTime（实际完成时间）、evaluation（评价结果）**）——按指标拆条、含历史命名兼容字段 | 内部 Spring 事件 `IndicatorChangedEvent`（旧模型 `EvalOrderService` / 新模型 `EvalScheduleOrderService` / `ExamineIndicatorWriteService` / `ToolService` 手动）→ `IndicatorChangedListener` 过**三道闸门**（①updatedEval 为空不发 ②早于 Apollo `synEffectiveTime` 不发 ③北京黑名单&&非排程不发）后转发 | **对外广播考核结果变更**，订阅方自行解析；⚠️ Listener try-catch 全包，广播失败不报错不重试 |

| 2 | **Hive 报表** `rpt.rpt_indicator_eva_da` | 离线 ETL（数据团队维护） | `eval_result` JSON **explode 打平成指标粒度**（DDL 与 JSON 路径硬绑定） | ⚠️ 改 eval_result JSON 结构 = 改报表 DDL/ETL，必须同步数据团队 |

## 七、交互中的隐式契约（跨系统对不上的常见根因）

| # | 隐式契约 | 双方 | 风险 |
|---|---|---|---|
| 1 | `1970-01-01 00:00:00` = "无实际时间"占位；`estimatedTime < 2000-01-01` = "需补算"占位 | 上游时间字段 → workbench 硬编码魔法值识别 | 不写在任何接口文档里，上游改默认值即静默破坏 |
| 2 | `indicator_event.code = 品类 + ofcCode` 字符串精确匹配 | OFC → workbench | 无 ID 化、无版本兼容层，改 code 即断链 |
| 3 | 日历 bitmask 翻译依赖旧 jar 枚举（`1 << value`） | 施工排程 → workbench | 上游新增日历类型 → `typeBitmaskMap` 查空 NPE → 全局考核失败 |
| 4 | 考核时间回传 payload 无 schema 强校验 | workbench → 施工排程 | 单方改结构，对方解析静默错乱 |
| 5 | starlord `n_material_time_cfg` 与 workbench 规则**同构但两份独立配置** | starlord ↔ workbench | 无一致性校验，跨系统时效对不上是必然 |
