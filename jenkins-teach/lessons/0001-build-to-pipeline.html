从 build.sh 到 Pipeline：一次构建到底发生了什么

用你自己的 edar-starlord 工程当例子，先建立"一次构建"的心智模型，再认识 Jenkins 的五个核心角色。

你现在的工程里已经有打包脚本 build.sh——它干的事，其实就是一条"没用 Jenkins 的流水线"。先别急着装 Jenkins，这一课我们把它拆开看明白，下一课你就能把同样的步骤原样搬进 Jenkinsfile。

1. 你现在手动做的事，Jenkins 都能替你自动做

在 edar-starlord 根目录跑 sh build.sh make，脚本实际做了三件大事：

# build.sh 的真实步骤（已读你项目，节选）
rm -rf release/
mvn clean package -Dmaven.test.skip=true      # ① 编译 + 打包
mkdir -p release/{bin,lib}
cp edar-starlord-web/target/*.jar release/lib/ # ② 收集制品
tar czvf release.tar.gz release                # ③ 打成 release.tar.gz
  • 人工痛点：每次发版都得有人登录机器敲命令；忘了 clean 可能带着旧 class；换个人就不知道参数；出错了要自己翻终端。
  • Jenkins 的价值：把上面三步变成"代码"，提交即触发、自动跑、全程有日志、失败了通知人。这就是 CI（持续集成）。
本课目标不是装软件，而是先在脑子里把"构建 = 一串有序步骤"这件事钉死。后面所有 Jenkins 概念都是为这件事服务的。

2. 认识五个核心角色（今天只记这五个）

对照你自己的脚本读这张图：

  • Controller 负责"决定现在该跑构建了"——比如你 git push 后它收到通知。
  • Agent 是真正执行 mvn 的机器；你的项目需要 Maven 和 JDK，所以这条 Agent 得带 maven 标签，或干脆用 agent { docker { image 'maven:3.9-eclipse-temurin-8' } } 临时起个容器。
  • Executor 是这条 Agent 上的一条通道；配 2 个就能同时跑 2 个构建。
  • Workspace 就是 Agent 上给这次构建建的目录，mvn 在这里克隆代码、把 target/*.jar 打出来。
  • Pipeline / Stage / Step：你 build.sh 的三大步，会翻译成三个 stage，每个 stage 里是具体 step。

3. 把 build.sh 翻译成"阶段"语言

先看你现在脚本的天然分段，再用 Jenkins 的话重新说一遍：

build.sh 里的动作 对应 Jenkins 概念
mvn clean package …stage('Build') 里的 step
cp *.jar release/lib/stage('Package') 里的 step
tar czvf release.tar.gzstage('Package') 里的 step，或 archiveArtifacts
（自动）克隆代码配置 Git SCM 后，Jenkins 自动 checkout 到 Workspace
注意：你项目用的是 -Dmaven.test.skip=true（跳过测试）。等你想认真做 CI，下一步就是把测试打开——那会多一个 stage('Test') 跑 mvn test。先记着这个"进阶点"。

4. 最小 Jenkinsfile 长什么样

不需要你现在运行它，先把骨架印进脑子。下面这段就是把"编译打包"搬进声明式流水线的样子：

// 放在项目根目录，文件名就叫 Jenkinsfile，随代码提交到 Git
pipeline {
  agent any                      // 在哪跑：any=任意可用 agent
  stages {
    stage('Build') {            // 对应 build.sh 的 mvn clean package
      steps {
        sh 'mvn clean package -Dmaven.test.skip=true'
      }
    }
    stage('Package') {          // 对应打 release.tar.gz
      steps {
        sh 'mkdir -p release/lib'
        sh 'cp edar-starlord-web/target/*.jar release/lib/'
        sh 'tar czvf release.tar.gz release'
        archiveArtifacts artifacts: 'release.tar.gz', fingerprint: true
      }
    }
  }
}

记住三件套：pipeline { agent ... stages { stage('名字') { steps { ... } } } }。缺了 agent 声明式流水线根本不合法——这是新人最常踩的坑。

5. 本课小练习（不用装 Jenkins 也能做）

练习 A（动手，5 分钟）：在你本地 edar-starlord 根目录跑一次 ./mvnw -o clean package -Dmaven.test.skip=true （-o 离线，用本地仓库更快），然后看一眼 edar-starlord-web/target/ 下是不是生成了 *.jar。 这一步，正是 Jenkins 的 Build 阶段要做的事——你只是提前用同一台机器手动验证了一遍。
练习 B（观察，3 分钟）：打开 build.sh 和 build-dayu.sh，用荧光笔（或在心里）把它们的步骤标成 Build / Package / 发布 三段，确认第 3 节的对照表没标错。

6. 检索练习（考考记忆）

凭记忆答，不要回上面翻——答完点"看答案"。

① 真正执行 mvn 命令的，是 Controller 还是 Agent？

答案是 Agent。Controller 只调度，不亲自编译；Workspace 只是目录，不是"谁"。

② 声明式流水线里，下面哪个指令必填、不写就整个不合法？

答案是 agent。没有它 Jenkins 不知道在哪分配执行器和工作区；stages 也必填，但本题单选出最可能的"忘了就跑不起来"的坑，agent 是首选。

③ 你项目的 build.sh 里 -Dmaven.test.skip=true 意味着什么？

答案是 根本没跑单元测试。真做 CI 时通常要去掉这个参数、加一个 Test 阶段。
