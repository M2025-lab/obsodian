## 一、需求概述  
  
安装/拆除工从整装组织体系独立，以个体工商户（安装项目经理/拆除项目经理）为经营主体承接业务。组织归属关系变化后，涉及上级审批与派单确认的三条链路需要改造。本文档整合以下三个模块：  
  
| 模块 | 需求点 | cube 侧改造 |  
|------|--------|------------|  
| A. 派单需确认列表 | `listPackageConstructionByManager` 新增「派单需确认」状态（待上级确认/待工人确认），支持筛选与排序（待上级确认在前、待工人确认在后、组内按时间序） | **有**，ES 查询链路 + VO 组装改造 |  
| B. 约工驳回查上级 | 上级改为「长期合作关系项目经理」（外包性质，非系统内部角色），从服务者中心查询 | **无**，服务者中心内部改造 `querySuperiorByWorkType` 返回值，cube 仅联调验证 |  
| C. 费用单审批链 | 一级审批由单人改为**项目经理 + COE 会签**（两人均通过才通过）；一级通过后若超额，查询 **COE 直属上级**加签审批 | **有**，`PcProblemQuotaServiceImpl` 全链路 + 数据模型改造 |  
  
**范围**：仅影响安装/拆除工种且命中「组织城市+工种」开关的施工包；整装原有链路（开关未命中）走原逻辑不受影响。  
  
**已确认的关键决策**（2026-07-26 与需求方对齐）：  
  
1. 费用单一级审批为**会签**：项目经理和 COE 都通过才算一级通过，任一人驳回即整体驳回。  
2. 超额判断时机：**一级（双人）会签通过时**执行 `validateSecondApproval`；超额则通过 **ceres 组织树查 COE 直属上级**加签。  
3. 约工驳回：沿用 `PersonManager.querySuperiorByWorkType()` 原接口，服务者中心内部改为返回合作关系项目经理，**cube 无代码改动**。`PcReconstructionServiceImpl` 两处同接口调用同理，不在 cube 改造范围。  
4. 派单二级确认状态为**两套编码**：ES 字段 `dispatchConfirmStatus`（0-无二级状态/1-待上级确认/2-待工人确认，派单平台写入）；DB/接口层 `packageSecondStatus`（31-待上级确认/32-待工人确认，`DispatchStatusEnum` 新增）。cube 负责映射：31↔1、32↔2。  
5. 模块 A、C 均受「组织城市+工种」Apollo 开关控制，开关关闭走原逻辑。

## 二、触发条件  
  
### 2.1 开关  
  
Apollo 开关 `install.demolition.worker.reform.switch`（组织城市 + 工种维度，与总设计文档统一）：  
  
- 判定入参：施工包 `branchOfficeCode`（或组织城市编码）+ `workerType`  
- 命中 → 新逻辑；未命中 → 原逻辑（模块 A 不下发新状态筛选项与新排序；模块 C 走单审批人流程）  
  
### 2.2 编码映射（模块 A）  
  
| 语义 | ES `dispatchConfirmStatus`（派单平台写入） | 接口/DB `packageSecondStatus`（DispatchStatusEnum） |  
|------|------|------|  
| 无二级状态 | 0 | —（不新增） |  
| 待接单-待上级确认 | 1 | 31 `TO_BE_MANAGER_CONFIRM` |  
| 待接单-待工人确认 | 2 | 32 `TO_BE_WORKER_CONFIRM` |  
  
前端沿用 `ExtraFieldTypeInfo` type=3（施工包二级状态）传 `"31"`/`"32"`，cube 在构建 ES 查询前转换为 `dispatchConfirmStatus` 的 1/2。  
  
### 2.3 模块 C 触发条件  
  
- `submitQuota`：施工包命中开关 → 会签模式（写入两个一级审批人）；未命中 → 原单审批人模式。  
- `approvalQuota`：按申请单创建时落库的审批模式执行（以数据为准，不在审批时二次判断开关，避免开关切换导致在途单流转错乱）。  
- 超额判断条件不变：`validateSecondApproval` —— Apollo `packageProblemQuotaLimitDTOList` 按 `branchOfficeCode + internalControlCategoryCode` 取 `limitAmount`，累计金额超限或二次上门费（`SECOND_VISIT_FEE`）超 1 次。

## 三、改动清单  
  
### 3.1 模块 A：派单需确认列表改造  
  
调用链：`PcController.listPackageConstructionByManager` → `WorkerServiceImpl.listPackageConstructionByManager`（L892-1005）→ `EsSearchService.searchEs/countByEs` → `EsSearchServiceImpl` → `EsPackageConstructionServiceImpl.queryConstructionListFromEs` → `KeEsQueryRequest` → `PcV2EsInvoker`（索引 1047900333）→ 回查 `PackageConstructionV2Dao.selectByPackageCodes` → `buildUnifiedWorkerTaskVOList`。  
  
#### A1. `EsPackageConstructionMessageDTO` 新增字段  
  
`utopia-cube-api/.../v2/dto/EsPackageConstructionMessageDTO.java`  
  
```java  
/** 派单二级确认状态 0-无 1-待上级确认 2-待工人确认（派单平台写入） */  
private Integer dispatchConfirmStatus;  
```  
  
#### A2. `PackageSearchParam` 新增筛选字段  
  
`utopia-cube-api/.../v2/param/PackageSearchParam.java`  
  
```java  
/** 派单二级确认状态筛选 1-待上级确认 2-待工人确认 */  
private List<Integer> dispatchConfirmStatusList;  
```  
  
#### A3. 枚举与入参映射  
  
- `DispatchStatusEnum` 新增 `TO_BE_MANAGER_CONFIRM(31)`、`TO_BE_WORKER_CONFIRM(32)`（若总设计文档改造已落，则复用）。  
- 新增映射枚举/工具（建议 `utopia-cube-base` 下 `DispatchConfirmStatusEnum`：`NONE(0)、TO_BE_MANAGER_CONFIRM(1, 31)、TO_BE_WORKER_CONFIRM(2, 32)`），提供 `secondStatus ↔ esStatus` 双向转换，映射关系只落在这一处。  
- `WorkerServiceImpl` 解析 `PackageListParam.extraFieldTypeInfoList` type=3 时（现有 `packageSecondStatusList` 处理位置 L933-940 附近）：valueList 中的 `"31"`/`"32"` 剥离出来转换为 `dispatchConfirmStatusList=[1]/[2]`，其余值仍走 `packageSecondStatusList`。  
  
#### A4. `EsSearchServiceImpl.convertSearchParam` 增加过滤与排序  
  
- **过滤**：仿照 L159-161 现有 matchMap 模式，`dispatchConfirmStatusList` 非空时加 terms 过滤 `dispatchConfirmStatus`。  
- **排序**：当本次查询携带 `dispatchConfirmStatusList`（即「派单待确认」tab）时，构建：  
  
```java  
FieldSortBuilder sort = SortBuilders.fieldSort("dispatchConfirmStatus")  
    .order(SortOrder.ASC)          // 1(待上级确认) 在前，2(待工人确认) 在后    .unmappedType("integer")       // 防御存量文档无此字段导致 DSL 报错    .missing("_last");keEsQueryRequest.setDefaultSortField("createTime"); // 复用现有机制追加 createTime desc 次级排序  
```  
  
`KeEsQueryRequest` 仅支持单排序字段 + `defaultSortField`（自动追加 `createTime desc`），恰好满足「状态分组 + 组内时间序」诉求，**不改 `KeEsQueryRequest` 排序结构**。  
  
#### A5. `WorkerServiceImpl` 主流程改造（L892-1005）  
  
1. 透传 `dispatchConfirmStatusList` 至 `PackageSearchParam`。  
2. `countByEs` 的 copy 参数（L942-947 现有模式 `packageSearchParamCopy.setPackageSecondStatusList(null)`）同步执行 `setDispatchConfirmStatusList(null)`，保证聚合计数不受当前 tab 筛选影响。  
3. **修复现存顺序隐患**：`selectByPackageCodes` 无 orderBy，最终返回顺序=DB 主键序≠ES 排序序。`buildUnifiedWorkerTaskVOList` 组装完成后，按 ES 返回的 packageCode 顺序对 VO 列表重排：  
  
```java  
Map<String, Integer> orderMap = new HashMap<>();  
for (int i = 0; i < esPackageCodes.size(); i++) { orderMap.put(esPackageCodes.get(i), i); }  
workerTaskVOList.sort(Comparator.comparingInt(  
    vo -> orderMap.getOrDefault(vo.getPackageCode(), Integer.MAX_VALUE)));  
```  
  
4. ES 命中文档的 `dispatchConfirmStatus` 以 `Map<packageCode, Integer>` 形式带出，回填 VO（DB 实体没有该字段，`BeanUtils.copyProperties` 带不过来）。  
  
#### A6. `WorkerTaskVO` 返回改造  
  
- `packageSecondStatus`：当 ES `dispatchConfirmStatus` 为 1/2 时，以 ES 值映射回 31/32 **覆盖** DB 值返回（避免派单平台反查刷 DB 滞后导致「筛选命中但展示不符」）；为 0 或字段缺失时维持 DB 值。  
- `tag` 新增「待确认」橙色标签、`buttonInfoList` 新增 confirm/reject 按钮（`buildButtonInfo()`，按钮动作接口为总设计文档 3.2.4/3.2.5 范围，本文档不展开）。  
  
#### A7.（可选）聚合角标  
  
若前端需要「派单待确认」tab 角标计数，`KeEsQueryRequest.toString()` 六个聚合按下标硬编码（`aggs#packageStatus` ~ `aggs#overdueType`），新增第 7 个 `aggs#dispatchConfirmStatus` 必须同步改 `toString()` 与 `AggregationFieldEnum`、`EsSearchServiceImpl` 的聚合解析。**默认不做**，前端确认需要后再纳入。  
  
### 3.2 模块 B：约工驳回查上级（cube 无代码改动）  
  
`PcReappointServiceImpl.reappointProblemSubmit`（L153-228）L162-173 调用 `personManager.querySuperiorByWorkType`（目标工种 DELIVERY_EXPERT / DELIVERY_INSTALLATION_EXPERT / ERECTOR_MANAGER / ERECTOR_LEADER）校验上级存在性，空则阻断提报（"请联系您的主管绑定关系完成后可开始申请"）。  
  
改造由**服务者中心（ceres）内部完成**：命中开关的工人，`querySuperiorByWorkType` 返回其长期合作关系项目经理（外包性质人员）。cube 侧联调验证项：  
  
| 验证项 | 说明 |  
|------|------|  
| 返回结构兼容 | `PersonPositionSimpleDTO` 的 ucId/name 字段填充是否与原逻辑一致；合作关系人员是否有系统 ucId |  
| 空结果行为 | 未绑定合作关系时返回空列表（而非报错），cube 现有阻断文案照常生效；确认文案「联系主管绑定关系」对外包场景是否需产品侧调整 |  
| 目标工种参数 | `targetWorkTypeList` 是否需要追加安装/拆除项目经理工种编码（以服务者中心接口约定为准，若需追加则 cube 有一行参数改动，联调时确认） |  
  
`PcReconstructionServiceImpl` 两处 `querySuperiorByWorkType`（问题反馈链路）、`RefreshDataController` 一处，同样由服务者中心内部改造覆盖，cube 不改。  
  
### 3.3 模块 C：费用单会签审批改造  
  
现状（`PcProblemQuotaServiceImpl`，749 行）：  
  
- `submitQuota`（L107-169）：`getFirstApproveUser` 查 ceres 上级取**第一个**返回人，写入 `package_quota_apply.auditUcId/auditName`（单字段）。  
- `approvalQuota`（L374-436）：一级审核中（AUDIT_PROCESS）审批通过时 `validateSecondApproval` 判超额 → `getSecondApproveUser`（组织树查工程经理）→ 不同人则置 `AUDIT_ADD_SIGN_PROCESS` 并更换 auditUcId。  
- `buildPackageQuotaButton`（L582-617）：`Objects.equals(apply.getAuditUcId(), ucid)` 单人判断审批按钮。  
  
#### C1. 新增审批人明细表 `package_quota_apply_auditor`  
  
单字段 `auditUcId` 无法承载会签的「双人各自审批状态」，新增子表（DDL 见第八章）。每条申请单在会签模式下写入 2 条明细（项目经理 + COE），超额加签时追加 1 条（COE 上级）。主表 `auditState` 继续表达整体状态，`auditUcId/auditName` 在会签模式下保留冗余写入项目经理（兼容存量查询/导出读该字段的场景，不作为审批判断依据）。  
  
新增 DAO：`PackageQuotaApplyAuditorDao`（insert/selectByApplyId/updateAuditStatus），对应 model 与 mapper。  
  
#### C2. `submitQuota` 改造  
  
```  
命中开关？  
├─ 否：原逻辑（getFirstApproveUser 单人写 auditUcId）  
└─ 是：  
   1. 项目经理 = personManager.querySuperiorByWorkType(...)（服务者中心已改为返回合作关系项目经理）   2. COE      = 复用现 getSecondApproveUser 中的组织树查询（queryPersonAndOrgTree 取 orgCode                 → queryByOrgCodeAndWorkType(orgCodes, DELIVERY_INSTALLATION_EXPERT)）抽取为 getCoeApprover()   3. 任一查询为空 → 抛 UtopiaBussinessException 阻断提报（文案见第六章）   4. 主表 auditState = AUDIT_PROCESS；子表写 2 条明细（auditRole=1 项目经理 / 2 COE，auditStatus=待审批）   5. IM 推送两个审批人（复用 imPushManager 现有模板）```  
  
去重防御：项目经理与 COE 为同一人（ucId 相同）时只写 1 条明细，单人通过即视为会签通过。  
  
#### C3. `approvalQuota` 会签流转  
  
```  
查当前操作人在子表中的待审批明细（applyId + ucid + auditStatus=待审批）  
├─ 无记录 → 抛"无审批权限"  
├─ 驳回   → 该明细置驳回；主表 auditState=AUDIT_NOT_PASS（任一人驳回即整体驳回）；  
│           另一人待审批明细置"已终止"；通知申请人  
└─ 通过   → 该明细置通过  
    ├─ 仍有其他一级明细待审批 → 主表保持 AUDIT_PROCESS，等待另一人（幂等：重复审批直接返回）    └─ 全部一级明细通过 → 一级会签通过        ├─ validateSecondApproval == false → 主表 AUDIT_PASS，走现有通过后置逻辑        └─ true（超额）→ getOverLimitApprover() 查 COE 直属上级            → 子表追加明细（auditRole=3 超额审批）            → 主表 auditState=AUDIT_ADD_SIGN_PROCESS，IM 推送 COE 上级            → COE 上级通过 → AUDIT_PASS；驳回 → AUDIT_NOT_PASS```  
  
超额审批人与 COE 为同一人时（组织树数据异常兜底），跳过加签直接 AUDIT_PASS（与现有 `approvalQuota` L374-436「审批人相同则不加签」的处理思路一致）。  
  
#### C4. `getOverLimitApprover()`：COE 直属上级查询  
  
复用现 `getSecondApproveUser`（L661-690）的组织树模式改造：`ceresManager.queryPersonAndOrgTree(COE 的 ucId)` 取 COE 所在 orgCode 的**父级 orgCode** → `queryByOrgCodeAndWorkType(parentOrgCode, 上级工种)` 查负责人。  
  
> ⚠️ 「COE 上级」的工种编码尚未定版（总设计文档待办项：「工程coe」在 ceres `WorkTypeEnum` 中的确切编码待确认），本文档以 `queryByOrgCodeAndWorkType(parentOrgCode, {待确认工种})` 占位，联调前与服务者中心对齐，作为**开发前置阻塞项**。  
  
#### C5. `buildPackageQuotaButton` 改造  
  
`Objects.equals(apply.getAuditUcId(), ucid)` → 改为查子表：当前用户存在 `auditStatus=待审批` 的明细即展示审批按钮。开关未命中的存量/新增单据无子表记录，回落原单字段判断（同一方法内先查子表、空则回落，天然兼容）。  
  
#### C6. 进展与详情展示  
  
- `buildProcessDTO` / `packageQuotaApplyProcessV2Dao`：会签下每人审批各写一条 process 记录（现有结构支持，无表变更）。  
- 费用单详情接口（`getPackageProblemQuotaList` 等）审批人展示：会签模式下展示两个一级审批人及各自状态，需要 DTO 增加 `auditorList` 字段（`PackageQuotaDTO` 及前端联动，见第四章）。

## 六、边界处理  
  
| 场景 | 行为 |  
|------|------|  
| ES 存量文档无 `dispatchConfirmStatus` 字段 | 排序 `unmapped_type=integer` + `missing=_last` 防御，不报错、排在最后 |  
| ES `dispatchConfirmStatus`=1/2 但 DB `packageSecondStatus` 未刷到 31/32 | VO 以 ES 值映射覆盖返回，保证筛选与展示一致 |  
| ES 命中但 DB 反查无记录 | 沿用现有行为（跳过该 code）；重排 orderMap 用 `getOrDefault(MAX_VALUE)` 防御 |  
| 费用单提交时项目经理或 COE 查询为空 | 阻断提报，抛业务异常，文案："未查询到合作项目经理/安装COE，请联系管理员确认绑定关系"（具体文案与产品确认） |  
| 项目经理与 COE 为同一人 | 子表只写 1 条，单人通过即会签通过 |  
| 超额审批人与 COE 为同一人 | 跳过加签，直接 AUDIT_PASS |  
| 会签中一人已通过、另一人驳回 | 整体 AUDIT_NOT_PASS，已通过明细保留记录，剩余待审批明细置"已终止" |  
| 同一审批人重复提交审批 | 明细状态已非"待审批"则幂等返回，不重复流转 |  
| 开关在途切换 | 审批模式以申请单创建时落库数据为准，开关切换不影响在途单 |

## 十一、上线方案  
  
### 11.1 发布范围  
  
utopia-cube 单服务（api/base/dao/manager/service/start 模块均有改动）；依赖方：派单平台（ES mapping+写入+刷数）、服务者中心（querySuperiorByWorkType 内部改造）、前端精工端。  
  
### 11.2 灰度策略  
  
Apollo 开关按「组织城市+工种」灰度：先单城市单工种（如拆除工先行）验证 → 逐步扩城扩工种。代码可先全量发布，开关不配即零影响。  
  
### 11.3 回滚方案  
  
- 优先开关回滚：清空开关配置，模块 A 不再下发新筛选/排序（ES 字段残留无害）、模块 C 新单回到单审批人流程。  
- 开关回滚后的在途会签单：按落库数据继续会签流转至终态（代码保留双模式兼容，不需数据订正）。  
- 代码回滚：仅当双模式兼容逻辑本身有缺陷时执行；子表为新增表，回滚无 schema 冲突。

## 十三、风险点  
  
| 风险 | 影响 | 缓解措施 |  
|------|------|----------|  
| **R1（最高）**：cube ES 写链路（binlog→`PackageStorageServiceImpl.store()`）对 V1 文档**全量覆写**，DTO 未含 `dispatchConfirmStatus` 时会把派单平台写入的值抹掉 | 筛选/排序失效，状态"闪没" | A1 已将字段加入 `EsPackageConstructionMessageDTO`；需与派单平台明确该字段的**唯一写入方与合并策略**（三方对齐：cube 覆写时是否透传回读值，或派单平台监听覆写后补写），联调必测"cube 触发覆写后字段仍在" |  
| R2：两套编码（0/1/2 vs 31/32）散落多处易写错 | 筛选错乱 | 映射收口到唯一枚举 `DispatchConfirmStatusEnum`，禁止裸数字 |  
| R3：COE 上级工种编码未定版 | 超额加签查不到人 | 开发前置阻塞项，与服务者中心尽早对齐；查不到时置加签失败告警并保持 AUDIT_ADD_SIGN_PROCESS 前置状态可人工介入 |  
| R4：服务者中心改造后返回结构/语义变化（合作关系人员 ucId 体系） | 约工驳回、费用单一级审批人异常 | 联调 checklist（见 3.2）；上线步骤 3 前置 |  
| R5：会签与原单审批人双模式并存，`auditUcId` 语义弱化 | 依赖 auditUcId 的隐性消费方（报表/导出/其他服务查询）判断错误 | 会签模式下 auditUcId 冗余写项目经理保持非空；全仓 grep `auditUcId` 消费点逐一确认 |  
| R6：`selectByPackageCodes` 顺序修复属于行为变更 | 其他复用 `buildUnifiedWorkerTaskVOList` 的入口顺序也会变化 | 重排逻辑仅在 ES 查询入口生效（以 ES code 列表为输入），回归其他列表入口 |  
| R7：`submitQuota` 的 `auditPass=true` 自动通过路径在会签下语义变化 | 该路径调用方可能预期一步到位通过 | 排查该参数的调用来源并与产品确认会签下的预期行为 |
