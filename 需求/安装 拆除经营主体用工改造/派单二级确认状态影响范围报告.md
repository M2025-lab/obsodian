# 安装拆除经营主体用工改造 — 全量影响范围报告  
  
## 改造总览  
  
本期需求包含**三个独立改造模块**，由同一个 Apollo 开关（`install.demolition.worker.reform.switch`，组织城市+工种维度）控制：  
  
| 模块 | 核心变更 | cube 侧改造量 |  
|------|---------|--------------|  
| **A. 派单确认** | 派单新增二级状态（待上级确认→待工人确认），状态同步到 ES，前端新增筛选 | **大** |  
| **B. 约工驳回查上级** | 审批人从组织直属上级改为长期合作关系项目经理 | **无**（服务者中心改造） |  
| **C. 费用单会签审批** | 一级审批由单人改为项目经理+COE 会签；超额时查 COE 直属上级加签 | **中** |  
  
---  
  
## 模块 A：派单确认  
  
### 改造要点  
  
minerva 侧状态流转新增二级状态，通过通知接口告知 cube，cube 反查 minerva 获取 `dispatchConfirmStatus` 后推送到 ES（**不落本地 DB**）。  
  
### 编码体系  
  
| 语义 | ES `dispatchConfirmStatus` | VO `packageDispatchConfirm` | 前端 type=5 valueList |  
|------|---------------------------|-----------------------------|----------------------|  
| 无二级状态 | 0 | — | — |  
| 待接单-待上级确认 | **1** | **2001** | **"2001"** |  
| 待接单-待工人确认 | **2** | **2002** | **"2002"** |  
  
收口枚举：`DispatchConfirmStatusEnum`（es↔vo 转换：1↔2001, 2↔2002）  
  
### 跨系统接口  
  
| 方向 | 定义位置 | 实现位置 | 路径 |  
|------|---------|---------|------|  
| minerva → Cube（通知） | `PackageConstructionFeign` | `PackageConstructionController` | `POST /package/dispatch/changeNotice` |  
| Cube → minerva（反查单条） | `MinervaManager.DispatchStatusFeign`（内嵌） | minerva 侧 | `POST /dispatch/dispatchConfirmStatus/query` |  
| Cube → minerva（反查批量） | 同上 | minerva 侧 | `POST /dispatch/dispatchConfirmStatus/batchQuery` |  
  
### 直接受影响  
  
| 功能 | 改造内容 | 涉及代码 |  
|------|---------|---------|  
| **派单状态通知** | 接收 minerva 通知 → 触发 store() 推 ES | `PackageConstructionController` |  
| **反查派单状态** | Feign 反查 minerva 获取 `dispatchConfirmStatus` | `MinervaManager.DispatchStatusFeign`（内嵌） |  
| **施工包列表（经理视角）** | 新增 type=5 筛选 + packageDispatchConfirm(2001/2002) 返回 + 排序 ASC | `WorkerServiceImpl`、`EsSearchServiceImpl`、`PackageListParam` |  
| **ES 数据同步（store）** | 推 ES 前反查 minerva，合并 dispatchConfirmStatus | `PackageStorageServiceImpl` |  
| **ES DTO** | 新增 dispatchConfirmStatus 字段（读写双端） | `EsPackageConstruction`、`EsPackageConstructionMessageDTO` |  
  
### 间接受影响  
  
| 功能 | 原因 | 风险 |  
|------|------|------|  
| EPX binlog 实时同步 | `store()` 内部新增反查 | 反查失败 catch 不抛异常，ES 缺字段靠 `missing=_last` 防御 |  
| MutationController 手动触发 | 走同一 `store()` 路径 | 同上 |  
| 定时比对修复（EsCompare） | 走同一 `store()` 路径 | 同上 |  
  
### 不受影响  
  
| 功能 | 原因 |  
|------|------|  
| 工人端接单/拒单 | minerva 处理，cube 不干预 |  
| 施工包列表（工人端） | 未修改 `listPackageConstructionByUcId` |  
| `package_construction` / `package_loan_task` | 无 DDL |  
| `DispatchStatusEnum` | 本期不新增值 |

## 模块 B：约工驳回查上级  
  
### 改造要点  
  
约工驳回时，审批人从「组织树直属上级」改为「工人长期合作关系项目经理」。该改造在**服务者中心（ceres）内部完成**，cube **无代码改动**，仅联调验证。  
  
### 直接受影响  
  
| 功能 | 改造内容 |  
|------|---------|  
| **约工驳回申请提报** (`PcReappointServiceImpl.reappointProblemSubmit`) | 调用 `PersonManager.querySuperiorByWorkType()`，服务者中心内部改为返回合作项目经理 |  
| **问题反馈上级查询** (`PcReconstructionServiceImpl` 两处) | 同上，服务者中心覆盖，cube 不改 |  
  
### cube 侧联调验证项  
  
| 验证项 | 说明 |  
|--------|------|  
| 返回结构兼容 | `PersonPositionSimpleDTO` 的 ucId/name 填充与原逻辑一致 |  
| 空结果行为 | 未绑定合作关系时返回空列表，现有阻断文案照常生效 |  
| 目标工种参数 | `targetWorkTypeList` 是否需要追加新工种编码 |

## 模块 C：费用单会签审批  
  
### 改造要点  
  
一级审批由**单人**改为**项目经理 + COE 会签**（两人均通过才算通过）；一级通过后若超额，查 **COE 直属上级**加签。  
  
### 新增/修改的数据  
  
| 对象 | 变更 |  
|------|------|  
| `package_quota_apply_auditor` 表 | **新增**：会签审批人明细表（id, quota_apply_id, package_code, audit_ucid, audit_name, audit_role 1-项目经理/2-COE/3-超额审批, audit_status） |  
| `PackageQuotaApplyAuditorDao` | **新增**：insert / selectByApplyId / updateAuditStatus |  
| `PackageQuotaDTO` | 新增 `auditorList` 字段 |  
| `package_quota_apply` 主表 | **不修改**，`auditUcId` 在会签模式下冗余写项目经理（兼容存量查询） |  
  
### 直接受影响  
  
| 功能 | 改造内容 |  
|------|---------|  
| **费用申请提交** (`submitQuota`) | 命中开关 → 查项目经理 + COE，写 2 条审批明细到子表；未命中 → 原单人逻辑 |  
| **费用申请审批** (`approvalQuota`) | 会签流转：查待审批明细→通过/驳回→双人通过→判超额→加签/完成 |  
| **审批按钮展示** (`buildPackageQuotaButton`) | 改为查子表判断当前用户是否有待审批明细，无子表记录回落原 `auditUcId` 判断 |  
| **超额审批人查询** (`getOverLimitApprover`) | **新增方法**：通过 ceres 组织树查 COE 直属上级 |  
| **COE 查询逻辑**（`getCoeApprover`） | **抽取为独立方法**：原 `getSecondApproveUser` 中的组织树逻辑复用 |  
| **进度与详情展示** | `PackageQuotaDTO` 新增 `auditorList`，前端展示会签进度 |  
  
### 间接受影响  
  
| 功能 | 原因 |  
|------|------|  
| **费用单列表/详情查询** | DTO 新增 `auditorList`，前端需适配展示 |  
| **存量在途费用单** | 升级前创建的单据无子表记录，按原单审批人流程流转至终态，不迁移 |  
| `auditPass=true` 自动通过路径 | 会签模式下仅通过操作人对应的明细，需回归验证调用来源 |  
  
### 不受影响  
  
| 功能 | 原因 |  
|------|------|  
| `validateSecondApproval` 超额判断规则 | 限额配置、二次上门费计数逻辑**不变**，仅调用时机从单人通过后变为会签全部通过后 |  
| 费用单审批接口入参 | 不变，会签下同一单可被两人分别调用 |  
| Apollo `packageProblemQuotaLimitDTOList` | 结构无变更 |

## 开关控制范围  
  
Apollo 开关 `install.demolition.worker.reform.switch`（组织城市+工种维度）：  
  
| 模块 | 命中开关 | 未命中开关 |  
|------|---------|-----------|  
| A. 派单确认 | 下发 type=5 筛选、packageDispatchConfirm、排序新逻辑 | 原列表逻辑不变 |  
| B. 约工驳回 | 服务者中心返回合作项目经理 | 原组织树上级查询 |  
| C. 费用单会签 | submit 写 2 条明细、approval 会签流转 | 原单人审批流程 |  
  
> 注意：**审批模式以申请单创建时落库数据为准**，开关切换不影响在途单。
