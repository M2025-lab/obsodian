# 识别结果接收接口与落库方案（一期）

> 本部分为「接收上游判断结果 → 落库」的落地设计。落点工程：**edar-starlord（主材任务系统）**。
> 数据表：`material_notify_task_automation`（主材通知任务自动化记录表）。
> 原则：**只新增、不更新**；一期仅暂存，不触发通知/任务业务逻辑。

## 1. 接口定义

| 项 | 值 |
| --- | --- |
| 路径 | `POST /api/deduct/task/result` |
| 调用方 | 调度层 → 主材（edar-starlord） |
| 用途 | 接收上游识别结果并暂存 |
| 请求体 | 见下方 `NotifyTaskResultParam` |
| 响应 | `ResultDTO<Void>`，成功返回 `success()` |
| 暴露形式 | **Controller + Feign**（参照 `SupplierMessageSyncFeign` / `SupplierMessageSyncController`） |

接口形式选型：api 模块定义 `@FeignClient("edar-starlord")` 接口，web 模块 Controller 实现之，供调度层 Feign 调用。

## 2. 数据表 DDL（最终版）

```sql
CREATE TABLE `material_notify_task_automation` (
    `id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
    `receive_time` DATE DEFAULT NULL COMMENT '主材接收上游识别结果日期，T的时间基准',
    `project_order_id` BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '项目订单id',
    `material_code` VARCHAR(50) NOT NULL DEFAULT '' COMMENT '品类编码',
    `material_name` VARCHAR(100) NOT NULL DEFAULT '' COMMENT '品类名字',
    `task_type` INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '任务类型',
    `task_name` VARCHAR(64) NOT NULL DEFAULT '' COMMENT '任务类型名称',

    `notify_status` TINYINT NOT NULL DEFAULT 1 COMMENT '通知任务状态：1-未完成通知任务，2-已完成通知任务',

    `judge_result` TINYINT DEFAULT NULL COMMENT '最新系统判定结果：1-任务可通知，2-任务不可通知，3-无法识别是否可通知，4-现场已完成任务需关闭',
    `judge_remark` VARCHAR(1024) DEFAULT NULL COMMENT '判断备注',

    `key_frame_urls` VARCHAR(8192) DEFAULT '' NOT NULL COMMENT '关键帧图片，逗号分隔',

    `recommend_visit_time` DATE DEFAULT NULL COMMENT '最新判定期望上门时间，T+3',

    `gmt_create` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `gmt_modified` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',

    PRIMARY KEY (`id`),
    KEY `idx_receive_time` (`receive_time`),
    KEY `idx_project_task_material` (`project_order_id`, `task_type`, `material_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='主材通知任务自动化记录表';
```

## 3. 字段映射

| 上游字段（我方定义） | 落库字段 | 处理 |
| --- | --- | --- |

| `project_order_id` = `123456789012345678` | `project_order_id` | 直接映射（Long） |
| `material_code` = `"029001001"` | `material_code` | 直接映射 |

| `task_type` = `9060` | `task_type` | 直接映射（Integer） |
| `task_name` = `"通知复尺"` | `task_name` | 直接映射 |
| （无来源） | `notify_status` | **固定写 1**（未完成通知任务，与列默认值一致） |
| `judge_result` = `1`（我方枚举值） | `judge_result` | 直接落库，取值见第 4 节枚举（上游按我方定义直传，**无映射**） |

| — | `recommend_visit_time` | `= receive_time + 3 天`（T+3） |
| — | `gmt_create` / `gmt_modified` | DB 默认值（CURRENT_TIMESTAMP） |

## 4. 判断结果枚举（我方定义，同步上游）

```java
public enum NotifyJudgeResultEnum {

    CAN_NOTIFY(1, "可通知"),

    CANNOT_NOTIFY(2, "不可通知"),

    CANNOT_JUDGE(3, "无法判断"),

    SITE_COMPLETED(4, "现场已完成，任务需关闭");
}
```

> 说明：枚举取值以**我方定义**为准，同步给上游；上游按枚举值**直接传入**（入参 `judge_result` 为 Integer），服务层不做任何字符串映射，直接落库 `judge_result`。

## 6. 逻辑要点

1. **只新增不更新**：每次回调 `insertSelective` 一条新记录，不做 upsert（索引仅 `idx_receive_time`，按接收日期查）。
2. **T+3 计算**：`recommend_visit_time = receive_time + 3 天`（用项目 `DateUtil` / `Calendar` 加天）。
3. **写库路由**：默认走 slave，插库实现参照现有 insert 服务写法（`CallRecordDaoImpl` 未显式 `routeMaster`），实施时验证实际命中 master。
4. **一期仅暂存**：不触发通知、不操作任务状态，仅做接收 + 落库。

## 7. 任务匹配与结果落点（automation → task_dispatch → task_dispatch_node）

### 7.1 匹配链路（上游不传 task_dispatch_id，按 项目+品类+任务类型 反查）

```sql
-- ① 主表定位：项目 + 品类 + 任务类型(=3 复尺) → task_dispatch_id
SELECT d.id
FROM task_dispatch d
WHERE d.project_order_id = ?
  AND d.material_code = ?
  AND d.task_type = 3          -- 复尺
  AND d.process_status = 2     -- 激活未完成
ORDER BY d.gmt_create DESC     -- 取最新（防御「再次复尺」产生多条）
LIMIT 1;

-- ② 节点定位：task_dispatch_id + 通知节点 → node_id（业务结果落 node 表）
SELECT n.id
FROM task_dispatch_node n
WHERE n.task_dispatch_id = ?
  AND n.node_type = 20         -- 通知可启动（通知复尺对应 20，已确认）
  AND n.process_status = 2
  AND n.state = 1
ORDER BY n.gmt_create DESC     -- 取最新（防御 restart 重启后多条通知节点）
LIMIT 1;
```

- `u_task_code` 暂不可用，匹配跳过。
- `executor_id` = 工长 ucid（与 Apollo 开关维度对齐）。

### 7.2 工长维度查询（automation 表为判定源）

**判定源 = `material_notify_task_automation`**（上游识别结果标记：`judge_result=1` 可通知、`notify_status=1` 未完成）。自动化表**无 foreman_id**，工长维度靠 node 表 `executor_id` 收敛工地范围，再回 automation 表取可通知标记，最后匹配到具体 node 任务。

```sql
-- ① 定位该工长全部工地：node 表 executor_id=工长 → project_order_id 集合
SELECT DISTINCT project_order_id
FROM task_dispatch_node
WHERE executor_id = ? AND state = 1;

-- ② 判定源：从 automation 表筛出该工长工地下的「可通知 + 未完成」记录集
--    得到 (project_order_id, material_code, task_type) 待处理集合
SELECT project_order_id, material_code, task_type
FROM material_notify_task_automation
WHERE project_order_id IN (工长工地集合)
  AND judge_result = 1      -- 上游判定可通知
  AND notify_status = 1;    -- 通知任务未完成

-- ③ 记录集逐条两跳匹配，落到具体 task_dispatch_node（见 7.1）
--    最终返回可执行通知的具体 node 任务（node_type=20 且激活未完成）
```

要点：
- **automation 表只提供"哪些任务可通知"的标记**，具体可执行的通知节点仍在 node 表（`node_type=20` + `process_status=2`）。
- 若①返回的工地集合较大，②可用 `idx_project_task_material` 索引命中。

### 7.3 结果落点（一键通知成功后写 node 表）

| 需求 | 落点字段 |
| --- | --- |
| 修改后交界面照片 | `images`（逗号分隔，已存在） |
| 修改后期望上门时间 | `notice_retain_time`（"通知类所用时间字段"，已确认） |
| AI 建议采纳情况 | `ai_adoption_type`（新加） |
| 通知执行方式 | `notify_execute_type`（新加） |

```sql
ALTER TABLE `task_dispatch_node`
    ADD COLUMN `ai_adoption_type` TINYINT DEFAULT NULL
        COMMENT 'AI建议采纳情况：1-采纳，2-未采纳，3-图片采纳，4-上门时间采纳'
        AFTER `qualified`,
    ADD COLUMN `notify_execute_type` TINYINT DEFAULT NULL
        COMMENT '通知执行方式：1-一键通知，2-自动通知，3-系统自动提交'
        AFTER `ai_adoption_type`;
```

### 7.4 并发保护（双层 CAS）

node 表无乐观锁，靠 `process_status` 条件更新，防止重复提交：

```sql
UPDATE task_dispatch_node
SET process_status = 3,            -- 激活未完成 → 激活已完成
    images = ?,                    -- 上传照片
    notice_retain_time = ?,        -- 期望上门时间
    ai_adoption_type = ?,
    notify_execute_type = 1,       -- 一键通知
    end_time = NOW()
WHERE id = ? AND process_status = 2;   -- CAS：affected=1 才成功
```

更新 `task_dispatch` 同理按其 `process_status`/`version` 二次校验。失败（affected=0）即"任务已被其他人处理"，返回给前端。
