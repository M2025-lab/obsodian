# 识别结果接收接口与落库方案（一期）

> 本部分为「接收上游判断结果 → 落库」的落地设计。落点工程：**edar-starlord（主材任务系统）**。
> 数据表：`material_notify_task_automation`（主材通知任务自动化记录表）。
> 原则：**只新增、不更新**；一期仅暂存，不触发通知/任务业务逻辑。

## 1. 接口定义

| 项 | 值 |
| --- | --- |
| 路径 | `POST /api/deduct/task/result` |
| 调用方 | 调度层 → 主材（edar-starlord） |
| 用途 | 接收上游识别结果并暂存 |
| 请求体 | 见下方 `NotifyTaskResultParam` |
| 响应 | `ResultDTO<Void>`，成功返回 `success()` |
| 暴露形式 | **Controller + Feign**（参照 `SupplierMessageSyncFeign` / `SupplierMessageSyncController`） |

接口形式选型：api 模块定义 `@FeignClient("edar-starlord")` 接口，web 模块 Controller 实现之，供调度层 Feign 调用。

## 4. 判断结果枚举（我方定义，同步上游）

```java
public enum NotifyJudgeResultEnum {

    CAN_NOTIFY(1, "可通知"),

    CANNOT_NOTIFY(2, "不可通知"),

    CANNOT_JUDGE(3, "无法判断"),

    SITE_COMPLETED(4, "现场已完成，任务需关闭");
}
```

> 说明：枚举取值以**我方定义**为准，同步给上游；上游按枚举值**直接传入**（入参 `judge_result` 为 Integer），服务层不做任何字符串映射，直接落库 `judge_result`。

## 4.1 task_type 拼接 / 拆分约定（重要）

上游传入的 `task_type` 是一个 **5 位拼接串**：`task_dispatch.task_type`（2 位，左补 0） + 分隔位 `0` + `task_dispatch_node.node_type`（2 位，左补 0）。

- **拆分（读取时）**：`"03020"` → 取前 2 位 `03` → `3`（去前导 0）+ 跳第 3 位分隔符 `0` + 取后 2 位 `20` → `20`。
  - `String type = s.substring(0, 2)`，`String node = s.substring(3, 5)`；`Integer` 解析自动去前导 0：`"03"→3`、`"11"→11`。
  - 示例：`"03020"` → taskType=3(复尺) + nodeType=20(通知可启动)；`"09020"` → taskType=9(预埋件安装) + nodeType=20。
  - 校验：taskType 存在于 `TaskTypeEnum`、nodeType 存在于 `NodeTypeEnum`，非法抛业务异常。
- **拼接（组装时）**：`String.format("%02d%02d", taskType, nodeType)`，如 `(3,20) → "03020"`。
- **边界**：task_type 仅 1-2 位（200/201 等 3 位变更/撤销单不适用，遇非定宽抛异常）；node_type 左补 0 至 2 位（如 `1 → "01"`）。
- **落库不解析**：接收接口直接照存上游原值 `task_type` 字符串；拆/拼只发生在**查询/匹配入口**。
- **工具落点**：service 层 `NotifyTaskTypeUtil`（`parse`/`pack`），改动收敛单点。

## 6. 逻辑要点

1. **只新增不更新**：每次回调 `insertSelective` 一条新记录，不做 upsert（索引仅 `idx_receive_time`，按接收日期查）。
2. **T+3 计算**：`recommend_visit_time = receive_time + 3 天`（用项目 `DateUtil` / `Calendar` 加天）。
3. **写库路由**：默认走 slave，插库实现参照现有 insert 服务写法（`CallRecordDaoImpl` 未显式 `routeMaster`），实施时验证实际命中 master。
4. **一期仅暂存**：不触发通知、不操作任务状态，仅做接收 + 落库。

## 7. 任务匹配与结果落点（automation → task_dispatch → task_dispatch_node）

### 7.1 匹配链路（上游不传 task_dispatch_id，按 项目+品类+任务类型 反查）

```sql
-- ① 主表定位：项目 + 品类 + 任务类型(=3 复尺) → task_dispatch_id
SELECT d.id
FROM task_dispatch d
WHERE d.project_order_id = ?
  AND d.material_code = ?
  AND d.task_type = 3          -- 复尺
  AND d.process_status = 2     -- 激活未完成
ORDER BY d.gmt_create DESC     -- 取最新（防御「再次复尺」产生多条）
LIMIT 1;

-- ② 节点定位：task_dispatch_id + 通知节点 → node_id（业务结果落 node 表）
SELECT n.id
FROM task_dispatch_node n
WHERE n.task_dispatch_id = ?
  AND n.node_type = 20         -- 通知可启动（通知复尺对应 20，已确认）
  AND n.process_status = 2
  AND n.state = 1
ORDER BY n.gmt_create DESC     -- 取最新（防御 restart 重启后多条通知节点）
LIMIT 1;
```

- `u_task_code` 暂不可用，匹配跳过。
- `executor_id` = 工长 ucid（与 Apollo 开关维度对齐）。

### 7.2 工长维度查询（automation 表为判定源）

**判定源 = `material_notify_task_automation`**（上游识别结果标记：`judge_result=1` 可通知、`notify_status=1` 未完成）。自动化表**无 foreman_id**，工长维度靠 node 表 `executor_id` 收敛工地范围，再回 automation 表取可通知标记，最后匹配到具体 node 任务。

```sql
-- ① 定位该工长全部工地：node 表 executor_id=工长 → project_order_id 集合
SELECT DISTINCT project_order_id
FROM task_dispatch_node
WHERE executor_id = ? AND state = 1;

-- ② 判定源：从 automation 表筛出该工长工地下的「可通知 + 未完成」记录集
--    得到 (project_order_id, material_code, task_type) 待处理集合
SELECT project_order_id, material_code, task_type
FROM material_notify_task_automation
WHERE project_order_id IN (工长工地集合)
  AND judge_result = 1      -- 上游判定可通知
  AND notify_status = 1;    -- 通知任务未完成

-- ③ 记录集逐条两跳匹配，落到具体 task_dispatch_node（见 7.1）
--    最终返回可执行通知的具体 node 任务（node_type=20 且激活未完成）
```

要点：
- **automation 表只提供"哪些任务可通知"的标记**，具体可执行的通知节点仍在 node 表（`node_type=20` + `process_status=2`）。
- 若①返回的工地集合较大，②可用 `idx_project_task_material` 索引命中。

    ADD COLUMN `ai_adoption_type` TINYINT DEFAULT NULL

### 7.4 并发保护（双层 CAS）

node 表无乐观锁，靠 `process_status` 条件更新，防止重复提交：

```sql
UPDATE task_dispatch_node
SET process_status = 3,            -- 激活未完成 → 激活已完成
    images = ?,                    -- 上传照片
    notice_retain_time = ?,        -- 期望上门时间
    ai_adoption_type = ?,
    notify_execute_type = 1,       -- 一键通知
    end_time = NOW()
WHERE id = ? AND process_status = 2;   -- CAS：affected=1 才成功
```

更新 `task_dispatch` 同理按其 `process_status`/`version` 二次校验。失败（affected=0）即"任务已被其他人处理"，返回给前端。

## 8. 第二步：批量查询通知任务详情 — batchQueryNotifyTasks（二期）

### 8.1 接口定义

| 项 | 值 |
| --- | --- |
| 路径 | `POST /api/material/notify/task/batch/query` |
| 调用方 | 小师傅 / 首页（前端） |
| 用途 | 查询该工长全部工地下「可通知」与「延期预警」任务详情 |
| 请求体 | `NotifyTaskQueryParam`：仅 `taskType`（原值拼接串，如 `"03020"`，为后续其他通知类型合并预留如 `"09020"`） |
| 工长来源 | `OperatorContextHandler.getContext().getOperator().getUcid()`（web 层取，前后端既有惯例），**不走 body** |
| 响应 | `NotifyTaskBatchQueryVO`：`notifyTasks` + `delayTasks` |
| 暴露形式 | Controller + Feign（参照一期） |

### 8.2 查询主体与判定规则

查询以 **`task_dispatch_node` 表「激活未完成」任务为主体**（不能只查 automation——延期预警含"未经系统判定"的任务，automation 无记录也要露出）；`material_notify_task_automation` **仅补充判定字段**。

| 通知节点状态 | 系统识别结果(automation) | 归组 |
| --- | --- | --- |
| 已完成/未激活/已取消 | 不区分 | 不处理 |
| 激活未完成(process_status=2) | judge_result=1（可通知） | `notifyTasks` |
| 激活未完成 | judge=2（不可通知）/3（无法识别）/无 automation 记录 | `delayTasks`（预警等级由前端按考核时间判断） |
| 激活未完成 | judge=4（现场已完成需关闭） | 本期不返回（另接口） |

### 8.3 查询链路（复用 `listTaskByCondition` 一次 JOIN）

```
入参 executorId（context 取）+ taskType("03020")
  → NotifyTaskTypeUtil.parse → taskType=3 + nodeType=20
  → taskDispatchNodeDao.listTaskByCondition:
       executorId(ucId 转 String)
       + taskTypeList=[3] + nodeTypeList=[20]
       + processStatus=2 + state=1×2（node/task）
  → 一次 JOIN task_dispatch 返回 TaskDispatchDTO
     （含 taskDispatchNodeId/projectOrderId/materialCode/Name/supplierName/platformCheckTime/noticeRetainTime）
  → automation 表按 (project_order_id, material_code, task_type原值) 批量取最新一条
     → 补 judgeResult/judgeReason/keyFrameUrls/recommendVisitTime
  → 内存归组 + 嵌套排序 → 平铺输出两数组
```

### 8.4 分组排序（后端做，只回考核时间）

两数组各自按三级排序键输出（前端按返回顺序直渲即形成分组）：工地(package_order_id) → 品类(material_code) → 组内「`assessmentTime`−当前时间」差值**升序（紧迫任务在前）**。响应仅含 `assessmentTime`（= `platform_check_time`），不放差值。

### 8.5 响应体字段映射

| 响应字段 | 来源 |
| --- | --- |
| projectOrderId | node.project_order_id |
| taskDispatchNodeId | node.id |
| projectAddress | TaskDispatchDTO.projectAddress（无则 ProjectInfo 兜底） |
| materialCode / materialName | task.material_code / material_name |
| supplierName | task.supplier_name |
| taskType | 上游原值（透传） |
