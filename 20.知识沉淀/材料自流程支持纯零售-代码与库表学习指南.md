# 材料自流程支持纯零售 — 代码地图与库表学习指南

> 调研基于 `edar-starlord`（材料域主材任务配置与派发）与 `utopia-cube`（施工包）两个仓库的真实代码，所有路径均带行号。
> 目的：把"材料自流程支持纯零售"技术讨论的 9 项改动，翻译成**「要做的几件事 + 该看哪些代码 + 查了哪些库表 + 表里存什么」**。

---

## 0. 一句话结论（先建立全局认知）

纯零售兼容的本质，是**在 6 条查询 / 生成链路上，把"分公司 + 业务类型"灰度判定出的 `mode` 升到 `7`（DELIVERY_FLOW 排程材料配置）**，从而让这些链路从读**老配置表**（`material_flow_rule*` / `n_material_template_unit`）改为读**排程新配置表**（`delivery_flow_rule*`），并配套把"八合一"老零售配置迁移过来。

理解这一切的钥匙是两个概念：
1. **`ModeEnum`**（业务模式枚举）—— 决定查哪套配置、读哪些表。
2. **`materialScheduleSwitch`（Apollo 灰度开关）** —— 决定某个分公司 + 业务类型 + 项目版本 + 单据类型 + 签单时间是否走排程（mode=7）。

## 2. 必须先懂的两块地基

### 2.1 `ModeEnum`（业务模式枚举）—— 一切分叉的依据
文件：`edar-starlord-base/.../enumeration/ModeEnum.java:14-22`

| value | 名称 | 含义 |
|---|---|---|
| 1 | BW | 北京被窝（老） |
| 2 | SD | HOME2.0 整装（老） |
| 3 | XLS | 新零售（遗留，老表 `mode=3`） |
| 4 | SELF_BUY | 业主自购 |
| 5 | HOME2_5 | 八合一（北京分支） |
| 6 | HOME2_5_MANPOWER | 八合一（全国分支） |
| 7 | DELIVERY_FLOW | **排程材料配置（本次纯零售要统一走的目标 mode）** |

关键判定方法：`isDelivery_Flow_MODE(mode)` → `mode==7`；`isHome2_5(mode)` → `5||6`；`isHome2_5_MODE(mode)` → `6||7`。

### 2.2 "八合一"是什么（设计里反复出现，但代码无此字面表）
推断依据（`ai-memory/项目知识/主材全链路与流程配置体系.md`、`ConfigCompareServiceImpl.java:188-195`、`MaterialFlowRuleQueryServiceImpl.java:336-342`）：
- **八合一 = 老零售配置聚合系统**，对应 **`mode=5`（北京）/ `mode=6`（全国）**，底层是 `material_flow_rule*` 表族 + 一个**外部 OFC 履约配置服务**（`OfcDispatchConfigQueryApi`）。
- "配置后双写同步履约配置侧"的履约侧即 OFC；两个 delivery 接口在 `configFlag=false` 时回退查的正是它。
- 八合一存的是：复尺 / 设计 / 安装 / 送货 等**节点任务（taskType）+ 角色（roleTypes）+ 触发时机 / 激活条件（n_material_node_transfer_condition）+ 激活时间**。

### 2.3 灰度开关 `materialScheduleSwitch`
- 配置注入：`ConfigQueryServiceImpl.java:101-102` `@ApolloJsonValue("${material.schedule.switch:null}") private MaterialScheduleSwitchBo materialScheduleSwitchBo;`
- 数据结构 `MaterialScheduleSwitchBo`：总开关 `enable` + `rules[]`，每条 rule 含：
  - `branchCompanyCodes`（分公司白名单）、`saleTypes`（业务类型 = 订单 decorateType）、`projectVersions`（项目版本）、`documentTypes`/`dispatchDocumentTypes`（单据类型）、`signTime`（正签时间阈值）、`projectOrderIds`（按单号白名单）。
- 判定逻辑 `materialScheduleSwitch(param, isDispatchDocument)`（`ConfigQueryServiceImpl.java:628-721`）：
  1. 取订单（`projectOrderManager.getByProjectOrderId`，优先读 Redis `order_info:<id>`）→ 得 `branchOfficeCode` / `saleType(decorateType)` / `projectVersion` / `signDate`。
  2. 遍历 rules：单据类型匹配 + （项目单号命中 **或** 分公司 ⊇ 订单分公司 且 业务类型 ⊇ 订单业务类型 且 版本 ⊇ 项目版本 且 签单时间达标）→ 命中返回 true。
- **这就是设计里说的"分公司 + 业务类型灰度"的核心实现**，6 个链路都靠它把 mode 升到 7。

## 3. 代码地图：6 条链路逐个看（先外后内）

### 3.1 中控 install-role/list（画像 E）
- 入口：`TaskTemplateFeign.java:46` → `TaskTemplateController.java:145` `#queryMaterialInstallRole` → `TaskTemplateRoleService#queryMaterialInstallRole`。
- 核心灰度方法：`TaskTemplateRoleServiceImpl.java:470-511` `#getTaskMode(projectOrderId, projectBusiness, mdmCode)`。
  - 判定优先级：`RETAIL_2_0`/`WHOLE_2_0` → `HOME2_5(5)`；`materialScheduleSwitch` 命中 → `DELIVERY_FLOW(7)`；`isBeijing(mdmCode)` → `HOME2_5(5)`；其余 2.5 各业务类型 → `HOME2_5_MANPOWER(6)`。
  - ⚠️ **当前 `RETAIL_2_0` 被硬编码为 mode=5 且在排程开关判断之前 return**，即 2.0 零售永远不走排程——这是纯零售改造要动的点。
- 调用方：`queryInstallRoleFromTaskTemplate`（`:216-364`，第 263 行调 `getTaskMode`），结果经 `queryInstallRole` → `taskTemplateService.listAll` 读配置。
- 读取的表：`n_material_template_unit`（按 mode + mdm_code + sale_type 查）+ `n_material_process_define`（节点角色从 START 节点的 `roleTypeList` 取）。mode=7 时改走 `delivery_flow_rule*`。

### 3.2 材料配置查询 list-all / list-all-compatibility（画像 F）
- 入口：`TaskTemplateFeign.java:39/43` → `TaskTemplateController.java:92/101` → `TaskTemplateServiceImpl#listAll`（`:1109`）。
- 设计点名方法：`TaskTemplateServiceImpl.java:1136-1192` `#convert2NMaterialTemplateUnitParam`。
  - **重要发现：该方法当前并没有"分公司+业务类型"灰度分支**！它只是把 `ListTemplateParam` 的 `mode` 直接透传（`unitParam.setMode(listTaskParam.getMode())`），唯一自动改 mode 的逻辑是 `processCode` 的 templateId 段长度 > 10 时强制 `DELIVERY_FLOW`。
  - 真正的灰度在调用方 `TaskTemplateController#resolveMode`（`:228-258`）：它综合 `materialScheduleSwitch` + `ProjectOrderUtil.isNewV2_5/isBeijing` + 精装全案判定，先解析出 mode，再传给 `listAll`。
- `listAll` 分叉：`mode==7` → `buildDeliveryFlowTaskTemplateDTO`（读 `delivery_flow_rule*`）；否则 `nMaterialTemplateUnitDao.selectMaterialTemplateUnitInfo`（读 `n_material_template_unit` LEFT JOIN `n_material_process_define`）。
- `list-all-compatibility` 与 `list-all` SQL 完全相同，区别仅在返回前对 `mode=5` 做旧前端枚举/角色结构兼容转换（节点类型映射、工种、北京供应商兜底）。**不是零售灰度分支**。
- 读取的表：`n_material_template_unit`、`n_material_process_define`、`n_material_node_cfg`（mode=7 时加 `delivery_flow_rule_unit` / `delivery_flow_rule_category`）。

### 3.3 主材任务生成 buildCondition（画像 G - 接口单任务）
- 入口：`ScmMeasureApplyServiceImpl#createTask` → `configQueryService.materialScheduleSwitch` 决定 supportMode → 新逻辑 `MaterialCreateV2ServiceImpl#execCreateMaterialProcess`（`:760`）。
- 核心方法：`MaterialCreateV2ServiceImpl.java:644-708` `#buildCondition`。
  - `mode` 直接来自 `context.getSupportMode()`（`:678`），**本身不做灰度**；灰度在更上层（同类的 supportMode 设置处，以及 `createByDelivery`）。
  - `saleType`/`documentType` 由 `getSaleTypeFromProjectOrder`（`:716-756`）推导；**关键：当 `projectOrder == null`（纯零售/货单无项目单）时直接返回 `SaleTypeEnum.RETAIL` + `RETAIL_REGULAR_SD_RETAIL_ORDER` 单据类型**——这是纯零售兼容的入口分支。
  - 触发时机排序后 `queryAllMaterialForm(condition)` 按 `isDelivery_Flow_MODE` 分叉：`mode==7` → `queryDeliveryFlowFormByUnit`（读 `delivery_flow_rule*`），否则 `queryAllMaterialFormByUnit`（读 `n_material_template_unit`）。
- 写入：任务落 `task_dispatch`（`taskDispatch.setMode(materialForm.getMode())`，`:1019`）+ `task_dispatch_node`。

### 3.4 货单触发 createByDelivery（画像 G - 货单）
- 文件：`DeliveryMaterialBizServiceImpl.java:113-230` `#createByDelivery`。
- mode 判定（`:186-194`）：默认 `HOME2_5(5)` → 非北京则 `HOME2_5_MANPOWER(6)` → 若 `materialScheduleSwitch(projectOrderId)` 命中则 `DELIVERY_FLOW(7)`。
- `mdmCode` 优先取项目订单的 officeCode（`ProjectOrderUtil.getOfficeCode`），`materialCode` 取货单前台品类 `splitFrontCategoryId`，`supplierCode` 取货单 `supplierId`。
- 之后调 `materialCreateV2Service.createMaterialTask` 进入 3.3 的 `queryDeliveryFlowFormByUnit` 分支。

### 3.5 施工包 queryAndChooseTemplate（画像 G - 施工包，在 utopia-cube 仓库！）
- **文件在同级仓库**：`/Users/mirror/IdeaProjects/utopia-cube/utopia-cube-service/.../cube/service/v2/impl/PcCreateServiceImpl.java:1459-1524`。
- mode / cfgType 三段式（`:1463-1487`）：
  1. 默认 `mode=6(HOME2_5_MANPOWER)`，`cfgType=2(CITY=北京)`，`saleType=businessType.getSaleType()` → **查北京**。
  2. 查全国分支（`:1466-1474`）：有订单且 `!isNewV2_5`（圣都2.0/团装/翻新等）且非（零售+精装全案）→ `mode=5`、`cfgType=null`、`saleType=null` → **查全国**（底层 SQL `cfg_type`/`sale_type` 过滤被省略 + `supplier_code` 含 `'9999999'` 全国标记）。
  3. 排程覆盖（`:1477-1482`）：`materialDeliveryFlowSwitch(projectOrderId)` 命中 → `mode=7`，并取 `deliveryProcessCfgId`。
- 经 Feign `taskTemplateFeign.listAllCompatibility` 调 edar-starlord 读 `n_material_template_unit`（mode=7 时读 `delivery_flow_rule*`）。
- ⚠️ **设计点"把查询全国的进行切换，只留下北京零售查询" = 改写/移除第 2 段（1466-1474）的查全国分支**。但当前代码里"无订单、精装全案零售"实际走的是默认=查北京，与设计规则文字（无订单→查全国、精装全案→查全国）不一致，需评审确认语义。

### 3.6 主材申请单 / 货 查询接口（画像 D）
- 入口：`CategoryProcessFeign.java:58/66` → `CategoryProcessController.java:94/99` → `ConfigQueryServiceImpl`：
  - 货：`queryConfigOFCList`（`:240-262`）
  - 主材申请单：`queryCategoryConfigOFCList`（`:264-306`）
- 逻辑都是 `configFlag` 二分支：
  - `true`（默认）→ 查**排程**配置：`deliveryFlowRuleDao.matchConfigByParam(...)` 读 `delivery_flow_rule*` + `materialConfigV2Service.queryProcessDefineV2` 读 `n_material_process_define`。

- 读取的表：`delivery_flow_rule` / `delivery_flow_rule_unit` / `delivery_flow_rule_category` + `n_material_process_define`（排程侧）；回退时查外部 OFC。

## 4. 涉及的数据库与存储的数据（核心交付）

### 4.1 排程材料配置（mode=7，本次目标表）

| 表 | 关键字段 | 存什么 |
|---|---|---|
| `delivery_flow_rule` | id, `delivery_process_cfg_id`(→外部排程流程配置), state | 排程规则头，关联一个排程流程配置 |
| `delivery_flow_rule_unit` | rule_id, `project_version`(2.5), `sale_type`(1整装/2零售), `document_type`, `mdm_company_code`(分公司), `product_combo_id`, gb_code | **主匹配维度**：分公司+版本+单据类型+销售类型+套餐+国标码 |
| `delivery_flow_rule_category` | rule_id, `category_id`, `material_code`, `supplier_code`, `node_process`/`node_process_name`, `delivery_template_id`(→外部施工包模板), state | **最细粒度**：品类+材料+供应商+节点流程，指向施工包模板 |

### 4.2 八合一配置（mode=5/6，迁移源）

| 表 | 关键字段 | 存什么 |
|---|---|---|
| `material_flow_rule` | id, is_default | 八合一规则头 |

| `material_flow_rule_template_mapping` | rule_category_id, `n_template_code`(老 NMaterial 模板), task_type | **八合一→老模板桥接**，复用 `n_material_process_define` |

### 4.3 老配置共享流程定义（所有 mode 共用）

| 表 | 关键字段 | 存什么 |
|---|---|---|
| `n_material_template` | id, sale_type, work_type, range_type | 流程模板头 |
| `n_material_template_unit` | `mode`, `mdm_code`, `material_code`, `supplier_code`, `sale_type`, `cfg_type`, `product_combo_id`, template_id | **按 分公司+套餐+材料+供应商+销售类型+mode 归属单元**（老配置主表，mode=3 即新零售遗留） |
| `n_material_process_define` | `template_id`, `process_code`, `task_type`, `source_type`, `delivery_type`, `work_type` | 模板下每个任务类型对应一条流程定义（复尺/设计/安装/送货等） |

| `n_material_node_transfer_condition` | node_id, `condition_type`/`condition_mode`/`relation_code`/`schedule_relation`/`duration`/`duration_type` | 节点流转的**触发时机/激活条件** |
| `n_material_define` | product_combo_id, material_code, supplier_code, task_type, process_code | "套餐+材料+供应商 → 要生成哪些任务"的定义 |
| `n_material_route` | type, process_code, source_code/target_code, rule_expression | 流程间前置/后置依赖路由 |

### 4.4 运行时表（配置驱动生成）

| 表 | 关键字段 | 存什么 |
|---|---|---|
| `task_dispatch` | `mode`, task_type, material_code, supplier_code, sale_type, mdm_code, project_order_id, process_code | 主材任务实例（mode 由 `materialForm.getMode()` 写入） |
| `task_dispatch_node` | task_dispatch_id, node_type, process_status, start/end_time, executor_* | 任务节点实例（节点类型/激活规则来自 `n_material_node_cfg`/`task_cfg`） |
| `material_notify_task_automation` | project_order_id, material_code, task_type, judge_result, recognize_time | 主材通知 AI 识别/自动化判定记录 |

> 关联要点：**八合一(mode=6) 与 排程(mode=7) 的品类层最终都回指 `n_material_process_define`**——即"新配置管匹配维度，老配置管流程内容"。`delivery_flow_rule_category.category_id` 直接作为 `n_material_process_define.template_id` 查流程定义。

## 5. 建议的学习顺序（怎么掌握这套东西）

## 6. 调研发现的 3 个"设计与代码不一致 / 待确认"点（务必关注）
