# 📚 功能开关位置写在循环外导致工程部配置不生效

> **踩坑对象**：配置功能开关（城市项目经理白名单 + 工程部配置）
> **一句话结论**：开关判断写在了**整体循环之外**，只对"第一个任务"判了一次——第一个任务若不属于该工程部就直接判空返回，导致后续任务根本没机会走到开关，工程部配置看起来"不生效"。
> **沉淀日期**：2026-08-26
> **关联笔记**：[[📚 批量List接口@Valid校验失效排查与解决方案]]（同样是"批量/循环里只有第一项被处理"的家族坑）、[[📚 Spring事务失效排查手册]]

## 1. 问题现象

功能开关的配置维度有两路：

- **城市项目经理白名单**：按城市项目经理粒度配置；
- **工程部配置**：按工程部粒度配置。

预期：任务归属某个工程部时，走工程部配置这一路开关判定是否生效。

实际：**工程部配置不生效**——开关始终表现为"没开"，工程部维度配置的任务全部被跳过。但城市项目经理白名单这一路是正常的。

更诡异的是：

- **本地测试无法复现**——本地怎么测都正常；
- **预发环境也能正确拿到完整的项目信息、工程部信息**，且工程部信息内容正确（排除了上下游信息没对齐）；
- 真正的工程部数据是对的、开关配置也是对的、入参链路也没丢字段，可开关就是"不生效"。

一句话：**数据全对、配置全对、链路全对，但开关不生效，且只在特定任务顺序/预发环境复现。**

## 2. 排查过程（时间线）

| 步骤 | 检查项 | 结论 |
|---|---|---|
| ① | 上下游信息是否对齐（项目、工程部是否拿得到、内容是否正确） | 预发上**能正确拿到完整项目信息和工程部**，工程部信息内容正确 ✅ 排除链路丢字段 |
| ② | 本地复现 | **本地无法复现**——本地数据/任务顺序恰好命中"第一个任务属于该工程部"，所以一直正常 |
| ③ | 开关逻辑本身是否有 bug | 逐行梳理开关判定逻辑，**逻辑本身没问题** ✅ |
| ④ | 开关**所在位置**（决定性转折） | 发现开关判断写在**整体循环之外**——循环只跑了一次开关，且取的是"第一个任务"的工程部 |
| ⑤ | 结合预发任务顺序验证 | 预发上**第一个任务不属于该工程部** → 开关直接判空返回 → 后续任务再也不会走到工程部开关 → 表现为"工程部配置不生效" |

### 2.1 为什么本地不复现、预发才复现

这是这类 bug 最迷惑的地方——**它是数据顺序敏感的**：

- 本地测试数据少、顺序可控，碰巧第一个任务就属于该工程部，开关只判一次也能判中 → 表现"正常"；
- 预发数据量大、顺序接近生产，第一个任务很可能不属于该工程部 → 开关判空直接返回 → 表现"不生效"。

**根因不在开关逻辑，而在开关位置**：开关被放在了循环外，本质上退化成了"只判定第一个任务"。

## 3. 根因分析

### 3.1 问题代码结构（开关在循环外）

出问题的代码骨架长这样——开关判断和循环**位置写反了**：

```java
// ❌ 开关判断在循环外，只对"第一个任务/任意一个固定任务"判定了一次
List<Task> tasks = ...;              // 待处理任务集合
String engDept = tasks.get(0).getEngDept();   // 取了第一个任务的工程部

// 开关判断 —— 在循环之外！
if (开关生效(engDept)) {
    // 工程部配置才生效
} else {
    // 直接判空 / 跳过
    return;   // ← 第一个任务不属于该工程部，直接 return，后续任务全没机会
}

// 下面才是遍历每个任务的处理
for (Task task : tasks) {
    process(task);
}
```

关键点：**开关判断拿的是 `tasks.get(0)` 的工程部**，且判断之后直接 `return`/`continue`。一旦第一个任务不属于目标工程部，整个工程部开关就被判空跳过，后面 `for` 循环里的任务**根本不会再到工程部开关这一步**。

### 3.2 正确结构（开关在循环内 / 每个任务各自判）

```java
// ✅ 开关判断放进循环内，每个任务各自判定
List<Task> tasks = ...;

for (Task task : tasks) {
    String engDept = task.getEngDept();          // 每个任务各自的工程部
    if (!开关生效(engDept)) {
        continue;   // 这个任务不开，跳过它，但不影响下一个任务
    }
    process(task);  // 工程部开关对该任务生效才处理
}
```

区别只有一行位置，但语义完全不同：

```text
❌ 循环外判定：  开关 ──► 取第一个任务的工程部 ──► 不中则直接 return ──► 循环(不执行)
✅ 循环内判定：  for 每个任务 ──► 取该任务的工程部 ──► 不中则 continue 下一个 ──► 中则处理
```

### 3.3 为什么"数据全对、配置全对、链路全对"却还是不生效

排查时一度怀疑链路：

- 项目信息 ✅ 拿到了
- 工程部 ✅ 拿到了，且内容正确
- 开关配置 ✅ 配的是对的

但这些都只验证了"**输入正确**"。真正的问题在**控制流**——开关判定和循环的相对位置决定了"哪些任务有机会被开关判定"：

- 开关在循环外 → 只有第一个任务参与判定 → 预发第一个任务不中 → 整组任务被 `return`/判空 → 表现"不生效"；
- 开关在循环内 → 每个任务都参与判定 → 该中的中、不该中的跳过 → 正常生效。

**所以这不是数据问题、不是配置问题、也不是开关逻辑问题，而是"开关放错了位置"的控制流问题。** 数据和配置再正确，也救不了一个压根没被执行到的开关。

### 3.4 链路流程图

```text
            ┌─────────────────────────────────────────┐
            │   tasks = [A(工程部X), B(工程部Y), C(工程部X)]   │
            └─────────────────────────────────────────┘
                                  │
        ┌─────────────────────────┴──────────────────────────┐
        ▼  (❌ 旧：开关在循环外)                              ▼  (✅ 新：开关在循环内)
  取 tasks[0] = A, engDept = X                      for task in tasks:
  开关生效(X)?                                          开关生效(task.engDept)?
        │                                                    │
   不中 ─┤ 中                                                ├─ A: 中 → 处理
        │                                                    ├─ B: 不中 → continue
   直接 return                                              └─ C: 中 → 处理
   (B、C 再也没机会)                                          (每个任务各自判定)
        │
   工程部配置"不生效"
```

### 3.5 生活比喻

把开关判断比作**门卫查包**，一批人（任务）排队进门：

- **开关在循环外** = 门卫只查了**队伍最前面那一个人**的包，发现他没带工牌，直接把门关了——后面排着的人不管带没带工牌，**全进不来**。
- **开关在循环内** = 门卫站在门口，**每个人进来都查一次包**——没工牌的拦下让他走，有工牌的放行，各自判断、互不影响。

工程部配置就是"工牌"，第一个任务恰好没带工牌，于是门卫关门，后面带工牌的也被挡在门外——看起来像"工牌（工程部配置）不生效"，其实工牌一点问题都没有，是门卫站错了位置、且查完就关门。

## 4. 解决方案

核心动作只有一句：**把开关判断从循环外挪进循环内，让每个任务各自判定。**

### 4.1 改造前后对照

```java
// ❌ 改造前：开关在循环外，只判第一个任务
String engDept = tasks.get(0).getEngDept();
if (!开关生效(engDept)) {
    return;   // 第一个任务不中 → 整组跳过 → 工程部配置"不生效"
}
for (Task task : tasks) {
    process(task);
}

// ✅ 改造后：开关在循环内，每个任务各自判
for (Task task : tasks) {
    if (!开关生效(task.getEngDept())) {
        continue;   // 这个任务不中 → 只跳过它，不影响下一个
    }
    process(task);
}
```

### 4.2 方案选型

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| ① 开关内移（最终采用） | 开关判断放进 `for` 循环内，每个任务各自取工程部、各自判定 | 改动最小、语义清晰、彻底解决 | 需要逐个任务查开关，开关查询可能被调多次（见 §4.3 优化） |
| ② 循环外预聚合工程部集合 | 先收集 `tasks` 里所有 `engDept` 去重，一次性查开关得到生效集合，循环里只做集合 `contains` | 开关只查一次、性能好 | 只在"开关查询成本高"时才值得引入，平时增加复杂度 |
| ③ 把开关判断包进单任务处理方法 | `process(task)` 内部自己判开关，循环只负责遍历 | 职责内聚，循环体干净 | 改动面稍大，需确认所有调用 `process` 的入口都该带开关 |

> 本次采用方案 ①：直接把开关挪进循环内、改为 `continue`。工程部开关查询本身是内存级判定，性能不敏感，没必要上方案 ② 的预聚合。

### 4.3 如果开关查询有外部调用（性能兜底）

若"开关生效(engDept)"内部是 Apollo 配置查询 / RPC / DB 查询，循环内逐个调用会被放大成 N 次 IO。此时用方案 ② 预聚合：

```java
// 一次性查出本批任务涉及的所有工程部开关，循环里只 contains
Set<String> engDepts = tasks.stream()
        .map(Task::getEngDept)
        .collect(Collectors.toSet());
Set<String> enabledDepts = 开关批量查询(engDepts);   // 一次 IO

for (Task task : tasks) {
    if (!enabledDepts.contains(task.getEngDept())) {
        continue;
    }
    process(task);
}
```

判定仍然是"每个任务各自判"，只是把开关查询从循环里提出来批量化——**位置语义没变，只是优化了查询次数**。

### 4.4 防回归：为什么本地测试要覆盖"第一个任务不命中"的场景

这个 bug 之所以能溜到预发，根因是**本地测试数据恰好让第一个任务命中**。防回归要点：

- 本地/单测构造数据时，**故意把目标工程部的任务排在第二个或更靠后**，第一个任务放一个不命中的工程部；
- 不要只用"全部命中"的 happy-path 数据自测——顺序敏感的 bug 会被 happy-path 永远掩盖；
- 预发验证时关注"第一个任务不中"的真实数据顺序，而不是本地精心构造的顺序。

## 5. 易混淆点

### 5.1 "开关不生效" vs "开关没开" vs "开关位置错"

| 现象 | 含义 | 本 bug 属于？ |
|---|---|---|
| 开关没开 | 配置上就是关的，行为正确 | ❌ 不是（配置是对的、是开的） |
| 开关不生效 | 配置开着，但代码没走到这个开关 | ✅ 就是这个 |
| 开关逻辑错 | 开关判定逻辑本身写错了 | ❌ 不是（逻辑本身没问题） |

**关键区分**：本 bug 的开关配置是开的、开关逻辑也是对的，但开关**放错了位置导致没被执行到**。排查时容易被"配置对、逻辑对"带偏，去查数据和逻辑，而忽略控制流位置。

### 5.2 `return` vs `continue` 在循环里的语义差异

| 关键字 | 在循环内的效果 | 用错后果 |
|---|---|---|
| `return` | 直接退出整个方法，**后续任务全部不执行** | 把开关不命中误写成 `return`，会变成"一个不中、全组陪葬" |
| `continue` | 只跳过当前任务，**继续下一个** | 开关"对单个任务不生效"的正确语义 |

> 本 bug 的根因之一就是把开关不命中处理成了"判空直接返回"，等价于 `return` 语义。挪进循环后必须用 `continue`，否则位置改了语义还是错的。

### 5.3 和 [[📚 批量List接口@Valid校验失效排查与解决方案]] 的家族共性

| 维度 | @Valid 批量校验失效 | 本次：开关在循环外 |
|---|---|---|
| 表象 | List 里的元素校验"没生效" | 工程部开关"没生效" |
| 根因 | `@Valid` 标在 List 根对象上，HV **不级联到元素** | 开关判断写在循环外，**不遍历每个任务** |
| 本质 | 批量结构里只有"根/第一个"被处理，其余被静默跳过 | 同左——**家族病：批量场景里只有一个元素被照顾到** |
| 排查盲区 | 以为是 Spring/HV 的 bug | 以为是数据/配置/链路的问题 |

**家族口诀**：凡是"批量"场景出现"看起来只有第一个生效、其余静默"的现象，第一反应去查——**这个判定到底是"对每个元素做"，还是"对集合做了一次"？**

### 5.4 本地不复现的常见陷阱

| 陷阱 | 本 bug 是否命中 |
|---|---|
| 数据量小，happy-path 掩盖边界 | ✅ 本地任务少、第一个恰好命中 |
| 顺序敏感，本地顺序和生产不同 | ✅ 本地第一个命中，预发第一个不命中 |
| 缓存/配置未刷新 | ❌ 排查时一度怀疑，但 Apollo 配置是对的 |
| 环境差异（JVM/依赖版本） | ❌ 与环境无关，纯控制流问题 |

**教训**：本地不复现 ≠ 没问题。当现象是"顺序/数据量相关"时，优先怀疑控制流里的"只处理一次"陷阱，而不是环境差异。

## 6. 生活比喻

把任务集合想象成**一筐要过安检的快递包裹**，工程部开关就是"这个包裹属于哪个工程部、要不要走加急通道"的检查：

- **开关在循环外（出 bug 的写法）** = 安检员从筐里**只拎出最上面那个包裹**看了一眼，发现它不属于加急工程部，于是**把整筐包裹都判空退回了**——筐里其他属于加急的包裹压根没被翻到。你看着加急通道没人走，以为是"加急配置（工程部配置）没生效"，其实是安检员**只看了第一个就下班了**。
- **开关在循环内（正确写法）** = 安检员**一个一个包裹地翻**，每个都看一眼工程部——该走加急的走加急，不该走的放普通通道，互不影响。加急配置是不是生效，每个包裹都能验证到。

核心：**不是配置没用，是检查没轮到。** 门卫只看了第一个就关门，后面的人再怎么带工牌也进不来。

## 7. 一句话记忆

> **开关要跟着循环走，别在门外只看第一个就关门。**

- **现象**：工程部配置"不生效"，但数据、配置、链路全对；本地不复现，预发才复现。
- **根因**：开关判断写在整体循环之外，只对第一个任务判了一次——第一个任务不中就判空返回，后续任务再没机会走到开关。
- **陷阱**：被"配置对、逻辑对、链路对"带偏去查数据，忽略了**控制流位置**；本地 happy-path 的任务顺序掩盖了 bug。
- **定位要点**：批量场景出现"只有第一个生效、其余静默"，立刻去查这个判定是**对每个元素做**还是**对集合做了一次**——开关/校验/过滤都要进循环，不命中用 `continue` 不是 `return`。
