# 📚 上线发布流程 SOP 与注意事项

> **沉淀对象**：master 分支上线发布流程（maven 构建 → git MR → 构建 master → 上线计划 → 灰度部署 → 全量发布）
> **一句话结论**：上线走"构建 → MR → 上线计划 → 灰度 1 台 → 全量 2~3 台"五步闭环；查询接口参数 < 3 一律用 GET；每次全量只推 2~3 台，避免瞬时负载打满造成读超时；部署前必看 Apollo。
> **沉淀日期**：2026-08-31
> **关联笔记**：[[📚 Apollo配置JSON注入Map启动失败]]（上线前 Apollo 检查项）、[[📚 Spring事务失效排查手册]]

## 1. 上线全流程总览

一条 master 上线链路，从改代码到全量生效，一共 **五个阶段**，前一步过了再进下一步，绝不跳步：

```text
┌──────────┐   ┌───────────┐   ┌──────────┐   ┌────────────┐   ┌─────────────┐
│ ① 构建    │──►│ ② git MR  │──►│ ③ 上线   │──►│ ④ 灰度部署  │──►│ ⑤ 全量发布   │
│ api+base │   │ 合并 master│   │  计划    │   │ 1 台试水   │   │ 每次 2~3 台  │
└──────────┘   └───────────┘   └──────────┘   └────────────┘   └─────────────┘
      ▲                                                                          │
      │                       Apollo 检查贯穿始终                                │
      └──────────────────────────────────────────────────────────────────────────┘
```

| 阶段       | 动作                           | 关键产物 / 校验点        | 不做的后果              |
| -------- | ---------------------------- | ----------------- | ------------------ |
| ① 构建     | maven 构建 `api` + `base` 两个模块 | 产物 jar            | 产物没出齐，后面构建不到最新代码   |
| ② git MR | 创建合并到 `master` 的合并请求         | master 分支含本次改动    | 上线计划选不到正确 master   |
| ③ 上线计划   | 填写 git 信息，创建上线计划             | 一条带 master 版本号的计划 | 无计划，工作负载无法选目标构建    |
| ④ 灰度部署   | 工作负载选 master 构建，**灰度 1 台**   | 1 台实例跑新版本         | 直接全量，异常无缓冲、无观测窗口   |
| ⑤ 全量发布   | 分批全量，**每次 2~3 台**            | 全量实例完成            | 一次推太多 → 负载打满 → 读超时 |

## 2. 分步操作手册

### 2.1 阶段一：maven 构建 api + base

**目标**：把本次改动编译成可部署的产物，`api`（对外接口/契约模块）和 `base`（基础/业务实现模块）都要构建。

```bash
# 在项目根目录下，按模块顺序构建（先 api 再 base，base 依赖 api）
mvn clean install -pl api -am          # 构建 api，并带上其依赖
mvn clean install -pl base -am         # 构建 base
# 或一次性把两者都带起来：
mvn clean install -pl api,base -am
```

**校验点**：

- 两个模块都 `BUILD SUCCESS`，无编译错误、无测试失败；
- 本地 `target/` 下确实产出了新的 jar；
- 如果 `api` 改了接口签名/契约，`base` 必须用**新构建的 api** 重新编译，不能跑老 api 的依赖——否则 master 分支构建出来的还是旧契约。

> 坑：只构建 `base` 忘了构建 `api`，CI/工作负载拉到的是老 api jar，接口对不上，运行期才报 `NoSuchMethodError` / `ClassNotFoundException`。

### 2.2 阶段二：git 创建 master 合并请求

**目标**：把开发分支合并到 `master`，走 MR（Merge Request）评审。

- 在 git 平台创建**目标分支为 `master`** 的合并请求；
- 确认 diff 只含本次上线改动，没有夹带无关提交；
- MR 评审通过、合并入 master 后，**记下这次 master 的 commit / 构建号**，下一步上线计划要填。

**校验点**：

- master 已包含本次改动（`git log origin/master` 看到合并提交）；
- master 上 CI 跑过、绿了；
- 如果 master 有别人的新提交，先确认没有冲突 / 没有互相覆盖的配置改动。

### 2.3 阶段三：创建上线计划（填写 git）

**目标**：在发布平台创建一条上线计划，绑定到刚才的 master。

- 新建上线计划；
- **填写 git 信息**：分支选 `master`、commit / 构建号选 2.2 记下的那次；
- 确认计划关联的应用、环境正确（预发 / 生产别选错）。

**校验点**：

- 计划里指向的 master 构建确实是本次改动的那次，不是更早的旧构建；
- 计划状态进入"待部署"，工作负载里能选到这个构建。

### 2.4 阶段四：工作负载灰度部署（1 台）

**目标**：去工作负载，选目标构建的 master，先灰度 **1 台**试水。

- 工作负载 → 选 2.3 上线计划对应的 master 构建；
- 部署策略选**灰度发布**，灰度实例数 = **1**；
- 触发部署，等这 1 台拉起新版本。

**灰度期要观测（这是上线最关键的窗口）**：

| 观测项 | 怎么看 | 异常处理 |
|---|---|---|
| 进程是否存活 | 实例健康检查 / 启动日志无报错 | 启动失败立即回滚这 1 台 |
| 接口是否正常 | 核心接口 RT、错误率 | 错误率抬升 → 回滚 |
| 日志有无新异常 | ERROR 日志、Apollo 加载日志 | 出现新异常 → 排查，必要时回滚 |
| Apollo 配置是否生效 | 业务日志里确认拿到的是新配置值 | 没生效 → 先查 Apollo，别继续全量 |

> 灰度这 1 台至少观察一个完整业务周期（一次流量高峰或定时任务一轮），别刚起来就急着全量。

### 2.5 阶段五：全量发布（每次 2~3 台）

**目标**：灰度无异常后，分批全量，**每批 2~3 台**，直到全部实例更新完成。

- 工作负载 → 全量发布；
- 单次推进实例数控制在 **2~3 台**；
- 每推一批，观察一批（RT、错误率、日志），无异常再推下一批；
- 重复直到全量实例更新到 master。

**为什么是 2~3 台而不是一次推完**：

- 一次全量推完，新版本实例同时承接流量，**瞬时负载集中**，DB / 缓存 / 下游 RPC 压力陡增；
- 请求堆积 → 线程池打满 → **读超时**（数据库连接等待、下游调用超时）；
- 分批 2~3 台，让负载平滑过渡，给下游留出适应时间，也给自己留出"推一批发现问题就停"的窗口。

**校验点**：

- 每批推完后实例全部 Ready，无 OOM / 重启；
- 全量完成后，所有实例版本号 = master 构建版本；
- 关键指标（RT、错误率、告警）回归基线。

## 3. 注意事项与发布规范

### 3.1 查询类接口：参数 < 3 一律用 GET

这是本次沉淀的一条**代码规范**，在阶段一构建前就要落实：

- **查询类逻辑**（只读、不改动状态），入参**小于三个**时，做成 `GET` 接口；
- 参数 ≥ 3 或参数体过大、有复杂对象时，才考虑 `POST` + body。

**为什么这么定**：

| 维度 | GET（参数 < 3 时） | POST |
|---|---|---|
| 语义 | 天然契合"读"操作 | 一般用于"写"或复杂查询 |
| 缓存 / 网关 | 可被网关 / CDN 缓存，幂等可重试 | 默认不缓存 |
| 可读性 | 参数直接在 URL，排查简单 | 需抓 body |
| 适用前提 | 参数少、无敏感信息、URL 长度可控 | 参数多 / 复杂对象 / 敏感数据 |

> 注意：GET 把参数放 URL，**别用来传敏感信息**（token、密码、身份证号等），这些走 POST + body + HTTPS。

### 3.2 全量发布每次 2~3 台，避免读超时

- 全量发布**单次推进 2~3 台**，不要图快一次推完；
- 核心目的是**避免瞬时负载压力过大造成读超时**：
  - 新实例同时上线 → 流量同时切入 → DB 连接池 / 缓存 / 下游 RPC 瞬时被打满；
  - 排队等待 → 调用方超时 → 表现为**读超时**（虽然逻辑没错，但资源跟不上）；
- 2~3 台一批，让下游资源有缓冲，流量平滑过渡。

**实操节奏建议**：

```text
灰度 1 台  ──观察──►  全量第一批 2~3 台  ──观察──►  第二批 2~3 台  ──观察──► ... ──► 全量完成
   ↑                                                                    │
   └───────── 任何一批异常，立即停止推进，排查或回滚 ──────────────────────────┘
```

### 3.3 部署前必看 Apollo

**上之前 Apollo 也要看**——这是上线前最后一道检查：

- 新代码依赖的 **Apollo 配置项是否已存在**、值是否正确；
- 配置的**数据类型**和代码接收方式是否匹配（参考 [[📚 Apollo配置JSON注入Map启动失败]]：配 JSON 类型，代码就得自己 `parseObject`，别指望 `@Value` 自动转 Map）；
- 配置是否需要**动态刷新**：需要热更新的，确认代码里监听了 `@ApolloConfigChangeListener`，否则改了配置不重启不生效；
- 环境：预发 / 生产的 Apollo 命名空间对不对，别拿了别的环境的配置。

**检查清单**：

| 检查项 | 关注点 |
|---|---|
| 配置项存在性 | 新代码用到的 key 在目标环境 Apollo 里已存在 |
| 配置值正确性 | 值的内容、格式（JSON / 字符串 / 数字）符合代码预期 |
| 类型匹配 | JSON 类型 → 代码自行解析；简单类型 → `@Value` 直接收 |
| 动态刷新 | 需要热更新的配置，代码是否监听了变更 |
| 命名空间 / 环境 | 拿的是目标环境的配置，没串环境 |

## 4. 易踩坑点与易混淆点

### 4.1 灰度 vs 全量：别混淆

| 维度 | 灰度部署 | 全量发布 |
|---|---|---|
| 实例数 | **1 台**试水 | 剩余全部，**每批 2~3 台** |
| 目的 | 验证新版本能跑、配置生效、无异常 | 把全量流量切到新版本 |
| 观测窗口 | 长，至少一个完整业务周期 | 每批短观测，异常即停 |
| 异常处理 | 立即回滚这 1 台 | 停止推进，排查或回滚已推批次 |

**易踩坑**：把"灰度"当成"少推几台全量"——灰度是**验证**，不是"少推一点"；灰度没观察够就急着全量，等于跳过验证窗口。

### 4.2 全量"一次推完" vs "每次 2~3 台"

| 做法 | 负载 | 读超时风险 | 回滚难度 |
|---|---|---|---|
| 一次全量推完 | 瞬时集中，打满下游 | **高**（DB/缓存/RPC 排队） | 大范围回滚 |
| 每批 2~3 台 | 平滑过渡 | 低 | 只回滚已推批次 |

### 4.3 GET vs POST：参数 < 3 的判断

| 场景 | 选 | 原因 |
|---|---|---|
| 查询、参数 < 3、无敏感信息 | GET | 语义契合、可缓存、排查简单 |
| 查询、参数 ≥ 3 或复杂对象 | POST | URL 承载不下 |
| 写操作 / 改状态 | POST | 幂等 / 语义 |
| 含敏感信息 | POST + HTTPS | 不暴露在 URL |

**易踩坑**：为了"统一风格"把所有查询都做成 POST——参数少的查询接口白白丢了 GET 的可缓存性和可读性。

### 4.4 Apollo 检查的常见盲区

| 盲区 | 后果 |
|---|---|
| 只看配置值对不对，没看**类型**是否匹配代码接收方式 | 启动失败 / 运行期解析错（见 [[📚 Apollo配置JSON注入Map启动失败]]） |
| 配了静态 `@PostConstruct` 解析，却指望它**动态刷新** | 改了配置不重启不生效 |
| 拿错**环境 / 命名空间**的配置 | 新代码跑到老环境配置上 |
| 新增配置项只在**本地**配了，生产没配 | 上线后取到默认值 / NPE |

## 5. 生活比喻

把一次上线想成**给一栋写字楼换新空调系统**：

- **灰度 1 台** = 先在**一间小会议室**装一台新空调试试——能制冷、不漏水、不跳闸，才敢往别的楼层装。这就是灰度那 1 台：用最小代价验证"新版本能跑"。
- **全量每次 2~3 台** = 给整栋楼换空调时，**一层一层地换**，而不是同一天把所有楼层的空调一起拆了装。要是同时全拆，整栋楼这一下午都没冷气，电梯里的人挤成一团、大厅排起长队（**瞬时负载打满 → 读超时**）。一层一层换，换好一层验一层，整栋楼平稳过渡。
- **Apollo 检查** = 换空调前先确认**新空调要接的电源规格、冷媒型号**和现场对得上——不然新空调装上去一通电就跳闸（配置类型不匹配 → 启动失败），或者装上去才发现冷媒管接错（配了却不生效）。
- **查询接口参数 < 3 用 GET** = 去前台**问一句简单问题**（"洗手间在哪？"），直接张嘴问就行，不用填表登记；但要是问的是复杂问题（"帮我查这三个月所有客户的对账单"），那才值得填张表（POST）。

核心：**先在一间屋试（灰度 1 台），再一层层铺（全量 2~3 台），铺之前先核对好电源冷媒（Apollo），简单问题别填表（GET）。**

## 6. 一句话记忆

> **构建两模块、MR 进 master、计划填 git、灰度先一台、全量两三台、上之前看 Apollo、查询参数少用 GET。**

- **五步闭环**：构建 api+base → git MR 合 master → 建上线计划填 git → 工作负载灰度 1 台 → 全量每批 2~3 台。
- **灰度 1 台**是验证窗口，不是少推一点，至少观察一个完整业务周期。
- **全量 2~3 台**是为了避免瞬时负载打满造成读超时——DB/缓存/下游 RPC 跟不上，逻辑没错也会超时。
- **查询参数 < 3 用 GET**：语义契合、可缓存、排查简单；含敏感信息或参数多才走 POST。
- **上之前看 Apollo**：配置项存在、值正确、类型匹配代码接收方式（JSON 类型要自己 parse）、需要热更新要监听变更、别拿错环境。
- **回滚意识**：灰度或任一批全量异常，立即停止推进、排查或回滚，别硬推。
