# Agent 系统提示词拆解：微信小师傅的角色定位、skill 路由与稳定性机制

> **拆解对象**：一份微信端施工项目经理助理（「微信小师傅」）的系统提示词
> **一句话结论**：它不是在要求模型表现稳定，而是把「没有规定动作的时刻」清零——事实走确定性管道、流程钉死、失败路径全覆盖、禁令可证伪、对话动作显式化
> **沉淀日期**：2026-11-26
> **关联笔记**：[[agent开发中可以直接模仿的上下文模式]]、[[需求 → 提示词「硬化」模板（附本任务逐节示例）]]

## 1. 六个值得抄的模式

**1.1 角色用否定式定边界。**
「APP 的遥控器，不是替代品」「赋能、不替代」「决策永远是项目经理拍板」——三个「不是什么」比十个「是什么」更能防越权。角色定位最重要的产出不是人设，是权限的隐式声明。

**1.2 路由键贴用户心智，不贴系统模块。**
能力地图按项目经理一天的时间轴排（早看待办 → 出门前看去哪 → 排路线 → 到工地看此刻该干啥 → 晚上看总结），两级判据是「问计划还是问执行」×「问全局还是问单家」。给模型做分类用的 taxonomy 得是用户问话的切法，不是后端域模型的切法。

**1.3 skill 按需加载，系统提示只常驻「路由表 + 纪律」。**
重的调用规范（参数、判定逻辑）放 skill 里用到再读。好处两个：系统提示不用塞满所有接口文档；能力可以独立演进。细节：`construction-arrival-brief 用 projectOrderId、不是 ucId` 这种一行防错提醒，是踩过的坑回填进 prompt 的痕迹——这套体系必须配「观察到一次偏差 → 回填一条规则」的机制，它是活的。

**1.4 「成品直转发」——最硬核的一条。**
「skill 脚本的输出是成品，直接转发，不复述、不做二次分析改写；多轮补充只能在脚本输出之后追加，不篡改判定结果」。等于把架构定死：**NL 理解和路由归 LLM，事实生成归确定性脚本**，中间不留 LLM 改写事实的口子——幻觉面积压到最小。机读中间态（JSON）只供自己消费不外发，是同一条纪律。

**1.5 实体定位是一台状态机。**
整节「订单定位与相似候选确认」就是 entity resolution 协议，见 §3。

**1.6 确认 ≠ 授权。**
「确认是哪笔订单，不等于授权执行写操作」——身份确认和操作授权是两道门。很多 agent 设计里这两件事糊在一起，这里显式拆开。
## 2. 稳定性机制总览

Agent 输出的方差只有三个来源——生成什么**事实**、走什么**流程**、做什么**对话动作**。这份 prompt 把三个都摁住了：

| 方差来源 | 管住它的机制 | 核心纪律 |
|---|---|---|
| 事实 | 确定性管道 | LLM 只理解意图和转述，事实全部走工具/脚本管道；算术强制 `calculator`；身份从登录上下文取 |
| 流程 | 钉死的工作流 | 固定三步（取 skill → 按规范查 → 提炼转发），路由维度正交 + 判据有次序；意图不清就问，不猜 |
| 对话动作 | 状态机 | 显式轮次终止、确认门、陈旧引用作废、固定输出形状 |

模型真正「自由生成」的只剩两样：理解用户说了什么、用什么语气说回去。随机性只作用于随机性该作用的地方——**LLM 只兜代码兜不住的底**（residual design）。

稳定性不是靠叮嘱「要认真、别出错」堆出来的，而是**把模型每一次「自由发挥」的时刻，都换成了确定性组件**。

## 3. 失败路径全覆盖（稳定性的主战场）

多数 prompt 只写 happy path，而**不稳定的真实形态是：遇到没规定的情况，模型即兴发挥**。这份 prompt 里失败路径的规则量远大于成功路径，每条都是「状态 → 规定动作」：

| 状态 | 规定动作 |
|---|---|
| 姓名未命中 | 去名留身份补查一次（pageSize=100），不让用户重输，不连猜同音 |
| 工具报错 | 即停，不进候选匹配，**不解释成「没有订单」** |
| 上下文缺身份 | 停，不静默放宽查询条件 |
| 分页截断 | 不得声称「查遍全部」 |
| 用户回复含糊 | 再问一句，不猜 |
| 用户说「都不是」 | 换钥匙（问小区/订单号），不选最近的凑合 |
| 唯一候选 | 照样等确认、**结束本轮回答** |
| 序号指代 | 仅对应最近一轮候选，不根据尾号猜测或拼接订单号 |
| 跨记录字段 | 候选姓名、订单号、小区必须来自同一条工具记录，不得混用 |
## 4. 禁令的写法：可证伪，专打「补全本能」

「要诚实」这类德性式指令基本不改变行为；这里的每条禁令都绑定到**可核查的具体情境**：

- 「返回总数大于展示条数时，不得声称查遍全部」——绑分页情境
- 「不根据尾号猜测或拼接订单号」——绑部分信息补全
- 「不得把猜测的同音姓名当成系统查询结果」——绑记忆补全
- 「不得把接口异常解释为业主没有订单」——绑异常折叠
- 「不得仅因同姓就推荐」「不得为凑数展示不相关订单」——绑列表生成

共性：模型的预训练目标是「有用」，所以它的本能是**把缺口用看似合理的内容填上**（编尾号、拼姓名、把异常圆成空结果）。写禁令不是列道德准则，是给本能发作点逐个装闸。

最有味道的一条是「报错即停，不把接口异常解释成没有订单」——这就是后端最基本的一条纪律：**异常和空结果是两个返回值，别把 Exception 折叠成空 List**。模型的训练惯性恰恰就是折叠（把任何异常状态叙述成最像的日常故事），所以这些禁令全是逆着它的本能写的：报错、空集、不存在，三种状态强制保持分离。

「候选字段必须来自同一条工具记录，不得混用」这条最细，防的是列表处理里真实存在的幻觉模式：**attention 把相邻两条记录的字段串了**。

## 5. 对话动作也是规定动作（会话状态机）

会话被当成状态机管理，不是自由聊天：

- **`await user` 是显式动作**：「必须等待用户确认，并结束本轮回答」——模型不许自己往下跑
- **对话状态有版本**：「回复的序号仅对应最近一轮展示的候选」——陈旧引用作废，模型只认最近一轮
- **确认 ≠ 授权**：「确认是哪笔订单，不等于授权执行写操作」——身份确认和操作授权两道门，写操作每次重新查接口，会话里看过的旧数据不许当新数据用
- **输出形状固定**：「一屏答完、结论第一行」——用户感知到的「稳定」，一半来自答案事实一致，另一半来自**每条答案长得一样**。输出格式跟信道走（微信单条消息的约束）
## 6. 这套稳定的代价

- **稳定性是刚性买来的。** 每个新边界情况 = 一条新规则，prompt 像判例法一样生长。防 `projectOrderId`/`ucId` 误传的那一行，明显是踩坑回填的痕迹——这套体系必须配一个「观察到一次偏差 → 回填一条规则」的机制，否则场景漂移后稳定性会衰减。
- **规则密度有预算。** 规则塞太多，模型开始丢条款。所以它才把重调用规范压进 skill 按需加载、常驻的只有路由表和纪律——**常驻上下文小，规则才跟得上**。这本身就是维持稳定性的机制。
- **稳定 ≠ 正确。** 成品直转发只保证「不添乱」，skill 算错照样错——质量责任从 prompt 转移到了 skill 脚本的测试上，不是消失了。

照搬前要想清楚的三点：

1. **成品直转发的前提是输出高度模板化**（行程/日报/简报）。如果输出天然发散、需要按上下文组织，LLM 改写这步就省不掉——那就得在改写处补事实校验，成本只是换了个位置。
2. **订单定位那节的密度是为「按人找单」这种高频高风险场景写的。** 低风险查询照抄就是过度设计。
3. **隐含前提是业务场景收敛、可枚举。** 场景发散的产品，这套路由表会失控。

## 7. 复刻顺序

1. 划出模型的生成面，压到只剩「理解 + 转述」；事实全部走工具/脚本管道
2. 固定工作流程，路由用正交维度 + 判据次序
3. 为每条失败路径写「状态 → 规定动作」，踩一个坑补一条
4. 禁令写成可证伪的具体行为，专打补全本能（部分信息、记忆、异常折叠、跨记录串字段）
5. 显式的轮次终止、确认门、固定输出形状

**最小可借骨架**：否定式角色边界 + 按用户节奏的能力路由 + 成品直转发（追加不改写）。涉及按名定位实体的场景（如单据/人员查询）再加一条定位协议。

一句话总结：**它不是在要求模型表现稳定，而是把「没有规定动作的时刻」清零。**
