# 📚 排程材料配置四表关联链路：入参 → 工艺节点的查询路径

> **踩坑对象**：排程材料配置（mode=7）下 `delivery_flow_rule` / `delivery_flow_rule_unit` / `delivery_flow_rule_category` / `n_material_process_define` 四张表怎么串起来，入参怎么一路查到最终工艺节点内容。
> **一句话结论**：入参维度 → `delivery_flow_rule_unit` 按维度匹配取 `rule_id` → 用 `rule_id` 关联 `delivery_flow_rule`（门禁）+ `delivery_flow_rule_category`（取 `category_id` 及品类/材料/供应商明细）→ 用 `category_id` 关联 `n_material_process_define` / `n_material_node_cfg` 取最终工艺节点内容；代码里的 `templateIdList` 实际就是映射到 `n_material_process_define.template_id` 列的 `IN` 查询，所以 **`delivery_flow_rule_category.category_id` 确实等于 `n_material_process_define.template_id`**。
> **沉淀日期**：2026-08-31
> **关联**：[[材料自流程支持纯零售-代码与库表学习指南]]（同域学习指南，第 4.4 节"关联要点"即是本链路的一句话版）

## 1. 问题现象

排程材料配置（`mode=7`，`DELIVERY_FLOW`）改造里，最绕的一件事是：**入参明明只是几个维度（分公司 + 业务类型 + 单据类型 + 套餐 + 品类 + 材料 + 供应商……），最终怎么变成"这一单要跑哪些工艺节点、节点上挂什么角色 / 触发时机"？**

读 `delivery_flow_rule*` 这一组表时容易卡在三个点：

1. **不知道哪张表负责"匹配入参"**：`delivery_flow_rule` 是门禁、`delivery_flow_rule_unit` 是维度匹配、`delivery_flow_rule_category` 是品类明细——三张表名字像，职责分不清。
2. **不知道 `rule_id` 往哪走**：`rule_id` 在 `delivery_flow_rule_unit` 里查出来，但"最终工艺节点内容"不在 `delivery_flow_rule` 族里，而在共享的 `n_material_process_define` / `n_material_node_cfg`。
3. **`templateIdList` 这个入参/出参字段到底对应哪一列**：代码里看到 `templateIdList` 做 `IN` 查询，表里却没有叫 `templateId` 的独立表——它其实就是 `n_material_process_define.template_id`，而这个 `template_id` 又来自 `delivery_flow_rule_category.category_id`。

业务代码里典型的调用长这样（以配置查询接口为例，见 [[材料自流程支持纯零售-代码与库表学习指南]] §3.6）：

```java
// 1. 入参维度先去 delivery_flow_rule_unit 匹配，拿到 rule_id
List<Long> ruleIds = deliveryFlowRuleUnitDao.matchRuleByDimension(param);

// 2. 用 rule_id 查门禁(delivery_flow_rule) + 品类明细(delivery_flow_rule_category)
List<DeliveryFlowRuleCategoryDTO> categories =
        deliveryFlowRuleCategoryDao.listByRuleIds(ruleIds);

// 3. 把品类明细里的 category_id 当成 template_id，去工艺定义表 IN 查
List<Long> templateIdList = categories.stream()
        .map(DeliveryFlowRuleCategoryDTO::getCategoryId)
        .collect(Collectors.toList());
List<NMaterialProcessDefine> defines =
        nMaterialProcessDefineDao.selectByTemplateIds(templateIdList); // IN 查询
```

**诡异点 / 易卡点**：

- `category_id` 和 `template_id` 字段名不一样，但存的是**同一个值**，靠它把"排程配置表族"和"工艺定义表族"接起来。
- `delivery_flow_rule` 表本身**不存工艺内容**，它只是"门禁/头表"，真正能跑出工艺节点的是后面两张 `n_material_*` 表。
- 老配置（mode=5/6 八合一）的 `material_flow_rule_template_mapping.n_template_code` 也是回指 `n_material_process_define.template_id`——**新老配置在这一步是"同一条出口"**，区别只在前面"维度匹配"走哪族表。

## 2. 根因分析：四表关联链路

整条链路本质是**"两族表接力"**：排程配置表族负责**匹配 + 取门禁 + 取品类明细**，工艺定义表族负责**出最终节点内容**。中间靠 `category_id == template_id` 这个"隐形桥"接起来。

**四步接力拆解**：

| 步 | 起点 → 终点 | 用什么字段接 | 做了什么 |
|---|---|---|---|
| ① | 入参维度 → `delivery_flow_rule_unit` | （入参字段 vs 表里的 `mdm_company_code`/`sale_type`/`document_type`/`project_version`/`product_combo_id`/`gb_code`） | 按维度匹配，**取出 `rule_id`** |
| ② | `delivery_flow_rule_unit` → `delivery_flow_rule` | `rule_id` | 取**门禁/头表**（`state`、`delivery_process_cfg_id`），判断规则启用没 |
| ③ | `rule_id` → `delivery_flow_rule_category` | `rule_id` | 取**品类明细**：`category_id`、`material_code`、`supplier_code`、`node_process` |
| ④ | `delivery_flow_rule_category` → `n_material_process_define` | **`category_id` = `template_id`**（隐形桥） | 用 `category_id` 当 `template_id` 做 `IN` 查询，拿**最终工艺节点内容** |

> 关键洞察：**前三步在排程配置表族里打转，第四步才跨到工艺定义表族**。`delivery_flow_rule_category` 是承上启下的"桥表"——对上拿 `rule_id`，对下吐 `category_id` 当 `template_id`。

## 3. 解决方案：标准查询路径

### 3.1 路径选型

| 路径 | 做法 | 适用 | 缺点 |
|---|---|---|---|
| ① 四表接力（推荐） | 按链路图逐步 `rule_id` → `category_id` → `template_id` 取值 | **排程配置查询 / 任务生成**的标准走法 | 需要理解两张表族的职责分工 |
| ② 一次性 JOIN | 一条 SQL 把四张表 JOIN 起来直接出节点 | 报表 / 一次性抽样核查 | 不利于复用、缓存，且 `n_material_*` 数据量大易拖慢 |
| ③ 跳过门禁直查 | 拿到 `rule_id` 跳过 `delivery_flow_rule`，直接查 `category` | `delivery_flow_rule_unit` 已保证 rule 有效时 | 丢失 `state` 启用校验，有"取到已停用规则"的风险 |

> **推荐①**：业务代码里按"取 `rule_id` → 取 `category` → 用 `category_id` 当 `template_id` 查 `process_define`"三步走，每一步职责单一、可缓存、可单测。

### 3.2 标准 SQL（对接链路图）

```sql
-- ① 按入参维度匹配，取 rule_id（排程配置表族）
SELECT rule_id
FROM delivery_flow_rule_unit
WHERE mdm_company_code = #{branchCode}
  AND sale_type         = #{saleType}        -- 1整装 / 2零售
  AND document_type     = #{documentType}
  AND project_version   = #{projectVersion}  -- 2.5
  AND product_combo_id  = #{productComboId}
  AND gb_code           = #{gbCode};

-- ② + ③ 用 rule_id 取门禁 & 品类明细（排程配置表族）
SELECT r.id            AS rule_id,
       r.state,
       c.category_id,
       c.material_code,
       c.supplier_code,
       c.node_process
FROM delivery_flow_rule r
JOIN delivery_flow_rule_category c ON c.rule_id = r.id
WHERE r.id IN ( /* 上一步的 rule_id 列表 */ )
  AND r.state = 1;   -- 门禁：只取启用

-- ④ 用 category_id 当 template_id，去工艺定义表族 IN 查最终节点内容
SELECT template_id,
       process_code,
       task_type,
       delivery_type,
       work_type
FROM n_material_process_define
WHERE template_id IN ( /* 上一步的 category_id 列表 */ );
```

### 3.3 代码层映射（对应业务代码里的写法）

```java
// templateIdList 就是 category_id 列表，对应 n_material_process_define.template_id 的 IN 查询
List<Long> templateIdList = categories.stream()
        .map(DeliveryFlowRuleCategory::getCategoryId)   // ← 隐形桥：category_id → template_id
        .distinct()
        .collect(Collectors.toList());

// 例：materialConfigV2Service.queryProcessDefineV2(templateIdList)
List<NMaterialProcessDefine> defines =
        nMaterialProcessDefineDao.selectByTemplateIds(templateIdList);
//   ↳ 对应 SQL：WHERE template_id IN (...)
```

> 在 [[材料自流程支持纯零售-代码与库表学习指南]] §3.6 的两个 delivery 查询接口（`queryConfigOFCList` / `queryCategoryConfigOFCList`）里，`configFlag=true` 分支走的就是这条链路：`deliveryFlowRuleDao.matchConfigByParam` 读排程表族 + `materialConfigV2Service.queryProcessDefineV2` 读 `n_material_process_define`。

## 4. 进阶：`category_id` 为什么确实等于 `template_id`

这是整条链路里最容易让人犯嘀咕的一步——两个字段名完全不同，凭什么说它俩是同一个值？

### 4.1 三条证据互相印证

1. **字段定义层**：`delivery_flow_rule_category.category_id` 是"排程规则下某条品类明细的主键/标识"，长度由 `DELIVERY_FLOW_CATEGORY_LENGTH` 常量约束（长 id，见 §3.7 迁移构件）；`n_material_process_define.template_id` 是"工艺流程定义归属的模板 id"。两者类型、长度口径一致。
2. **代码使用层**：业务代码里 `templateIdList` 的来源就是 `categories.getCategoryId()`，紧接着做 `WHERE template_id IN (...)`——如果它俩不是同一个值，这条查询根本查不到东西，而线上是通的。
3. **迁移构件层**：八合一 → 排程迁移时（[[材料自流程支持纯零售-代码与库表学习指南]] §3.7），`saveMaterialProcessDefineNew` 写入新 `n_material_process_define` 时，用的 `template_id` 正是新 `delivery_flow_rule_category` 的 `category_id`（长 id）。即"写入时就让二者相等"。

### 4.2 新老配置的"同一条出口"

| 配置族 | 维度匹配表 | 品类明细表 | 桥到 `n_material_process_define` 的字段 |
|---|---|---|---|
| 排程（mode=7，新） | `delivery_flow_rule_unit` | `delivery_flow_rule_category` | `category_id` = `template_id` |
| 八合一（mode=5/6，老） | `material_flow_rule_unit` | `material_flow_rule_category` + `material_flow_rule_template_mapping.n_template_code` | `n_template_code` = `template_id` |

> **结论**：不管新配置还是老配置，"维度匹配"走各自的表族，但"出最终工艺节点内容"最后都汇到 `n_material_process_define`。这就是设计里反复强调的——**新配置管匹配维度，老配置管流程内容（共享）**。排程改造把匹配维度迁到 `delivery_flow_rule*`，但工艺节点内容仍复用 `n_material_process_define` / `n_material_node_cfg`，不重复造一套。

## 5. 易混淆点

### 5.1 三张 `delivery_flow_rule*` 表的职责

| 表 | 一句话职责 | 容易记错的点 |
|---|---|---|
| `delivery_flow_rule` | **门禁/头表**：规则启用没、挂哪个排程流程配置 | 它**不存工艺节点**，只存 `state` + `delivery_process_cfg_id` |
| `delivery_flow_rule_unit` | **主匹配维度**：分公司+版本+单据类型+销售类型+套餐+国标码 | 匹配发生在**这里**，不是在 `delivery_flow_rule` |
| `delivery_flow_rule_category` | **品类明细**：品类+材料+供应商+节点流程，承上启下 | 它才是吐 `category_id`（= `template_id`）的桥表 |

> 记法：`rule`（门禁）→ `rule_unit`（按维度匹配拿 rule_id）→ `rule_category`（按 rule_id 拿品类明细）。**先匹配，再门禁，再明细**——顺序别倒。

### 5.2 `templateId` 不是独立表，是列

代码里看到的 `templateIdList`、`queryProcessDefineV2(templateIdList)`、`selectByTemplateIds`——这里 `templateId` 指**列**（`n_material_process_define.template_id`），不是某张叫 `template` 的表。它的取值来自上一步的 `category_id`。新手容易满库找 `template` 表找不到，原因就在这。

### 5.3 `category_id` vs `delivery_template_id`：两个都叫 template，不是一回事

`delivery_flow_rule_category` 表里有两个"template"相关字段，别混：

| 字段 | 指向 | 用途 |
|---|---|---|
| `category_id` | `n_material_process_define.template_id`（工艺定义） | **本链路**：取最终工艺节点内容 |
| `delivery_template_id` | 外部施工包模板 | 施工包生成侧用，不在本"工艺节点查询"链路 |

### 5.4 门禁 `state` 该不该查

`delivery_flow_rule.state` 是规则启用状态。链路图第②步取门禁时建议带 `state=1` 过滤，避免拿到已停用规则；但 `delivery_flow_rule_unit` 已保证 rule 存在、`category` 也有自己的 `state`——三处 `state` 含义不同，排查"查不到配置"时要分别确认是哪一层的 `state` 关掉了。

## 6. 生活比喻

把这条链路想成**拿着快递单去仓库取货，最后领到一份"组装说明书"**：

- **入参维度** = 你递给前台的单据：收件城市（分公司）+ 物品类型（业务类型）+ 单据种类（documentType）+ 套餐版本 + 国标码。前台拿这张单子去**档案柜**找你的档案编号——这就是 `delivery_flow_rule_unit`，**匹配维度 → 拿到档案号 `rule_id`**。
- **`delivery_flow_rule`** = 档案封面的**启用章**（门禁）。档案号有了，但先看封面上盖没盖"启用"——没盖章的档案（`state` 关闭）哪怕查到也不能用。
- **`delivery_flow_rule_category`** = 档案里的**明细页**：这一单涉及哪些品类、哪些材料、哪个供应商、走哪条节点流程。明细页上有个**条形码**叫 `category_id`。
- **隐形桥** = 明细页的条形码，正好就是**隔壁仓库（工艺定义仓库）的取件码**。前台不生产说明书，只给你一个取件码。
- **`n_material_process_define` / `n_material_node_cfg`** = 隔壁工艺定义仓库：拿取件码（`template_id`）去 `IN` 查，领到**真正的组装说明书**——要跑哪些工序节点、每个节点什么角色、什么时候触发。

一句话：**前台（排程配置表族）只管"你是谁、查哪份档案"，隔壁仓库（工艺定义表族）才管"具体怎么组装"。两边靠一张条形码（`category_id` = `template_id`）对接。**

> 新老配置的差别只是"前台换了套档案柜"——八合一用老档案柜（`material_flow_rule*`），排程用新档案柜（`delivery_flow_rule*`）；但**隔壁工艺定义仓库是同一个**，新旧档案最后都去那儿取组装说明书。

## 7. 一句话记忆

> **入参匹配 unit 取 rule_id，rule_id 连 rule（门禁）+ category（明细），category_id 就是 template_id，IN 查 process_define 出节点。**

- **现象**：排程配置查询从入参到工艺节点，中间要跨两张表族，字段名对不上（`category_id` vs `template_id`），看着断链。
- **根因**：排程配置表族（`delivery_flow_rule*`）只管"匹配 + 门禁 + 品类明细"，工艺节点内容在共享的 `n_material_process_define` / `n_material_node_cfg`；二者靠 `category_id` = `template_id` 这个隐形桥接起来。
- **陷阱**：
  - `delivery_flow_rule` 不存工艺内容，只是门禁，别在那儿找节点。
  - `templateIdList` 是**列**（`n_material_process_define.template_id`）不是表。
  - `category_id` 和 `delivery_template_id` 都叫 template 相关，但一个指工艺定义、一个指施工包模板，不是一回事。
- **根治**：按"unit 匹配 → rule 门禁 → category 明细 → process_define 出节点"四步接力，每步只传一个 id（`rule_id` → `rule_id` → `category_id` → `template_id`）。
- **定位口诀**：排程查不到工艺节点时，先确认"前三步有没有拿到 `category_id`"，再确认"`category_id` 当 `template_id` 去 `n_material_process_define` 的 IN 查询有没有命中"——断点必在这两环之一。
