## ✅ 正向验证：一次通过的重构（2026-09-09 queryConfigOFCList）

**对照实验**：同一文件、同一批代码，前几轮返工 6+ 次；本次重构**一次编译通过、零返工**。差异不在代码能力，在流程：

| 本次做了什么 | 对应清单项 |
|---|---|
| 需求方指令本身就是"清单式"的：给了精确实现约束（for 放外层、内部判 configFlag、不抽方法、documentType 统一并入 list、`[1,12,16]` 行为说明）——**写死了结构，没写概念** | 清单全文 |
| AI 动手前先**复述理解 + 一次问清 9 个歧义点**（参考方法确认 / configFlag=true 是否判开关 / 顺序 / 合并去重 / 拼接方式 / 返回行数 / 取码来源 / 空值兜底 / 改动范围） | A1–A5（必填项） |
| 交付前先给**可评审的完整伪代码**，需求方批准后再落地 | C10 验收标准 |
| 语义已在前几轮摸清（documentType 单值/列表、开关语义），本次是**结构调整而非语义设计**，复杂度天然低 | B8/B9 |

**为什么这次不用返工——四条可复用经验**：

1. **返工的根源是"没说清就写"，不是代码能力**。返工轮次里没有一次是"AI 看不懂"，全是"AI 不知道你想的细节"；一次把细节问完（9 个问题）≈ 省 3–4 轮试错。
2. **需求方的指令本身就是最好的模板**：连"不抽方法""不去重""维持先新后旧"这种约束都写清——即"**写死字符串，不写概念**"。此前 `all` / `grayRatio` 返工都是因为只说"加个开关/灰度"，没说字段与语义。
3. **Ask 模式（先问后动）是优势不是限制**：它强制"先对齐 → 再方案 → 后落地"，天然踩刹车，避免"边猜边写"。流程顺序比速度重要。
4. **前几轮返工不是白费的**：documentType 单值/列表、开关语义已在前期摸透并沉淀，使本次只剩"结构调整"——语义问题清空后，后续改动复杂度天然降低。

**一句话总结**：能一次通过，是因为"该问的一次问清 + 要的约束一次给全"——把返工成本前置成了提问成本。
