## 1. 现状与定位

- [ ] **1.1 分支与基线**
  - 当前分支名；该分支相对 `master` **是否已有 commit**（有几个、commit 内容是什么）。
  - 明确"**禁止复用**"的历史分支/实现（如：旧分支已有一版，但本次要从零做，不要抄）。
  - ⚠️ 坑：分支一旦有 commit，`git show HEAD:` 就是改动后版本，**不能当基线**；基线要用 `git show master:<file>`。
- [ ] **1.2 相关文件路径 + 行号 / 方法名**
  - 逐个改造点列出：`文件:行号` 或 `类#方法`。
  - 已知相关的枚举、配置类、DAO、Feign 接口一并列出。
- [ ] **1.3 当前（改造前）实际行为**
  - 用"输入 → 走哪个分支 → 输出"描述，最好**逐场景**列出（如：`configFlag=true 走排程；false 走旧八合一`）。
  - 这是判断改动是否幂等的唯一依据，务必给。
- [ ] **1.4 外部依赖契约**
  - 涉及的外部/Feign 接口：**入参是单个还是批量？返回是否与入参一一对应？可能返回 null 吗？**
  - 例：批量接口若只传子集，外部服务行为是否变化。

## 2. 目标与验收标准

- [ ] **2.1 期望行为（逐场景）**
  - 用表格列出"场景 → 期望走哪条路径"，覆盖**修改场景**和**不修改场景**。
- [ ] **2.2 可判定的完成条件**
  - 如："编译通过（给出具体 mvn 命令）"、"某接口返回 X"、"非纯零售场景返回与改造前完全一致"。
- [ ] **2.3 开关 / 灰度的准确语义（高频返工点）**
  - 需要几个开关？每个字段**代表什么**？（总开关 / 全国开关 / 白名单 / 比例）
  - **"灰度"在本项目/本需求里的定义**：是逐步放开分公司名单？按流量百分比？按订单号？
  - **回滚方式**：关掉开关 / 清空名单 / 改配置，期望哪种？
  - 默认态（Apollo 未配置时）应该**放行还是不放行**？——这决定会不会"上线即改变现网行为"。

## 3. 约束与边界

- [ ] **3.1 不可改动的代码**
  - 明确"只迁移 X，不得改动 Y"、"保持完全兼容"。
- [ ] **3.2 兼容性 / 幂等范围（高频返工点）**
  - 明确哪些场景**必须改动前后完全一致**（不只是"结果对"，还包括：入参、调用次数、返回结构、日志）。
  - 点名重点关注的方法（如"主材申请单查询配置、货查询配置一定要先确认能不能走到"）。
- [ ] **3.3 性能要求**
  - 是否允许循环内查库/调接口、批量接口是否允许拆成多次调用、有无 QPS/耗时红线。

## 4. 技术环境

- [ ] **4.1 语言 / 框架 / 版本**
  - 例：Java 8 + Spring Boot 2.1 + Spring Cloud Greenwich + MyBatis + Apollo + Lombok。
- [ ] **4.2 构建与运行方式**
  - 给出**可执行命令**（如 `sh mvnw -o compile -pl edar-starlord-service -am`）、启动 profile、测试库地址。
- [ ] **4.3 模块边界与放置约定（高频返工点）**
  - 模块依赖方向（如 `web → service → manager → dao → base ← api`）。
  - **对外 DTO/Param 放哪、内部 BO 放哪**（放错包 = 编译失败）。
  - 配置注入方式（如 `@ApolloJsonValue`）、Apollo key 命名风格。
- [ ] **4.4 既有实现参照物**
  - "仿照 XXX 类 / XXX 方法实现"——比任何文字描述都准确（本次：仿 `MaterialScheduleSwitchBo`）。
- [ ] **4.5 代码风格与命名约定**
  - 缩进、行宽、日志风格（如 `log.info("中文说明，参数：{}", x)`）、注释语言、是否允许新增私有方法。

## 5. 错误与复现

- [ ] **5.1 完整报错信息**（不要截断，含文件路径 + 行号 + 原始堆栈）
- [ ] **5.2 最小复现步骤**（接口 + 入参 + 期望/实际返回）
- [ ] **5.3 已尝试方案及失败原因**（避免助手重复踩坑）
- [ ] **5.4 已知缺陷 / 历史坑**
  - 例："`getDocumentTypeList()` 可能返回 null，for-each 会 NPE"。

## 6. 输出偏好

- [ ] **6.1 交付形态**：完整文件内容 / diff / 只给改动片段？
- [ ] **6.2 解释程度**：先给方案再改代码，还是直接改？要不要逐条说明改动理由？
- [ ] **6.3 版本控制动作**：改完是否 `git add` 暂存？**是否允许 commit**（默认只允许 add，不 commit）？
- [ ] **6.4 验收动作**：是否需要助手自行编译验证？跑哪些命令？
- [ ] **6.5 文档沉淀**：改动是否要同步到计划文档 / wiki？

## 一句话心法

> **把你脑子里的"理所当然"写下来**——尤其是：基于哪个分支、改造前到底怎么跑的、"灰度"这类词在本项目指什么、哪些场景绝对不能变。
> 这四类信息给全，返工能从 6 轮压到 1–2 轮。
