# 专利选题评估：我的知识沉淀里哪些能写成专利

> **评估目的**：从个人知识沉淀（20.知识沉淀 / 00.需求 / 10.项目整理）中筛选可专利化的选题，并按专利申请要求（背景技术、技术方案、有益效果均需明确）给出差距分析和行动建议。
> **评估日期**：2026-09-13
> **结论速览**：首推 **候选①（模板驱动的主材任务调度方法）** 和 **候选②（图像识别驱动的主材通知任务自动化方法）**，二者"技术问题→技术手段→技术效果"链条完整；候选③ 可作从属或合并；候选④ 有客体风险需改包装。

---

## 一、先对齐：专利授权的三道门槛

写之前必须知道审查员按什么砍：

| 门槛 | 要求 | 对你的影响 |
|---|---|---|
| **客体合格** | 必须是"利用技术手段解决技术问题并获得技术效果"的方案。纯算法、智力活动规则、商业方法本身不授权（专利法第 25 条 + 审查指南） | "提示词模板"这类容易被认定成智力活动规则，需要包装成数据处理/生成质量验证方法 |
| **新颖性** | 申请日前未被公开（包括你自己对外分享！博客、公开演讲、开源都会破坏新颖性） | **先交底、后分享**，顺序不能反 |
| **创造性** | 对本领域技术人员非显而易见。要能指出与现有技术（工作流引擎、规则引擎、RPA 等）的差异点 | 每个候选都给了"查新重点"和"差异化主张" |

另外两条现实约束：

1. **职务发明**：你的发明创造专利申请权归公司（贝壳），个人不能自行申请。走公司 IP 流程：填《技术交底书》→ 提给专利对接人/法务 → 专利工程师检索评估 → 代理撰写 → 申请。发明人是你的名字。
2. **交底书四要素**：① 背景技术（现有方案缺陷）② 发明内容（技术问题 + 完整技术方案 + 有益效果）③ 附图说明（流程图/架构图/时序图）④ 具体实施方式（能复现的程度，含关键表结构、判定逻辑、接口交互）。**你的技术方案文档质量已经接近交底书水平**，这是优势。

## 二、候选选题评估（按推荐度排序）

### 候选①：模板驱动的双层主材履约任务调度方法 ★★★★★

**素材来源**：`10.项目整理/主材全链路业务与系统配置总结.md`、`材料配置问题.md`、`20.知识沉淀/📚 排程材料配置四表关联链路.md`、edar-starlord 新人文档

| 维度 | 内容 |
|---|---|
| **技术问题** | 家装交付场景中，主材履约流程因 品类 × 城市 × 套餐 × 业务模式 配置维度爆炸而无法用固定代码表达；任务与工序节点的状态流转需要跨多个下游系统保持一致；新老配置体系（八合一 / 全国 / 排程）并存导致重复建设 |
| **技术手段** | ① 双层实例模型：任务级实例（task_dispatch，4 态）+ 节点级实例（task_dispatch_node，阶梯 node_type 0/20/40/60/65/80/85），任务激活驱动 current_node_type 前移；② 模板驱动生成：按维度匹配模板（processChain），运行时实例化节点有序序列；③ 维度匹配四表接力：unit 匹配取 rule_id → rule 门禁校验 → category 明细 → category_id 当 template_id IN 查共享工艺定义表（新老配置同一条出口）；④ 多配置模式（mode5/6/7）统一出口收敛 |
| **技术效果** | 新增业务模式/城市/品类近似零代码接入；配置维度解耦（匹配维度与流程内容分离）；任务状态跨系统可追溯 |
| **权利要求方向** | 标准三件套：方法 + 装置 + 计算机可读存储介质。独立权利要求写"一种基于模板匹配的任务调度方法"，从属权利要求逐条覆盖双层状态机、四表接力、模板实例化 |
| **查新重点** | Activiti/Flowable/Camunda 等工作流引擎、低代码流程编排、订单履约中台类专利。**差异化主张**：'任务级-节点级双层激活模型 + 配置维度与工艺内容分离的共享出口' 这个组合，通用工作流引擎没有 |
| **风险** | 需把公司特有名词（贝壳/家装/SKU）抽象成通用"订单履约"表述；配置维度爆炸的"问题"论述要落到技术缺陷（硬编码不可扩展、状态不一致），不能只说业务痛点 |

### 候选②：基于现场图像识别的主材通知任务自动判定与执行方法 ★★★★★

**素材来源**：`00.需求/通知复尺自动化/`（作业层技术方案、开发总结、最终汇总）

| 维度 | 内容 |
|---|---|
| **技术问题** | 装修工地主材履约中的通知类任务（通知复尺/通知安装）依赖项目经理人工判断是否满足通知条件并手动提交，时效差、标准不一、易漏办 |
| **技术手段** | 完整闭环，创新点密度最高：① 识别结果结构化落表（judge_result 四态枚举：可通知/不可通知/无法判断/现场已完成需关闭）；② 多维度灰度开关（城市-工程部-品类-工长 id 四级）控制自动化范围；③ T+N 期望上门时间计算（识别日期为基准）；④ 双通道执行（一键通知人工确认 / 自动通知）；⑤ **AI 建议采纳情况回写（ai_adoption_type 四态）形成人机协同反馈闭环** —— 这是最好讲创新性的点；⑥ 每日轮巡 + 缓存预取关键帧，避免实时查询上游 |
| **技术效果** | 通知任务处理从"人工逐单判断"变为"AI 预判 + 人工兜底"，效率提升且判断标准统一；采纳率数据可反哺识别模型 |
| **权利要求方向** | 独立权利要求写"一种基于图像识别结果的工地任务通知方法"，从属覆盖：判定结果分态处理、灰度开关维度、时间推算规则、采纳反馈闭环 |
| **查新重点** | RPA + 订单自动化、智能家居/工地 AI 巡检类专利。**差异化主张**：识别结果四态分态处置 + 采纳情况回写的反馈闭环 + 四级灰度控制的组合 |
| **风险** | 上游图像识别算法不是你做的，交底书里必须**划清边界**：你的发明点是"识别结果的消费、判定与执行决策"，图像识别本身作为前置输入引用即可（写"通过上游识别服务获取…"） |

### 候选③：供应商汰换的三态判定与在途履约编排方法 ★★★★

**素材来源**：`00.需求/供应商汰换20260709/`（技术方案、编排步骤 3.1~3.6、领域模型）

| 维度 | 内容 |
|---|---|
| **技术问题** | SKU 供应商变更时，在途履约任务的归属方（新商/老商）不确定；紧急汰换要求快速生效但需保证跨系统（OMS 货单）一致性；大规模订单数据无法实时查询 |
| **技术手段** | ① 消息驱动的变更落表；② 大数据侧建 API + 中间表，分批（1000/批）拉取"有用量的"订单范围数据；③ **三因子判定矩阵**：汰换方式（常规/紧急+立即/紧急+不立即）× 新老商角色 × 老商任务状态 → 决定履约方与是否取消 OMS 货单；④ 分步编排（3.1~3.6）保证幂等与顺序 |
| **技术效果** | 汰换决策自动化、紧急场景分钟级生效、履约不中断 |
| **与候选①的关系** | 同属 starlord，可以：a) 独立成案；b) 作为候选① 的从属权利要求。若公司偏好"一件多案"，独立申报更好 |
| **查新重点** | 供应链供应商切换、订单路由类专利。差异化在"汰换方式 × 角色 × 状态"三因子判定矩阵 + 大数据分批取数 |

### 候选④：面向 AI 编码的需求结构化转换与生成质量验证方法 ★★★（客体风险，需改包装）

**素材来源**：`20.知识沉淀/需求 → 提示词「硬化」模板.md`、`10.项目整理` 下纯零售进排程 AI 编码实验（r1 失败 8 点 → v3 全部修复的对照数据）

| 维度 | 内容 |
|---|---|
| **优势** | 有罕见的**实证对照数据**（r1 散文题面 vs v3 决策表题面、基线分支、8 类功能性错误归类），这在"AI 辅助编码"类交底书里非常稀缺 |
| **客体风险** | 裸的"提示词模板/写法规范"大概率被认定为智力活动规则（专利法 25 条）。**必须**包装成技术方案：例如"基于判定表/决策表的需求结构化转换方法及其代码生成质量验证方法"，把**机器可验证的验收特征**（契约常量逐字校验、落点锚点比对、改动清单范围断言、分支条数算例）作为技术手段，把对照实验（错误归因→模板迭代→复测通过率）作为有益效果证据 |
| **建议** | 先不急。优先推①②③；此方向更稳的落点是 **软著 + 公司 AI 创新奖 + 技术博客**，若公司有 AI 专项专利征集再包装申报 |

### 不适合单独成专利的沉淀（避免浪费精力）

| 沉淀 | 不推荐原因 |
|---|---|
| 踩坑手册系列（事务失效、NPE、线程池、@Valid 失效等） | 通用技术常识，无新颖性 |
| 排程四表关联链路单独成案 | 太内部、太细，应并入候选① 作为从属权利要求或实施例 |
| 上线发布 SOP、Redis/Kafka 学习手册 | 知识整理，非技术方案 |
| 前端查询小工具 | 功能过于常规，创造性弱（除非把"数据代理 + 聚合查询"讲出独特架构，性价比低） |

```text
主案：候选① 模板驱动的双层任务调度方法
  ├─ 从属：四表接力维度匹配（四表链路沉淀）
  ├─ 从属：多配置模式统一出口（mode5/6/7）
  └─ 从属：任务级/节点级双层激活与风险拦截

副案1：候选② 图像识别驱动的通知任务自动化（反馈闭环是亮点）
副案2：候选③ 供应商汰换三态判定与编排（大数据取数 + 判定矩阵）
储备：候选④ 改包装后视公司 AI 专项政策再报
```

优先级理由：候选①② 的"技术问题→手段→效果"三段在你已有文档里最完整，补齐交底书的工作量最小；候选① 还是你的系统主线认知，写起来最顺。

## 四、下一步行动清单

1. **走公司流程**：找到部门专利对接人（或贝壳法务 IP 团队），确认本年度专利申报窗口与奖励政策。
2. **自行预检索**（提交前必做）：在 Google Patents / incoPat / 智慧芽 用关键词检索：
   - 候选①：`任务调度 模板 状态机 履约`、`workflow template dispatch node`
   - 候选②：`图像识别 任务通知 自动化 工地`、`recognition result notification automation`
   - 候选③：`供应商 切换 在途订单 履约`
3. **写交底书**：以候选②为第一篇练手（闭环结构清晰），按上文"技术问题/手段/效果"三段直接扩写，附图用你已有的系统逻辑图 + 状态流转图（mermaid/飞书画板导出均可）。
4. **管住新颖性**：交底书提交给公司之前，不要把这些方案写成对外博客、公开分享或开源。

## 五、独立权利要求示例（以候选②为骨架，供感受写法）

> 权利要求 1：一种基于图像识别结果的主材履约任务通知方法，其特征在于，包括：
> 接收上游识别服务对工地影像数据进行分析得到的判定结果，所述判定结果包括可通知、不可通知、无法判断及现场已完成至少四种状态；
> 将所述判定结果与项目标识、品类标识及任务类型关联存储至自动化记录表；
> 根据预设的多级灰度配置确定所述任务的通知执行方式，所述多级灰度配置至少包括城市、工程部门、品类及作业人员维度；
> 当所述执行方式为自动通知时，基于所述判定结果对应的识别日期计算期望上门时间，并自动填充通知内容；当所述执行方式为人工通知时，将所述判定结果及关键帧图像推送至作业端以供确认；
> 记录所述任务的通知执行结果及对自动填充内容的采纳情况，并将所述采纳情况回写至所述自动化记录表。

从属权利要求按"四态分态处置 / 时间推算规则 / 轮巡与缓存预取 / 采纳反馈闭环"逐条展开即可。
