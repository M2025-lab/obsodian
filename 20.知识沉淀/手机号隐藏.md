## 防复发方案（2026-09-15 复盘沉淀）

### 一、差距的共性：隐含契约在三次交接里各丢一次

| 交接环节 | 丢的东西 | 表现 |
|---|---|---|
| 需求 → 方案 | 字段字典 | 角色名靠猜，同一个角色三套叫法 |
| 方案 → 代码 | 约束验证 | 没先查 DTO 里到底有什么字段，方案落地必然改契约 |
| 代码 → 验证 | 配置契约 | 测试环境配置恰好掩盖了 id 口径不一致 |

丢掉的是「没有人被迫写出来的那个假设」。这些差距都不是代码写错。

### 二、动作一：方案里强制一张四列表

| 接口 | 字段（代码名） | 开关 | 前端展示名 |
|---|---|---|---|
| queryProjectDetail | designerPhone | designerMobile | 设计师 |
| queryProjectDetail | assistantPhone | qualityControlMobile | 管家【品控】 |
| queryProjectDetail | foremanPhone | projectManagerMobile | 工长【项目经理】 |
| queryTaskDetail | purchaseDetailDTO.supplierContactorPhone | 无对应开关 | 供应商联系人 |
| queryByCode | projectServerBaseInfos[type=designer].phone | designerMobile | 设计师 |
| queryByCode | projectServerBaseInfos[type=foreman].phone | projectManagerMobile | 工长【项目经理】 |
| queryByCode | projectServerBaseInfos[type=butler].phone | qualityControlMobile | 管家 |

规则：**角色名必须引用仓库里的字典，不允许自造或按字面理解。**

本项目已有字典（不要再造）：`TaskDetailVo` 的 `@ApiModelProperty` 注释、`ProjectRelationEnum`（HOUSEKEEPER = 管家）。

真实踩坑：`assistantPhone` 字面像「助理」、`butler` 前端叫「管家」、`qualityControlMobile` 在采购单详情页叫「品控」——**三个名字同一个角色**。当时的错判是把 `assistantPhone` 当「助理」、把 `butler` 当「需求没点名的角色」判为不处理，两行都错。一条 grep 就能拿到的字典，没去查。

### 三、动作二：配置契约写进代码注释，不靠口口相传

- 在配置类（本项目 `PurchaseMobileFieldConfig`）类注释里写明：`supplierIds` 是哪一套 id（供应商 companyId？真实 supplierId？是否已 offset 归一化）。
- 本项目 id offset 常量在 `SupplierIdUtils.SUPPLIER_ID_OFFSET = 10000000`；入口处是否走 `getRealSupplierId` 归一化，直接决定配置能否命中。
- 新增"取供应商"的入口前，先确认与既有入口是否同一 id 空间。**同一需求里两个入口取到不同供应商 id**，是本次的真实缺陷（一边取登录态 `RequestContextHolder.getSupplierId()`，一边取下游 `supplierCode`）。

### 四、动作三：Apollo 回归用例必须覆盖 `supplierIds` 非空

只配「分公司级兜底规则」（`supplierIds=[]`）时，供应商 id 对不上也测不出来。测试数据覆盖度不足会掩盖**整类**配置契约风险——不是漏测一个分支，是整类风险在 offline 阶段不可见。

### 五、开工前 5 问（通用自查）

1. 我要改的字段，响应对象里真的存在吗？——先查 DTO，不靠假设。
2. 角色 / 枚举名有权威字典吗？——有就引用，没有就先建。
3. 仓库里有没有同语义的既有实现？——有就收敛复用，别复制改名（复制后必然语义漂移）。
4. 配置项的 id 口径和既有入口一致吗？
5. 下游失败 / 字段缺失时，我的代码是 fail-open 还是 fail-closed？——脱敏类逻辑必须 fail-closed。

### 六、本次遗留（角色映射已澄清，不在遗留内）

- `findMobileFieldConfig` 与 `PurchaseOrderFusionController` 的同名方法语义漂移，且 `supplierIds` 白名单失效（分支命中后未 `continue`）、单轮 `break` 顺序敏感、`null == null` 误命中 → 应收敛为一份。
- `supplierIds` 的 id 口径统一 / 归一化。
- `queryProjectDetail` 缺 `getData()` 判空，`.get(0)` 与 `Integer.valueOf` 未兜底（已出缺陷单，但只覆盖「服务角色缺失」一处）。
- `taskDispatchNodeId` 设为 `required = false` 造成 fail-open：调用方不传即可绕过供应商维度的隐藏。
- `queryByCode` 多施工包时只取 `packageInfoList.get(0)`。
- 脱敏值三套口径未对齐（需求文档 `"***********"` / 沟通结论 `null` / 实现 `""`），需与前端确认。
- 需求文档把 `qualityControlMobile` 注释成「供应商电话」，与本系统真实语义（品控 / 管家）冲突，建议直接改掉文档；从业务目的（防止供应商联系设计师）反推，供应商本人的联系方式无需脱敏。
