## 防复发方案（2026-09-15 复盘沉淀）

### 一、差距的共性：隐含契约在三次交接里各丢一次

| 交接环节 | 丢的东西 | 表现 |
|---|---|---|
| 需求 → 方案 | 字段字典 | 角色名靠猜，同一个角色三套叫法 |
| 方案 → 代码 | 约束验证 | 没先查 DTO 里到底有什么字段，方案落地必然改契约 |
| 代码 → 验证 | 配置契约 | 测试环境配置恰好掩盖了 id 口径不一致 |

丢掉的是「没有人被迫写出来的那个假设」。这些差距都不是代码写错。

### 二、动作一：方案里强制一张四列表

| 接口 | 字段（代码名） | 开关 | 前端展示名 |
|---|---|---|---|
| queryProjectDetail | designerPhone | designerMobile | 设计师 |
| queryProjectDetail | assistantPhone | qualityControlMobile | 管家【品控】 |
| queryProjectDetail | foremanPhone | projectManagerMobile | 工长【项目经理】 |
| queryTaskDetail | purchaseDetailDTO.supplierContactorPhone | 无对应开关 | 供应商联系人 |
| queryByCode | projectServerBaseInfos[type=designer].phone | designerMobile | 设计师 |
| queryByCode | projectServerBaseInfos[type=foreman].phone | projectManagerMobile | 工长【项目经理】 |
| queryByCode | projectServerBaseInfos[type=butler].phone | qualityControlMobile | 管家 |

规则：**角色名必须引用仓库里的字典，不允许自造或按字面理解。**

本项目已有字典（不要再造）：`TaskDetailVo` 的 `@ApiModelProperty` 注释、`ProjectRelationEnum`（HOUSEKEEPER = 管家）。

真实踩坑：`assistantPhone` 字面像「助理」、`butler` 前端叫「管家」、`qualityControlMobile` 在采购单详情页叫「品控」——**三个名字同一个角色**。当时的错判是把 `assistantPhone` 当「助理」、把 `butler` 当「需求没点名的角色」判为不处理，两行都错。一条 grep 就能拿到的字典，没去查。

### 三、动作二：配置契约写进代码注释，不靠口口相传

- 在配置类（本项目 `PurchaseMobileFieldConfig`）类注释里写明：`supplierIds` 是哪一套 id（供应商 companyId？真实 supplierId？是否已 offset 归一化）。
- 本项目 id offset 常量在 `SupplierIdUtils.SUPPLIER_ID_OFFSET = 10000000`；入口处是否走 `getRealSupplierId` 归一化，直接决定配置能否命中。
- 新增"取供应商"的入口前，先确认与既有入口是否同一 id 空间。**同一需求里两个入口取到不同供应商 id**，是本次的真实缺陷（一边取登录态 `RequestContextHolder.getSupplierId()`，一边取下游 `supplierCode`）。

### 四、动作三：Apollo 回归用例必须覆盖 `supplierIds` 非空

只配「分公司级兜底规则」（`supplierIds=[]`）时，供应商 id 对不上也测不出来。测试数据覆盖度不足会掩盖**整类**配置契约风险——不是漏测一个分支，是整类风险在 offline 阶段不可见。

### 五、开工前 5 问（通用自查）

1. 我要改的字段，响应对象里真的存在吗？——先查 DTO，不靠假设。
2. 角色 / 枚举名有权威字典吗？——有就引用，没有就先建。
3. 仓库里有没有同语义的既有实现？——有就收敛复用，别复制改名（复制后必然语义漂移）。
4. 配置项的 id 口径和既有入口一致吗？
5. 下游失败 / 字段缺失时，我的代码是 fail-open 还是 fail-closed？——脱敏类逻辑必须 fail-closed。

### 六、本次遗留（角色映射已澄清，不在遗留内）

- `findMobileFieldConfig` 与 `PurchaseOrderFusionController` 的同名方法语义漂移，且 `supplierIds` 白名单失效（分支命中后未 `continue`）、单轮 `break` 顺序敏感、`null == null` 误命中 → 应收敛为一份。
- `supplierIds` 的 id 口径统一 / 归一化。
- `queryProjectDetail` 缺 `getData()` 判空，`.get(0)` 与 `Integer.valueOf` 未兜底（已出缺陷单，但只覆盖「服务角色缺失」一处）。
- `taskDispatchNodeId` 设为 `required = false` 造成 fail-open：调用方不传即可绕过供应商维度的隐藏。
- `queryByCode` 多施工包时只取 `packageInfoList.get(0)`。
- 脱敏值三套口径未对齐（需求文档 `"***********"` / 沟通结论 `null` / 实现 `""`），需与前端确认。
- 需求文档把 `qualityControlMobile` 注释成「供应商电话」，与本系统真实语义（品控 / 管家）冲突，建议直接改掉文档；从业务目的（防止供应商联系设计师）反推，供应商本人的联系方式无需脱敏。

# 检索协议：把「人喂事实」改成「AI 自己查」——第二轮迭代报告

> 模型 deepseek-v4-flash｜任务 VSS 作业详情页手机号显隐（需求 50557689）｜日期 2026-09-15
> 核心结论：首轮散文题面人工删改 ~80%；补全"事实清单"后降到 28%；进一步把可检索项从题面移出、改写成【检索任务】+ 算子后，**题面里真正需要人写的只剩 4~5 条决策**。

## 0、适用

承接《优化提示词对 AI 代码生成质量的提升报告》§7.2「问题一：需要人给的信息太多」。
适用于**入口明确、但要人补大量外界事实**的改造类需求 —— 尤其是"某字段存不存在 / 某配置什么口径 / 有没有同类实现"这类问题。

## 一、背景

需求本身很小（按 Apollo 配置隐藏 VSS 复尺 / 报价复核 / 安装三个页面的联系人手机号），
但它踩中了上一份报告没覆盖的一类偏差：**题面把"事实"当成了"需求"来写**，而事实本可以从代码里拿到。

| 轮次 | 题面形态 | 结果 |
|---|---|---|
| 第 1 轮 | 散文 + 页面截图 + 两段 JSON | 代码生成 2 轮，**人工删改 ~80%**（多数是删减） |
| 第 2 轮 | 六槽硬化版（7 条硬性事实 + 字段映射表 + 12 条禁止清单） | 代码生成 **1 轮，人工删改 28%** |
| 第 3 轮（本次） | 把可检索的条目从题面移出，改写成【检索任务】+ 算子 | 见 §四、§五 |

## 二、实验设置

- **指标**：沟通轮数 = 首次指令到可接受代码的交互轮次；返工率 = 人工修改行数 ÷ AI 生成行数。
- **口径（必须声明）**：返工率按 **churn（增+删）** 计；分母为 AI 生成量；**含** Controller 层的纯格式改动（本次 5 行）。
  > 同一份代码、三档口径给出 **117% / 29% / 11%**，差三倍 —— 不声明口径的百分比不可比。
- **对照**：同一需求两个分支落地（`feat/aiTest/R1` = AI 产出；`feat-20260914-IphoneDisplay` = 人工多轮产物）。
  两侧**文件集完全相同**（3 个文件）、`G1/F1 = 100%`、无越界 → 对照有效。
  人工分支自身 `R5 = 45.2%`（累计 churn 248 / 净 136）→ 说明"一次到位"不现实，验收阈值应定"轮次 ≤ 2"而非 0。

## 三、问题分析

| # | 现象 | 根因 | 对应机制 |
|---|---|---|---|
| 1 | `assistantPhone` 被当"助理"、`butler` 被当"没点名的角色"，两行都判错 | 题面没给**业务黑话字典**，AI 按字面理解 | §4.1 可检索性判定 + 算子 A4 |
| 2 | 复制了一份 `findMobileFieldConfig` 并改名改语义，与权威实现漂移 | 没检索**同类既有实现** | 算子 A5（配置 key 反查） |
| 3 | 首轮多出新类、抽方法、try-catch、日志，删了 80% | 题面没给**生成预算** | 偏差 5 +【生成预算】+`【必须新增】`授权 |
| 4 | 供应商 id 一边取登录态、一边取下游 `supplierCode`，两套口径无人能答 | **id 口径是隐性知识**，代码里只有注释、没有结论 | 隐性知识外化 + 算子 A7 穷举 |
| 5 | 拿方案里**自造的类名**去 grep 同类实现 → 0 命中 → 误判"仓库里没有" | 算子没有**种子**，AI 自己编了一个去搜 | §4.3 种子纪律（一级 / 二级算子） |
| 6 | 脱敏值 `"***********"` → `null` → `""` 三轮才定；某角色是否纳入也分两次问 | 开放决策**挤牙膏式**分次问 | §九 桶三：开工前一次性问完 |

> 1–3 对应上一份报告的歧义 / 联动类；**4–6 是本次新识别的一类：信息供给方式**。

## 四、机制（对应上一份报告的「四、模板」）

本次**没有改六槽本身**，而是新增了一层"信息从哪来"的协议。

### 4.1 可检索性判定（题面前置关）

判据一句话：**这条信息，AI 自己在代码里能找到吗？**

- **能** → 不写结论，写【检索任务】（结论是快照会腐化，检索路径不会）
- **不能** → 才写进题面

> 实证：写死 `PackageBaseInfoDTO.getWorkerId()` = javap 快照，API 改名即失效；
> 写成"去该类找供应商 id 字段，优先 `workerId`，否则 `materialSupplierList[].supplierCode`" = 长期有效。

本需求的实测分布见本文件上方表格：**10 条里 5 条可转检索任务**，
真正需人拍板的只剩 4~5 条（脱敏值 / 供应商电话是否脱敏 / 是否新增签名入参 / 生成预算 / id 口径结论）。

**压缩"人拍板项"的规则**：默认**跟随既有先例**（可检索）；**偏离先例必须先问**（不可检索）—— 把开放问答降级成审批题，人只需回一个字。护栏：先例本身可能是缺陷。

### 4.2 检索算子（九个，分两级）

| 级别 | 算子 | 能否作起点 |
|---|---|---|
| **一级**（种子由外部给定：需求原文 / 报文 / 已有配置） | A4 搜中文注释 / A5 配置 key 反查 / A6 响应字段名反查 DTO / A7 jar 字段穷举 / A8 `git log -S` | ✅ 可作起点 |
| **二级**（需要一个符号种子） | A1 顺藤摸瓜 / A2 命名约定 / A3 找兄弟方法 | ❌ **只能作扩展** |

**A4 / A5 是 AI 的天然盲区**：它默认只搜英文标识符，不会搜"管家"这类中文业务词，也不会用配置 key 反查使用者。
**A2 最危险**：`Phone|Mobile|Contact` 会命中一堆无关字段，AI 容易从中"挑一个看起来对的"。

核心操作点：**人给的应是"命令"不是"意图"**。`javap -p` 一条命令列全字段，胜过"去看一下这个类"。

### 4.3 种子纪律（本次新增）

种子必须**已确证存在**：需求 / 报文里逐字出现的名字、已确认的代码字面、上一轮算子命中的结果。
**不合格种子**：臆想的字段名、按语义翻的英文名（把"管家"翻成 `housekeeper`）、**方案里自造的新类名**（它们还不存在）。

- 开工前先写 `算子 | 种子 | 种子出处`；**写出不来源 → 不许搜**。
- **0 命中只有两条合法动作**：① 换合格种子重搜；② 报「未命中 + 种子 + 出处」交回。
  **禁止**自编名字再搜；**禁止**由 0 命中推出"不存在"。

### 4.4 检索任务构成

`算子 + 种子 + 种子出处 + 指针 + 要找 + 验收证据 + 歧义交回 + 预算`
其中**只有"指针"和"种子"由人给**，其余由 AI 自答。四条护栏：多源交叉（≥2 独立来源，单源要标注）、分层与预算（L1 广搜 / L2 定点读 / L3 深读需批准）、**报告"文档与代码不一致"**、结果**回写检索地图**。

### 4.5 返工归因闭环

每轮记「人工修改行数 + 四类归因」，把 ①（多写）翻成禁止清单、②③④ 翻成前置验证清单。

- **口径必须先声明**（churn / 净增？含不含纯格式？含不含配套？）
- **给归因设上限**：修正后返工率应与基准自身 `R5` 同量级，否则多出来的**不是信息缺失造成的** —— 别往题面堆约束，那正是腐化起点。
- **形态对齐**：抽不抽方法由基准形态决定（`M7 > |M6|` 才要求抽，单文件纯叠加则禁止）；基建只有打 `【必须新增】` 才允许生成。

## 六、边界与结论

- **适用**：入口明确、但需要人补大量外界事实的改造类需求。
  **不适用**：探索型 / 考古型任务（还不知道要改哪）、一次性脚本、实验分支 —— 先让 AI 调研出结论，再基于结论生成。
- **结论一**：第 2 轮剩下的 28% 里，"多写的代码"仍占大头 → 靠【生成预算】+ 禁止清单压，**不靠多解释**。
- **结论二**：**可检索项不该进题面**。把 5/10 条移出去后，题面从"事实清单"变成"**检索计划 + 决策清单**"；人的工作是"给指针 + 拍板"，不是"搬运"。
- **结论三**：**不能指望算子解决全部**。三件 AI 学不像人的事：领域常识（靠项目词典补）、问同事（只能回来问人，但要**批量一次问完**）、注释缺失时代码会骗人（只能靠"贴证据 + 多源交叉"）。
- **结论四**：**抽不抽方法、要不要建基建，由度量形态决定，不由题面单方面规定** —— 否则与 `git-change-metrics` 的两条规则互相抵消。

## 七、下一步

### 7.1 待验证

1. **种子纪律是否真能拦住"臆想字段"** —— 下一轮把 `算子|种子|出处` 从"建议"改成"必须输出"，看 AI 是否会主动暴露"出处 = 我推测"。
2. **`【必须新增】` 标签能否双向可用** —— 它现在既是题面的"授权凭证"，也是度量侧 `G1` 越界判定的"审计凭证"；越界清单里出现没打标签的新类 = 过度生成。需实测能否自动区分"该做的没做"与"不该做的做了"。
3. **检索地图的增量质量** —— 每轮回写后，下一轮题面能省掉多少行。

### 7.2 现在的问题

1. **检索地图要人维护**，"去哪找"的锚点会随代码演进失效。
2. **可检索 / 不可检索的边界靠人工判定**，判错（把不可检索的当成可检索）会造成静默错误。
3. **样本仍只有 1 个需求**，`5/10` 这个比例不可外推。

### 7.3 初步解决办法

| 问题 | 做法 | 风险 |
|---|---|---|
