# 📚 父子任务共用线程池导致接口超时无返回

> **踩坑对象**：接口内"父任务提交子任务到同一个线程池并行处理，再用 `Future.get(timeout)` 阻塞等待子任务结果"
> **一句话结论**：父子任务共用同一个线程池，并发上来后父任务占满所有核心线程、又在队列里排子任务，自己却阻塞在 `get()` 上等子任务——子任务拿不到线程、父任务等不到子任务，形成**线程池饥饿死锁**；父任务虽有固定超时，但超时只是打断了自己的等待、并没有兜底返回值，接口最终表现为**固定卡到超时时长、且无返回**。
> **沉淀日期**：2026-09-11
> **关联笔记**：[[📚 异常排查 & 调用链分析 完整手册]]、[[📚 功能开关位置写在循环外导致工程部配置不生效]]（同样是"本地不复现、上了量才暴露"的家族坑）

---

## 1. 问题现象

业务场景：一个聚合接口，内部把多个下游查询拆成子任务丢进线程池并行跑，父任务用 `Future.get(timeout)` 收集结果后聚合返回。接口配置了固定超时时长（如 3s）。

预期：子任务并行执行，父任务收集完结果在超时内返回；即使某个子任务慢，父任务也应在超时时长内兜底返回部分结果或降级结果。

实际：

- **低并发 / 本地**：完全正常，秒回；
- **上量后（预发 / 生产）**：接口固定在超时时长（3s）后才返回，且**无返回结果**（前端 / 调用方看到的是超时、空响应）；
- 线程池监控：核心线程打满、队列堆积、任务大量堆积；
- GC、CPU、下游 RT 都正常，下游单独压测也没问题。

一句话：**下游没问题、机器没问题，但接口固定卡到超时且无返回，且只在并发上来后复现。**

## 2. 根因分析

### 2.1 问题代码结构（父子共用一个池）

```java
// ❌ 父任务和子任务共用同一个线程池 sharedExecutor
@Resource
private ExecutorService sharedExecutor;   // 比如 core=8, queue=200

public AggResult aggregate(List<Param> params) {
    List<Future<SubResult>> futures = new ArrayList<>();
    for (Param p : params) {
        // 子任务提交到同一个 sharedExecutor
        futures.add(sharedExecutor.submit(() -> queryDownstream(p)));
    }

    AggResult result = new AggResult();
    for (Future<SubResult> f : futures) {
        // 父任务阻塞等待子任务，固定超时 3s
        result.add(f.get(3, TimeUnit.SECONDS));   // ← 卡死在这里
    }
    return result;
}
```

关键点：**父任务跑在 `sharedExecutor` 的线程里**（接口入口或上层调用就在该池），**子任务又被提交回 `sharedExecutor`**。并发一上来，池里的线程全被父任务占着等 `get()`，子任务全在队列里排不上线程。

### 2.2 死锁形成链路

```text
  父任务A ──持有线程T1──► submit 子任务A1 ──► 子任务A1 入队列排队
           └──阻塞在 f.get() 等子任务A1结果────────────────▲
                                                            │
  父任务B ──持有线程T2──► submit 子任务B1 ──► 子任务B1 入队列排队
           └──阻塞在 f.get() 等子任务B1结果────────────────▲
                                                            │
              ... 所有核心线程都被父任务占满、都在阻塞等待 ...    │
                                                            │
              子任务在队列里拿不到空闲线程 ──────────────────────┘ 永远轮不到执行

  → 父任务等子任务，子任务等线程 → 线程池饥饿死锁（Thread Starvation Deadlock）
```

这就是经典的 **"任务在同一个池里等待自己池里的任务"** → 资源自循环依赖 → 死锁。和数据库死锁不同，这种死锁**不抛异常、不打印 stack**，线程全 `WAITING` 在 `get()` 上，线程池表面"活着"实际已僵死。

### 2.3 为什么"有超时"还是"无返回"

这是本坑最容易误判的点——**超时只是打破父任务的等待，并不等于接口有返回**：

1. `f.get(3, SECONDS)` 在死锁场景下到点抛 `TimeoutException`；
2. 如果代码里**没有 catch 兜底 / 降级返回**，异常往上抛 → 接口 500 / 超时无返回；
3. 即使 catch 了，子任务还在队列里**继续占位**，下一波请求进来继续堆积，线程池长期僵死；
4. 接口配置的"固定超时时长"本质就是这个 `get(3s)` 的等待，所以表现为**固定卡在 3s、且无返回**。

```text
有超时 ≠ 有返回：
  ┌─ 父任务 f.get(3s) ──超时抛 TimeoutException──┐
  │   (打破了等待，但子任务还在队列里)              │
  └─ 没有 catch 兜底 ──► 异常上抛 ──► 接口无返回 ◄─┘
```

### 2.4 链路流程图

```text
                 ┌──────────────────────────────────┐
                 │   并发请求涌入（N 个父任务）        │
                 └────────────────┬─────────────────┘
                                  ▼
                 ┌──────────────────────────────────┐
                 │ sharedExecutor 核心线程被父任务占满 │
                 │  父任务都阻塞在 f.get() 等子任务      │
                 └────────────────┬─────────────────┘
                                  ▼
                 ┌──────────────────────────────────┐
                 │  子任务进队列，拿不到空闲线程        │
                 └────────────────┬─────────────────┘
                                  ▼
                    ┌──────────────────────────┐
                    │ 父等子 / 子等线程 = 死锁    │
                    └────────────┬─────────────┘
                                 ▼
                 ┌──────────────────────────────────┐
                 │ f.get(3s) 超时抛 TimeoutException  │
                 │ 无兜底 → 接口超时且无返回            │
                 └──────────────────────────────────┘
```

## 3. 解决方案

核心原则：**父子任务不能共用同一个线程池——要么隔离池，要么父任务不阻塞等待。**

### 3.1 方案选型

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| ① 父子隔离线程池（最终采用） | 父任务用池 A，子任务用池 B，两个池物理隔离 | 彻底切断"任务等任务"的自循环依赖，根治死锁 | 需要规划两个池的容量，多占一点内存 |
| ② CompletableFuture + 异步编排 | `supplyAsync(task, subExecutor)` + `allOf().join()` 收口，父任务不占子池线程 | 异步非阻塞，编排灵活，天然隔离 | 需改造为异步风格，`join` 仍要控制超时 |
| ③ 父任务直接跑在当前请求线程，不进池 | 接口入口就跑在请求线程上（如 Tomcat 线程），只把子任务丢池里 | 父任务不占子池线程，结构上避免死锁 | 需确认上层调用方没把父任务也丢进同一个池 |
| ④ 单纯调大池 / 换无界队列 | 扩大 core/max、换无界队列、加超时 | 改动小 | 治标不治本，并发再涨照样死锁，且无界队列会 OOM |

> 本次采用方案 ①：父子任务用两个物理隔离的线程池，并给子任务单独设超时 + 兜底降级。

### 3.2 方案①：父子隔离线程池

```java
// ✅ 父任务和子任务用不同的池，物理隔离
@Resource(name = "parentExecutor")   // 父任务池（或直接用请求线程）
private ExecutorService parentExecutor;
@Resource(name = "childExecutor")    // 子任务池
private ExecutorService childExecutor;

public AggResult aggregate(List<Param> params) {
    List<Future<SubResult>> futures = new ArrayList<>();
    for (Param p : params) {
        // 子任务丢到 childExecutor，不再和父任务抢同一个池
        futures.add(childExecutor.submit(() -> queryDownstream(p)));
    }

    AggResult result = new AggResult();
    for (Future<SubResult> f : futures) {
        try {
            result.add(f.get(800, TimeUnit.MILLISECONDS));   // 子任务单独超时
        } catch (TimeoutException e) {
            f.cancel(true);                                   // 超时就取消，别留在队列里占位
            result.add(SubResult.degraded());                 // 兜底降级，必须有返回
        } catch (Exception e) {
            result.add(SubResult.degraded());
        }
    }
    return result;   // ← 无论如何都有返回
}
```

两个关键改动：

1. **子任务单独走 `childExecutor`**——父任务占的池和子任务跑的池不是同一个，子任务总能拿到线程；
2. **`get()` 超时后 `cancel(true)` + 兜底降级**——超时不是终点，必须有返回值，子任务也要从队列里清掉。

### 3.3 方案②：CompletableFuture 异步编排

```java
// ✅ CompletableFuture + 独立子池，allOf 收口
public AggResult aggregate(List<Param> params) {
    List<CompletableFuture<SubResult>> cfs = params.stream()
            .map(p -> CompletableFuture.supplyAsync(
                    () -> queryDownstream(p), childExecutor)                   // 子任务走 childExecutor
                    .completeOnTimeout(SubResult.degraded(), 800, TimeUnit.MILLISECONDS)  // 单任务超时降级
                    .exceptionally(ex -> SubResult.degraded()))
            .collect(Collectors.toList());

    CompletableFuture.allOf(cfs.toArray(new CompletableFuture[0]))
            .join();   // 等全部完成（每个都有自己的超时降级，不会无限等）

    AggResult result = new AggResult();
    cfs.forEach(cf -> result.add(cf.join()));
    return result;
}
```

`completeOnTimeout` + `exceptionally` 保证了**每个子任务都有兜底返回**，`allOf` 收口时不会再死等。

### 3.4 子池容量怎么配

隔离后子池容量要按"子任务并发数 × 单任务 RT"估算，避免子池本身成为新瓶颈：

```text
子池核心线程 ≈ 接口峰值 QPS × 单子任务 RT(秒)
例如：1000 QPS × 0.1s = 100 个线程（再按实际压测调整）
队列：用有界队列（如 ArrayBlockingQueue(500)），拒绝策略用 CallerRunsPolicy 兜底
```

> 无界队列 = 把"快速失败"变成"OOM 慢死"，并发场景下宁可拒绝也不能堆积。

### 3.5 防回归

- 本地压测必须**打满父任务并发**，让池里同时有多个父任务排队，才能复现"父等子"；
- 线程池监控加告警：**队列堆积量、活跃线程数、拒绝次数**——死锁前兆是"活跃线程满 + 队列涨 + 任务不消费"；
- Code Review 检查项：**凡是 `executor.submit(...)` 后紧跟 `future.get()` 的，确认子任务和当前线程不在同一个池**。

## 4. 易混淆点

### 4.1 "超时" vs "有返回" vs "降级"

| 概念 | 含义 | 本坑表现 |
|---|---|---|
| 超时 | `get(timeout)` 打破等待，抛 `TimeoutException` | ✅ 有超时（固定 3s） |
| 有返回 | 接口给出正常 / 降级响应 | ❌ 无返回（没兜底，异常上抛） |
| 降级 | 超时 / 异常时给兜底值 | ❌ 缺失（这是"无返回"的直接原因） |

**关键区分**：超时是手段不是结果。超时后没有 `catch` + 降级返回，接口就是"超时且无返回"。**有超时 ≠ 有返回**，必须显式补降级。

### 4.2 线程池饥饿死锁 vs 数据库死锁

| 维度 | 线程池饥饿死锁 | 数据库死锁 |
|---|---|---|
| 触发 | 同一池里任务等待任务 | 事务互相持有对方需要的锁 |
| 现象 | 线程全 WAITING、任务不消费、接口超时 | 抛 DeadlockFoundException |
| 是否报错 | ❌ 静默僵死，不抛异常 | ✅ 数据库主动报错回滚 |
| 解除 | 需重启 / 隔离池，超时只是打断等待 | 数据库自动检测回滚一方 |

> 线程池死锁最阴险的是**不报错、不打印、表面正常**，只能靠监控"活跃线程满 + 队列涨 + 无消费"发现。

### 4.3 `Future.cancel(true)` 到底有没有用

| 场景 | `cancel(true)` 效果 |
|---|---|
| 任务还在队列里没跑 | ✅ 从队列移除，不再占用 |
| 任务正在跑 | ⚠️ 仅设置中断标志，能否真停取决于任务代码是否响应中断（`Thread.sleep` / 阻塞 IO 会抛 `InterruptedException`，纯 CPU 循环不会停） |
| 任务已完成 | ❌ 无效 |

> 所以 `cancel(true)` 主要价值是**清掉队列里还没跑的任务**，别让它继续占位；对正在跑的慢任务别指望它立即停。这也意味着——**超时降级后，慢子任务可能还在后台跑**，要靠下游自身的超时控制兜底。

### 4.4 为什么本地不复现

| 陷阱 | 本坑是否命中 |
|---|---|
| 并发不够，父任务没占满池 | ✅ 本地单线程压测，池里就一个父任务，子任务随时拿得到线程 |
| 本地子任务 RT 短，没积压 | ✅ 本地下游 Mock 秒回，队列不堆积 |
| 没有模拟"多个父任务同时阻塞" | ✅ 这是复现的必要条件 |
| 环境差异 | ❌ 与环境无关，纯并发资源争用 |

**教训**：线程池类问题必须用**多线程压测**复现，单线程跑永远是"正常"的。

## 5. 进阶问题

### 5.1 父任务跑在 Tomcat 线程上，还要不要单独建父池？

如果接口入口就在 Tomcat / 请求线程上，父任务**根本没进任何业务线程池**——这种结构本身就不会死锁（子池和请求线程池是分开的）。这种情况下：

- **不需要父池**，父逻辑直接跑在请求线程，子任务丢 `childExecutor`；
- 注意别让上层调用方（如某个调度任务）把这段逻辑又丢进 `childExecutor`，否则隔离失效。

### 5.2 已经用 `CompletableFuture` 了还会死锁吗？

会。如果 `supplyAsync(task, executor)` 用的 executor 和外层 `join()` 所在的线程属于同一个池，照样死锁。**隔离看的是"任务跑的池"和"等待任务结果的线程所属的池"是不是同一个**，和用 Future 还是 CompletableFuture 无关。

### 5.3 用 `ForkJoinPool` / `parallelStream` 有没有这个问题？

有，而且更隐蔽。`ForkJoinPool` 的 work-stealing 在**子任务和父任务在同一个池**时同样会遇到"所有 worker 都在 join 等子任务、子任务没 worker 执行"的饥饿。Java 8 的 `parallelStream` 默认用公共 `ForkJoinPool.commonPool()`，在它里面 `join` 自己提交的任务同样会死锁。**ForkJoinPool 的正确用法是子任务用 `fork` 而非另起 `submit`，且不要在池里阻塞等待。**

## 6. 生活比喻

把线程池想象成**一家餐厅的厨师团队**，接口就是一桌客人点的菜：

- **父子共用一个池（出 bug）** = 餐厅只有一组厨师。服务员（父任务）冲进厨房**占了所有厨师去接单记账**，然后又喊"厨师们去做配菜（子任务）"——可厨师全被服务员占着呢，配菜没人做；服务员又端着盘子干等配菜上桌 → **整桌菜卡死上不出来，最后到点（超时）直接撤桌、客人什么都没吃着（无返回）**。

- **父子隔离两个池（正确）** = 餐厅有"服务员组"和"厨师组"两组人。服务员只管接单催菜，厨师只管做菜——服务员不会被拉去炒菜占着灶台，配菜总有厨师做，到点上不齐的菜就走"预制菜兜底（降级返回）"，客人**至少能吃到东西**。

核心：**别让等菜的人把灶台都占了，做菜的人反倒没灶用。** 等的人和做的人必须是两拨人（两个池），而且到点没上齐的菜要有兜底（降级），不能让客人空手走。

## 7. 一句话记忆

> **父子不同池，超时必降级——别让等菜的人占了灶台。**

- **现象**：接口固定卡在超时时长且无返回，下游 / CPU / GC 都正常，只在并发上来后复现。
- **根因**：父子任务共用一个线程池，父任务占满线程等子任务、子任务在队列里拿不到线程 → 线程池饥饿死锁；超时只是打断等待，没有兜底降级 → 接口无返回。
- **陷阱**：以为"有超时就有返回"——超时不等于返回，缺降级就是空响应；以为本地能复现——单线程压测永远正常；线程池死锁不报错、不打印，静默僵死。
- **定位要点**：监控看"活跃线程满 + 队列涨 + 任务不消费"；Code Review 看 `submit` 后紧跟 `get` 的地方，确认子任务和当前线程不在同一个池；解决一律"父子池隔离 + 单任务超时 + 兜底降级"。
