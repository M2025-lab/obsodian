# 02 配置体系与数据来源

> 回答的问题：配置人员现在怎么配置？模板（"测量→复尺"、"测量→下单送货"）这种流程数据来自哪里？node_type 来自哪里？category 表数据是不是前端拉 OFC 后填写提交的？

## 0. 重要认知纠偏：配置人员**不再用流程编辑器画图**

当前配置方式是"**表格勾选维度 + 下拉选现成流程模板**"：

- 排程主规则 `POST /material/flow/rule/save`：勾选单据类型/订单版本/分公司/店铺/套餐（`MaterialFlowCreateParam`）→ 落 `material_flow_rule` + `material_flow_rule_unit` + Feign 同步 OFC `OfcDispatchConfigMergeApi.saveMainRule`。
- 品类规则 `POST /material/flow/category/save`：勾选品类+供应商+下拉选模板（`MaterialFlowCatgoryCreateParam.nodeProcess` = 模板id）→ 落 `material_flow_rule_category`（每供应商一条，category_id=雪花id）+ OFC `saveSecondRule`。
- 模板从 OFC 拉现成列表（queryTemplateList），edar-starlord 只存引用。

老画图入口（`manpower/cfg/processDefineSave`、`category/process/route/save`）代码仍在但属老体系，是否废弃无法从代码判定（见 99 篇）。

## 1. 品类规则绑定模板：落在品类规则表本身（每供应商一行）

| 字段 | 注释 | 含义 |
|---|---|---|
| `rule_id` | 规则id | 所属主规则 |
| `category_id` | 品类规则code | 雪花ID，一条记录一个 |
| `material_code` / `supplier_code` | 品类code / 供应商code | 维度：**品类+供应商 唯一确定一条** |
| `node_process` | 节点流程 | **模板ID**（下拉选中的 OFC 模板 templateId） |
| `node_process_name` | 节点流程信息(测量-设计-复尺-报价变更-送货-安装) | 模板名（展示用） |
| `state` | 0:编辑,1:有效,2:失效 | 生效状态 |

两张体系表（语义相同）：

| 体系 | 表 | 写入点（文件:行号） |
|---|---|---|
| 排程体系（当前主用） | `material_flow_rule_category` | `MaterialFlowCategoryServiceImpl.java:660-661`（categorySave）、`:850-851`、`:924-925` |
| 老体系 | `delivery_flow_rule_category` | `DeliveryFlowCategoryServiceImpl.java:365`、`:708`、`:884` |

⚠️ 易混淆：`material_flow_rule_template_mapping`（rule_category_id ↔ n_template_code ↔ task_type ↔ state）也叫"模板映射"，但它**不是**品类规则绑模板——是模板与具体任务类型/模板编码的映射，写入入口分散（processSave / copyCategoryTemplate / categoryInfoUpdate），web 层只有 TestController 注入，生产入口未完全钉死。

## 2. 模板清单（"测量→复尺"这类任务序列）来自哪里

**两个同名 `queryTemplateList`，代表两套平行来源：**

| 来源 | 调用链 | 数据形态 | 谁维护 |
|---|---|---|---|
| **OFC 供应链远程**（排程配置页下拉用） | `/material/flow/query/selected/ofcNodeProcessTemplateList` → `MaterialFlowSelectQueryServiceImpl.queryOfcNodeProcessTemplateList`(:407) → `OfcDispatchConfigMergeManagerImpl.queryOfcNodeProcessTemplateList`(:152) → Feign `OfcDispatchConfigMergeApi.queryTemplateList` | `DispatchTemplateDto`：templateId + nodeList[nodeCode/nodeName/rank] | **OFC 供应链侧** |
| **本地表 `n_material_process_template`**（deliveryflow 包读取） | `DeliveryFlowSelectQueryServiceImpl.queryTemplateList`(:494-523) 全表查，按 template_id 分组 | 每行 = 模板内一个任务（template_id/template_name/task_type/task_name/rank） | 本仓库**只读** |

### OFC 模板 nodeCode → 任务类型映射

`MaterialFlowCategoryServiceImpl.getTaskTypeListByNodeProcess`（:734，映射在 :741-751）：用 `TaskTypeEnum.getFulfillmentLinkCode()` 与 nodeCode 相等匹配，把模板节点映射为任务类型（测量/设计/复尺/送货…），构成任务序列。

## 3. 本地镜像表 `n_material_process_template` 的数据来源（排查结论）

**判定：OFC「履约流程模板」的本地只读镜像；edar-starlord 应用自身没有任何写入入口，同步/落库动作不在本仓库内。**

证据链：

| 排查点 | 结果 | 证据 |
|---|---|---|
| DAO 层方法 | 只有 `queryList` / `queryByTemplateId`，无 insert/update/delete | `NMaterialProcessTemplateDao.java:9-11` |
| DAO 实现 | 只调 `selectByExample` | `NMaterialProcessTemplateDaoImpl.java:22-32` |
| 直接注入 Mapper 的调用方 | `DeliveryFlowSelectQueryServiceImpl`（:70 注入，:496 调用）也只调 `selectByExample` | — |
| base Mapper XML 写语句 | insert/update/delete/batchInsert 都在，但**全仓库无任何调用方** | `NMaterialProcessTemplateMapper.xml:98-348` |
| 定时任务 / MQ 消费者 | 无任何 ProcessTemplate 相关写入或同步逻辑 | 全局 grep 无命中 |
| 建表来源 | MyBatis Generator 从数据库逆向生成（DBA 先建表、应用后接） | generatorConfig `<table>` 节点 |

**git 佐证**：commit `f27e1754f`（2025-10-20，fanfuxin，需求[50504234]「主材进排程」调度及品类流程配置 增加模版表）只新增查询侧（DTO/DAO/Mapper/model/generatorConfig/DeliveryFlowSelectQueryServiceImpl 查询逻辑），无任何写入或同步代码——设计上就是"读一份现成的数据"。

**字段同构**（本地 model 注释 ↔ OFC queryTemplateList 返回）：

| 本地字段 | 注释 | OFC 对应 |
|---|---|---|
| `template_id` | 履约流程模板ID | templateId |
| `template_name` | 履约流程模板名称 | 模板名 |
| `task_type` | 任务Code | nodeList[].nodeCode 映射后的任务类型 |
| `task_name` | 任务名称 | nodeList[].nodeName（如"测量""复尺"） |
| `rank` | 顺序 | nodeList[].rank |

OFC Feign 客户端 `OfcDispatchConfigMergeApi` 来自外部依赖 jar（`com.ke.utopia.scm.ofc.api.conf`），不在本仓库——模板定义、维护都在 OFC 供应链服务里，本仓库只能查、写不到。

OFC 数据落进本地表的三种可能（**未决**，需 OFC 侧或 DBA 确认）：① 共享库直写；② DBA/脚本定时同步；③ 数据管道（DataX 等）。可用线上 `template_id` 与 OFC 接口返回的 `templateId` 对比验证镜像关系。

## 4. 真正跑流程的"执行细节"存在哪（本地表，页面配置生成）

模板清单只回答"流程里有哪几个任务"，每个任务怎么跑落在另一组本地表，**以品类 category_id 当 template_id**：

| 表 | 内容 |
|---|---|
| `n_material_process_define` | 一条 = 一个 taskType 的流程定义（process_code 归属） |
| `n_material_node_cfg` | 节点：node_type、activateMode、时限 |
| `n_material_task_cfg` | 任务：角色 role_types 等 |
| `n_material_route` / `n_material_edge` | 节点间连线/流转 |

写入由**配置页面基于所选模板配置/复制生成**，不是 OFC 下发：

- `DeliveryFlowCategoryServiceImpl.categoryUpdate`(:892) → `effectiveCategoryProcess(旧categoryId, 新categoryId, processInfoParam, state)` —— processInfoParam 就是页面配置的节点细节；
- `categorySupplierUpdate`(:716-734) 换模板时，用 `nMaterialProcessTemplateDao.queryByTemplateId` 比较新旧模板的任务名，把减少的任务配置**物理删除**——说明模板决定 define 结构，细节由页面维护。

## 5. `n_material_node_cfg.node_type` 来自哪里

**结论：配置人员在页面上逐节点选择的「节点类型」枚举值（NodeTypeEnum），随品类流程保存参数落表；不是 OFC 下发，也不是运行时生成。**

落表链路：

```
前端 nodeList[].nodeType（CategoryProcessDefineSaveParam.ProcessDefineDTO）
  → DeliveryFlowTaskNodeSaveParam（:345 遍历）
  → NMaterialNodeForm（:347 copy）
  → NMaterialNodeCfg（:1037 copy）
  → n_material_node_cfg.node_type（:1040 insertSelective）
```

| 环节 | 位置 |
|---|---|
| 保存接口入口 | `CategoryProcessController.processDefineInfoSave`(:134) |
| 组装节点表单 | `CategoryProcessServiceImpl.buildMaterialNodeForm`(:325-347) |
| 保存明细 | `saveProcessDefineDetail`(:926-940) |
| 最终落表 | `batchInsertMaterialNodes`(:1024-1040) |

node_type 取值域 = `NodeTypeEnum`（`edar-starlord-base/.../NodeTypeEnum.java:14-21`）：

| 值 | 枚举名 | 页面含义 |
|---|---|---|
| 1 | NODE_START | 开始节点 |
| 20 | NOTIFY_CAN_START | 约工（通知启动） |
| 40 | NOTIFY_START | 派单（启动派单） |
| 50 | SELF_CHECK | 进场 |
| 60 | START | 提交自检 |
| 65 | SELF_CHECK_ACCEPTANCE | 自检验收 |
| 80 | FINISH_START | 实地验收 |
| 85 | OWNER_CONFIRM | 业主确认 |

其他旁路入口（同表不同保存通道）：`MaterialTemplateV2Controller.processDefineSave`(:125，模板体系)、`ManpowerCfgController.processDefineSave`(:328，老画图体系)。

## 6. 验证：category 表和 node_type 是不是都来自"前端拉 OFC 后填写提交"？

**对一半——category 表是的，node_type 不是。**

| 数据 | 来自 OFC？ | 谁决定 |
|---|---|---|
| `rule_category.node_process`（模板引用） | ✅ 模板列表拉自 OFC，下拉选中提交 | OFC 定义模板 → 配置人员选择 |
| `process_define.task_type`（任务序列） | ✅ 模板 nodeCode 映射 | OFC |
| `node_cfg.node_type`（节点类型） | ❌ 本地枚举 | 配置人员基于模板逐节点配置 |

关键澄清：**排程体系 categorySave 提交只做两件事**（写 rule_category + 同步 OFC saveSecondRule，`MaterialFlowMixServiceImpl:134-152`），**不写 node_cfg/process_define**；流程定义数据走「流程定义保存/模板复制」独立链路（`CategoryProcessServiceImpl`、`MaterialFlowMixTemplateServiceImpl` 模板复制 :1760-1769 校验 NMaterialProcessDefineForm+MaterialNodeList 的 nodeType/角色/时间）。

## 7. OFC 与本地配置的分工（一句话）

- **OFC 决定"流程里有哪些任务、什么顺序"**（task_type：测量/设计/复尺/送货）；
- **node_type 决定"每个任务里的节点"**（约工→派单→进场→…→验收），配置人员基于模板在页面逐节点配置；
- category 表只存"模板引用"（ID+名字），模板内容本身不在本地 category 表。
