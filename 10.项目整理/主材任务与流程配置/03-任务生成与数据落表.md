# 03 任务生成与数据落表

> 回答的问题：主材任务创建时会查配置吗？写入 task_dispatch.node_task 的数据来自哪里？表间怎么关联？

## 1. 创建时查配置是前置必要条件

`MaterialCreateV2ServiceImpl.execCreateMaterialProcess`（:760-822）：`materialConfigV2Service.queryAllMaterialForm(condition)` 查不到模板 → **直接 return，不生成任务**。

## 2. 两条配置查询路线（按 mode 分流）

`MaterialConfigV2ServiceImpl` 内两条路线：

| 路线 | 入口 | 查表顺序 |
|---|---|---|
| 老配置 | `queryAllMaterialFormByUnit`(:482) | `n_material_template_unit` → `n_material_process_define` → `queryAllMaterialFormByProcessCodes`(:813 查 `n_material_node_cfg` + `n_material_task_cfg`) |
| 排程 | `queryDeliveryFlowFormByUnit`(:330) | `delivery_flow_rule_unit` → `delivery_flow_rule_category`（**category_id 当 template_id 查 n_material_process_define**）→ 同一节点查询 |

**生成侧只读本地表，不调 OFC。**

排程路线详细（:330-440）：rule unit → category(DELIVERY_ACTIVE) → category_id 当 template_id 查 `n_material_process_define`（按 taskType 过滤）→ processCode → node/task 配置 → 构建 task_dispatch.node_task。指定供应商优先取，取不到用"不限制"（:387-399）。

HOME2_5 / HOME2_5_MANPOWER 新链路见 [[05-业务类型与整装零售]] 第 3 节。

## 3. task_dispatch.node_task 数据来源

- 直接来源：`NMaterialForm.materialNodeList`（`n_material_node_cfg.node_type`）。
- 写入点：`MaterialCreateV2ServiceImpl.java:1106-1107`：按 nodeCode（=nodeType×1000，NODE_CODE_FACTOR=1000）升序后 nodeType join(",")。
- 分支模式（非 home2.5，:1111-1116）：`MaterialRouteServiceImpl.calculateNodeExecutePath` → `n_material_route`+`n_material_branch_condition`（SpEL）算实际路径 → `getNodeTypesByCodes` 重写 node_task。
- `task_dispatch_node.node_type` 同源（buildAndSaveTaskDispatchNode :1162）。

## 4. 生成侧落表清单

| 表 | 固化的关键字段 |
|---|---|
| `task_dispatch` | node_task / node_path / current_node_type / process_status / process_code / condition_code |
| `task_dispatch_node` | node_type / node_code / task_code / u_task_code / process_status=1（待激活） / template_node_id |

## 5. 主键关联链（配置 → 生成）

```
material_flow_rule (rule_id)
  → material_flow_rule_unit
    → material_flow_rule_category (category_id)
      → n_material_process_define (template_id = category_id, process_code)
        → n_material_node_cfg / n_material_task_cfg
          → task_dispatch.process_code
```

## 6. 数据流转全景（表级，三阶段）

### 阶段一：配置侧

| 动作 | 落表 |
|---|---|
| rule/save（勾选维度） | `material_flow_rule` + `material_flow_rule_unit` + OFC saveMainRule |
| category/save（勾品类供应商+选模板） | `material_flow_rule_category`（草稿）+ OFC saveSecondRule |
| 绑定模板 | `material_flow_rule_template_mapping`(rule_category_id↔n_template_code↔task_type↔state) + 本地 `n_material_template`（草稿） |
| 生效 category/effective | OFC secondRuleChangeStatus + 本地模板草稿→有效 + mapping 置 VALID + category 置 VALID（旧→INVALID）+ `material_flow_rule_template_record` |

### 阶段二：生成侧

按 mode 分排程/老配置两路（见上）→ 落 `task_dispatch` + `task_dispatch_node`。

### 阶段三：运行侧

只读固化数据，不碰配置（详见 [[04-任务流转机制]]）。

## 7. 运行时字段用法速查

| 字段 | 用法 |
|---|---|
| `task_dispatch.node_task` | getNextNodeType binarySearch 取下一个节点 |
| `node_path` | 已走路径 |
| `condition_code` | 分支条件（DELIVER_WAY(10)=scmSubOrder、CRAFT_TYPE(50)=craftCodeList、NEED_RECHECK(30)=recheckDataList） |
| `task_dispatch_node.process_status` | 1 待激活 / 2 激活（按 task_dispatch_id+node_type+process_status=1 更新为 2） |
